A key is not decoration. It is how a database points at the right row without squinting.

This lesson explains how primary keys uniquely identify records, how foreign keys link tables, and how relationships connect data without repeating everything. The focus is precise Cambridge vocabulary: unique, non-null, reference, related table and integrity.

Why this matters

Key questions are often mark-scheme strict: name the field, say which table it belongs to, and explain the link.

Common trap

Do not choose a name as a primary key. Two students can share a name, and names can change. Databases dislike identity drama.

Knowledge point 1

Primary keys uniquely identify records

A primary key is a field, or combination of fields, that uniquely identifies each record in a table. It should be unique and not null.

UniqueNo two records in the table have the same key value.
Not nullEvery record must have a key value; blank identity is not identity.
StableA good key is unlikely to change, such as an allocated ID.
MinimalDo not use extra fields when one suitable field is enough.

Knowledge point 2

Foreign keys link tables

A foreign key is a field in one table that references the primary key in another table. It creates a link between related records.

Knowledge point 3

Relationships describe how records connect

A relationship describes how records in one table are associated with records in another table.

One-to-oneOne record in A relates to one record in B. Example: person and passport in a simplified system.
One-to-manyOne record in A relates to many records in B. Example: one student can have many loans.
Many-to-manyMany records in A relate to many in B. Often resolved using a linking table. Example: students and clubs.
Chinese support: primary key = 主键；foreign key = 外键；relationship = 关系；one-to-many = 一对多。

Knowledge point 4

Referential integrity

Referential integrity means a foreign key value must match an existing primary key value in the referenced table.

ValidLoan.StudentID = S0234 is valid if Student.StudentID = S0234 exists.
InvalidLoan.StudentID = S9999 is invalid if no student with that ID exists.
WhyIt prevents orphan records, such as a loan assigned to a non-existent student.

Extra practice

Foreign keys and referential integrity

A foreign key is an attribute in one table that refers to a primary/candidate key in another table. Referential integrity requires every non-null foreign-key value to match an existing referenced key.

The rule prevents orphan records. Insert, update and delete operations may be rejected or handled by an explicit cascade/null policy; the DBMS must not silently leave an invalid reference.

Worked example: Delete a department

If Employee.DepartmentID refers to Department.DepartmentID, deleting a department with employees would break referential integrity unless deletion is rejected or an authorised cascading policy handles dependent rows.

Targeted practice

1. Where is the referenced key stored?

Show answer

In the parent/referenced table.

2. What is an orphan record?

Show answer

A child record whose foreign key has no matching parent key.

3. Name one valid delete response.

Show answer

Reject the delete, cascade it, or set nullable foreign keys to null according to defined rules.

Show MS

  2. B1 references a key in the parent table
  3. B1 each foreign-key value must match an existing referenced value (or valid null)
  4. B1 prevents orphan/inconsistent relationships

Summary

Keep the roles separate

Primary keyUniquely identifies each record in its own table.
Foreign keyReferences a primary key in another table to create a link.
RelationshipDescribes how records in two tables are associated.
