A join is the database version of introducing two people who already have the same ID card.

This lesson shows how related tables are joined using matching key fields. You will read table relationships, write join conditions, trace joined rows and avoid the classic exam mistake: naming three tables but forgetting how they are connected.

Do not just invite tables to the party. Tell SQL how they know each other.

Teaching cue

Draw the relationship path before writing SQL. The join path is the plan; the query is the final sentence.

Why this matters

Cambridge-style mark schemes often credit the correct join condition separately from SELECT and FROM.

Common trap

Student.StudentID = Book.BookID looks tidy but is logically wrong. Join fields must represent the same item.

Warm-up hook

Which condition correctly links students to their loans?

If a table relationship is a bridge, a wrong join is a bridge drawn in pencil over a lake. Dramatic, not useful.

Choose the condition where both fields store the same kind of value.

Knowledge point 2

Join conditions say which fields match

For this lesson, use explicit join conditions. The key idea is not the exact SQL flavour; it is the matching relationship.

Three-table pattern: FROM Student, Loan, Book WHERE Student.StudentID = Loan.StudentID AND Loan.BookID = Book.BookID
Correct matchStudent.StudentID = Loan.StudentID because both values identify the same student.
Correct matchLoan.BookID = Book.BookID because both values identify the same book.
Extra filterUse another AND condition for a filter, such as Loan.Returned = FALSE.

Knowledge point 3

Table-qualified names and aliases prevent ambiguity

If two tables have a field with the same name, write the table name or alias before the field.

Full nameStudent.StudentID clearly means the field from Student.
AliasStudent AS S lets you write S.StudentID.
Exam cautionOnly use aliases if they make the query clear. Do not hide the join logic.
