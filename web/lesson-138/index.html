A debugger is not magic. It is a very patient witness.

Debugging means finding and correcting faults in an algorithm or program. In this lesson, traces show how variable values change, while breakpoints pause execution so the program can be inspected before it confidently walks into the wrong answer. Why this matters

Paper 2 may ask students to trace an algorithm, identify a logic error, or explain why breakpoints help debugging.

Common trap

A syntax error stops code from running. A logic error runs, but produces the wrong result. Traces are especially useful for logic errors.

Debugging

Debugging locates and corrects faults

A program can be syntactically valid and still wrong. Debugging checks the actual behaviour against the intended behaviour, then narrows down where the fault occurs.

Faulty pseudocode

INPUT Mark
IF Mark > 50 THEN
    OUTPUT "Pass"
ELSE
    OUTPUT "Resit needed"
ENDIF

Intended rule

A mark of 50 should pass. The code uses >, so 50 incorrectly goes to the ELSE branch.

The bug is small. Its exam mark consequences are not.

Breakpoint

A breakpoint pauses execution at a chosen line

Best place

Place a breakpoint before or on the line where the suspected decision or calculation happens.

What to inspect

Check variable values, the next line to execute, and whether the condition is true or false.

What not to do

Do not scatter breakpoints randomly. Random pausing is just procrastination wearing a technical hat.

Stepping

Step through code one instruction at a time

Step over

Run the next line without entering a called procedure or function. Useful when the call itself is not suspicious.

Step into

Enter a called procedure or function. Useful when the fault may be inside that subroutine.
