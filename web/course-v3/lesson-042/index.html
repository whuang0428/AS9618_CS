Explanation · 2 / 4

Separate redundancy from inconsistency

Data redundancy is unnecessary repeated storage of the same fact. It uses storage and creates extra update work. Data inconsistency occurs when copies that should agree contain different values. Repetition creates the opportunity for this disagreement; two identical copies have redundancy even before they disagree.

Explanation · 3 / 4

Share a fact through linked tables

A relational database organises data into related tables. Store Asha’s current phone once in Member. Each Loan stores MemberID 1 to identify whose borrowing event it records. When an application needs the phone, it retrieves the shared Member value. Repeated identifiers preserve links; they do not duplicate the phone itself.

Explanation · 4 / 4

Connect other file problems to mechanisms

Separate application files may have different formats and duplicated validation or access-control code. A DBMS provides shared definitions, query facilities and centrally enforced rules. Related data can be retrieved consistently through those facilities. These benefits depend on a suitable design: merely calling a collection of files a database does not remove bad duplication.

Original question · Cambridge 9618/12

1. Explain the move to a relational database

Cambridge 9618/12 · October/November 2024 · 6(a) · 3 marks

Selected parts: 6(a) [3].

Hint — reading the question

Explain benefits compared with separately maintained files. Use the repair company to make the effect of each benefit clear.

Reasoning and model answer — teacher-written

A customer’s details can be stored once and referenced from their repair jobs, reducing repeated data. Updating that single customer record means that queries for their jobs use the same current details, improving consistency. Different views can show employees only the information needed for their work.

Official mark scheme
Why this earns marks — teacher explanation

The scheme accepts three points at most. Redundancy, consistency, independence, queries, views and concurrent access are alternatives, not a requirement to list everything.

Common mistakes — teacher analysis

A relational database does not automatically copy every change into every table. In this example, jobs reference the same customer record; referential constraints and update rules govern changes to keys.

Explanation · 1 / 4

Use rules, not a lucky sample

A name appearing once today is not guaranteed unique. A candidate key is a minimal field or combination of fields that uniquely identifies a record under the business rules. Both MemberID and SchoolEmail are candidate keys under the stated guarantees.

MemberIDMemberNameSchoolEmailTutorGroup
1Ashaa1@school.example8A

Explanation · 2 / 4

Explain minimality

MemberID plus MemberName is unique when MemberID is unique, but it is not minimal: remove MemberName and identification still works. Therefore that unnecessary combination is not a candidate key. Minimal means no component can be removed while preserving the uniqueness guarantee.

Explanation · 3 / 4

Choose and enforce a primary key

Select one candidate key as the primary key. Choosing MemberID gives a short identifier that need not change when a name changes. Primary-key values must be unique and must not be null. Other candidate keys remain possible identifiers; the choice of primary key does not erase them.

Explanation · 4 / 4

Use a secondary key for a different purpose

A secondary key is an additional retrieval key, such as TutorGroup when finding everyone in 8A. It need not identify only one record. Secondary key does not mean the second candidate key or an unchosen alternative primary key.

Work together

Assess four proposed keys

Work together · 1 / 2

Accept the minimal identifiers

MemberID and SchoolEmail each independently identify one record, so each is a candidate. Choose MemberID as the primary key.

Work together · 2 / 2

Reject unnecessary and non-unique proposals

(MemberID, MemberName) is not minimal. MemberName alone is not guaranteed unique. TutorGroup finds a useful set of members and can be a secondary key, but cannot serve as the primary key.

Explain both uniqueness and minimality when justifying a candidate key.

Check

Explain it yourself · Teacher-written

Check your reasoning

Connect

Keep this idea

Choose a minimal guaranteed identifier; distinguish identification from retrieving a matching set.

A related table needs to refer to that identifier without copying the member’s details.

Check a common misunderstanding

Uniqueness in the displayed sample does not establish a business guarantee.

Read one-to-many from both ends

One Member may have many Loan records; each Loan belongs to one Member. This is a one-to-many relationship from Member to Loan. The MemberID reference goes on the many side so that every loan names its member.

Explanation · 2 / 4

Compare one-to-one

Suppose every library assistant is assigned one dedicated locker and no locker is shared. Each assistant has one locker and each assigned locker has one assistant: one-to-one. If sharing is later allowed, the relationship must be reconsidered.

Explanation · 3 / 4

Recognise and resolve many-to-many

A member can join several reading groups, and each group can have several members. A Membership table records each member-group pair. Member to Membership is one-to-many, and ReadingGroup to Membership is one-to-many. The pair can identify an association under the one-membership-per-pair rule.

Dara has no current loans, which is allowed. That does not turn Member–Loan into a different maximum cardinality. State whether zero is permitted separately from whether many is permitted; use the ER notation consistently.

Question 1 · Command word: Explain4 teacher marks

A garage repeats a customer's phone number in repair and invoice files. Explain two problems this can cause and describe how a linked Customer table addresses each problem.

S8.01.A01S8.01.A02
Answer and checking points — teacher-written
  1. Multiple phone-number copies consume avoidable storage.
  2. A Customer record can hold one shared number while repair and invoice records retain the customer reference.
  3. Changing only one file leaves conflicting phone numbers.
  4. Retrieving the number from the updated Customer record avoids separate phone-number updates.

Common error: Pair each problem with the specific mechanism that reduces it.

Question 2 · Command word: Identify4 teacher marks

A school assigns each pupil a unique PupilID and a unique exam number. Names and tutor groups may repeat. Identify the candidate keys, choose a primary key, suggest a secondary key for finding tutor-group members, and explain why Attendance.PupilID is a foreign key.

S8.02.A02
Answer and checking points — teacher-written
  1. PupilID and ExamNumber are separate candidate keys under the stated uniqueness rules.
  2. PupilID can be chosen as the primary key; ExamNumber is also a valid choice if used consistently.
  3. TutorGroup is a suitable secondary key for the specified retrieval.
  4. Attendance.PupilID refers to the identifier of the pupil whose attendance is recorded.

Common error: An unused candidate key is not automatically a secondary key.

Question 5 · Command word: Identify4 teacher marks

Identify the entity, one record and two attributes represented by Book(BookID, Title, Price), containing (7, 'Dunes', 12.50). Give the equivalent terms for record and field.

S8.02.A01
Answer and checking points — teacher-written
  1. Book is the entity type.
  2. The row for BookID 7 is one record.
  3. Title and Price are two attributes; BookID is also acceptable.
  4. Tuple corresponds to record, and attribute corresponds to field.

Common error: Do not call 'Dunes' the name of a field.

Question 6 · Command word: State4 teacher marks

State the relationship in each case: every employee has one parking permit and each permit belongs to one employee; each customer places many orders and every order has one customer; each actor appears in many films and every film has many actors. Explain how to store the final relationship.

S8.02.A03
Answer and checking points — teacher-written
  1. Employee to permit is one-to-one.
  2. Customer to order is one-to-many.
  3. Actor to film is many-to-many.
  4. A linking table stores ActorID and FilmID for each appearance, creating two one-to-many links.

Common error: Read both directions before assigning cardinality.

Question 7 · Command word: Explain3 teacher marks

A club guarantees a unique MemberID for each member but allows names and towns to repeat. Explain whether (MemberID, Town) is a candidate key. The club also records annual membership of several societies: a member may join the same society again in another year. Propose a minimal membership key under that rule.

S8.02.A02S8.02.A03
Answer and checking points — teacher-written
  1. (MemberID, Town) is unique but not minimal because MemberID alone already identifies a member; the pair is not a candidate key.
  2. Use (MemberID, SocietyID, Year) for an annual membership, assuming one membership per member, society and year.
  3. Omitting Year would wrongly treat the same member joining the same society in two years as a duplicate.

Common error: Test both uniqueness and minimality under the changed rule.

Topic recap
  • Why does the library need shared records?

    Store shared facts with the object they describe and use identifiers to connect related records.

  • Read a table as facts about things and events

    An entity is what the table describes; a tuple is one occurrence; an attribute is a named property.

  • Choose a key that really identifies one record

    Choose a minimal guaranteed identifier; distinguish identification from retrieving a matching set.

  • Connect a loan without confusing its two identifiers

    Use foreign keys to reference other records and a primary key to identify this record.

  • Reject a loan for a member who does not exist

    A valid reference points to an existing related record; uniqueness and required values are separate constraints.

  • Read every relationship in both directions

    Relationship cardinalities come from allowed associations, not accidental patterns in a few rows.

  • Find records through an index

    Explain which search an index helps, and include its storage and update costs.
