From file-based systems to relational databases

Connect file-based problems to relational mechanisms, then identify records, keys, relationships and indexes.

How can a clinic update a patient's address once and keep related records consistent?

Before you start

An address appears in three separate application files. Only one copy is changed. What can go wrong?

Check your answer

The files can disagree about the patient's current address; the repeated copies have become inconsistent.

01

From repeated facts to linked tables

S8.01.A01S8.01.A02

Visual overview

Core explanation

A file-based approach keeps data in files managed by individual applications. Repeating a patient's address in appointment and billing files uses extra storage. If only the billing copy is updated, the two applications may report different addresses for the same patient.

A relational design can store the address in Patient and put PatientID in related records. Applications retrieve the shared fact through that relationship. Central queries, constraints and access controls also reduce isolated retrieval and duplicated control code; the benefits depend on the design and its enforcement.

Worked example · A patient moves house

  1. Before

    Appointment and Billing each store PatientID 14 and Address '8 Oak Road'.

  2. File-based update

    Billing changes to '20 Hill Road', but Appointment still gives the old address.

  3. Relational design

    Patient(14, '20 Hill Road') stores the address; Appointment and Billing retain PatientID 14.

  4. Check

    Both applications retrieve the address from Patient rather than updating independent address copies.

Common misconception

A database does not automatically remove every duplicate fact; keys, relationships and controlled updates must be designed.

Check your understanding

Is repeating PatientID in several appointments the same redundancy problem as repeating the address?

Check your answer

No. PatientID is the reference needed to link appointments to the shared patient facts.

02

Entities, tables, records and fields

S8.02.A01

Visual overview

Core explanation

An entity is a type of real-world object or concept about which data is stored, such as Patient. A table represents occurrences of that entity. One row is a record, also called a tuple; it describes one particular patient.

An attribute is a named property of the entity, such as PatientName. A field is the corresponding column in its table. Distinguish the property from one value: PatientName is the field, while 'Imani' is a value in a particular record.

Common misconception

An entity type, one entity occurrence and the value in one field are different things.

Check your understanding

In the displayed table, what do tuple and attribute refer to?

Check your answer

A tuple is one patient row; an attribute is a property represented by a column, such as Town.

03

Choose keys for identification and retrieval

S8.02.A02

Visual overview

Core explanation

Identify records
  • Candidate key: A minimal field or combination that uniquely identifies a record.
  • Primary key: The chosen candidate; values must be unique and not null.
  • Composite key: Uses several fields, with every component needed for uniqueness.
Retrieve and relate records
  • Secondary key: Another retrieval route, such as Town; it need not be unique.
  • Foreign key: References a key in another table. A patient identifier may therefore recur across several appointment records.
Common misconception

Secondary key does not mean an unchosen candidate key; it may identify a set of matching records.

Check your understanding

Two patients share a name. Can PatientName uniquely identify every patient?

Check your answer

No. A primary key must distinguish those patients; a dedicated PatientID is suitable.

04

Read relationship cardinality in both directions

S8.02.A03

Visual overview

Core explanation

Relationship cardinality describes how many occurrences on one side may be associated with an occurrence on the other. Read the business rule in both directions before choosing one-to-one, one-to-many or many-to-many.

If a student can join several clubs and a club can have several students, the relationship is many-to-many. A Membership table records each student-club association and gives two one-to-many relationships. The pair of identifiers can be its composite key when each membership occurs only once.

Common misconception

Matching column names alone do not establish a relationship; the association must follow the scenario.

Check your understanding

Why does Membership need both StudentID and ClubID?

Check your answer

Together they identify which student belongs to which club; either identifier alone loses one side of the association.

05

Prevent references to missing records

S8.02.A04

Visual overview

Core explanation

Referential integrity requires each non-null foreign-key value to match an existing referenced key value. If an appointment names PatientID 99 but no such patient exists, a declared foreign-key constraint can reject that appointment.

Updates and deletions must also preserve valid links. Deleting a referenced patient can be rejected, or handled by an explicitly defined referential action. A nullable foreign key may be null where the design allows no association; it must not hold an arbitrary unmatched identifier.

Common misconception

A foreign key usually permits repeated values; uniqueness is not the rule that prevents orphan records.

Check your understanding

Would PatientID 18 in two appointments violate referential integrity?

Check your answer

No. Both references match patient 18; the appointments have their own identifiers.

06

Use an index to find matching records

S8.02.A05

Visual overview

Core explanation

An index is an additional lookup structure associated with one or more fields. It relates indexed values to record locations so the DBMS can find matches without inspecting every table row in suitable queries.

An index on Town can help retrieve all patients in York even when Town is not unique. The index occupies storage and must be maintained when indexed data changes. It improves an access path; it does not replace the table or guarantee that stored facts are correct.

Common misconception

Do not describe indexing as sorting every output automatically; query result order is specified separately.

Check your understanding

Why might an index slow an update?

Check your answer

The DBMS may need to change the index as well as the underlying record.

Practice questions

Question 1 · Command word: Explain4 marks

A garage repeats a customer's phone number in repair and invoice files. Explain two problems this can cause and describe how a linked Customer table addresses each problem.

S8.01.A01S8.01.A02
Answer and marking points
  1. Multiple phone-number copies consume avoidable storage.
  2. A Customer record can hold one shared number while repair and invoice records retain the customer reference.
  3. Changing only one file leaves conflicting phone numbers.
  4. Retrieving the number from the updated Customer record avoids separate phone-number updates.

Common error: Pair each problem with the specific mechanism that reduces it.

Question 2 · Command word: Identify4 marks

Identify the entity, one record and two attributes represented by Book(BookID, Title, Price), containing (7, 'Dunes', 12.50). Give the equivalent terms for record and field.

S8.02.A01
Answer and marking points
  1. Book is the entity type.
  2. The row for BookID 7 is one record.
  3. Title and Price are two attributes; BookID is also acceptable.
  4. Tuple corresponds to record, and attribute corresponds to field.

Common error: Do not call 'Dunes' the name of a field.

Question 3 · Command word: Identify4 marks

A school assigns each pupil a unique PupilID and a unique exam number. Names and tutor groups may repeat. Identify the candidate keys, choose a primary key, suggest a secondary key for finding tutor-group members, and explain why Attendance.PupilID is a foreign key.

S8.02.A02
Answer and marking points
  1. PupilID and ExamNumber are separate candidate keys under the stated uniqueness rules.
  2. PupilID can be chosen as the primary key; ExamNumber is also a valid choice if used consistently.
  3. TutorGroup is a suitable secondary key for the specified retrieval.
  4. Attendance.PupilID refers to the identifier of the pupil whose attendance is recorded.

Common error: An unused candidate key is not automatically a secondary key.

Question 4 · Command word: State4 marks

State the relationship in each case: every employee has one parking permit and each permit belongs to one employee; each customer places many orders and every order has one customer; each actor appears in many films and every film has many actors. Explain how to store the final relationship.

S8.02.A03
Answer and marking points
  1. Employee to permit is one-to-one.
  2. Customer to order is one-to-many.
  3. Actor to film is many-to-many.
  4. A linking table stores ActorID and FilmID for each appearance, creating two one-to-many links.

Common error: Read both directions before assigning cardinality.

Question 5 · Command word: Explain3 marks

Department contains IDs 3 and 6. Employee.DepartmentID is a non-null foreign key. Explain whether values 6 and 8 can be inserted, and whether two employees may both contain 3.

S8.02.A04
Answer and marking points
  1. Value 6 is permitted because department 6 exists.
  2. Value 8 must be rejected because no referenced department has that identifier.
  3. Two employees may reference 3 because a valid foreign-key value need not be unique.

Common error: Check the referenced table, not uniqueness in Employee.

Question 6 · Command word: Explain3 marks

A catalogue has 200000 products and users frequently search by Category. Explain one benefit and two costs of adding an index on Category.

S8.02.A05
Answer and marking points
  1. The lookup structure can locate matching products without scanning all catalogue records.
  2. The additional structure occupies storage.
  3. Changes to indexed category values require index maintenance.

Common error: Do not promise that every possible query becomes faster.

Question 1 · Command word: Explain · 4 marks

A charity stores donor addresses separately in subscription and donation files. Staff update only the donation file when a donor moves. Explain the resulting data problem and propose a relational change, including the roles of the identifier fields.

Answer and marking points
  • The same donor now has inconsistent addresses across the two applications.
  • A Donor table should retain the current address for each identified donor.
  • DonorID uniquely distinguishes a donor in that table.
  • Subscription and Donation rows reference DonorID so their address retrieval reaches the shared donor record.

Common error: Link the proposed table design to the stated partial-update failure.

Question 2 · Command word: Describe · 4 marks

A theatre records Performer(PerformerID, Name) and Production(ProductionID, Title). Each performer can appear in several productions and each production uses several performers. Describe a suitable linking table and its keys, assuming only one role per performer per production.

Answer and marking points
  • An Appearance table represents the association between one performer and one production.
  • It contains PerformerID and ProductionID as references to the two parent tables.
  • The combined pair can uniquely identify an appearance under the one-role rule.
  • Each performer can have many Appearance records and each production can have many Appearance records.

Common error: Neither parent identifier alone distinguishes every appearance.

Question 3 · Command word: Explain · 4 marks

A delivery record names DepotID 12, but Depot contains only IDs 4 and 9. An index on DepotName is also proposed to speed searches. Explain why the record should be rejected, what the index can improve, and why that index does not solve the invalid reference.

Answer and marking points
  • There is no depot row matching the supplied foreign-key value 12.
  • Enforcing the reference constraint prevents a delivery being assigned to a nonexistent depot.
  • A name index provides an access path to depots matching a requested name.
  • Faster name lookup does not create depot 12 or enforce the identifier relationship by itself.

Common error: Separate integrity enforcement from retrieval efficiency.
