01

Distinguish ordinary, invalid and extreme values

S12.07.A01S12.07.A02

Visual overview

Core explanation

Classify the test data
  • Normal: Valid data representative of ordinary use.
  • Abnormal: Data violating a range, type or format rule; expect the specified rejection or error response.
  • Extreme: The valid endpoints of the accepted range.

Boundary testing checks a limit and useful values on either side. Label each case with its expected result: boundary describes position, not whether the input is valid.

Keep the type rule separate

For integer marks from 0 to 100, the endpoints are accepted and -1 and 101 are rejected. The text "fifty" fails the integer type rule before a range check can apply.

Common misconception

Data categories do not determine a result by themselves; the stated input rule determines validity.

Check your understanding

Why can 101 be described as both abnormal and a boundary check?

Check your answer

It is invalid under the range rule and specifically tests the position just beyond the upper limit.

Core explanation

Choose cases from the input rule

First identify the rule, data type, limits and inclusive or exclusive comparisons. Choose a normal case, values exactly at each limit and values just outside. Where useful, include values just inside so an incorrect narrow equality test is exposed. Supply the expected result of each case, not just a label such as boundary.

Use real values and the stated precision

For a username length from 6 to 12 inclusive, lengths 5 and 13 must be rejected, while 6 and 12 must be accepted. Strings with these lengths are actual test data; the word short is not. For real-valued measurements, select nearby values at the precision permitted by the specification rather than assuming that one whole unit is the next value.

Worked example · A one-decimal temperature input

  1. Rule

    Accept temperatures from -5.0 to 30.0 inclusive, entered to one decimal place.

  2. Lower limit

    -5.1 is rejected; -5.0 and -4.9 are accepted.

  3. Upper limit

    29.9 and 30.0 are accepted; 30.1 is rejected.

  4. Reason

    These values distinguish incorrect strict comparisons and misplaced endpoints.

Common misconception

Test values immediately beside a boundary depend on the stated type and precision.

Check your understanding

Why is 6.0 not enough to test the lower length boundary of a username?

Check your answer

The input is a string. Supply a six-character string and state that it should be accepted.

Practice questions

Question 1 · Command word: Give2 marks

Give one normal integer mark and the valid extreme marks for the inclusive range 0 to 100. State their expected results.

S12.07.A01S12.07.A02
Answer and marking points
  1. An ordinary valid example is 55, expected Accepted.
  2. The extreme values are 0 and 100, both expected Accepted.

Common error: Do not use an out-of-range value as a valid extreme.

Question 2 · Command word: Give2 marks

Give abnormal inputs that test the range and the type checks of an integer mark field from 0 to 100, and state the expected responses.

S12.07.A01S12.07.A02
Answer and marking points
  1. 101 is outside the permitted range and should be rejected.
  2. The text "fifty" does not represent an integer and should be rejected at input validation.

Common error: Assume the field accepts raw input for validation; a typed INTEGER variable cannot itself store arbitrary text.

Question 3 · Command word: Write2 marks

Write four username test strings to check just below, on, on and just above the limits of 6 to 12 characters. State the expected results in that order.

S12.07.A01S12.07.A02
Answer and marking points
  1. abcde has length 5 and is rejected; abcdef has length 6 and is accepted.
  2. abcdefghijkl has length 12 and is accepted; abcdefghijklm has length 13 and is rejected.

Common error: Count the supplied characters rather than merely labelling the tests.

Question 4 · Command word: Explain2 marks

Explain why testing only mark 55 cannot distinguish the correct range check from one that rejects 0 and 100. Give the additional tests that reveal that particular defect.

S12.07.A01
Answer and marking points
  1. 55 is accepted by both checks, so the results agree for the single interior case.
  2. Inputs 0 and 100 should be accepted and expose a check that incorrectly excludes either endpoint.

Common error: Use data that make the competing conditions behave differently.

Question 1 · Command word: Give · 3 marks

A ticket quantity must be an integer from 2 to 8 inclusive. Give a normal value and four tests at or immediately outside the two limits, with each expected result.

Answer and marking points
  • A normal example is 5, expected Accepted.
  • 1 is rejected and 2 is accepted at the lower limit.
  • 8 is accepted and 9 is rejected at the upper limit.

Common error: Classify out-of-range neighbours as invalid rather than valid extremes.

Question 2 · Command word: Give · 3 marks

A sensor accepts temperatures from 10.0 to 20.0 inclusive with one decimal place. A programmer uses Temperature < 20.0 for the upper check. Give a test exposing the defect and its expected result, and two neighbouring tests with their expected results.

Answer and marking points
  • 20.0 should be accepted, but the strict upper comparison rejects it.
  • 19.9 should be accepted.
  • 20.1 should be rejected.

Common error: At this precision the adjacent values differ by 0.1, not 1.

Question 3 · Command word: Give · 4 marks

A product code must contain exactly four characters, all digits. Give three abnormal strings that separately test too few characters, too many characters and a non-digit, and explain why one valid string cannot check these restrictions.

Answer and marking points
  • "123" is rejected for being too short.
  • "12345" is rejected for being too long.
  • "12A4" is rejected for its non-digit character.
  • A valid code such as "1234" does not exercise any of these rejection conditions.

Common error: Keep leading zeroes and code values as strings; numeric conversion can lose length information.

Specify the rule

Attach an acceptance, rejection or required output to each input.
