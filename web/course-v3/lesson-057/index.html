Integrated design: a ticket purchase

Connect decomposition, IPO and refinement in one complete, traceable purchase algorithm.

Do the module responsibilities, calculations and final pseudocode implement the same purchase rules?

Before you start

Two tickets cost 25.00 each before a 10% student discount. What are the subtotal and final total?

Check your answer

Subtotal is 50.00; Total is 50.00 × 0.90 = 45.00. Quantity is applied once when calculating the subtotal.

01

Decompose the purchase requirements

S9.02.A01S9.02.A02

Visual overview

Core explanation

Rules for this ticket purchase
  • Quantity: Integer Quantity must be at least 1 and no greater than non-negative PlacesLeft.
  • Charge: Each identical ticket costs 25.00. Student TRUE gives 10% off the whole subtotal.
  • Payment: After showing Total, confirm, give change and reduce PlacesLeft only if Paid >= Total.
Agree responsibilities and effects

Assume correctly typed inputs and non-negative Paid. Decompose the work into checking quantity, calculating charge and completing payment. The charge function returns the amount; the completion procedure reports the result and updates availability only after sufficient payment. The detailed algorithm expands these responsibilities inline.

Worked example · Trace the agreement between modules

  1. Request

    Quantity 2, PlacesLeft 8, Student TRUE.

  2. Quantity decision

    The requested 2 tickets fit the available 8.

  3. Charge result

    Two tickets give 50.00 before discount and 45.00 due.

  4. Payment result

    Paid 50.00 gives change 5.00 and leaves 6 places after confirmation.

Common misconception

A module boundary must preserve the values another part needs; calculating a charge does not itself confirm payment.

Check your understanding

Should insufficient payment reduce PlacesLeft?

Check your answer

No. The stated rule updates availability only after a successful purchase.

Core explanation

Derive the charging and change calculations

Derive the purchase calculations from the rules before placing them into pseudocode. Subtotal is the ticket count multiplied by the fixed price. Apply the discount to that subtotal once; Total is either 90% of Subtotal or Subtotal itself. Change subtracts the amount due from the amount paid.

Let earlier decisions control later input

The input path depends on earlier decisions. An unavailable request ends with Unavailable, without asking for a student choice or payment. A valid request obtains Student, calculates and displays Total, and then obtains Paid. Keeping those dependencies explicit prevents using payment or discount data on a path that never reads it.

Follow the input dependencies

  1. RequestInput Quantity and PlacesLeft; check availability.
  2. Valid requestInput Student; calculate and output Total.
  3. PaymentInput Paid only after displaying the amount due.
  4. OutcomeConfirm with change and updated places, or report insufficient payment.
Common misconception

Multiplying Subtotal by Quantity again double-counts the number of tickets.

Check your understanding

For two non-student tickets, what is Total?

Check your answer

50.00, because Total equals the already calculated Subtotal.

Core explanation

Expand the rules into control flow

Refine check request into two comparisons joined by AND. Refine calculate charge into multiplication followed by a student decision. Refine complete payment into a sufficient-payment comparison with separate success and failure actions. These expansions resolve each high-level responsibility into programmable statements.

Trace all the relevant outcomes

Trace successful and rejected cases against the original rules. Zero quantity and requests above availability must exit before charging. Exact payment is sufficient and gives zero change. Underpayment must preserve the available-place count. The final pseudocode provides a complete endpoint, with no placeholder such as process payment left unresolved.

Worked example · A complete purchase algorithm

  1. Requirements

    Implement the rules and input assumptions in this lesson for one ticket request.

  2. Pseudocode
    CONSTANT TicketPrice = 25.00
DECLARE Quantity : INTEGER
DECLARE PlacesLeft : INTEGER
DECLARE Student : BOOLEAN
DECLARE Subtotal : REAL
DECLARE Total : REAL
DECLARE Paid : REAL
DECLARE Change : REAL
INPUT Quantity
INPUT PlacesLeft
IF (Quantity >= 1) AND (Quantity <= PlacesLeft) THEN
    INPUT Student
    Subtotal <- Quantity * TicketPrice
    IF Student THEN
        Total <- Subtotal * 0.90
    ELSE
        Total <- Subtotal
    ENDIF
    OUTPUT Total
    INPUT Paid
    IF Paid >= Total THEN
        Change <- Paid - Total
        PlacesLeft <- PlacesLeft - Quantity
        OUTPUT "Confirmed", Change, PlacesLeft
    ELSE
        OUTPUT "Insufficient payment"
    ENDIF
ELSE
    OUTPUT "Unavailable"
ENDIF
  3. Check

    For 2 tickets, 8 places, Student TRUE and Paid 50, the outputs are 45, Confirmed, 5 and 6, in that order.

Common misconception

A successful price calculation does not imply successful payment; the stock update belongs only on the payment-success path.

Check your understanding

Which comparison admits exact payment?

Check your answer

Paid >= Total; using Paid > Total would incorrectly reject exact payment.

Question 1 · Command word: Describe3 marks

For the purchase in this lesson, describe the data passed into charge calculation and the result passed to payment handling. Explain why printing the charge without returning or otherwise supplying its value is insufficient.

S9.02.A01S9.02.A02
Answer and marking points
  1. Charge calculation needs Quantity and Student, with the fixed TicketPrice available.
  2. The calculated Total must be supplied to payment handling.
  3. The payment comparison needs the numeric amount; display text alone does not provide that interface.

Common error: Distinguish reporting an amount from making it available to another module.

Question 2 · Command word: Calculate4 marks

Calculate the results using the lesson's ticket rules for Quantity 3, PlacesLeft 7, Student FALSE and Paid 80. Calculate Subtotal, Total, Change and the new PlacesLeft, and state the output sequence.

S9.05.A01
Answer and marking points
  1. Subtotal is 3 * 25 = 75 and Total is 75 without a student discount.
  2. Change is 80 - 75 = 5.
  3. PlacesLeft becomes 7 - 3 = 4.
  4. The outputs are 75, Confirmed, 5 and 4.

Common error: Do not multiply the subtotal by three a second time.

Question 3 · Command word: Develop4 marks

Develop the final payment step of the lesson's purchase algorithm into explicit operations. Explain the result for Total 45, Paid 44, Quantity 2 and PlacesLeft 8.

S9.08.A01
Answer and marking points
  1. Compare Paid >= Total.
  2. On success, calculate Change <- Paid - Total and PlacesLeft <- PlacesLeft - Quantity, then output confirmation and both values.
  3. On failure, output "Insufficient payment" without changing PlacesLeft.
  4. The supplied underpayment follows the failure branch and leaves 8 places.

Common error: Place the availability update inside the successful-payment branch.

Question 1 · Command word: Describe · 4 marks

A museum hires audio guides at 4.00 each and requires a refundable deposit of 10.00 per order. It checks available guides, calculates the payment due and records an accepted hire. Describe three corresponding modules, including a suitable interface for the charge calculation.

Answer and marking points
  • An availability module receives requested Quantity and GuidesLeft and determines whether the request can be met.
  • A charge function receives Quantity and returns Quantity * 4.00 + 10.00.
  • A recording module uses the accepted quantity and payment outcome to record the hire.
  • The returned amount is available to the payment check rather than being recalculated independently.

Common error: The deposit is per order, not per guide.

Question 2 · Command word: Write · 4 marks

A venue sells tickets at 12.00 each with no discounts. Write an IPO table and pseudocode for a positive quantity and sufficient Paid amount. Output the total and change. State both outputs for Quantity 3 and Paid 50.

Answer and marking points
  • Inputs are Quantity and Paid; processing multiplies quantity by 12 and subtracts the total from Paid; outputs are Total and Change.
  • The pseudocode obtains both inputs before using them.
  • Total <- Quantity * 12 and Change <- Paid - Total implement the rules.
  • OUTPUT Total, Change gives 36 and 14 for the supplied case.

Common error: This scenario has its own ticket price and no student discount.

Question 3 · Command word: Develop · 5 marks

Develop complete pseudocode for a pool purchase. The pool sells one session pass at 6.00 when PlacesLeft is positive. Implement these rules: input the non-negative integer PlacesLeft; if no place remains output "Full"; otherwise input non-negative Paid, accept at least 6.00, output change and reduce PlacesLeft by one; on underpayment output "Not paid" and leave PlacesLeft unchanged. Output the updated PlacesLeft only after success.

Answer and marking points

One valid pseudocode solution

DECLARE PlacesLeft : INTEGER
DECLARE Paid : REAL
DECLARE Change : REAL
INPUT PlacesLeft
IF PlacesLeft > 0 THEN
    INPUT Paid
    IF Paid >= 6.00 THEN
        Change <- Paid - 6.00
        PlacesLeft <- PlacesLeft - 1
        OUTPUT Change, PlacesLeft
    ELSE
        OUTPUT "Not paid"
    ENDIF
ELSE
    OUTPUT "Full"
ENDIF
  • INPUT PlacesLeft is followed by a decision PlacesLeft > 0.
  • The no-place branch outputs "Full" without reading payment.
  • The available branch inputs Paid and tests Paid >= 6.00.
  • Success computes Change <- Paid - 6.00 and PlacesLeft <- PlacesLeft - 1.
  • Success outputs Change and PlacesLeft; failure outputs "Not paid" without the update.

Common error: The rejected payment must not consume a place.
