Test strategies and test plans

Relate the overall testing approach to concrete cases, expected results and recorded outcomes.

What must be planned before a tester can judge whether the program passed?

Before you start

Is a list of input values enough to establish that testing passed?

Check your answer

No. Each value needs an expected result and an observed result to compare; the overall testing responsibilities and approach also need to be decided.

Plan the overall testing approach

Core explanation

A test strategy sets the overall approach: what will be tested, which levels and methods will be used, the sequence of work, responsibilities, resources and conditions for starting or finishing a phase. It helps a team coordinate testing and decide how the evidence will address project risks and requirements.

For a room-booking program, individual module checks can precede integration tests of the availability and booking modules. Customer acceptance can then use agreed booking rules. Naming a method alone is insufficient planning: identify who performs it, what environment or data it needs, and what results allow work to proceed.

Common misconception

A strategy is broader than one test case; it coordinates the work and its evidence.

Check your understanding

Why agree a test database before integration begins?

Check your answer

Repeatable known bookings let testers judge combined results against a controlled starting state.

Record cases and compare outcomes

Core explanation

A test plan records the cases to run, with identifiers, purposes, input data or initial conditions and expected results. Expected results are decided from the specification before execution. The plan can then record actual results and a pass/fail decision, with defect and retest records where needed.

Give enough detail for another tester to repeat the case. For a room limited to 30 people, a request of 31 should be rejected; an actual acceptance is a failure even if the program runs without an error message. When corrected, preserve the original failure record and record the new run so the evidence shows what changed.

Worked example · Use a failed case

  1. Before execution

    T03 records Quantity 31 and expected Rejected from the capacity rule.

  2. Observe

    The faulty build accepts 31, so T03 fails.

  3. Follow up

    Link the result to the defect and retest T03 after correction.

  4. Keep evidence

    Record the revised build and new outcome without erasing the original observation.

Common misconception

The expected result is not copied from the program's output after execution.

Check your understanding

What is wrong with a row containing only T03, 31 and Pass?

Check your answer

It omits the case purpose and expected/actual results that justify the pass decision.

Practice questions

Question 1 · Command word: Explain2 marks

Explain why a booking project needs both an overall test strategy and a record of individual test cases.

S12.06.A01
Answer and marking points
  1. The strategy coordinates scope, methods, order and responsibilities across the project.
  2. Individual cases specify repeatable inputs and expected behaviour and record the observed outcomes.

Common error: Two names for one input list do not provide these different levels of planning.

Question 2 · Command word: State3 marks

A test row for a 30-person room records Quantity 31, expected Rejected and actual Accepted. State the outcome and describe two records needed after the fault is corrected.

S12.06.A01
Answer and marking points
  1. The outcome is Fail because the actual decision contradicts the expectation.
  2. Record the corrected build or version and the repeated case.
  3. Record the new actual result and its comparison with the unchanged expected rejection.

Common error: Do not rewrite the expectation to Accepted.

Question 3 · Command word: Describe3 marks

Describe three likely contents of a test strategy other than a list of individual input values.

S12.06.A01
Answer and marking points
  1. The scope and testing methods or levels to use.
  2. Who is responsible and what resources or environment are needed.
  3. The sequence and criteria for completing the planned testing phases.

Common error: Use project-level decisions rather than stub definitions.

Question 1 · Command word: Explain · 4 marks

Explain why a test plan stating only "test login with suitable data" cannot produce repeatable evidence. Describe the missing information for a case where a locked account must be refused access.

Answer and marking points
  • Suitable data does not specify the account state and credentials another tester must use.
  • The row needs a case identifier and the locked-account initial condition.
  • The expected outcome is refusal of access under the given rule.
  • The tester records the actual outcome and the pass/fail comparison.

Common error: Use the locked-account requirement to state a concrete expected result.

Question 2 · Command word: Explain · 3 marks

A team proposes customer acceptance before integrating its report and data modules. Explain one problem with this sequence and describe two strategy decisions needed before acceptance.

Answer and marking points
  • Broken module interfaces may prevent the customer from assessing the complete reporting behaviour.
  • Agree integration completion criteria and resolve blocking interface defects first.
  • Assign customer representatives and prepare the required dataset and expected reports for acceptance.

Common error: A test strategy should coordinate dependencies, not simply name phases.

Question 3 · Command word: Explain · 2 marks

A tester runs the same valid payment case five times and writes Pass each time without recording the output. Explain two weaknesses in the recorded evidence.

Answer and marking points
  • No actual output is recorded to substantiate the comparison with the specified payment result.
  • Repeating one ordinary case gives no evidence about other planned conditions such as refusal or exact-payment boundaries.

Common error: Repeated execution alone does not establish completeness or a justified result.
