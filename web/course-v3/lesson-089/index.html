Test strategies and test plans

Relate the overall testing approach to concrete cases, expected results and recorded outcomes.

What must be planned before a tester can judge whether the program passed?

Before you start

Is a list of input values enough to establish that testing passed?

Check your answer

No. Each value needs an expected result and an observed result to compare; the overall testing responsibilities and approach also need to be decided.

Make project-level decisions

A test strategy coordinates the overall approach: what is in scope, which methods and levels to use, who is responsible, what environment and resources are needed, and what evidence allows work to proceed. Its purpose is to prevent important work from being omitted or attempted before its dependencies are ready.

Link strategy and cases

A list saying “black-box, integration, acceptance” does not explain the strategy. State which risks each method addresses and how the results support the next activity. A plan of individual cases provides the repeatable details needed to carry out these decisions.

Core explanation · Exam essentials

  • A strategy coordinates scope, methods, sequence, responsibilities, resources and completion evidence.
  • Explain why those choices fit the project and its dependencies.
Common misconception

A strategy is broader than one test case; it coordinates the work and its evidence.

Check your understanding

Why agree a test database before integration begins?

Check your answer

Repeatable known bookings let testers judge combined results against a controlled starting state.

Record cases and compare outcomes

S12.06.A01

Visual overview

From a requirement to repeatable evidence

  1. SpecifyState the rule, initial conditions and exact input.
  2. PredictDerive the required result before observing the program.
  3. RecordIdentify the version, actual result and comparison.
  4. Follow upCorrect faults and retain the original and retest records.

Specify the case before recording the run

A test plan makes cases repeatable. Record an identifier, purpose, starting conditions, actual input values and an expected result derived before execution. A test record adds the version, observed result and pass/fail comparison, with a linked defect and retest when needed. Projects may organise plans and records differently; the evidence must still be recoverable.

The plan is not yet a systematic selection of all useful cases. Lesson 090 adds lower-boundary and other discriminating cases to this same requirement. A small example in this lesson demonstrates complete records without pretending three rows establish comprehensive testing.

Worked example · Trace V1 to produce the failure record

  1. Requirements and initial conditions

    The requirement is INTEGER Quantity in 1–30 inclusive. This deliberately faulty version uses 31 as the upper limit.

  2. Cambridge pseudocode
    DECLARE Quantity : INTEGER
INPUT Quantity
IF (Quantity >= 1) AND (Quantity <= 31) THEN
    OUTPUT "Accepted"
ELSE
    OUTPUT "Rejected"
ENDIF
  3. Expected result and checks

    15 and 30 give the required Accepted result. 31 incorrectly produces Accepted instead of Rejected.

Worked example · Trace V2 after correcting the upper limit

  1. Requirements and initial conditions

    Use the unchanged 1–30 requirement and the same input conditions.

  2. Cambridge pseudocode
    DECLARE Quantity : INTEGER
INPUT Quantity
IF (Quantity >= 1) AND (Quantity <= 30) THEN
    OUTPUT "Accepted"
ELSE
    OUTPUT "Rejected"
ENDIF
  3. Expected result and checks

    31 now gives Rejected; 30 remains Accepted. Retain the original failure record and append these new trace results.

Core explanation · Exam essentials

  • Specify purpose, conditions, input and independently expected results before execution.
  • Record version, actual result and comparison; retain failure and retest evidence.
Optional extension: identify the version under test

A short version label such as V1 or V2 connects a result to the statements actually examined. Keep the input and expected result beside that label so another tester can repeat it. A full version-control workflow is outside this lesson.

Common misconception

The expected result is not copied from the program's output after execution.

Check your understanding

What is wrong with a row containing only T03, 31 and Pass?

Check your answer

It omits the case purpose and expected/actual results that justify the pass decision.

Practice questions

3 core tasks · 11 teacher marks · 14–20 minutes (teacher estimate). Explain your reasoning before checking the answer.

Question 1 · Command word: Explain2 teacher marks

Explain why a booking project needs both an overall test strategy and a record of individual test cases.

S12.06.A01
Answer and checking points — teacher-written
  1. The strategy coordinates scope, methods, order and responsibilities across the project.
  2. Individual cases specify repeatable inputs and expected behaviour and record the observed outcomes.

Common error: Two names for one input list do not provide these different levels of planning.

Question 2 · Command word: State3 teacher marks

A test row for a 30-person room records Quantity 31, expected Rejected and actual Accepted. State the outcome and describe two records needed after the fault is corrected.

S12.06.A01
Answer and checking points — teacher-written
  1. The outcome is Fail because the actual decision contradicts the expectation.
  2. Record the corrected build or version and the repeated case.
  3. Record the new actual result and its comparison with the unchanged expected rejection.

Common error: Do not rewrite the expectation to Accepted.

Question 3 · Command word: Develop6 teacher marks

Develop a small test plan for independent INTEGER requests accepted exactly from 1 to 30. Include an ordinary valid request, both valid endpoints and values just outside them. Give identifiers, purpose, starting conditions, inputs and expected results. State which fields must be completed after each run and two strategy decisions needed before running the cases.

S12.06.A01
Answer and checking points — teacher-written
  1. Give distinct identifiers and purposes, with each request starting a fresh run and no retained booking state.
  2. An ordinary case such as 15 expects Accepted.
  3. 1 and 30 each expect Accepted.
  4. 0 and 31 each expect Rejected.
  5. Record the tested version, actual output and pass/fail comparison; link a defect and retest where necessary.
  6. Specify who runs or reviews the cases and which methods, environment or completion criteria organise the work.

Common error: Do not fill an actual-output column by copying the expected result before execution.

Question 1 · Command word: Describe3 teacher marks

Describe three likely contents of a test strategy other than a list of individual input values.

S12.06.A01
Answer and checking points — teacher-written
  1. The scope and testing methods or levels to use.
  2. Who is responsible and what resources or environment are needed.
  3. The sequence and criteria for completing the planned testing phases.

Why this earns marks — teacher explanation

One mark is available for each completed row containing all three fields, four overall. The official scheme also permits some nearby accepted values and type labels. The table above uses the exact valid endpoints.

Common mistakes — teacher analysis

−1 cannot be generated under the stated sensor constraint. A fractional value does not belong to the specified integer input domain. Valid boundary data is accepted; “boundary” does not mean invalid.
