Develop a booking system · Concept 19

Plan the whole testing approach

Observe

A release planning note

  • The quantity check, calculation and screen are built by different people.
  • The availability function will arrive later than its caller.
  • School staff can trial the screen on Friday; the customer needs acceptance evidence next week.

Look, then discuss

Which decisions must the team make before listing individual inputs?

The project needs more than a table of numbers. Decide what is tested first, how unfinished parts are handled, who supplies user feedback and what evidence allows release.

Recall

Recall method, data and expected result

A method explains how testing is organised or cases are selected. Data supplies specific inputs. Expected results describe the behaviour required for those inputs. A complete approach coordinates all three.

Explain

Explanation · 1 / 3

Set scope, priorities and stages

A test strategy describes the overall approach: what will be tested, the methods and sequence, significant risks, responsibilities, environments, resources and completion criteria. A test plan then makes the work concrete and repeatable with schedules and individual cases.

Explanation · 2 / 3

Connect methods to specific risks

Review and dry-run calculations; select black-box range cases and white-box branch cases; use a stub while the availability module is absent; check integration after replacement. Plan user trials and acceptance with their participants and environments.

Explanation · 3 / 3

Specify responsibilities and evidence

Name who prepares cases, runs them, investigates failures and decides whether the completion criteria are met. Record environment and version so another tester can reproduce a failure. Define what must pass rather than using “we tested for an hour” as a release criterion.

Work together

Write a small, usable strategy

The highest risks are a wrong charge, an invalid quantity being accepted and a missing availability response.

Work together · 1 / 2

Sequence dependent work

First review calculation and range rules; test modules; exercise the caller with controlled responses; replace the stub and test integration; then use representative staff environments and customer acceptance cases.

Work together · 2 / 2

Choose completion evidence

All agreed range and charge cases must match expected results. Required availability paths must pass after integration. Unresolved failures need recorded decisions, and the customer checks the agreed acceptance requirements.

The strategy explains the overall approach; individual records make its execution inspectable.

Look, then discuss

What information would another tester need to repeat and judge this case?

The record omits the requirement, initial availability, program version, expected output and actual output. “Wrong” cannot explain which operation to investigate.

Recall

Recall the independent expectation

For the booking range, derive Accepted or Rejected from the agreed 1–6 rule before observing the program. A valid boundary value can be accepted; being a boundary does not make a value invalid.

Explain

Explanation · 1 / 4

Write the case before running it

Record a case ID, requirement or purpose, initial conditions, exact input and expected outcome. Include data type or category where relevant. For this case use Available 6, integer Seats 6 and expected Accepted.

Explanation · 2 / 4

Add actual evidence after the test

Record the version, observed result and pass/fail comparison. If the code is only dry-run, label the result as a trace, not a computer execution. A case not yet run has no observed actual result to invent.

Explanation · 3 / 4

Retain the failure and append the retest

After changing < to <=, run or trace the same case on the corrected version. Keep V1’s failure as evidence; record V2 separately and add neighbouring regression cases.

Explanation · 4 / 4

Respect the input source in the next paper

A sensor may produce non-negative integers only. For such a sensor, a negative number or text cannot be a real test input from that source. Use attainable values, and provide the requested category, value and expected outcome together.

Work together

Complete a test record from a different rule

For a sensor accepting integer readings 0–60 inclusive, the source never produces negative or fractional values.

Work together · 1 / 2

Use the required domain

0 and 60 are valid endpoint tests. 15 is an ordinary valid value. 61 is attainable but outside the accepted range, so it must be rejected.

Work together · 2 / 2

Separate a plan from a report

Write those expected results before running the sensor program. Leave actual and outcome pending until evidence exists. A plan can be complete even before the test is executed; a result claim cannot.

Keep the requirement, prediction, observation and version together so the comparison can be repeated.

Question 1 · Command word: Explain2 teacher marks

Explain why a booking project needs both an overall test strategy and a record of individual test cases.

S12.06.A01
Answer and checking points — teacher-written
  1. The strategy coordinates scope, methods, order and responsibilities across the project.
  2. Individual cases specify repeatable inputs and expected behaviour and record the observed outcomes.

Common error: Two names for one input list do not provide these different levels of planning.

Question 2 · Command word: State3 teacher marks

A test row for a 30-person room records Quantity 31, expected Rejected and actual Accepted. State the outcome and describe two records needed after the fault is corrected.

S12.06.A01
Answer and checking points — teacher-written
  1. The outcome is Fail because the actual decision contradicts the expectation.
  2. Record the corrected build or version and the repeated case.
  3. Record the new actual result and its comparison with the unchanged expected rejection.

Common error: Do not rewrite the expectation to Accepted.

Question 3 · Command word: Develop6 teacher marks

Develop a small test plan for independent INTEGER requests accepted exactly from 1 to 30. Include an ordinary valid request, both valid endpoints and values just outside them. Give identifiers, purpose, starting conditions, inputs and expected results. State which fields must be completed after each run and two strategy decisions needed before running the cases.

S12.06.A01
Answer and checking points — teacher-written
  1. Give distinct identifiers and purposes, with each request starting a fresh run and no retained booking state.
  2. An ordinary case such as 15 expects Accepted.
  3. 1 and 30 each expect Accepted.
  4. 0 and 31 each expect Rejected.
  5. Record the tested version, actual output and pass/fail comparison; link a defect and retest where necessary.
  6. Specify who runs or reviews the cases and which methods, environment or completion criteria organise the work.

Common error: Do not fill an actual-output column by copying the expected result before execution.

Question 4 · Command word: Describe3 teacher marks

Describe three likely contents of a test strategy other than a list of individual input values.

S12.06.A01
Answer and checking points — teacher-written
  1. The scope and testing methods or levels to use.
  2. Who is responsible and what resources or environment are needed.
  3. The sequence and criteria for completing the planned testing phases.

Common error: Use project-level decisions rather than stub definitions.
