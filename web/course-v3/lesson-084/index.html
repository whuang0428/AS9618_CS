01

Purpose and stages of a development life cycle

S12.01.A01S12.01.A02

Visual overview

Core explanation

Purpose

A development life cycle coordinates the route from the problem to a tested, maintained solution. Records connect requirements, design decisions and results; following stages alone does not guarantee a suitable product.

What each activity establishes
  • Analysis: The problem, user requirements and constraints.
  • Design: Data, algorithms, module interfaces and tests.
  • Coding: An implementation of the design.
  • Testing: Actual behaviour compared with expected results, exposing defects.
  • Maintenance: Changes after delivery as faults, environments and user needs change.
Use evidence to revisit decisions

Feedback can reveal a need to revisit earlier work. The chosen development model determines how the team organises these activities.

A library renewal feature through five stages

StageConcrete output
AnalysisRule: a book with a waiting reservation cannot be renewed
DesignDecision algorithm and the reservation-status interface
CodingStatements that implement the renewal decision
TestingReserved and unreserved cases with expected decisions
MaintenanceChanges after delivery, such as support for a new lending policy

Worked example · Resolve an ambiguous request

  1. Request

    The librarian asks for easier renewals.

  2. Analysis

    Agree which loans qualify and what message a refused renewal needs.

  3. Design and coding

    Specify the decision and then implement its branches.

  4. Testing and maintenance

    Check agreed examples before release; record later policy changes separately.

Common misconception

Analysis determines what is required; coding is not a substitute for agreeing the requirement.

Check your understanding

Which stage establishes whether reserved books may be renewed?

Check your answer

Analysis agrees the rule with users; design specifies how the program applies it.

02

Waterfall: planned sequential stages

S12.01.A03

Visual overview

A stable payroll rule

  1. AnalyseAgree pay rules and statutory deductions.
  2. DesignApprove data definitions and calculations.
  3. CodeImplement the approved design.
  4. TestCompare calculated payslips with independently calculated expected amounts.
  5. MaintainRespond to faults or revised external rules after delivery.

Core explanation

Sequence, documentation and suitable requirements

Waterfall completes planned stages largely in sequence. The output of one stage is reviewed before the next proceeds, so requirements and designs provide a documented basis for implementation and testing. It is useful where requirements are well understood and stable and formal approval records are valuable.

Milestones and the cost of late change

The staged structure makes milestones and responsibilities clear. However, users may see working software late, and a requirement change discovered after design or coding can force substantial rework. Returning to earlier work is possible; it undermines the assumption that the earlier stage was settled.

Common misconception

Waterfall is not a promise that requirements can never change; late changes are a drawback because they can be expensive.

Check your understanding

Why is a new pay rule discovered during final testing costly?

Check your answer

It can require changes to the agreed requirements, design, code and previous tests.

03

Iterative development: learn from successive versions

S12.01.A04

Visual overview

Core explanation

Learn from successive versions
  1. Develop a version: Revisit analysis, design, coding and testing for an agreed scope.
  2. Review working behaviour: Users inspect the result before the whole system is finished.
  3. Set the next cycle: Use findings to refine requirements and priorities.
Benefit and control

Early feedback reduces the risk of building the wrong solution. Control scope, versions, schedule and stopping criteria: repeated changes can otherwise delay completion and leave documentation inconsistent.

Common misconception

Iteration means reviewing and improving versions, not repeatedly running the same finished program.

Check your understanding

What evidence should determine the next iteration?

Check your answer

Observed defects and user feedback evaluated against the intended requirements and priorities.

RAD and choosing a suitable model

S12.01.A05S12.01.A06

Visual overview

Select using the project constraints

Project evidenceReasoned choice
Fixed calculation rules with formal sign-offWaterfall supports approved stage outputs
Rules likely to evolve after demonstrationsIterative versions allow feedback to refine the solution
Available users and a short interface prototype deadlineRAD supports rapid prototypes within time boxes

Swipe horizontally to compare every column →

Core explanation

Prototypes, time boxes and user feedback

Rapid application development (RAD) emphasises rapid prototyping, time-boxed development and frequent user involvement. Users inspect early working prototypes and give prompt feedback that changes the next version. Short agreed development periods concentrate effort on a usable result rather than waiting for every feature.

Judge suitability from the constraints

RAD can suit an interactive booking interface when users are available and components can be prototyped quickly. Limited user availability or tightly dependent components can make this approach difficult. A project needing exhaustive assurance and stable approved documentation may find rapid changes harder to control. Choose a model by relating these features to requirement stability, delivery time, user access and assurance needs.

Common misconception

Speed alone does not justify RAD; explain how user participation and prototype feedback fit the actual project.

Check your understanding

Why could unavailable users undermine RAD?

Check your answer

The rapid review cycle depends on timely feedback; delayed decisions can invalidate a time box or produce unsuitable features.

Practice questions

Question 1 · Command word: Describe4 marks

Describe the purpose of a development life cycle and identify the stage responsible for each output: agreed user requirements, a module design, executable statements, recorded test results and a post-release correction.

S12.01.A01S12.01.A02
Answer and marking points
  1. It organises development work and the evidence needed to check progress towards a suitable program.
  2. Agreed requirements belong to analysis; the module design belongs to design.
  3. Executable statements are produced during coding; recorded comparisons belong to testing.
  4. A correction to the delivered program is maintenance.

Common error: Distinguish the required behaviour from the algorithm used to implement it.

Question 2 · Command word: Explain2 marks

A tax calculator has fixed rules and requires written approval of each stage. Explain one benefit and one drawback of using waterfall.

S12.01.A03
Answer and marking points
  1. Stage documents provide an agreed basis for approving the fixed calculation rules.
  2. If a rule is corrected late, already approved design and implementation work may need revision.

Common error: Link both points to staged development.

Question 3 · Command word: Explain2 marks

A timetable team revises its interface after each demonstration. Explain how iterative development helps and give one management problem it creates.

S12.01.A04
Answer and marking points
  1. Each demonstration supplies evidence that can change the next working version.
  2. Repeated revisions require control of priorities and versions to prevent continuing scope growth.

Common error: Describe how feedback changes a version, rather than merely saying that work repeats.

Question 4 · Command word: Describe4 marks

Describe three defining features of RAD. Explain why an interface project with available users and a two-week prototype deadline could use it.

S12.01.A05S12.01.A06
Answer and marking points
  1. Rapid prototypes make an early interface available for inspection.
  2. Time boxes set short fixed development periods.
  3. Frequent user participation supplies feedback during development.
  4. The available users can evaluate the prototype within the short deadline and guide subsequent changes.

Common error: The three features are distinct; rapid coding alone does not describe RAD.

Question 1 · Command word: Explain · 3 marks

A hospital specifies an alarm rule before development. During testing, staff discover that the design uses the wrong threshold. Explain the roles of analysis, design and testing in resolving this discrepancy.

Answer and marking points
  • Analysis confirms the intended alarm threshold with the responsible users.
  • Design revises the decision rule so the algorithm represents that threshold.
  • Testing uses independently expected alarm results to check the implemented rule, including its boundary.

Common error: A test result must be judged against the requirement, not used to redefine it.

Question 2 · Command word: Explain · 4 marks

Explain why a staged waterfall model may suit a controller with stable requirements and mandatory documented approvals, and why RAD could be difficult if specialist users can attend only one review at the end.

Answer and marking points
  • Sequential reviewed outputs support the controller project's formal approval process.
  • Stable requirements reduce the likelihood of costly changes to completed stages.
  • RAD normally needs repeated access to users to evaluate prototypes.
  • One late review prevents prompt feedback within the rapid development cycles.

Common error: Base the choice on both approval requirements and user availability.

Question 3 · Command word: Compare · 3 marks

A delivery company has uncertain route-display requirements. Compare waterfall and iterative development for obtaining feedback, and explain one risk of choosing the iterative approach.

Answer and marking points
  • Waterfall typically settles requirements before implementation, so working-display feedback may arrive late.
  • Successive iterative versions let drivers inspect a display while the solution is still being refined.
  • Repeated requests could extend scope and delay delivery unless the team controls priorities and completion criteria.

Common error: Compare the same feature of both models before discussing the risk.
