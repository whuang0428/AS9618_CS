01

Purpose and stages of a development life cycle

S12.01.A01S12.01.A02

Visual overview

Connect activities through their outputs

A development life cycle coordinates the work from a problem to a delivered, supported solution. Analysis establishes what is needed; design decides how to achieve it; coding implements that design; testing compares behaviour with independently expected results; maintenance responds to changes after delivery. Keeping the evidence connected helps a team find the source of a disagreement.

One booking requirement through the five stages

StageConcrete result for the next activity
AnalysisAgree that Quantity is an INTEGER, 1–30 inclusive is accepted, and every other integer is rejected. Each request is independent; no seats are accumulated across requests.
DesignRead Quantity, evaluate both limits with AND, output Accepted or Rejected, then finish this request. Identify boundary cases before implementation.
CodingImplement the complete roomRule program below with a declaration, input, both branches and ENDIF.
Testing1 and 30 must produce Accepted; 0 and 31 must produce Rejected. Compare these expectations with the chosen implementation.
MaintenanceA later capacity change to 35 changes the specification, comparison and expected boundary tests together. The reason for the capacity change determines the maintenance category.

Follow feedback to the right decision

The agreed rule is the source of the expected results. If code accepts 31, testing has exposed a discrepancy; it has not changed the capacity to 31. If users actually need a larger room, analysis must establish a revised requirement before design and code change. A model organises this work but cannot replace judgement about the requirement.

Keep the example boundary explicit

The short program demonstrates one complete requirement. It assumes integer input and does not claim to validate raw text. The five-stage library example is a separate illustration of stage responsibilities, not a complete library program.

Worked example · Resolve an ambiguous request

  1. Request

    The librarian asks for easier renewals.

  2. Analysis

    Agree which loans qualify and what message a refused renewal needs.

  3. Design and coding

    Specify the decision and then implement its branches.

  4. Testing and maintenance

    Check agreed examples before release; record later policy changes separately.

Worked example · Implement the agreed capacity rule

  1. Requirements and initial conditions

    Each independent request supplies one INTEGER Quantity. Accept 1–30 inclusive; reject all other integers. No text parsing or cumulative bookings are included.

  2. Cambridge pseudocode
    DECLARE Quantity : INTEGER
INPUT Quantity
IF (Quantity >= 1) AND (Quantity <= 30) THEN
    OUTPUT "Accepted"
ELSE
    OUTPUT "Rejected"
ENDIF
  3. Expected result and checks

    1, 15 and 30 are accepted in separate runs. 0 and 31 are rejected.

Core explanation · Exam essentials

  • Connect analysis, design, coding, testing and maintenance through requirements and evidence.
  • A development model organises the work; successful translation or a completed stage list does not establish suitability.
Common misconception

Analysis determines what is required; coding is not a substitute for agreeing the requirement.

Check your understanding

Which stage establishes whether reserved books may be renewed?

Check your answer

Analysis agrees the rule with users; design specifies how the program applies it.

02

Waterfall: planned sequential stages

S12.01.A03

Visual overview

A stable payroll rule

  1. AnalyseAgree pay rules and statutory deductions.
  2. DesignApprove data definitions and calculations.
  3. CodeImplement the approved design.
  4. TestCompare calculated payslips with independently calculated expected amounts.
  5. MaintainRespond to faults or revised external rules after delivery.

Explain what the sequence achieves

Waterfall organises development largely in a planned sequence. Requirements are reviewed before the solution design becomes the basis for coding; later tests check the implemented behaviour against those requirements. Clear stage outputs make progress, responsibilities and approval decisions easier to track.

Apply the benefit to a requirement

For a fixed booking-capacity calculation with stable rules and required written approvals, a team can agree the range and messages before coding. Each approved output gives the next activity a defined starting point. This is a reasoned benefit of the model, rather than a claim that all small projects need waterfall.

Trace the cost of a late change

Suppose users see the working form near final testing and explain that their group bookings need an additional rule. The team may need to revise the requirements, design, implementation and existing tests. Returning to earlier work is possible, but the late discovery makes previously completed work less reusable. That is why uncertain interaction requirements can make a strongly sequential approach costly.

Core explanation · Exam essentials

  • Waterfall uses largely sequential, reviewed stages and documented outputs.
  • Stable requirements support planning; late requirement changes can require substantial rework.
Common misconception

Waterfall is not a promise that requirements can never change; late changes are a drawback because they can be expensive.

Check your understanding

Why is a new pay rule discovered during final testing costly?

Check your answer

It can require changes to the agreed requirements, design, code and previous tests.

03

Iterative development: learn from successive versions

S12.01.A04

Visual overview

Give each cycle a purpose

Iterative development revisits analysis, design, coding and testing through successive versions. An iteration has a defined aim, produces something that can be evaluated, and uses the findings to decide the next change. Repeatedly executing an unchanged program is not an iteration of its development.

Improve the booking form through evidence

  1. First version: Implement the agreed 1–30 rule and the two decision messages. Verify those outputs.
  2. Review: Users can see a refusal but do not understand which value to enter. Record that specific finding.
  3. Next version: Keep the range rule and add a useful explanation of the permitted range. Test the old acceptance decisions and the new message.
  4. Decide whether to continue: Compare the result with the agreed goals. Prioritise any remaining issue instead of adding every suggestion.

Balance feedback with control

Early feedback reduces the risk of completing an unsuitable solution. Smaller changes can also be easier to diagnose. However, repeated requests can expand scope, and code, documents and tests can drift apart unless the team controls versions, priorities and completion criteria. A new iteration may improve existing behaviour, add a planned part, or do both.

Core explanation · Exam essentials

  • Successive versions use feedback to refine the solution.
  • Define scope and completion criteria for each iteration and keep documents and tests consistent.
Common misconception

Iteration means reviewing and improving versions, not repeatedly running the same finished program.

Check your understanding

What evidence should determine the next iteration?

Check your answer

Observed defects and user feedback evaluated against the intended requirements and priorities.

04

RAD and choosing a suitable model

S12.01.A05S12.01.A06

Visual overview

Connect the defining features

Rapid application development uses rapid prototypes, frequent user involvement and short agreed time boxes. A prototype makes selected behaviour tangible so users can evaluate it early. A time box limits the time spent on the agreed scope; it does not guarantee that every suggested feature can be delivered.

Explain how rapid construction is possible

A team can reuse a suitable form component to build a booking interface quickly. Separable parts may be developed alongside one another, then integrated through agreed interfaces. Reuse avoids repeating suitable work; modularity reduces interference between parts. Unsuitable components, tightly coupled modules or difficult integration can remove those advantages.

State the conditions and limits

Daily access to booking staff allows a prototype to reveal unclear messages while there is still time to revise them. If users cannot review it until delivery, the feedback mechanism is absent. Skilled developers still need to check validation, data transfers and required outputs; an attractive prototype does not establish a complete, reliable system.

Make a choice when the constraints change

EvidenceImplication
Stable calculation rules; formal approvalsWaterfall may make planned stage evidence easier to manage.
Major purpose known; interaction details evolveIterative review can improve working versions as needs become clearer.
Short prototype deadline; available users; separable componentsRAD can shorten the route to useful feedback.
A short deadline but no users or reusable componentsThe deadline alone does not establish that RAD fits. Explain the missing conditions.

Core explanation · Exam essentials

  • RAD combines rapid prototypes, user feedback and time-boxed development.
  • Justify the model using stability, user access, modularity, delivery needs and assurance constraints.
Common misconception

Speed alone does not justify RAD; explain how user participation and prototype feedback fit the actual project.

Check your understanding

Why could unavailable users undermine RAD?

Check your answer

The rapid review cycle depends on timely feedback; delayed decisions can invalidate a time box or produce unsuitable features.

Practice questions

Question 1 · Command word: Describe4 teacher marks

Describe the purpose of a development life cycle and identify the stage responsible for each output: agreed user requirements, a module design, executable statements, recorded test results and a post-release correction.

S12.01.A01S12.01.A02
Answer and checking points — teacher-written
  1. It organises development work and the evidence needed to check progress towards a suitable program.
  2. Agreed requirements belong to analysis; the module design belongs to design.
  3. Executable statements are produced during coding; recorded comparisons belong to testing.
  4. A correction to the delivered program is maintenance.

Common error: Distinguish the required behaviour from the algorithm used to implement it.

Question 2 · Command word: Explain2 teacher marks

A tax calculator has fixed rules and requires written approval of each stage. Explain one benefit and one drawback of using waterfall.

S12.01.A03
Answer and checking points — teacher-written
  1. Stage documents provide an agreed basis for approving the fixed calculation rules.
  2. If a rule is corrected late, already approved design and implementation work may need revision.

Common error: Link both points to staged development.

Question 3 · Command word: Explain2 teacher marks

A timetable team revises its interface after each demonstration. Explain how iterative development helps and give one management problem it creates.

S12.01.A04
Answer and checking points — teacher-written
  1. Each demonstration supplies evidence that can change the next working version.
  2. Repeated revisions require control of priorities and versions to prevent continuing scope growth.

Common error: Describe how feedback changes a version, rather than merely saying that work repeats.

Question 4 · Command word: Explain3 teacher marks

A booking form has a fixed 1–30 range rule but uncertain screen messages. Staff can review a prototype daily. Explain how RAD could obtain useful feedback, and how your choice would change if staff could review only at final delivery.

S12.01.A03S12.01.A04S12.01.A05S12.01.A06
Answer and checking points — teacher-written
  1. A rapid prototype makes the uncertain messages available for staff to evaluate early.
  2. Short time boxes and daily decisions allow the messages to be revised while preserving the agreed range rule.
  3. Without timely staff access, the proposed RAD feedback cycle loses a necessary condition; another model must be justified using the remaining requirements and approval constraints.

Common error: Do not claim that a short deadline alone guarantees RAD suitability.

Question 1 · Command word: Describe4 teacher marks

Describe three defining features of RAD. Explain why an interface project with available users and a two-week prototype deadline could use it.

S12.01.A05S12.01.A06
Answer and checking points — teacher-written
  1. Rapid prototypes make an early interface available for inspection.
  2. Time boxes set short fixed development periods.
  3. Frequent user participation supplies feedback during development.
  4. The available users can evaluate the prototype within the short deadline and guide subsequent changes.

Common error: The three features are distinct; rapid coding alone does not describe RAD.

Original question · Cambridge 9618/21

1. Choose a development model for changing requirements

Cambridge 9618/21 · May/June 2023 · 5(a)(i), 5(a)(ii) · 3 marks

Selected parts: 5(a)(i) [2]; 5(a)(ii) [1].

Reading the question — teacher guidance

Use both pressures in the scenario: reach the market early and respond as console features become known.

Solution / model answer — teacher-written

5(a)(i): A waterfall approach may not produce working software until late, so a competitor may demonstrate the console first. It also makes changing requirements harder to accommodate after earlier stages have been completed.

5(a)(ii): An iterative model or Rapid Application Development (RAD) is more appropriate.

Official mark scheme
Why this earns marks — teacher explanation

Part (i) gives one mark for each of two accepted reasons. Part (ii) gives one for an accepted alternative. An unsupported claim that waterfall is always unsuitable does not use the scenario.

Common mistakes — teacher analysis

A model choice is justified by project conditions. Do not claim that waterfall never permits any feedback; explain the difficulty and delay when requirements change.
