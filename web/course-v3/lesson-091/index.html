Develop a booking system · Concept 23

Follow a change after delivery

Observe

A new booking-desk message

  • The delivered system follows the agreed maximum of 6 seats per request.
  • A new approved arrangement allows up to 8 seats per request.
  • The input hint still says 1–6, the code still checks <= 6, and the old maximum test still uses 6.

Look, then discuss

Which connected parts must change before the new rule is consistently supported?

Predict what happens if only the help text changes. Then predict what happens if only the code changes. Neither change alone keeps the user instruction, behaviour and evidence aligned.

Recall

Recall requirement, implementation and test

A required limit determines the design, comparison, user guidance and expected boundary results. The new limit is a revised requirement; it does not mean the original 1–6 implementation was faulty.

Explain

Explanation · 1 / 3

Explain why maintenance continues

Real use can expose faults not found before delivery. Operating systems, devices, libraries or external rules can change. Users may need additional functions or better performance. Maintenance changes delivered software so that it remains useful under these circumstances.

Explanation · 2 / 3

Record what changed and why

Confirm the new 1–8 rule and its reason before editing. Identify every dependent location: the interface guidance, validation condition, documentation and test cases. A change request should distinguish a new requirement from a defect in the old one.

Explanation · 3 / 3

Update affected evidence coherently

After the approved change, 7 and 8 should be accepted, while 9 should be rejected. Old 0 must remain rejected and old ordinary values must remain accepted. Change expectations because the requirement changed, not because an arbitrary patch happens to produce them.

Work together

Check the new maximum without losing the minimum

The old rule is 1–6; the new approved rule is 1–8. Every request remains independent.

Work together · 1 / 2

List changed and retained behaviour

Inputs 7 and 8 deliberately change from rejection to acceptance. Input 6 still passes. Input 0 still fails. The next rejected upper neighbour is now 9.

Work together · 2 / 2

Prepare a coherent revision

Revise the displayed range and upper comparison to 8, update the specification and expected cases, then repeat the revised boundary cases and relevant unchanged cases. Record which version implements which rule.

A maintenance change includes its impact on users, code and evidence.

Experiment

Predict which outputs deliberately change when the maximum moves from 6 to 8. Update the dependent rule, guidance and tests in the activity, then compare 0, 6, 7, 8 and 9 with the new requirement.

Check

Try it yourself · Teacher-written

A revised limit makes input 7 valid. Is changing its expected result from Rejected to Accepted always hiding a defect?

Check your reasoning

No. It is correct when an approved requirement changed from maximum 6 to maximum 8. It would hide a defect if the original 1–6 requirement still applied and the expected result were changed merely to match faulty code.

Develop a booking system · Concept 24

Classify the cause of the change

Observe

Three delivered-system change tickets

TicketReason
Fix the charge for exactly 6 seatsThe original calculation requirement is not met
Support a replacement printer interfaceThe external device environment changed
Add an optional booking-summary chartUsers want an improvement to a working report

Look, then discuss

Why can all three tickets change code but belong to different categories?

Look for the cause stated in each ticket. The number of edited lines, adding a function or changing a screen does not determine the category.

Recall

Recall old and revised requirements

A defect means the program fails a requirement that already applied. A new environment or improvement request can create a new requirement even when the old behaviour was correct.

Explain

Explanation · 1 / 4

Corrective: repair an existing fault

Corrective maintenance restores behaviour the system should already provide. Repairing a wrong total or an existing response-time violation is corrective because the original requirement was not met.

Explanation · 2 / 4

Adaptive: respond to the changed environment

Adaptive maintenance lets a program work with changed operating systems, hardware, library interfaces, external rules or operational circumstances. A new printer interface requires an adaptation even if the old printer support was correct.

Explanation · 3 / 4

Perfective: improve a delivered system

Perfective maintenance improves functionality, efficiency or usability beyond the currently satisfied requirements. An extra report or a faster already-compliant search can be perfective. Classify from the stated reason, not from the word “faster” alone.

Explanation · 4 / 4

Split mixed requests and ask what changed

“Fix duplicate charges, support a new printer and add a chart” contains three different causes. A changed tax rate could be corrective if the old value was already wrong, or adaptive if a new external rule changes it. The same edited line can serve different maintenance purposes.

Work together

Explain why a correct program still needs adaptation

The booking program calls a printer library. A system update replaces the library’s interface.

Work together · 1 / 2

Identify the external change

The old program worked with the old interface. Its caller now needs the replacement interface, so the trigger is environmental change rather than a newly discovered old fault.

Work together · 2 / 2

Give a contextual consequence

Update the printer call and any affected data handling, then test the connection. The same reasoning applies to a factory program when its control hardware or a library it uses changes.

A classification earns its explanation by linking the change to the stated cause.

Check

Try it yourself · Teacher-written

A search already meets its required response time. Users request a faster version. Then a different search is found to exceed its existing required time. Classify the two changes.

Check your reasoning

The requested improvement to the already-compliant search is perfective. Repairing the search that violates an existing response-time requirement is corrective.

Original question · Cambridge 9618/22

1. Explain why a working program needs adaptation

Cambridge 9618/22 · May/June 2025 · 1(b)(i) · 3 marks

Selected parts: 1(b)(i) [3].

Hint — reading the question

Adaptive maintenance responds to changes around the program. Give three reasons applicable to controlling this factory’s production line.

Reasoning and model answer — teacher-written

The production-line requirements change. New control hardware or technology replaces equipment used by the program. A library module used by the program changes its interface or required behaviour.

Official mark scheme
Why this earns marks — teacher explanation

There is one mark for each accepted reason, to three. A change in relevant legislation is another official option.

Common mistakes — teacher analysis

Repairing an existing defect is corrective maintenance. Improving efficiency without an external change is normally perfective maintenance.

Question 1 · Command word: Explain2 teacher marks

Explain two reasons why a delivered booking system may need maintenance after acceptance.

S12.08.A01
Answer and checking points — teacher-written
  1. Actual use can expose previously undetected booking faults.
  2. A changed external platform or a new user requirement can make an otherwise correct version insufficient.

Common error: Acceptance assesses the agreed system at that time, not all future circumstances.

Question 2 · Command word: Identify3 teacher marks

Identify and explain the maintenance type for each request: restore an omitted required report row; support a new printer interface; add a requested chart.

S12.08.A02S12.08.A03S12.08.A04
Answer and checking points — teacher-written
  1. Restoring required output is corrective because it repairs an existing fault.
  2. The new printer interface requires adaptive maintenance because the environment changed.
  3. The extra chart is perfective because it improves the delivered functionality.

Common error: Use the stated cause rather than the size of the edit.

Question 3 · Command word: Explain2 teacher marks

Explain why two edits to the same invoice calculation could belong to different maintenance categories: fixing an incorrect existing tax rate and implementing a newly legislated tax rate.

S12.08.A02S12.08.A03
Answer and checking points — teacher-written
  1. Fixing a rate that already contradicted the required rule repairs a fault, so it is corrective.
  2. Implementing a newly imposed legal rate responds to an external change, so it is adaptive.

Common error: The calculation file is the same; the reasons for changing it differ.

Question 4 · Command word: Describe3 teacher marks

A booking program correctly enforces a 30-person limit. The building is modified and its approved capacity becomes 35. Describe the impact analysis and tests needed to implement the changed requirement. Explain why changing the expected result for Quantity 31 is justified here but was not justified when correcting the original <= 31 defect.

S12.08.A01S12.08.A03
Answer and checking points — teacher-written
  1. Identify the range comparison, displayed guidance, related interfaces, documentation and test data that depend on the capacity.
  2. Use the new approved range for tests, including 35 accepted and 36 rejected, and keep relevant checks such as 0 rejected.
  3. 31 is now valid because the requirement changed; under the old 30-person rule, altering its expected rejection would only hide a defect.

Common error: A regression check protects still-required behaviour; it does not forbid an approved requirement change.
