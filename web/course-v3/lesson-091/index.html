Corrective, adaptive and perfective maintenance

Explain why delivered software changes and classify each change by its cause.

Is the change repairing a fault, responding to a changed environment or improving the system?

Before you start

Does passing acceptance testing mean a program can never need changing?

Check your answer

No. Later use can reveal faults, the external environment can change and users can request improvements.

01

Why maintenance continues after delivery

S12.08.A01

Visual overview

Control a post-release change

  1. RequestRecord the problem or desired improvement and its reason.
  2. ImpactIdentify affected calculations, data and module interfaces.
  3. AmendImplement a coherent change and update relevant documentation.
  4. VerifyCheck the new behaviour and repeat tests for existing functions.

Explain why delivery is not the end

Acceptance checks agreed requirements at a particular time. Later use can expose undiscovered defects; operating systems, equipment and external rules can change; users can request improvements. Continuing maintenance keeps the delivered program useful under these changing circumstances.

Control a post-delivery booking change

  1. Understand the request: Record what changed, why, and which existing requirement is being corrected or replaced.
  2. Assess impact: Identify the range rule, input guidance, connected modules, documentation and tests that depend on the limit.
  3. Amend coherently: Update the approved rule and its implementation together; do not change an unrelated module just because it is nearby.
  4. Verify and record: Test the revised requirement and relevant unchanged behaviour; retain the version and reason for the change.

Distinguish a changed requirement from a regression

If a room capacity legitimately changes from 30 to 35, old input 31 is now expected to pass. Updating that expectation follows the revised requirement. It is different from rewriting an expected result merely to hide the old program’s defect. Regression checks protect behaviour that is still required, such as rejecting 0 and accepting ordinary valid requests.

Core explanation · Exam essentials

  • Maintenance responds to faults, environmental changes and requested improvements after delivery.
  • Assess affected requirements, interfaces, documents and tests before changing the program.
Common misconception

Maintenance is not limited to fixing bugs; a correct program can need changes for new circumstances.

Check your understanding

Why retain the reason for a change?

Check your answer

It explains the requirement or external constraint behind the revised behaviour and helps later maintenance decisions.

Use a paired counterexample

The same calculation file can receive a corrective change when its tax rate was already wrong, or an adaptive change when a new external rule sets a different rate. Adding code does not automatically mean perfective maintenance. Similarly, making a search faster is perfective when it already meets its requirement, but repairing a violation of an existing response-time requirement can be corrective.

Handle mixed or incomplete descriptions

A request can contain several causes. Split “fix duplicated charges, support a new driver and add a chart” into three changes rather than assigning one category to the whole batch. If the reason is absent, state what further information would distinguish a fault repair from an enhancement; do not invent a history.

Worked example · Separate a fault from an enhancement

  1. Original requirement

    The search must return all matching titles.

  2. Fault report

    The final matching title is omitted; restoring it is corrective.

  3. New request

    Show results in a sortable table; adding this feature is perfective.

  4. External change

    Update the search service client for a new API; that reason is adaptive.

Core explanation · Exam essentials

  • Corrective repairs existing faults; adaptive responds to external change; perfective improves the delivered system.
  • Justify the category from the stated cause, including when similar edits have different reasons.
Common misconception

A feature added to meet a changed external rule may be adaptive; adding code does not automatically make a change perfective.

Check your understanding

Is a faster search always a correction?

Check your answer

No. If the existing system meets its required behaviour and users request an improvement, it is perfective.

Cambridge command words

Practice questions

Question 1 · Command word: Explain2 marks

Explain two reasons why a delivered booking system may need maintenance after acceptance.

S12.08.A01
Answer and marking points
  1. Actual use can expose previously undetected booking faults.
  2. A changed external platform or a new user requirement can make an otherwise correct version insufficient.

Common error: Acceptance assesses the agreed system at that time, not all future circumstances.

Question 2 · Command word: Identify3 marks

Identify and explain the maintenance type for each request: restore an omitted required report row; support a new printer interface; add a requested chart.

S12.08.A02S12.08.A03S12.08.A04
Answer and marking points
  1. Restoring required output is corrective because it repairs an existing fault.
  2. The new printer interface requires adaptive maintenance because the environment changed.
  3. The extra chart is perfective because it improves the delivered functionality.

Common error: Use the stated cause rather than the size of the edit.

Question 3 · Command word: Explain2 marks

Explain why two edits to the same invoice calculation could belong to different maintenance categories: fixing an incorrect existing tax rate and implementing a newly legislated tax rate.

S12.08.A02S12.08.A03
Answer and marking points
  1. Fixing a rate that already contradicted the required rule repairs a fault, so it is corrective.
  2. Implementing a newly imposed legal rate responds to an external change, so it is adaptive.

Common error: The calculation file is the same; the reasons for changing it differ.

Question 4 · Command word: Describe3 marks

A booking program correctly enforces a 30-person limit. The building is modified and its approved capacity becomes 35. Describe the impact analysis and tests needed to implement the changed requirement. Explain why changing the expected result for Quantity 31 is justified here but was not justified when correcting the original <= 31 defect.

S12.08.A01S12.08.A03
Answer and marking points
  1. Identify the range comparison, displayed guidance, related interfaces, documentation and test data that depend on the capacity.
  2. Use the new approved range for tests, including 35 accepted and 36 rejected, and keep relevant checks such as 0 rejected.
  3. 31 is now valid because the requirement changed; under the old 30-person rule, altering its expected rejection would only hide a defect.

Common error: A regression check protects still-required behaviour; it does not forbid an approved requirement change.

Question 1 · Command word: Identify · 3 marks

A map application already meets its agreed search-time requirement. Users request faster searches and an additional offline map view. Identify the maintenance type and justify it for both changes.

Answer and marking points
  • Both changes are perfective.
  • A faster compliant search improves performance beyond the existing requirement.
  • An offline view adds useful functionality requested after delivery.

Common error: Do not invent a prior performance fault.

Question 2 · Command word: Identify · 2 marks

A school replaces its operating system and discovers that an otherwise correct attendance program can no longer call the printer driver. Identify the maintenance type and explain why it is not necessarily corrective.

Answer and marking points
  • The change is adaptive because the operating environment has been replaced.
  • Failure under the new driver does not show that the program violated the requirements of its former environment.

Common error: Classify the cause of incompatibility rather than just the visible failure.

Question 3 · Command word: Identify · 4 marks

A library adds barcode input, corrects a double-charge defect and supports a changed national reporting format. Identify the type of each change and explain why the team should assess their effects before editing the loan module.

Answer and marking points
  • Barcode input is perfective when it adds a requested way to use the system.
  • Repairing the double charge is corrective.
  • Supporting the changed external reporting format is adaptive.
  • Shared loan data or interfaces may affect existing charges and reports, so impact analysis identifies what must be changed and retested.

Common error: Distinguish the three causes even if the changes share code.

Lesson review

Summary

Continuing need

Real use, external changes and new demands keep maintenance necessary.

Classify the cause

Fault repair is corrective; environment response is adaptive; improvement is perfective.

Control the impact

Check revised behaviour and protect the functions that must remain.
