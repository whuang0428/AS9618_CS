Before you start

Does a function call merely display a result?

Check your answer

No. A function returns a value that the caller can use in an expression; a separate output statement or procedure can display it.

01

Decompose a problem into a structure chart

S12.02.A01S12.02.A02S12.02.A03

Visual overview

Start with responsibilities

A structure chart decomposes a problem into modules. A box names a coherent responsibility; a hierarchy line shows which parent calls a child. The controlling module sits above the modules it invokes. A large responsibility can be refined again, giving another level. Individual assignments inside a module do not each require a box.

Explain the chosen decomposition

For one order, the parent coordinates input, calculation and display. ReadOrder obtains Quantity and UnitPrice; CalculateCost computes their product; DisplayCost presents the supplied Cost. These responsibilities are separated because the reader supplies facts, the function answers a calculation question, and the writer performs an output action.

Read the chart’s conventions

The parent connects the work: an amount returned by CalculateCost must reach DisplayCost through the parent. Drawing a direct ReadOrder-to-DisplayCost call would claim a different hierarchy. The grey connections in the supplied chart show calls; labelled teal arrows show values and direction. Its left-to-right order is part of this example’s stated sequence, not a substitute for all internal control flow.

Core explanation · Exam essentials

  • A structure chart shows module hierarchy, responsibilities and interfaces.
  • Decompose further when a subtask still contains several coherent responsibilities.
Common misconception

A structure chart is not a flowchart: module hierarchy does not show each decision or loop inside a module.

Check your understanding

Why should DisplayCost receive Cost rather than ask for the quantity again?

Check your answer

It displays the result already calculated for the current order; obtaining fresh inputs could make the output describe a different order.

Make parameters and returned values explicit

Account for every transferred value

For every module, ask which data it needs before it starts and which results or changes it supplies afterwards. A parameter label without direction leaves the caller unsure whether it should provide a value or expect one back. The interface must also state types and meanings, not just names.

Use the interface from Lessons 080–081

Argument position determines which formal parameter receives which value. Check number, order, types and passing modes at every call. A BYREF update and a function return both communicate a result, but by different mechanisms. The reader uses reference parameters here because it supplies two entered values to the caller; that is a design choice for this interface, not a rule that every input routine must use BYREF.

Core explanation · Exam essentials

  • Label data direction and match argument order, types and parameter modes.
  • Distinguish a function return, an OUTPUT action and a BYREF caller update.
Common misconception

A printed number is not a function return value. CALL DisplayCost(Cost) does not assign a numeric result.

Check your understanding

What changes if ReadOrder receives Quantity only by value?

Check your answer

Assigning the local copy does not supply the entered quantity to the parent.

03

Derive and check equivalent pseudocode

S12.02.A03S12.02.A04

Visual overview

From chart to implementation

  1. InterfacesSpecify reader outputs, calculation inputs and returned result.
  2. DefinitionsWrite the input, multiplication and output bodies.
  3. ParentDeclare data and connect the calls through its variables.
  4. TraceUse Quantity 3 and UnitPrice 2.50; the displayed cost must be 7.50.

Derive complete pseudocode from the chart

  1. Define interfaces: Turn each named responsibility into a procedure or function with the stated typed parameters and result.
  2. Supply bodies: Use the problem rule to implement input, arithmetic and output. The chart does not invent the calculation.
  3. Connect the parent: Declare its variables, call the reader, assign the returned Cost, then call the writer.
  4. Start and trace: Include the controlling call and trace the same values through definitions and call sites.

Check completeness and ordering

The complete order example supplies all definitions and the startup call. ReadOrder must finish before the calculation can use the inputs, and the parent must assign Cost before displaying it. Correct headers alone do not constitute an implementation: calls, bodies and local declarations are needed.

Check meaningful limits of the example

Use the ordinary case 3 and 2.50 to obtain 7.50. A single item at price 0 legitimately gives 0 under the stated non-negative-price assumption. Negative prices and text input are outside this example’s contract; do not claim that the program validates them.

Worked example · Order chart translated into a complete program

  1. Assumptions

    One order; Quantity is a positive integer and UnitPrice a non-negative real. Inputs already have these types.

  2. Equivalent pseudocode
    PROCEDURE ReadOrder(BYREF Quantity : INTEGER, BYREF UnitPrice : REAL)
    INPUT Quantity
    INPUT UnitPrice
ENDPROCEDURE

FUNCTION CalculateCost(BYVAL Quantity : INTEGER, BYVAL UnitPrice : REAL) RETURNS REAL
    RETURN Quantity * UnitPrice
ENDFUNCTION

PROCEDURE DisplayCost(BYVAL Cost : REAL)
    OUTPUT Cost
ENDPROCEDURE

PROCEDURE ProcessOrder
    DECLARE Quantity : INTEGER
    DECLARE UnitPrice : REAL
    DECLARE Cost : REAL
    CALL ReadOrder(Quantity, UnitPrice)
    Cost <- CalculateCost(Quantity, UnitPrice)
    CALL DisplayCost(Cost)
ENDPROCEDURE

CALL ProcessOrder
  3. Trace

    ReadOrder supplies 3 and 2.50; CalculateCost returns 7.50; DisplayCost outputs 7.50.

Core explanation · Exam essentials

  • Match module definitions, calls and data flow to the same design.
  • Include declarations, bodies, startup, expected results and relevant input assumptions.
Common misconception

Preserving module names is insufficient if the call order or direction of data changes.

Check your understanding

Why must the parent assign CalculateCost's result before displaying Cost?

Check your answer

Cost must contain the returned amount before DisplayCost receives it.

04

Represent repeated and conditional module calls

S12.02.A01S12.02.A03S12.02.A04

Visual overview

Add repetition and conditional calls

The next design repeats ProcessOrder for a known number of orders. Inside CalculateCost, Member chooses one of two price functions. The chart therefore has both another level of refinement and a condition deciding which lower-level module is called. The curved repetition annotation applies to the ProcessOrder call, not to every line in the whole chart.

State the complete batch contract

ProcessBatch inputs an already valid non-negative INTEGER OrderCount. If it is zero, output No orders without reading an order. Otherwise each order supplies a positive INTEGER Quantity, non-negative REAL UnitPrice and BOOLEAN Member. A member pays 90% of the base amount; a non-member pays the base amount. Rounding to a currency display is not an extra operation in this algorithm.

Connect the added level to executable meaning

Quantity, UnitPrice and Member belong to each ProcessOrder invocation. They are read again for the next order. CalculateCost returns the selected child function’s result; DisplayCost receives that result from ProcessOrder. A function is used as an expression, whereas CALL invokes a procedure. The chart’s symbols and labels are explained here to support design and translation, without treating a structure chart as a statement-by-statement flowchart.

Worked example · Implement the complete batch structure chart

  1. Requirements and initial conditions

    Input non-negative INTEGER OrderCount, then that many triples: positive INTEGER Quantity, non-negative REAL UnitPrice and BOOLEAN Member. Members pay 90%; output one amount per order. Zero orders outputs No orders.

  2. Cambridge pseudocode
    PROCEDURE ReadOrder(BYREF Quantity : INTEGER, BYREF UnitPrice : REAL, BYREF Member : BOOLEAN)
    INPUT Quantity
    INPUT UnitPrice
    INPUT Member
ENDPROCEDURE

FUNCTION StandardCost(Quantity : INTEGER, UnitPrice : REAL) RETURNS REAL
    RETURN Quantity * UnitPrice
ENDFUNCTION

FUNCTION MemberCost(Quantity : INTEGER, UnitPrice : REAL) RETURNS REAL
    RETURN Quantity * UnitPrice * 0.90
ENDFUNCTION

FUNCTION CalculateCost(Quantity : INTEGER, UnitPrice : REAL, Member : BOOLEAN) RETURNS REAL
    IF Member THEN
        RETURN MemberCost(Quantity, UnitPrice)
    ELSE
        RETURN StandardCost(Quantity, UnitPrice)
    ENDIF
ENDFUNCTION

PROCEDURE DisplayCost(BYVAL Cost : REAL)
    OUTPUT Cost
ENDPROCEDURE

PROCEDURE ProcessOrder()
    DECLARE Quantity : INTEGER
    DECLARE UnitPrice : REAL
    DECLARE Member : BOOLEAN
    DECLARE Cost : REAL
    CALL ReadOrder(Quantity, UnitPrice, Member)
    Cost <- CalculateCost(Quantity, UnitPrice, Member)
    CALL DisplayCost(Cost)
ENDPROCEDURE

PROCEDURE ProcessBatch()
    DECLARE OrderCount : INTEGER
    DECLARE Index : INTEGER
    INPUT OrderCount
    IF OrderCount = 0 THEN
        OUTPUT "No orders"
    ELSE
        FOR Index <- 1 TO OrderCount
            CALL ProcessOrder()
        NEXT Index
    ENDIF
ENDPROCEDURE

CALL ProcessBatch()
  3. Expected result and checks

    Input 2, 3, 2.50, FALSE, 2, 5.00, TRUE outputs 7.50 then 9.00. Input 0 alone outputs No orders and reads no order. One member item at zero price costs zero.

Core explanation · Exam essentials

  • Show which calls repeat and which calls are selected conditionally.
  • Trace one complete invocation, then account for the next invocation and the zero-call path.
Common misconception

A conditional call does not mean both alternative functions execute.

Check your understanding

Which calculation functions execute for one non-member order?

Check your answer

CalculateCost calls StandardCost; MemberCost is not called for that order.

Practice questions

Question 1 · Command word: Explain2 teacher marks

Explain why ReadOrder uses by-reference parameters while CalculateCost can use by-value parameters.

S12.02.A01
Answer and checking points — teacher-written
  1. ReadOrder must update the caller's variables with the newly entered order data.
  2. CalculateCost needs copies for arithmetic and supplies its single result through RETURN.

Common error: A function return and a by-reference update are different ways to supply a result.

Question 2 · Command word: Write4 teacher marks

Write the parent ProcessOrder procedure for the supplied chart, including declarations, the reader call, the calculation and the display call. The three child definitions are those shown in the worked example.

S12.02.A04
Answer and checking points — teacher-written

    INPUT UnitPrice
ENDPROCEDURE

FUNCTION CalculateCost(BYVAL Quantity : INTEGER, BYVAL UnitPrice : REAL) RETURNS REAL

PROCEDURE ProcessOrder

    CALL ReadOrder(Quantity, UnitPrice)

    CALL DisplayCost(Cost)
ENDPROCEDURE

CALL ProcessOrder
  1. Quantity is INTEGER; UnitPrice and Cost are REAL within the parent.
  2. CALL ReadOrder(Quantity, UnitPrice) obtains the two values.
  3. Cost <- CalculateCost(Quantity, UnitPrice) stores the returned result.
  4. CALL DisplayCost(Cost) follows the calculation, and ENDPROCEDURE closes the parent.

Common error: Do not use CALL for the function expression.

Question 3 · Command word: Draw6 teacher marks

Draw a structure chart from this specification: ProcessBatch reads non-negative OrderCount and calls ProcessOrder that many times, or outputs No orders for zero. ProcessOrder calls ReadOrder to obtain Quantity, UnitPrice and Member, CalculateCost to return Cost, and DisplayCost to display it. CalculateCost calls MemberCost when Member is TRUE, otherwise StandardCost; both receive Quantity and UnitPrice and return the price. Show repetition, conditional calls and labelled data transfers.

S12.02.A01S12.02.A03
Answer and checking points — teacher-written
  1. ProcessBatch controls repeated ProcessOrder calls, with no order call for zero.
  2. ProcessOrder is the parent of ReadOrder, CalculateCost and DisplayCost.
  3. ReadOrder supplies Quantity, UnitPrice and Member to its caller.
  4. CalculateCost receives those values and returns Cost, which the parent supplies to DisplayCost.
  5. The Member condition selects exactly one lower-level function.
  6. Both price-function interfaces receive Quantity and UnitPrice and return a REAL result.

Common error: A hierarchy line is a call relationship, not an assertion that every child always executes.

Original question · Cambridge 9618/22

1. Complete a structure chart from module interfaces

Cambridge 9618/22 · October/November 2023 · 7(a), 7(b) · 6 marks

Selected parts: 7(a) [4]; 7(b) [2].

Reading the question — teacher guidance

Use the headers to label data and control transfers. Reset has a reference parameter, so its value can travel back to its caller; functions return values too.

Solution / model answer — teacher-written
ConnectionTransfers
Module-A → Module-XT1 (INTEGER) and S2 (REAL)
Module-X ↔ ResetCode (INTEGER), passed by reference
Module-A → Module-ZSA (INTEGER)
Module-Z → Module-AINTEGER return
Module-A → Module-YRA (INTEGER) and RB (BOOLEAN)
Module-Y → RestoreOldCode (INTEGER)
Restore → Module-YBOOLEAN return
Module-Y → Module-ABOOLEAN return

7(b): The diamond means selection. Module-A calls one of Module-X, Module-Y or Module-Z according to the decision made at run time.

Official mark scheme
Why this earns marks — teacher explanation

Part (a) awards four grouped points: names; Module-X/Reset transfers; Module-Z input and return; and Module-Y/Restore transfers and returns. Part (b) gives one point for selection and one for correctly naming the four modules.

Common mistakes — teacher analysis

A Boolean is a control couple, shown with a filled circle in the original chart. An integer or real value uses an unfilled data-couple circle. The diamond here is not a flowchart box containing a written condition.
