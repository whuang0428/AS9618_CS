Databases · Concept 01

Read a statement before predicting its effect

Observe

SELECT MemberName
FROM Member
WHERE MemberName = 'Asha';

Look, then discuss

Which words name stored objects, and which values are part of the request?

Look at a request for MemberName from Member. Then compare it with a table definition. The same language can retrieve a current value or define what future records may contain.

Explain

Keep the starting data in view
SELECT MemberName
FROM Member
WHERE MemberName = 'Asha';

Explanation · 1 / 4

Separate commands, identifiers and literals

SELECT and FROM are SQL keywords. Member and MemberName are identifiers naming a table and a field. In a condition such as MemberName = 'Asha', the quoted text is a literal value to compare with the field. MemberName and 'MemberName' therefore mean different things.

SELECT MemberName
FROM Member
WHERE MemberName = 'Asha';

Explanation · 2 / 4

Read operators exactly

The condition Fee >= 3 includes 3, while Fee > 3 excludes it. AND requires both conditions; OR permits either. Do not paraphrase “at least” as “more than”. Explain what exact records satisfy a condition using the supplied data.

Explanation · 3 / 4

Read types and constraints in a definition

In CREATE TABLE Member (MemberID INTEGER PRIMARY KEY, MemberName VARCHAR(40)); INTEGER is a data type, 40 is the permitted maximum text length, and PRIMARY KEY imposes unique non-null identity. This statement defines an empty structure; it does not create forty members.

CREATE TABLE Member (
    MemberID INTEGER PRIMARY KEY,
    MemberName VARCHAR(40)
);

Explanation · 4 / 4

State the effect and its limits

Describe whether the statement retrieves data, changes values or changes structure; name the target and any restrictions. If a required input or referenced table is missing, explain the dependency instead of inventing a successful result.

Work together

Explain a small change in the condition

Loan 205 has Fee 3, while Loan 203 has Fee 6. The rest of the initial fees are 2, 4 and 0.

Work together · 1 / 2

Read the inclusive condition

Fee >= 3 matches loans 202, 203 and 205. The boundary value 3 is allowed by the equals part of the operator.

Work together · 2 / 2

Read the changed condition

Fee > 3 matches only loans 202 and 203. The stored records have not changed; the result condition is different.

A good explanation names the objects and exact effect instead of translating keywords one at a time.

Check

Explain it yourself · Teacher-written

Explain why CREATE TABLE Member (MemberName VARCHAR(40)); does not add a member named MemberName.

Check your reasoning

MemberName is the column identifier, VARCHAR(40) defines variable-length text up to 40 characters, and CREATE TABLE defines a structure. A separate insertion with an actual name value is needed to create a member record.

Connect

Keep this idea

Read identifiers, values, operators and definitions in their roles before predicting the result.

Use this reading method while building queries, then return to define the tables with DDL.

Check a common misunderstanding

A number in VARCHAR(40) is a size limit, not a record count or a stored member value.

Name the database to create

CREATE DATABASE SchoolLibrary; requests a database named SchoolLibrary. The identifier names the database, not a table or member. The command is DDL because it establishes structure.

Explanation · 1 / 4

Choose text types

CHARACTER(n) stores fixed-length character data, such as a one-character initial. VARCHAR(n) stores variable-length text up to n characters, such as a name of up to 40 characters. A phone number is normally text even when its characters are digits, because leading zeroes and symbols matter and arithmetic is not its purpose.

Explanation · 2 / 4

Choose logical and numeric types

BOOLEAN represents logical TRUE or FALSE. INTEGER stores whole numbers such as identifiers or counts. REAL stores numbers that may have fractional parts. Type choice defines what values and operations make sense; REAL may use approximate numeric representation, so it is not a promise of exact decimal arithmetic.

Explanation · 3 / 4

Keep dates and times meaningful

DATE represents a calendar date and TIME a time of day. They allow suitable validation and comparison instead of treating every input as arbitrary text. Quoted ISO-style values such as '2027-03-01' make the examples unambiguous.

Explanation · 4 / 4

Write a complete table definition

Place the field definitions inside parentheses, separate them with commas and end the statement with a semicolon. This teaching Visit table includes all seven syllabus types and refers to an existing Member. The shorter Member and Loan tables remain the query fixtures. The next concept explains the key declarations line by line.

CREATE TABLE Visit (
    VisitID INTEGER PRIMARY KEY,
    Initial CHARACTER(1),
    VisitorName VARCHAR(40),
    Active BOOLEAN,
    Fee REAL,
    VisitDate DATE,
    ArrivalTime TIME,
    MemberID INTEGER NOT NULL,
    FOREIGN KEY (MemberID) REFERENCES Member(MemberID)
);

Work together

Work together · 1 / 2

Match each fact to its definition

VisitID 101 is an integer. A fits CHARACTER(1). Asha fits VARCHAR(40). TRUE is Boolean, 2.5 fits REAL, and the date and time use their separate types. MemberID 1 refers to the member already created in the preceding laboratory step.

Work together · 2 / 2

Check changed inputs

An initial EL exceeds the one-character definition. A name longer than 40 characters exceeds the declared bound. A calendar value such as 2027-02-30 is not a valid date. The exact error message depends on the DBMS, but do not silently describe invalid input as stored correctly.

A table definition declares the type and permitted structure of every field before records are added.

Databases · Concept 04

Declare primary and foreign keys in SQL

Observe

CREATE TABLE Member (
    MemberID INTEGER,
    MemberName VARCHAR(40),
    Active BOOLEAN,
    PRIMARY KEY (MemberID)
);

Look, then discuss

Which part of a CREATE TABLE statement makes Loan.MemberID a reference?

An INTEGER field can store the number 9 without knowing whether member 9 exists. Compare a plain type declaration with the explicit REFERENCES clause.

Explain

Keep the starting data in view
CREATE TABLE Member (
    MemberID INTEGER,
    MemberName VARCHAR(40),
    Active BOOLEAN,
    PRIMARY KEY (MemberID)
);

Explanation · 1 / 4

Create the referenced table first

Define Member and declare PRIMARY KEY (MemberID). The key is unique and non-null. A table-level constraint names the field to which it applies; an inline MemberID INTEGER PRIMARY KEY declaration expresses the same single-field intention.

CREATE TABLE Member (
    MemberID INTEGER,
    MemberName VARCHAR(40),
    Active BOOLEAN,
    PRIMARY KEY (MemberID)
);

Explanation · 2 / 4

Name both sides of the foreign key

FOREIGN KEY (MemberID) names the local Loan field. REFERENCES Member(MemberID) names the target table and key. Matching names alone would not declare a reference. Compatible field types and an appropriate referenced key are required.

CREATE TABLE Loan (
    LoanID INTEGER,
    MemberID INTEGER NOT NULL,
    Fee REAL,
    Returned BOOLEAN,
    PRIMARY KEY (LoanID),
    FOREIGN KEY (MemberID) REFERENCES Member(MemberID)
);

Explanation · 3 / 4

Separate required-value and reference rules

NOT NULL is included to express our explicit rule that every loan must have a member. REFERENCES checks that a supplied member exists. The primary key prevents repeated LoanIDs while the foreign key permits several loans for the same member.

Explanation · 4 / 4

Declare a composite key together

For Membership with one member-group association per pair, use PRIMARY KEY (MemberID, GroupID). Do not declare two independent primary keys: the combination identifies the association, and each component remains a separate foreign key to its parent.

Work together

Predict the first inserted loan

Member contains only (1, Asha, TRUE). Loan has the displayed definition and is empty.

Work together · 1 / 2

Evaluate a valid reference

Loan (201, 1, 2, FALSE) has a new LoanID and a member reference that exists. It passes the shown identity and reference constraints.

Work together · 2 / 2

Evaluate two failures

A second LoanID 201 violates the primary key. A new LoanID 202 with MemberID 9 violates the foreign key. A missing member value violates the separate NOT NULL declaration.

Read the local field, referenced table and referenced key separately to understand a foreign-key declaration.

Check

Explain it yourself · Teacher-written

In FOREIGN KEY (BorrowerID) REFERENCES Member(MemberID), must the two field names be identical? What does each name mean?

Check your reasoning

No. BorrowerID is the local field in the referencing table; MemberID is the referenced key in Member. The declared relationship and compatible types establish the reference, not matching spelling.

Change a definition while preserving its records

Observe

ALTER TABLE Loan ADD DueDate DATE;

Look, then discuss

After adding DueDate, what date belongs to a loan that already existed?

An earlier Loan table stores only LoanID and Returned, including (201, FALSE). The library now needs a due date field. Predict the definition and the existing record after adding a nullable DATE field.

Explain

Keep the starting data in view
ALTER TABLE Loan ADD DueDate DATE;

Explanation · 1 / 4

Name the table and the structural change

ALTER TABLE Loan ADD DueDate DATE; adds a field to the existing definition. It does not insert a new loan, assign a date to loan 201 or recreate every row as a new borrowing event.

ALTER TABLE Loan ADD DueDate DATE;

Explanation · 2 / 4

Read the result for existing records

With this nullable field and no supplied default, the existing loan has no due date value, represented as NULL. The LoanID and Returned values remain. A later UPDATE can supply a date for a selected loan.

Explanation · 3 / 4

Add a relationship when the fields already exist

If a legacy Loan table already has MemberID but no reference constraint, an ALTER statement can declare the foreign key. Existing non-null values must satisfy the new rule; adding the constraint is not a repair of unmatched values.

ALTER TABLE Loan
ADD FOREIGN KEY (MemberID) REFERENCES Member(MemberID);

Explanation · 4 / 4

Check names and prior state

The table and required fields must exist. Adding DueDate twice generally fails because the name is already present. The SQL laboratory resets its own exercise state so that a repeated demonstration starts from a known schema.

Question 2 · Command word: Write7 teacher marks

Write CREATE TABLE for Event with EventID (whole number), Code (one character), EventName (up to 30 characters), Confirmed (true/false), Duration (fractional hours), EventDate (calendar date) and StartTime (time of day). Use the seven syllabus data types. Then check whether Code = "AB" and Duration = 1.5 match your chosen field definitions, explaining both decisions.

S8.09.A02
Answer and checking points — teacher-written

One valid SQL answer

CREATE TABLE Event (
    EventID INTEGER,
    Code CHARACTER(1),
    EventName VARCHAR(30),
    Confirmed BOOLEAN,
    Duration REAL,
    EventDate DATE,
    StartTime TIME
);
  1. EventID uses INTEGER in the Event table definition.
  2. Code uses CHARACTER(1); "AB" exceeds the declared length.
  3. EventName uses VARCHAR(30).
  4. Confirmed uses BOOLEAN.
  5. Duration uses REAL and can represent the supplied fractional value 1.5.
  6. EventDate uses DATE.
  7. StartTime uses TIME, with valid comma-separated field definitions inside CREATE TABLE brackets.

Common error: Each type must match the field's meaning; do not quote type names as data values.

Question 3 · Command word: Write2 teacher marks

Write DDL to add Room, containing at most 12 characters, to the existing Event table. Explain why an UPDATE statement is insufficient.

Answer and checking points — teacher-written

One valid SQL answer

ALTER TABLE Event ADD Room VARCHAR(12);
  1. ALTER TABLE Event ADD Room VARCHAR(12);

Question 4 · Command word: Write3 teacher marks

Write a Locker table definition containing LockerID as INTEGER and Location as VARCHAR(30), making LockerID its primary key. State the two requirements this identifier must satisfy.

S8.09.A04
Answer and checking points — teacher-written

One valid SQL answer

CREATE TABLE Locker (LockerID INTEGER, Location VARCHAR(30), PRIMARY KEY (LockerID));
  1. The definition declares PRIMARY KEY (LockerID).
  2. LockerID values must be unique across Locker records.
  3. A record must not have a null LockerID.

Common error: Do not substitute a unique-looking example value for a declared key constraint.

Question 5 · Command word: Write3 teacher marks

Locker(LockerID) already has its primary key. Write Allocation with integer AllocationID as primary key and integer LockerID as a foreign key to Locker. Explain whether several allocations can reference the same locker under these constraints alone.

S8.09.A05
Answer and checking points — teacher-written

One valid SQL answer

CREATE TABLE Allocation (AllocationID INTEGER, LockerID INTEGER, PRIMARY KEY (AllocationID), FOREIGN KEY (LockerID) REFERENCES Locker(LockerID));
  1. Allocation defines its two integer fields and its own AllocationID primary key.
  2. FOREIGN KEY (LockerID) REFERENCES Locker(LockerID) declares the parent link.
  3. Repeated LockerID references are permitted unless an additional uniqueness rule forbids them.

Common error: The referencing field and the referenced table/key must all be named.

Question 6 · Command word: Write3 teacher marks

Venue(VenueID INTEGER PRIMARY KEY) and Booking(BookingID INTEGER PRIMARY KEY, VenueID INTEGER) already exist. Venue contains 4; Booking contains (20, 4). Write ALTER TABLE to add the missing foreign key. Explain the resulting constraint and whether this same addition would succeed if Booking instead contained (20, 9).

S8.09.A03S8.09.A05
Answer and checking points — teacher-written

One valid SQL answer

ALTER TABLE Booking ADD FOREIGN KEY (VenueID) REFERENCES Venue(VenueID);
  1. ALTER TABLE Booking ADD FOREIGN KEY (VenueID) REFERENCES Venue(VenueID);
  2. Each non-null Booking.VenueID must match Venue.VenueID; the successful addition preserves (20, 4).
  3. With (20, 9) and no venue 9, the existing data violates the proposed constraint, so adding it fails until the mismatch is corrected.

Common error: ALTER adds a missing rule to the existing table; do not recreate it or add the already-existing field.
