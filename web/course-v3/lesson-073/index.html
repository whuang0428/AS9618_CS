Name and declare the data

Look, then discuss

What must the program know before it can produce a booking receipt?

Look at one request: Mina wants three seats at 12.50 each. The booking code is 0072 and payment is not yet confirmed. Describe each fact before writing any statements.

Recall

Recall variables and data types

In Section 10 a variable was a named storage location and its data type described the values it could represent. A declaration sets up that name and type. It does not automatically give the variable zero, an empty string or any other initial value.

Explain

Explanation · 1 / 3

Choose names that explain the role

Seats describes a count; Price describes the cost of one seat. Names such as A and B give the reader less help. The same INTEGER type can represent a seat count or a loop counter, but those variables have different responsibilities.

Explanation · 2 / 3

Choose a type from the permitted values

Use INTEGER for whole seats, REAL for a price, STRING for a name or code, BOOLEAN for payment confirmation and CHAR for a single zone letter. DATE is available for a calendar day, using the declared calendar convention. A value containing digits is not necessarily a number for arithmetic.

Explanation · 3 / 3

Declare each variable before use

Write DECLARE, the identifier, a colon and its data type. The next learning steps will give these variables values; declaration alone is not enough to calculate a receipt.

DECLARE Name, BookingCode : STRING
DECLARE Seats : INTEGER
DECLARE Price : REAL
DECLARE Paid : BOOLEAN
DECLARE Zone : CHAR
DECLARE EventDate : DATE

Work together

Translate a booking card into declarations

The desk adds a zone, B, and the event date 12/05/2027 using dd/mm/yyyy.

Work together · 1 / 2

Explain the text choices

BookingCode must keep 0072, so STRING is appropriate. Zone holds exactly one character, so CHAR is appropriate. If zones could include AB, Zone would need STRING.

Work together · 2 / 2

Separate type and current value

DECLARE Seats : INTEGER permits integer values. It does not mean that Seats currently contains 3, or that negative integers are valid booking requests. Those are separate assignment and validation decisions.

Declare from the full data requirement, then explicitly obtain or assign the current value.

Check

Try it yourself · Teacher-written

A room code is "003". Write a suitable declaration and explain why INTEGER would lose useful information.

Check your reasoning

DECLARE RoomCode : STRING. The code identifies a room and must retain all three characters; interpreting it as integer 3 loses the leading zeros.

Connect

Keep this idea

Some values change between bookings, while a configured price stays fixed during the program run.

Program a booking system · Concept 02

Define a fixed value once

Observe

One rule used in three places

  • Receipt: multiply by 12.50.
  • Booking summary: multiply by 12.50.
  • Daily report: multiply by 12.50.

Look, then discuss

If every seat costs 12.50, should the program contain the literal 12.50 in every calculation?

The receipt, booking summary and daily report all need the same price. Imagine that a later version uses 13.00 and one of three repeated numbers is overlooked.

Recall

Recall a literal

A literal is a value written directly in the program: 12.50 is numeric, "0072" is STRING, 'B' is CHAR and FALSE is BOOLEAN. Quotation marks and spelling affect the literal’s type.

Explain

Explanation · 1 / 3

Give the literal a meaningful name

CONSTANT SeatPrice = 12.50 declares and initialises a named constant. Its value remains fixed during that execution. Use = in the declaration, not the assignment arrow.

CONSTANT SeatPrice = 12.50
CONSTANT EventName = "School workshop"
CONSTANT MaximumSeats = 6

Explanation · 2 / 3

Use the constant wherever its rule applies

SeatPrice explains why a number is being multiplied. A later version can change the single definition to 13.00; each use then follows the same revised rule. This reduces missed edits and inconsistent values.

Explanation · 3 / 3

Distinguish a fixed declaration from a calculation

Cambridge constant declarations use a literal: CONSTANT DoublePrice = SeatPrice * 2 is not the required declaration form. Calculate such a result into a suitably declared variable. A constant can be edited in source between versions, but cannot be reassigned during execution. In the following paper excerpt, IF branches choose which postal rate applies: read each branch as a conditional choice. The question here asks about the repeated rate values and their maintenance; writing those decisions is taught later.

A program uses 2.50 as the booking fee in four places.

Work together · 1 / 2

Declare the rate once

Write CONSTANT BookingFee = 2.50 and replace the four fee literals with BookingFee. Retain other unrelated occurrences of 2.50; equal numbers do not necessarily mean the same rule.

Work together · 2 / 2

Explain the benefit in context

A fee change needs one edit to the definition rather than four edits to the calculations. Each calculation still uses the same fee, and the identifier makes its purpose clear.

A useful explanation links the named constant to a specific maintenance task.

Original question · Cambridge 9618/22

1. Make repeated postal rates maintainable

Cambridge 9618/22 · May/June 2023 · 1(a)(i), 1(a)(ii) · 4 marks

Selected parts: 1(a)(i) [1]; 1(a)(ii) [3].

Hint — reading the question

The same postal costs appear at several places in the program. Explain how your representation improves this specific maintenance problem.

Reasoning and model answer — teacher-written

1(a)(i): Use named constants for the postal rates.

1(a)(ii): Each rate is defined once, so a rate change requires one edit rather than changes throughout the program. Reusing that constant avoids inconsistent or mistyped rate values in different calculations. A meaningful name also makes the purpose of a postal rate clear where it is used.

Official mark scheme
Why this earns marks — teacher explanation

Part (i) is one mark. Part (ii) has three marks from four accepted benefits, including defining rates once, avoiding errors, changing a rate once and improving understanding.

Common mistakes — teacher analysis

A constant’s definition can be edited between program versions; its value is not reassigned during a run. A meaningless name such as C1 loses much of the readability benefit.

Program a booking system · Concept 03

Read, calculate and replace a value

Observe

Trace these statements in order

  • Seats <- 3
  • SavedSeats <- Seats
  • Seats <- Seats + 1

Look, then discuss

When Seats contains 3, how can Seats <- Seats + 1 be correct?

Mina first requests three seats, then adds one. Keep a copy of the original request in SavedSeats. Predict whether that copy also changes when Seats is updated.

Recall

Recall a trace

A trace records the state after each executed statement. Read <- as “is assigned”. Assignment is an action, not the mathematical assertion that two expressions are equal.

Explain

Explanation · 1 / 3

Read the old value on the right

For Seats <- Seats + 1, the right side reads the existing 3. This is why Seats must already have a value before the update.

Explanation · 2 / 3

Calculate before storing

The expression 3 + 1 produces 4. Store 4 in the variable named on the left, replacing its old 3. The variable’s name and declared type stay the same.

Explanation · 3 / 3

Keep a copied value separate

SavedSeats <- Seats copies the current value 3. It does not create a permanent connection. A later update to Seats leaves SavedSeats as 3.

DECLARE Seats, SavedSeats : INTEGER
Seats <- 3
SavedSeats <- Seats
Seats <- Seats + 1
OUTPUT Seats
OUTPUT SavedSeats

Program a booking system · Concept 04

Obtain inputs before producing a result

Observe

Receipt requirement

  • Each seat costs 12.50.
  • Read one integer seat quantity.
  • Display the calculated total with a label.

Look, then discuss

What must happen before the program can display the total booking cost?

The seat price is fixed, but each attendee chooses a different quantity. Put the actions “ask”, “read”, “calculate” and “display” into a workable order.

Recall

Recall sequence

Statements run in order unless a control structure changes that order. A calculation cannot use an input that has not yet been read. A prompt is output text telling the user what to enter.

Explain

Explanation · 1 / 3

Ask and read are separate operations

OUTPUT "Enter seats" displays a prompt. INPUT Seats then obtains a value and stores it in Seats. The prompt does not itself read the value.

Explanation · 2 / 3

Calculate from defined values

After INPUT, Seats has the entered quantity and SeatPrice has its constant value. Total <- Seats * SeatPrice calculates the product. Total must be REAL because the result may have a fractional part.

Explanation · 3 / 3

Display the result explicitly

OUTPUT "Total: ", Total displays a label followed by the value. Commas separate output items; this is different from building a stored STRING. Assume the input is an integer at this stage; range validation is taught later.

CONSTANT SeatPrice = 12.50
DECLARE Seats : INTEGER
DECLARE Total : REAL
OUTPUT "Enter seats"
INPUT Seats
Total <- Seats * SeatPrice
OUTPUT "Total: ", Total

Work together

Produce the first receipt

The user enters 3 at the prompt.

Work together · 1 / 2

Follow the data dependency

INPUT stores 3 in Seats. The multiplication reads 3 and 12.50, producing 37.5, which is stored in Total.

Work together · 2 / 2

Explain the visible result

The final output displays Total: followed by 37.5. A display format with two decimal places is a separate presentation requirement; the calculated amount is the same as 37.50.

The full sequence is declaration and constant definition, prompt and input, calculation, then output.

Check

Try it yourself · Teacher-written

A program declares Seats and immediately executes Total <- Seats * 12.50 before INPUT Seats. Why is the calculation unsafe?

Check your reasoning

Seats has not yet been given a value. Move INPUT Seats before the multiplication, and declare Total as REAL before using it.

Connect

Keep this idea

INPUT stores an entered value; assignment stores a calculated value; OUTPUT displays a value.

Different pricing rules need different expression grouping. Build those expressions before adding decisions.

DECLARE Quantity : INTEGER
DECLARE Price, Total : REAL

INPUT Price
Total <- Price * Quantity
