Testing methods through development

Use traces and reviews, select tests from code or specifications, and distinguish integration and user testing.

What does this method examine, who uses it, and which evidence can it provide?

Before you start

A valid program outputs the wrong result for a boundary input. Which evidence is more useful: another translation or a trace using that input?

Check your answer

The trace follows the actual decisions and values; translation alone does not test the requirement.

Distinguish execution by hand from collaborative review

A dry run follows an algorithm manually with stated inputs. Start with its declarations and initial values, execute the actual statements, and record variables, decisions and outputs. A walkthrough is a structured review in which the author explains the design or code to other people. Reviewers can use a dry run, but also question assumptions, omitted requirements and interfaces.

Explain what each trace row means

In the positive-total program, Total starts at 0. Inputs 4, -2 and 3 make Value > 0 TRUE, FALSE and TRUE, so the recorded totals are 4, 4 and 7. The final OUTPUT occurs after the third iteration. The skipped negative value is still an input that advances the loop; it is simply excluded from the total.

Walk through the same requirement as a group

  1. Prepare: The author supplies the complete program, three inputs and the rule that only positive values contribute.
  2. Review: One reviewer traces the ordinary case; another asks what happens for zero and for three negative values.
  3. Record: Note the expected zero result for all non-positive inputs and any mismatch between the requirement and statements.
  4. Follow up: Assign corrections or clarifications and check them after revision. A meeting without recorded findings gives little usable evidence.

Worked example · Trace a positive-value total

  1. Requirement

    The program reads three integers and adds only positive values. Follow the supplied input order.

  2. Pseudocode
    DECLARE Index : INTEGER
DECLARE Value : INTEGER
DECLARE Total : INTEGER
Total <- 0
FOR Index <- 1 TO 3
    INPUT Value
    IF Value > 0 THEN
        Total <- Total + Value
    ENDIF
NEXT Index
OUTPUT Total
  3. Expected result

    For 4, -2 and 3, OUTPUT Total produces 7.

Core explanation · Exam essentials

  • A dry run records the actual sequence of values and decisions without computer execution.
  • A walkthrough uses collaborative explanation and review to identify faults or omissions.
Common misconception

A dry run records values along the actual path; it is not a list of guesses about the final output.

Check your understanding

What should a walkthrough team record besides the final output?

Check your answer

Questions, detected defects, missing requirements and the actions needed to resolve them.

White-box and black-box test design

Name the basis for choosing a case

White-box test design uses the internal code structure. For IF Member, choosing TRUE and FALSE exercises both branches. A trace or execution record establishes which decisions occurred. Black-box test design begins with the specification and predicts required outputs without depending on how the code implements them.

Use a shared case for different reasons

The discount rule requires Amount 100 to produce 90 for a member and 100 for a non-member. These same cases can be justified from the two code branches or from the promised prices. The labels describe the selection approach, so a test input is not permanently owned by just one approach.

Explain the limit of coverage

Suppose a specification also requires a staff discount, but no staff branch was implemented. Every existing branch could execute while that requirement remains untested. Conversely, one correct output does not show that each internal path works. Combine specification-based expectations and relevant structural checks; passing branch checks is not proof of complete requirements coverage.

Worked example · Select cases for a price decision

  1. Requirement

    Amount is a non-negative REAL and Member is BOOLEAN. Members pay 90% of Amount; other customers pay Amount.

  2. Pseudocode
    DECLARE Amount : REAL
DECLARE Member : BOOLEAN
DECLARE Due : REAL
INPUT Amount
INPUT Member
IF Member THEN
    Due <- Amount * 0.90
ELSE
    Due <- Amount
ENDIF
OUTPUT Due
  3. Expected result

    (100, TRUE) → 90; (100, FALSE) → 100.

Core explanation · Exam essentials

  • White-box selects from internal structure; black-box selects from specified behaviour.
  • Record expected outputs and explain the selection basis; coverage of existing code can miss an omitted requirement.
Common misconception

White-box coverage can miss a feature absent from the code; black-box expected results come from the requirement.

Check your understanding

Can a test selected from the specification also execute a particular branch?

Check your answer

Yes. Black-box and white-box describe test design approaches, not mutually exclusive input values.

03

Integration testing and stubs

S12.05.A05

Visual overview

Test a connection, not just two separate modules

Integration testing checks modules working together, particularly their interfaces. A calculation and display may each pass isolated checks yet disagree about argument order, units, data meaning or the destination of a result. Matching REAL types alone cannot resolve a disagreement between metres and centimetres.

Investigate the supplied height mismatch

  1. Establish independent contracts: The sensor returns 180 centimetres; the display expects a value in metres.
  2. Observe the combined result: Passing 180 directly makes the display show 180 m, but the required result is 1.80 m.
  3. Locate the interface disagreement: The numeric type matches, but the transferred unit does not. Decide where the conversion belongs.
  4. Correct and retest: Convert once, so 180 cm becomes 1.80 m. Include 0 cm → 0 m and 200 cm → 2 m to test additional values.

Connect integration to staged development

Agree one interface contract so both modules do not independently convert the same quantity. When a called module is unfinished, a temporary stub can allow some caller tests to proceed; the next unit shows exactly which evidence this provides and what must be retested later.

Worked example · Expose an interface mismatch

  1. Modules

    A sensor module returns 180 centimetres; a display module expects metres.

  2. Combined test

    The display shows 180 m instead of the required 1.80 m.

  3. Locate

    Each module used its own documented units, but the interface contract disagreed.

  4. Correct and retest

    Agree the transferred unit, convert once if needed, and repeat the combined test.

Core explanation · Exam essentials

  • Integration testing checks connected modules and the meaning of data crossing their interfaces.
  • A type-correct call can still pass the wrong unit, argument or result.
Optional extension: isolate a module before integration

A unit test checks one module in isolation against its interface contract. This can make a fault easier to locate before modules are combined. The contrast helps explain integration; no test framework or mocking library is required.

Common misconception

A stub is not the caller, a permanent replacement, or proof that the real called module works.

Check your understanding

What must happen when the availability module becomes ready?

Check your answer

Replace the stub and repeat integration tests with the real returned values and interfaces.

04

Use a complete stub, then test its replacement

S12.05.A05S12.05.A09

Visual overview

Define the interface before substituting a module

A stub is a temporary replacement for a called module. It keeps a usable interface while supplying controlled behaviour, such as a fixed result. Here IsAvailable takes INTEGER RoomID and returns BOOLEAN; the caller displays Available on TRUE and Unavailable on FALSE. The only permitted IDs are 101 and 102.

Separate caller evidence from availability evidence

VersionInputExpected caller outputWhat this checks
Stub returning TRUE101 or 102AvailableThe caller uses the TRUE result to select its positive message.
Stub returning FALSE101 or 102UnavailableThe caller uses the FALSE result to select its negative message.
Real fixture function101AvailableThe known available room is identified and the result is displayed correctly.
Real fixture function102UnavailableThe known unavailable room is identified and the result is displayed correctly.

State what a passing stub test means

The real fixture specifies room 101 as available and room 102 as unavailable; it is a complete small lookup rule, not a database connection. The TRUE stub deliberately reports Available for 102. That is expected under the temporary stub contract, so it does not by itself identify a caller defect; it also cannot satisfy the real system’s acceptance requirement for that room.

Test both branches and the real replacement

Replace the stub with the real function and repeat both room cases. A stub that only returned TRUE could never show whether the caller handles FALSE. The three complete versions below keep the same name, parameter and result type so the replacement does not silently change the caller interface.

Worked example · Complete caller with the TRUE stub

  1. Requirements and initial conditions

    Input INTEGER RoomID, restricted to 101 or 102. Temporarily return TRUE for either argument to exercise the caller’s positive path.

  2. Cambridge pseudocode
    FUNCTION IsAvailable(RoomID : INTEGER) RETURNS BOOLEAN
    RETURN TRUE
ENDFUNCTION

DECLARE RoomID : INTEGER
INPUT RoomID
IF IsAvailable(RoomID) THEN
    OUTPUT "Available"
ELSE
    OUTPUT "Unavailable"
ENDIF
  3. Expected result and checks

    Either ID outputs Available; actual room availability is not verified.

Worked example · Complete caller with the FALSE stub

  1. Requirements and initial conditions

    Keep the same interface but return FALSE for either argument.

  2. Cambridge pseudocode
    FUNCTION IsAvailable(RoomID : INTEGER) RETURNS BOOLEAN
    RETURN FALSE
ENDFUNCTION

DECLARE RoomID : INTEGER
INPUT RoomID
IF IsAvailable(RoomID) THEN
    OUTPUT "Available"
ELSE
    OUTPUT "Unavailable"
ENDIF
  3. Expected result and checks

    Either ID outputs Unavailable, exercising the other caller branch.

Worked example · Replace the stub with the real fixture rule

  1. Requirements and initial conditions

    For this complete small fixture, room 101 is available and 102 is unavailable. Inputs are restricted to these two INTEGER IDs.

  2. Cambridge pseudocode
    FUNCTION IsAvailable(RoomID : INTEGER) RETURNS BOOLEAN
    RETURN RoomID = 101
ENDFUNCTION

DECLARE RoomID : INTEGER
INPUT RoomID
IF IsAvailable(RoomID) THEN
    OUTPUT "Available"
ELSE
    OUTPUT "Unavailable"
ENDIF
  3. Expected result and checks

    101 outputs Available; 102 outputs Unavailable. Test both after replacement.

Core explanation · Exam essentials

  • A stub replaces a called module with controlled behaviour to exercise available code.
  • Test different controlled results, then replace the stub and check the real connected behaviour.
Common misconception

A stub test cannot verify an implementation that is absent.

Check your understanding

Does a TRUE stub returning Available for room 102 prove an integration defect?

Check your answer

No. That is the controlled stub behaviour. It does not establish real room availability; replace it and check the actual fixture.

Use the purpose and setting in a scenario

Alpha is not defined by “developers are the only people allowed to test”, and beta is not simply a later run of the same laboratory script. Control, environment and purpose matter. Beta feedback can reveal unexpected conditions, but uneven participation does not guarantee every requirement was checked. Acceptance testing in the next unit asks a different question: whether agreed requirements have been met.

Core explanation · Exam essentials

  • Alpha uses a developer-controlled setting before wider release.
  • Beta uses selected external users and realistic environments to reveal further problems.
Common misconception

Acceptance is not simply the last beta session; it evaluates agreed requirements for a customer decision.

Check your understanding

Which method best checks a required invoice total before customer sign-off?

Check your answer

Acceptance testing with invoices whose expected totals have been calculated independently.

Connect customer decisions to criteria

Acceptance testing checks the delivered system against agreed user requirements so the customer can decide whether to accept it. The customer or suitable representatives need clear criteria, a known environment and independently expected results. “The users liked it” is useful feedback but does not establish that the required calculation or refusal rule works.

Allow compatible testing descriptions

A test can be black-box because its inputs and results come from the specification, and also be an acceptance test because it supports the customer’s decision. White/black-box describe the basis of test design; integration describes connected components; alpha, beta and acceptance describe other aspects of purpose and setting. Do not force them into one mutually exclusive list.

Core explanation · Exam essentials

  • Acceptance checks agreed requirements for a customer decision.
  • Give explicit cases and expected evidence; broad user feedback alone is insufficient.
Common misconception

Customer approval needs evidence against requirements, not only favourable comments.

Check your understanding

Can an acceptance test also be black-box?

Check your answer

Yes. Acceptance is its customer-decision purpose; black-box describes selection from the specification.

Question 1 · Command word: Explain · 3 marks

Explain why source-based branch coverage alone might miss a required discount for staff that was never implemented. Describe a complementary test approach and give a suitable case.

Answer and marking points
  • No staff-discount branch exists for a branch-coverage measure to count as untested.
  • Black-box tests derived from the full price specification can include the missing staff requirement.
  • A staff purchase with a known expected discounted price can expose the omission.

Common error: High coverage of existing code is not complete requirements coverage.

Question 2 · Command word: Describe · 4 marks

A payroll caller receives a tax amount from CalculateTax. The real function is unfinished, so a replacement always returns 12.00. Describe what testing this enables, what remains uncertain and what should be tested when the real function arrives.

Answer and marking points
  • The replacement is a stub that lets the caller process a predictable tax value.
  • The test can check deduction of 12.00 and its transfer to the payslip.
  • The real tax calculation and its interface behaviour remain unverified.
  • Integration tests must then use real tax results, including values different from 12.00.

Common error: Do not assume a fixed stub value covers all possible results.

Question 3 · Command word: Identify · 5 marks

A team first reviews a design together, then tests a build in its laboratory, invites selected users to try it on home devices and finally asks the customer to check contracted outputs. Identify the four methods and give suitable evidence for the last one.

Answer and marking points
  • The collaborative design review is a walkthrough.
  • The controlled laboratory phase is alpha testing.
  • The selected home-user phase is beta testing.
  • The contracted-output check is acceptance testing.
  • Actual contracted outputs should be compared with independently specified expected results and recorded for sign-off.

Common error: Keep the customer acceptance criteria separate from general usability comments.

Question 4 · Command word: Give · 4 marks

A caller outputs Accepted if CheckCode returns TRUE and Rejected otherwise. CheckCode takes one STRING argument; the real rule accepts only "AB12". Two stubs return fixed TRUE and fixed FALSE respectively. Give one test for each stub, state its expected caller output and limitation, then give tests for the real replacement.

Answer and marking points
  • With the TRUE stub, any supplied string such as "ZZ99" must lead to Accepted.
  • With the FALSE stub, any string such as "AB12" must lead to Rejected.
  • These results exercise the caller branches but do not establish that the real code rule is implemented.
  • After replacement, "AB12" must give Accepted and a different code such as "ZZ99" must give Rejected.

Common error: A controlled stub’s result need not match the real validation result for that argument.
