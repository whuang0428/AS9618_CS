Develop a booking system · Concept 14

Dry-run the values and walk through the reasoning

Observe

Three independent accepted requests

  • Seats values arrive in this order: 3, 2, 4.
  • Total begins at 0 and should report 9.
  • The program executes Total <- Total + Seats after each input.

Look, then discuss

What evidence could you produce before running this program on a computer?

Take turns being the computer: read one statement at a time and record the values that change. Do not calculate the final answer and fill in a trace backwards.

Recall

Recall accumulation

Total <- Total + Seats reads the old Total, adds the current Seats, then replaces Total. Initialisation belongs before the loop; otherwise each visit discards the previous accumulation.

  • Review loop traces and running totals

Explain

Explanation · 1 / 3

Perform a dry run manually

Choose exact input values and follow the written statements in execution order. Record changing variables, condition results and outputs in a trace table. The aim is to predict what this implementation actually does, even if it is wrong.

Explanation · 2 / 3

Compare with an independent expectation

The requirement says the total should be 3 + 2 + 4 = 9. Compare that expected result with the trace. A trace can reveal repeated initialisation, a missing update or a wrong stopping condition without executing the code.

Explanation · 3 / 3

Use a walkthrough to review with other people

In a walkthrough, the author explains the design or code step by step to others. Reviewers question assumptions, conditions and interfaces. They may trace sample values, but a walkthrough is the collaborative review activity, not merely another name for an individual trace.

Choose from the specification or the code

Observe

Two testers receive different information

TesterInformation availableProposed test
ASpecification: accept 1–6 inclusiveUse 6; expect Accepted
BIF Paid THEN confirm ELSE ask for paymentUse Paid TRUE and FALSE to execute both branches

Look, then discuss

What determines the difference between black-box and white-box testing?

It is how test cases are selected. Both testers can compare actual output with expected output, and the same input might be useful to both.

Recall

Recall a path through IF

Only one IF/ELSE branch executes on a particular test. A passing test for the TRUE branch does not tell you what the FALSE branch will do.

Explain

Explanation · 1 / 3

Black-box: start from required inputs and outputs

Select cases from the specification without relying on internal code structure. For a 1–6 rule, input 6 must be accepted regardless of how the programmer wrote the condition. This can expose wrong results or failures during execution.

Explanation · 2 / 3

White-box: use the implementation structure

Inspect code to choose inputs that exercise particular statements, branches or paths. For an IF Paid condition, TRUE and FALSE exercise both alternatives. For a loop, consider no iterations where possible, one iteration and several iterations.

Explanation · 3 / 3

Explain what each result does and does not show

Black-box tests can miss an internal branch that the chosen requirements examples never reach. White-box branch coverage can execute incorrect logic without proving the requirements are satisfied. Use independent expected outcomes in both methods; successful coverage is evidence of execution, not proof of correctness.

Work together · 1 / 2

Derive the black-box case

From the specification alone, choose Seats 6 and expect Accepted. Observing Rejected reveals a fault without needing the source.

Work together · 2 / 2

See why two branches are not enough

Develop a booking system · Concept 16

Test a caller before its real module is ready

Observe

The booking interface is ready first

  • The caller asks ValidSeats(Seats) for a BOOLEAN result.
  • TRUE should display Accepted; FALSE should display Rejected.
  • The real quantity checker is unfinished. Its eventual rule accepts integers 1–6 inclusive.

Look, then discuss

How can you check both caller branches without pretending that the real validation has been implemented?

Give the caller a controlled TRUE response, then a controlled FALSE response. Identify which part is being exercised and which part is still absent.

Recall

Recall a Boolean function interface

A function header states the ordered parameters and return type. The caller uses the returned BOOLEAN in its condition. Replacing a function safely requires preserving the interface expected by that caller.

Explain

Explanation · 1 / 4

Separate a module from its connections

A module may calculate correctly in isolation, yet integration can reveal reversed arguments, a wrong returned type or values sent to the wrong place. Integration testing checks cooperating modules and their interfaces when they are combined.

Explanation · 2 / 4

Substitute a small temporary stub

A stub stands in for an unfinished called module. It uses the required interface and supplies a controlled response, such as a fixed TRUE. A separate FALSE version lets the caller’s other branch be exercised.

FUNCTION ValidSeats(BYVAL Seats : INTEGER) RETURNS BOOLEAN
    RETURN TRUE
ENDFUNCTION

DECLARE Seats : INTEGER
INPUT Seats
IF ValidSeats(Seats) THEN
    OUTPUT "Accepted"
ELSE
    OUTPUT "Rejected"
ENDIF

Explanation · 3 / 4

Keep the claim within the evidence

A TRUE stub makes every entered quantity produce Accepted because that is its programmed response. This can show that the caller handles TRUE, but it does not verify the required range or the missing implementation. Change the controlled return to FALSE to check the other branch.

Explanation · 4 / 4

Replace the stub and retest the integration

The real ValidSeats function returns (Seats >= 1) AND (Seats <= 6). Test 0 and 7 expecting Rejected, and 3 and 6 expecting Accepted. The caller, parameter interface and real result now need to agree.

FUNCTION ValidSeats(BYVAL Seats : INTEGER) RETURNS BOOLEAN
    RETURN (Seats >= 1) AND (Seats <= 6)
ENDFUNCTION

DECLARE Seats : INTEGER
INPUT Seats
IF ValidSeats(Seats) THEN
    OUTPUT "Accepted"
ELSE
    OUTPUT "Rejected"
ENDIF

Work together

Read evidence without overclaiming

Use the independent integer requests 0, 3, 6 and 7. The real rule is 1–6 inclusive.

Work together · 1 / 2

Use the controlled versions

With a TRUE stub all four inputs display Accepted, so 0 and 7 disagree with the real requirement. With a FALSE stub all four display Rejected, so 3 and 6 disagree with it. These are the substitutes’ known limitations, not discovered defects in the absent real module.

Work together · 2 / 2

Check the connected real version

After replacement, the expected outputs are Rejected, Accepted, Accepted and Rejected. If all still display Accepted, inspect the selected implementation, returned Boolean and caller branch. Use the white-box view to identify which caller branches were visited; use the black-box view to judge outcomes from the specification.

    Original question · Cambridge 9618/22

    1. Explain stubs and an error detected by black-box testing

    Cambridge 9618/22 · May/June 2025 · 2(b)(ii), 2(b)(iii) · 4 marks

    Selected parts: 2(b)(ii) [2]; 2(b)(iii) [2].

    Hint — reading the question

    A stub temporarily stands in for an unfinished called module. The completed program already compiles, so the later test is about behaviour during execution.

    Reasoning and model answer — teacher-written

    2(b)(ii): Replace unfinished modules with simple temporary modules that use the required interfaces. A stub can return an expected value or display a message to show that the calling program reached it.

    2(b)(iii): A logic error: the program runs but gives a result different from the specified result, for example a wrong bonus for a valid hours-and-sales combination.

    Official mark scheme
    Why this earns marks — teacher explanation

    Part (ii) gives two points for replacement modules and their simple response. Part (iii) gives one for the error type and one for its matching description. A run-time error with a suitable description is an official alternative.

    Common mistakes — teacher analysis

    A stub is not a complete implementation of the missing calculation. Passing one black-box test does not show that all internal paths have been exercised.

    Test in controlled and real user environments

    Observe

    Two trials of the booking screen

    TrialWhere and whoFinding
    ADeveloper-controlled environment with the test teamA saved booking does not reopen correctly
    BSelected school staff use a trial release at their own desksA message is cut off on one school display

    Look, then discuss

    Why can both trials find useful problems even after module tests pass?

    The completed screen now meets different equipment, users and work patterns. Compare the level of control and the source of feedback in the two trials.

    Recall

    Recall evidence against a requirement

    A useful issue report includes version, environment, exact steps, expected behaviour and actual behaviour. “It is broken” is difficult to reproduce, whichever testing stage produced it.

    Explain

    Explanation · 1 / 3

    Alpha: check a release under controlled conditions

    Alpha testing takes place within the developing organisation or another controlled test environment, typically with internal testers and sometimes invited users. Problems can be investigated while the developers control the setup.

    Explanation · 2 / 3

    Beta: obtain feedback from outside users

    Beta testing makes a trial version available to selected users in their real environments. Their equipment, data and workflows can expose problems the development setup did not reproduce. Gather specific feedback and defect reports for the next change.

    Explanation · 3 / 3

    Choose the method for the uncertainty

    Use controlled testing when you need reproducible conditions and close inspection. Use beta feedback when you need evidence from real user environments. A beta release may still contain defects; distributing it does not itself mean that the customer has accepted the finished system.

    Work together

    Turn a beta comment into a useful test

    A school user reports that the booking confirmation is clipped on their display.

    Work together · 1 / 2

    Capture the conditions

    Record the trial version, screen size, browser and steps leading to the clipped message, plus the complete expected confirmation text.

    Work together · 2 / 2

    Reproduce and follow up

    Recreate those conditions, correct the responsible layout and repeat the case. Check a normal display as well, so the correction preserves its working layout.

    Real-environment feedback becomes useful when it can be reproduced and checked.

    Check

    Try it yourself · Teacher-written

    Selected users try an unfinished release on their own equipment and submit reports. Name the testing stage and one advantage of this environment.

    Check your reasoning

    Beta testing. It can expose compatibility, usability or workflow problems arising in real user environments that the controlled development environment did not reveal.

    Connect

    Keep this idea

    Alpha uses controlled conditions; beta gathers feedback from selected users in their own environments.

    The customer still needs evidence that the completed system satisfies the agreed requirements.

    Continue: Decide whether the agreed requirements are met →
    Check a common misunderstanding

    Beta testing and acceptance testing have different purposes. User participation alone does not make them the same stage.

    Decide whether the agreed requirements are met

    Observe

    The customer’s completion checklist

    Agreed requirementAcceptance evidence
    Accept integer quantities 1–6 inclusive1 and 6 accepted
    Reject other integers0 and 7 rejected with agreed guidance
    Display the calculated charge3 at 12.50 displays 37.50

    Look, then discuss

    What distinguishes “staff like it” from accepting the agreed system?

    A pleasant interface can still calculate the wrong amount. The customer needs repeatable evidence against the actual requirements, not just a general impression.

    Recall

    Recall the test plan

    A test case links a requirement to initial conditions, input and an independently expected result. Actual results support a decision only when it is clear what was tested.

    Explain

    Explanation · 1 / 3

    Use customer requirements as the basis

    Acceptance testing checks the completed system against agreed requirements so the customer can decide whether to accept it. Include the outputs and constraints that the agreement specifies, not only the developer’s favourite features.

    Explanation · 2 / 3

    Keep purpose separate from test design technique

    An acceptance test can be black-box because its cases come from required behaviour rather than code. Acceptance identifies the customer-decision purpose; black-box identifies the basis for selecting the cases.

    Explanation · 3 / 3

    Record unmet requirements and the next action

    If the system rejects a valid maximum request, record the failure and resolve it before claiming that requirement is met. A new requested feature needs an agreed change; it should not silently replace an existing acceptance criterion.

    Work together

    Judge a partial success

    The booking system correctly accepts 1 and rejects 0, but rejects 6. All planned alpha and beta trials have finished.

    Work together · 1 / 2

    Evaluate the agreed boundary

    The customer’s rule includes 6. Passing the other two cases does not satisfy that requirement.

    Work together · 2 / 2

    Name the current purpose

    The customer is checking the completed system against its agreement: acceptance testing. Finishing alpha and beta does not guarantee acceptance.

    Acceptance connects the end of the current delivery to the requirements agreed at its beginning.

    Complete a dry run of the positive-total program for inputs 2, 0, 5. State Total after each iteration and the final output.

    DECLARE Index : INTEGER
DECLARE Value : INTEGER
DECLARE Total : INTEGER
Total <- 0

    INPUT Value

        Total <- Total + Value
    ENDIF
NEXT Index
