Testing methods through development

Use traces and reviews, select tests from code or specifications, and distinguish integration and user testing.

What does this method examine, who uses it, and which evidence can it provide?

Before you start

Check your answer

The trace follows the actual decisions and values; translation alone does not test the requirement.

Core explanation

Trace the algorithm manually

A dry run manually follows an algorithm with selected input data. Record changing variables, decisions and output in a trace table; use the actual statements, including initialisation and loop limits. This can expose logic faults without running the program on a computer.

Review the design or code in a walkthrough

A walkthrough is a structured review in which the author explains the design or code to others. Participants follow representative cases, question assumptions and record faults or omissions. A walkthrough can include a manual trace, but the collaborative discussion is distinct from a person carrying out a dry run alone.

Worked example · Trace a positive-value total

  1. Requirement

    The program reads three integers and adds only positive values. Follow the supplied input order.

  2. Pseudocode
    DECLARE Index : INTEGER
DECLARE Value : INTEGER
DECLARE Total : INTEGER
Total <- 0
FOR Index <- 1 TO 3
    INPUT Value
    IF Value > 0 THEN
        Total <- Total + Value
    ENDIF
NEXT Index
OUTPUT Total
  3. Expected result

    For 4, -2 and 3, OUTPUT Total produces 7.

Common misconception

A dry run records values along the actual path; it is not a list of guesses about the final output.

Check your understanding

What should a walkthrough team record besides the final output?

Check your answer

Questions, detected defects, missing requirements and the actions needed to resolve them.

White-box and black-box test design

Core explanation

White-box: select from internal structure

White-box testing uses knowledge of the internal code structure to choose test cases, for example inputs that make a decision true and false. Coverage evidence records which branches or paths have executed. Exercising every branch is useful but does not prove that every requirement was implemented.

Black-box: select from the specification

Black-box testing derives inputs and expected outputs from the specification without relying on the internal algorithm. For a 10% member discount, tests should distinguish a member from a non-member and compare the amount due with the specified calculation. Both approaches can use the same input values; what differs is the reason for selecting them.

Worked example · Select cases for a price decision

  1. Requirement

    Amount is a non-negative REAL and Member is BOOLEAN. Members pay 90% of Amount; other customers pay Amount.

  2. Pseudocode
    DECLARE Amount : REAL
DECLARE Member : BOOLEAN
DECLARE Due : REAL
INPUT Amount
INPUT Member
IF Member THEN
    Due <- Amount * 0.90
ELSE
    Due <- Amount
ENDIF
OUTPUT Due
  3. Expected result

    (100, TRUE) → 90; (100, FALSE) → 100.

Common misconception

White-box coverage can miss a feature absent from the code; black-box expected results come from the requirement.

Check your understanding

Can a test selected from the specification also execute a particular branch?

Check your answer

Yes. Black-box and white-box describe test design approaches, not mutually exclusive input values.

03

Integration testing and stubs

S12.05.A05

Visual overview

Core explanation

Check interfaces between modules
  • Arguments: Verify their number, order and types.
  • Meaning: Check units and interpretation: metres supplied to a centimetre input can fail even when both values are REAL.
  • Results: Confirm that returned values reach the intended caller and parameter.
Use a stub for controlled early integration

A stub temporarily replaces an unavailable called module and returns a controlled value. It exercises the caller and available interfaces. Record what it simulates; replace it with the real module and retest. A passing stub test does not verify the absent implementation.

Worked example · Expose an interface mismatch

  1. Modules

    A sensor module returns 180 centimetres; a display module expects metres.

  2. Combined test

    The display shows 180 m instead of the required 1.80 m.

  3. Locate

    Each module used its own documented units, but the interface contract disagreed.

  4. Correct and retest

    Agree the transferred unit, convert once if needed, and repeat the combined test.

Common misconception

A stub is not the caller, a permanent replacement, or proof that the real called module works.

Check your understanding

What must happen when the availability module becomes ready?

Check your answer

Replace the stub and repeat integration tests with the real returned values and interfaces.

Alpha, beta and acceptance testing

S12.05.A06S12.05.A07S12.05.A08S12.05.A09

Discover real-environment problemsBetaSelected users try their actual devices and workflows
Decide whether contracted requirements are metAcceptanceA required report agrees with an independently calculated reference

Swipe horizontally to compare every column →

Core explanation

Choose who tests and what they establish

Alpha testing takes place under developer control before wider release, using internal testers and sometimes user representatives to expose faults in a controlled setting. Beta testing gives a near-complete version to selected external users in their own realistic environments, where different devices and usage patterns can reveal additional problems.

Match the method to the testing purpose

Acceptance testing checks the delivered system against agreed user requirements so the customer can decide whether to accept it. Select cases that demonstrate those requirements, rather than treating all user feedback as acceptance evidence. Beta feedback can be broad and uneven, while acceptance checks need explicit pass conditions linked to the agreed system.

Common misconception

Acceptance is not simply the last beta session; it evaluates agreed requirements for a customer decision.

Check your understanding

Which method best checks a required invoice total before customer sign-off?

Check your answer

Acceptance testing with invoices whose expected totals have been calculated independently.

Question 1 · Command word: Complete2 marks

Complete a dry run of the positive-total program for inputs 2, 0, 5. State Total after each iteration and the final output.

Use the stated input assumptions and this program.

DECLARE Index : INTEGER
DECLARE Value : INTEGER
DECLARE Total : INTEGER
Total <- 0
FOR Index <- 1 TO 3
    INPUT Value
    IF Value > 0 THEN
        Total <- Total + Value
    ENDIF
NEXT Index
OUTPUT Total
S12.05.A01
Answer and marking points
  1. Total becomes 2, remains 2, then becomes 7.
  2. The final output is 7.

Common error: The zero input does not satisfy Value > 0.

Question 2 · Command word: Describe3 marks

Describe how three team members could perform a walkthrough of a registration algorithm and state one useful outcome.

S12.05.A02
Answer and marking points
  1. The author presents the algorithm while the group follows selected registration scenarios.
  2. Reviewers question logic, inputs and assumptions and record any defects or omissions.
  3. The review produces specific actions to correct or clarify the algorithm.

Common error: A solitary manual trace does not describe the collaborative review.

Question 3 · Command word: Explain4 marks

Explain how white-box and black-box testing could each guide the choice of tests for the supplied member-discount program. Give a member input and a non-member input with expected prices.

S12.05.A03S12.05.A04S12.05.A09
Answer and marking points
  1. White-box design uses Member TRUE and FALSE to exercise both branches.
  2. Black-box design starts from the promised discount and checks independently expected prices for members and non-members.
  3. Amount 100.00 with Member TRUE should produce Due 90.00.
  4. Amount 100.00 with Member FALSE should produce Due 100.00.

Common error: Give the basis of selection, not just two method names.

Question 4 · Command word: Explain3 marks

A booking caller uses an unfinished IsAvailable function. Explain how a stub can help test the caller and identify one limitation.

S12.05.A05
Answer and marking points
  1. The stub can return controlled TRUE and FALSE values in place of IsAvailable.
  2. Those values exercise the caller's confirm and reject behaviours.
  3. They do not test how the real function determines availability.

Common error: Later testing must use the completed function.

Question 5 · Command word: Identify3 marks

Identify and justify the method for each purpose: internal pre-release fault finding; selected customers trying their own devices; customer sign-off against agreed report requirements.

S12.05.A06S12.05.A07S12.05.A08S12.05.A09
Answer and marking points
  1. Alpha fits fault finding in the developer's controlled environment.
  2. Beta fits external users exercising realistic device combinations.
  3. Acceptance fits evidence that the agreed reports meet their requirements.

Common error: The purpose and environment distinguish the methods.

Question 1 · Command word: Explain · 3 marks

Explain why source-based branch coverage alone might miss a required discount for staff that was never implemented. Describe a complementary test approach and give a suitable case.

Answer and marking points
  • No staff-discount branch exists for a branch-coverage measure to count as untested.
  • Black-box tests derived from the full price specification can include the missing staff requirement.
  • A staff purchase with a known expected discounted price can expose the omission.

Common error: High coverage of existing code is not complete requirements coverage.

Question 2 · Command word: Describe · 4 marks

A payroll caller receives a tax amount from CalculateTax. The real function is unfinished, so a replacement always returns 12.00. Describe what testing this enables, what remains uncertain and what should be tested when the real function arrives.

Answer and marking points
  • The replacement is a stub that lets the caller process a predictable tax value.
  • The test can check deduction of 12.00 and its transfer to the payslip.
  • The real tax calculation and its interface behaviour remain unverified.
  • Integration tests must then use real tax results, including values different from 12.00.

Common error: Do not assume a fixed stub value covers all possible results.

Question 3 · Command word: Identify · 5 marks

A team first reviews a design together, then tests a build in its laboratory, invites selected users to try it on home devices and finally asks the customer to check contracted outputs. Identify the four methods and give suitable evidence for the last one.

Answer and marking points
  • The collaborative design review is a walkthrough.
  • The controlled laboratory phase is alpha testing.
  • The selected home-user phase is beta testing.
  • The contracted-output check is acceptance testing.
  • Actual contracted outputs should be compared with independently specified expected results and recorded for sign-off.

Common error: Keep the customer acceptance criteria separate from general usability comments.
