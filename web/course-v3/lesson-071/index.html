Choosing and combining data structures

Combine indexed storage with the access rules needed by different parts of an application.

How can several structures serve different access needs in one system?

Before you start

Must a booking system choose one structure for all its data and operations?

Check your answer

No. Indexed seats, pending requests and undo history have different access requirements.

01

Choose dimensions for retained application data

S10.04.A01

Visual overview

Separate stored facts from processing order

Separate the values the application must retain from the order in which it processes actions. A theatre can store one occupancy flag per row and seat in a 2D BOOLEAN array. A separate 1D INTEGER array can store one booking total per performance, because performance number alone identifies each total.

Give every index one meaning

Describe the meaning and bounds of each dimension explicitly. Occupied[Row, Seat] uses two indices; Bookings[Performance] uses one. The declaration should follow the data's actual indexing needs. Adding dimensions simply because a system is large creates an unnecessary or misleading model.

Questions that determine a structure

QuestionConsequence
Do fields describe different attributes of one request?Use a record for its ID, row and seat.
Does one index select the required value?Use a 1D array, for example a performance total.
Do row and seat together select the required value?Use a 2D occupancy array for one performance.
Must values survive the execution?Write the required representation to persistent storage.

Keep the model’s scope honest

The occupancy model below covers one performance. The separate six-element totals array does not add a performance index to that occupancy array. State the limits of each model; handling every performance’s full seating map would require another explicit arrangement.

Worked example · Choose two arrays for a theatre

  1. Seat data

    DECLARE Occupied : ARRAY[1:8, 1:12] OF BOOLEAN stores one flag for each of 96 seats.

  2. Performance totals

    DECLARE Bookings : ARRAY[1:6] OF INTEGER stores six totals.

  3. Access

    Occupied[3, 7] selects row 3, seat 7; Bookings[2] selects the total for performance 2.

Core explanation · Exam essentials

  • Choose dimensions from the selectors needed to locate one value.
  • Use records for named attributes and files when persistence is required.
Common misconception

The number of different kinds of data is not the number of array dimensions; dimensions describe independent indices.

Check your understanding

What additional index is needed if occupancy for all six performances must be retained?

Check your answer

Performance must also be represented. The stated 2D occupancy array holds one performance at a time; a separate per-performance arrangement would be needed.

Justify each ADT by its operation order

Match each responsibility to its operation order

The same theatre can use a queue for booking requests processed in arrival order and a stack for reversing the most recent completed edits. A linked list can represent a running order of acts that frequently receives insertions between known neighbours. Each choice follows a specific access or update requirement.

Store enough information to reverse a change

Explain how the structures cooperate: dequeue a request, use its row and seat to access the occupancy array, and push an undo record containing the previous state after a successful change. The request queue and undo stack contain different items and have different removal orders. Merely naming all three ADTs does not justify a design.

Distinguish waiting work from successful changes

A request record and an undo record serve different purposes. A request identifies what the user wants. An undo record retains the location and previous value of a change that actually succeeded. A rejected request must not add an undo entry for a change that never happened.

Describe the responsibility of each structure

  1. Queue: Select the earliest waiting request.
  2. Occupancy array: Read and update the requested seat using its two indices.
  3. Undo stack: Retain and later remove the newest successful change with its previous state.
  4. Text log: Append an explicit event line without deleting earlier history.

Worked example · Follow one booking through the structures

  1. Before

    Queue front is request R for row 3, seat 7; Occupied[3,7] is FALSE.

  2. Process

    Dequeue R, check the seat and change Occupied[3,7] to TRUE.

  3. Undo information

    Push an undo record holding row 3, seat 7 and previous value FALSE; a later undo restores that previous value.

Core explanation · Exam essentials

  • Justify a queue by FIFO, a stack by LIFO and a linked list by linked sequence updates.
  • Describe which data each structure holds and preserve the old state needed for Undo.
Common misconception

An undo record must preserve the old state; storing only the new state may not provide enough information to reverse the change.

Check your understanding

Why would replacing the request queue with the undo stack change service order?

Check your answer

The newest request would be selected before older waiting requests, violating the specified arrival order.

03

Run a booking, reject a duplicate and undo a success

S10.02.A03S10.05.A01S10.07.A02S10.09.A01S10.09.A02

Visual overview

State the complete small-system rules

The request queue initially holds R1(1,1), R2(1,1), R3(2,2), in front-to-rear order. Occupied[1:2,1:2] is initially all FALSE; the undo stack is empty and Bookings.txt is an empty existing file.

Follow success, rejection and undo to final states

Each successful booking stores an undo record with request ID, row, seat and PreviousState = FALSE. A rejected request produces no seat change or undo entry. After all requests have been processed, Undo once reverses the latest successful booking.

Initial conditions and notation

This is a complete conceptual state trace using named ADT operations, not an ADT implementation program. One performance has two rows of two seats. All seats start FALSE. Request and undo capacities are three, sufficient for this example. Each request record contains ID : STRING, Row : INTEGER and Seat : INTEGER; every supplied coordinate is in range.

Apply the same rules to each request

  1. Select: Dequeue the next request; stop processing when no requests remain.
  2. Reject an occupied seat: Leave occupancy and undo history unchanged; append a REJECT event.
  3. Accept an available seat: Retain its old value in an undo record, set occupancy TRUE, push the undo record, and append an ACCEPT event.
  4. Undo once: If the undo stack is non-empty, pop its top record, restore that seat’s previous value and append an UNDO event. Otherwise report no change without reading a record.

Define what persistence means here

The log is an event history, so Undo appends an event rather than erasing the earlier acceptance. This log format records ID, coordinates and outcome for inspection; it is not presented as a complete reloadable seating-file format.

Worked example · Follow all requests and one Undo

  1. Prepare

    Declare Occupied as ARRAY[1:2,1:2] OF BOOLEAN and initialise every cell to FALSE. Queue and stack capacities are 3. Request fields: ID : STRING, Row : INTEGER, Seat : INTEGER. Undo fields add PreviousState : BOOLEAN. All coordinates are valid.

  2. R1 succeeds

    Dequeue R1; save (R1,1,1,FALSE), set Occupied[1,1] TRUE and push that undo record. Append ACCEPT R1 1 1.

  3. R2 is rejected

    Dequeue R2; seat (1,1) is TRUE. Leave occupancy and the stack unchanged. Append REJECT R2 1 1.

  4. R3 succeeds

    Dequeue R3; save (R3,2,2,FALSE), set Occupied[2,2] TRUE and push that record. Append ACCEPT R3 2 2. The queue is now empty.

  5. Undo R3

    Pop (R3,2,2,FALSE); restore Occupied[2,2] to FALSE. Append UNDO R3 2 2.

  6. Final state

    Rows of Occupied are [TRUE,FALSE] and [FALSE,FALSE]. The queue is empty; the stack contains only (R1,1,1,FALSE). The log has the four event lines below, in order.

Worked example · Persist the stated events

  1. Mode and initial contents

    Bookings.txt starts empty. Open it FOR APPEND before processing. Each event string below is written with WRITEFILE at the corresponding action; close the log after Undo.

  2. Exact operations within that open session
    OPENFILE "Bookings.txt" FOR APPEND
WRITEFILE "Bookings.txt", "ACCEPT R1 1 1"
WRITEFILE "Bookings.txt", "REJECT R2 1 1"
WRITEFILE "Bookings.txt", "ACCEPT R3 2 2"
WRITEFILE "Bookings.txt", "UNDO R3 2 2"
CLOSEFILE "Bookings.txt"
  3. Scope

    These are the complete file operations for the four already-traced events, not a booking implementation. The four strings become four saved lines. If old event lines existed, APPEND would retain them before these lines.

Core explanation · Exam essentials

  • A failed booking changes neither seat occupancy nor undo history.
  • Undo restores the previous value of the latest successful change; record the resulting event explicitly.
Common misconception

The latest request is not necessarily the latest successful change; rejected requests must not create undo records.

Check your understanding

After one more Undo, which seat changes and what remains?

Check your answer

Undo R1 restores (1,1) to FALSE. All seats are FALSE, both ADTs are empty, and an UNDO R1 1 1 line is appended.

Question 1 · Command word: Suggest2 marks

A school retains one total per class and one mark per pupil per test. Suggest a suitable array dimension for each and explain the index meanings.

S10.04.A01
Answer and marking points
  1. A 1D array uses a class index for the class totals.
  2. A 2D array uses pupil and test indices for individual marks.

Common error: Two independent selectors require two dimensions.

Question 2 · Command word: Justify2 marks

A drawing program queues commands received from a device and retains completed changes for Undo. Justify a queue for the incoming commands and a stack for the undo history.

S10.09.A01S10.09.A02
Answer and marking points
  1. The queue processes incoming commands in arrival order.
  2. The stack reverses the latest completed change first.

Common error: Waiting work and completed undoable work are different collections.

Question 3 · Command word: Explain2 marks

A programme of performances often inserts an act after a known act. Explain why a linked list can be suitable and identify the links changed during insertion.

S10.09.A03
Answer and marking points
  1. A linked list can insert between neighbours without shifting all later act data.
  2. The new node points to the original successor, and the known predecessor points to the new node.

Common error: The advantage assumes the insertion point has been located.

Question 4 · Command word: State4 marks

Start a fresh 2×2 performance with every seat FALSE, an empty undo stack and a queue holding A(1,2), B(1,2), C(2,1). Apply the lesson's rules to all requests, then Undo twice. State the outcomes, undo order, final occupancy and all log events. Both ADTs have capacity 3.

S10.05.A01S10.07.A02S10.09.A01S10.09.A02
Answer and marking points
  1. A succeeds, B is rejected and C succeeds; the request queue becomes empty.
  2. Undo returns C then A; B has no undo record.
  3. All four seats are FALSE and the undo stack is empty.
  4. The five events are ACCEPT A 1 2; REJECT B 1 2; ACCEPT C 2 1; UNDO C 2 1; UNDO A 1 2.

Common error: Only successful changes supply undo entries; retain rejected events in the log.

Question 5 · Command word: Write3 marks

RequestRecord is already defined with ID : STRING, Row : INTEGER and Seat : INTEGER. Occupied is already declared as ARRAY[1:2,1:2] OF BOOLEAN and every cell is FALSE. Write pseudocode to declare Req of RequestRecord, save request A for row 1, seat 2 in its fields, and display that seat's current occupancy through Req's fields. State the output.

S10.02.A03S10.05.A01
Answer and marking points

One valid pseudocode answer

DECLARE Req : RequestRecord
Req.ID <- "A"
Req.Row <- 1
Req.Seat <- 2
OUTPUT Occupied[Req.Row, Req.Seat]
  1. DECLARE Req : RequestRecord creates the variable.
  2. Req.ID <- "A", Req.Row <- 1 and Req.Seat <- 2 save the request fields.
  3. OUTPUT Occupied[Req.Row, Req.Seat] selects and displays FALSE.

Common error: Use the record's row and seat fields as the two array indices.

Question 1 · Command word: State · 3 marks

A laboratory records one REAL result per sample for each of five tests. It has 20 samples. Declare a suitable array and state the element selecting sample 12, test 4.

Answer and marking points
  • DECLARE Result : ARRAY[1:20, 1:5] OF REAL.

  • Result[12, 4] selects the required value.

Common error: Keep the same dimension convention in the declaration and access.

Question 2 · Command word: State · 3 marks

A text editor receives edits A, B and C, processes them in arrival order and then undoes two completed edits. State the processing order, undo order and suitable ADT for each stage.

Answer and marking points
  • A queue processes A, B, C in arrival order.
  • A stack reverses C then B after all three have completed.
  • The queue applies FIFO to waiting edits; the stack applies LIFO to completed edits.

Common error: Do not use the same removal rule for both stages.

Question 3 · Command word: Compare · 3 marks

A route planner stores waypoints that are frequently inserted between existing neighbours. Compare using a linked list with a 1D array for maintaining this order, and state a cost of accessing the tenth waypoint in a singly linked list.

Answer and marking points
  • A linked list can preserve the order by updating neighbour links when an insertion point is known.
  • An ordered array may require shifting later elements to make space at that position.
  • A singly linked list normally reaches the tenth waypoint by following links from the head, rather than direct access by ordinal position.

Common error: The array index storing a node is not necessarily its ordinal position in the list.

04

Lesson review

Summary

Indexed data

Choose 1D or 2D arrays by how many independent indices locate one value.

Access rules

Use a stack for latest-first reversal, a queue for arrival order and a linked list for linked sequence updates.

Cooperation

Only successful changes enter undo history. Rejection preserves the seat state; Undo restores the saved old value and appends an event.
