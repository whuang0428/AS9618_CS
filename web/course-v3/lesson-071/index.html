Build a booking system · Concept 40

Choose dimensions and record fields for different facts

Observe

Different facts need different accesses

  • One booking: name Mina, paid FALSE.
  • Booking collection: one numbered position per booking.
  • Seating plan: a row number and a seat position identify each seat.

Look, then discuss

Should a booking record and a seating plan use the same representation?

One booking has a name and a payment state. The room has rows and seat positions. A collection of bookings and a grid of seats organise different kinds of relationships.

Recall

Recall record fields versus array elements

A record groups named fields that may have different types. An array has one declared element type and indexed positions. That element type can itself be a defined record type.

Explain

Explanation · 1 / 3

Match each access to the required coordinates

Use a 2D BOOLEAN array for occupancy by row and seat. Use a 1D array of booking records for bookings located by one booking index. Each record can hold a STRING name and BOOLEAN Paid field.

Explanation · 2 / 3

Read an array-of-records access in two stages

Bookings[2].Paid first selects the second record and then its Paid field. It is different from a two-dimensional array access: .Paid is a named field, not a second numerical coordinate.

TYPE BookingRecord
    DECLARE Name : STRING
    DECLARE Paid : BOOLEAN
ENDTYPE
DECLARE Bookings : ARRAY[1:2] OF BookingRecord
DECLARE Index : INTEGER
FOR Index <- 1 TO 2
    INPUT Bookings[Index].Name
    Bookings[Index].Paid <- FALSE
NEXT Index
Bookings[2].Paid <- TRUE
FOR Index <- 1 TO 2
    OUTPUT Bookings[Index].Name
    OUTPUT Bookings[Index].Paid
NEXT Index

Explanation · 3 / 3

Avoid a type mismatch disguised as a table

A single ordinary 2D array has one element type. Do not use it to claim that one column is STRING and another is BOOLEAN. A record preserves the different field types directly.

Work together

Interpret one updated field

Input names Mina and Jo into the two-element record array.

Work together · 1 / 2

Trace initialisation

Both Paid fields become FALSE. Bookings[1].Name is Mina and Bookings[2].Name is Jo.

Work together · 2 / 2

Apply the selected update

Bookings[2].Paid <- TRUE changes only Jo’s payment field. The outputs are Mina, FALSE, Jo, TRUE on separate lines.

Choose dimensions for indexed relationships and fields for differently typed facts about one object.

Build a booking system · Concept 41

Choose and combine FIFO, LIFO and linked order

Observe

Initial transfer state

  • Stack, bottom to top: A, B, C
  • Queue: empty, with sufficient capacity
  • Move all stack items to the queue, then move them back.

Look, then discuss

Why should the waiting list and the undo history not share the same removal rule?

Requests must be served in arrival order, while completed changes must be undone in reverse completion order. A programme of activities may need insertion between known neighbours.

Recall

Recall the three rules

A queue removes the earliest remaining arrival. A stack removes the latest remaining addition. A linked list follows its node links and supports controlled link changes to its sequence.

Explain

Explanation · 1 / 4

Assign one responsibility to each collection

Use a queue for waiting requests, a stack for undo entries and a linked list when the activity programme needs insertion between known nodes. Justify each choice with the required operation rather than only naming a familiar example.

Explanation · 2 / 4

Trace a transfer by the source removal rule

To transfer a stack into a queue, repeatedly pop the stack and enqueue the removed item. The first item placed in the queue is the original stack’s top item. Its arrival position is now governed by the queue.

Explanation · 3 / 4

Transfer back using the queue rule

Repeatedly dequeue and push onto the stack. The queue preserves the order in which the original stack was popped. Pushing that sequence builds a stack whose bottom-to-top order is reversed from the original.

Explanation · 4 / 4

Read the question’s pointer meanings

When the queue’s rear pointer means next insertion position, store at Rear and then advance it. When Top means last occupied stack position, read before decrementing on pop and advance before storing on push. Follow any alternative directions or bounds stated by the supplied diagram.

Work together

Reverse a stack through a queue

The original stack contains A, B, C from bottom to top. The queue begins empty and has sufficient capacity.

Work together · 1 / 2

Empty the stack into the queue

Pops return C, then B, then A. Enqueue in that order, so the queue contains C, B, A from front to rear.

Work together · 2 / 2

Empty the queue back into the stack

Dequeues return C, B, A in that same order. Push each value. The final stack is C, B, A from bottom to top, so its next pop is A.

Track the returned item at every transfer and state which end each order describes.

Check

Try it yourself · Teacher-written

After the two transfers, is the queue responsible for reversing the order of its own arrivals?

Check your reasoning

No. The queue preserves its arrival order. The overall reversal results from first removing the original stack top-first and then pushing that sequence back onto the stack.

Original question · Cambridge 9618/21

1. Reverse a stack through a queue

Cambridge 9618/21 · May/June 2025 · 5 · 7 marks

Selected parts: 5 [7].

Hint — reading the question

The number of items is unknown. Continue each phase until its source is empty. Here the queue’s rear pointer indicates the next insertion location, unlike the earlier circular-queue question.

Reasoning and model answer — teacher-written

Phase 1: While the stack is not empty, read the item at its top pointer and move that pointer to the next occupied stack location. Store the removed item at the queue’s rear pointer and advance the rear pointer to the next insertion location.

Phase 2: While the queue is not empty, read the item at its front pointer and advance that pointer. Move the stack’s top pointer to its next free stack location and store the removed queue item there.

StageOrder
Popped from original stack6, 5, 4, 3, 2, 1
Removed from queue6, 5, 4, 3, 2, 1
Final stack, bottom to top6, 5, 4, 3, 2, 1
Official mark scheme
Why this earns marks — teacher explanation

The official list contains ten operational points but the total is capped at seven. Explain both transfers, pointer updates and stopping conditions. A six-iteration loop does not handle the stated unknown stack size.

Common mistakes — teacher analysis

A second stack would reverse the order at a different stage. FIFO removal preserves the pop sequence as items are pushed back, making item 1 the new top.

Build a booking system · Concept 42

Follow a booking from input to a consistent outcome

Observe

Two requests for one seat

  • Seat [1,2] is initially free.
  • Mina requests [1,2].
  • Jo later requests [1,2].
  • Waiting rule: queue a request whose seat is occupied.

Look, then discuss

Which stored facts should change when a seat request succeeds, and which should change when it is rejected?

The booking system has seat occupancy, waiting requests and an undo history. Assigning a free seat and adding someone to the waiting queue are both successful state changes. A rejected request changes neither collection and creates no undo entry.

Recall

Recall a state transition

Describe the values before an operation, the checks it makes and the values after it. Keep a saved log separate from an undo entry: a log records events, while undo needs the previous state required to reverse a successful change.

Explain

Explanation · 1 / 4

Check before changing the booking

Validate the requested position, then check occupancy and the person’s existing membership. Assign a free seat or, under the stated waiting rule, enqueue a new person requesting an occupied seat. Reject a duplicate person or an addition to a full waiting queue without changing the state.

Explanation · 2 / 4

Store enough information to undo

Before each successful change, push the previous seat and waiting-queue state. Both a seat assignment and a new waiting entry need an undo record because both change the system. Undo pops the latest entry and restores that previous state. A rejected attempt that changes nothing adds no entry.

Explanation · 3 / 4

Save the intended persistent information

When the task requires a persistent audit log, append a clearly formatted line and close the file. Saving the current complete register is a different requirement and may use a replacement file. Choose the mode from the desired final saved content.

Explanation · 4 / 4

Verify each structure after the operation

Check the selected field and grid cell, the front-to-rear waiting order, the bottom-to-top undo order and the saved file content where applicable. A success message alone does not prove those values agree.

Work together

Undo two different successful changes

The experiment uses a simplified one-dimensional list of seats 1:4. Seat 2 is initially free. Mina requests it, then Jo requests the same occupied seat.

Work together · 1 / 3

Trace the seat assignment

Assign seat 2 to Mina and push the previous state. This creates one undo entry.

Work together · 2 / 3

Trace the successful waiting entry

Keep Mina’s seat assignment and enqueue Jo at the rear. Save the prior state before this second change. There are now two undo entries. A repeated request from Jo would be rejected because Jo is already waiting and would add no third entry.

Work together · 3 / 3

Undo the changes one at a time

The first Undo removes Jo’s waiting entry and leaves Mina in seat 2. A second Undo restores the state before Mina’s assignment, making seat 2 free. Each Undo restores the saved whole state rather than applying an unstated automatic promotion rule.

State the application’s rules, then check that every affected representation agrees with the outcome.

Experiment

This lab simplifies the earlier 2D seating grid to seats 1:4. Predict seat state, waiting order and history for a free-seat assignment, an occupied-seat request by another person and a repeated request from that same person. Undo the successful changes one at a time and explain why the rejected duplicate adds no history.

Seats, a waiting queue and an undo stack

A booking uses the chosen free seat. If it is occupied, the person joins a queue for any next available seat. A cancellation serves the first waiting person.

Predict: What changes after the next operation?

State changes · describe this operation in words
A repeated person, a full waiting queue or cancelling a free seat is rejected. Rejected requests add no undo entry. Previous state replays the demonstration; UNDO is an operation inside the booking system.

Question 2 · Command word: State4 teacher marks
Start a fresh 2×2 performance with every seat FALSE, an empty undo stack and a queue holding A(1,2), B(1,2), C(2,1). Apply the lesson's rules to all requests, then Undo twice. State the outcomes, undo order, final occupancy and all log events. Both ADTs have capacity 3.
S10.05.A01S10.07.A02S10.09.A01S10.09.A02
Answer and checking points — teacher-written
  1. A succeeds, B is rejected and C succeeds; the request queue becomes empty.
  2. Undo returns C then A; B has no undo record.
  3. All four seats are FALSE and the undo stack is empty.
  4. The five events are ACCEPT A 1 2; REJECT B 1 2; ACCEPT C 2 1; UNDO C 2 1; UNDO A 1 2.

Question 3 · Command word: Write3 teacher marks
RequestRecord is already defined with ID : STRING, Row : INTEGER and Seat : INTEGER. Occupied is already declared as ARRAY[1:2,1:2] OF BOOLEAN and every cell is FALSE. Write pseudocode to declare Req of RequestRecord, save request A for row 1, seat 2 in its fields, and display that seat's current occupancy through Req's fields. State the output.
S10.02.A03S10.05.A01
Answer and checking points — teacher-written
One valid pseudocode answer
DECLARE Req : RequestRecord
Req.ID <- "A"
Req.Row <- 1
Req.Seat <- 2
OUTPUT Occupied[Req.Row, Req.Seat]
  1. DECLARE Req : RequestRecord creates the variable.
  2. Req.ID <- "A", Req.Row <- 1 and Req.Seat <- 2 save the request fields.
  3. OUTPUT Occupied[Req.Row, Req.Seat] selects and displays FALSE.
Common error: Use the record's row and seat fields as the two array indices.
Question 4 · Command word: Justify2 teacher marks
A drawing program queues commands received from a device and retains completed changes for Undo. Justify a queue for the incoming commands and a stack for the undo history.
S10.09.A01S10.09.A02
Answer and checking points — teacher-written

  2. The stack reverses the latest completed change first.

Question 5 · Command word: Explain2 teacher marks
A programme of performances often inserts an act after a known act. Explain why a linked list can be suitable and identify the links changed during insertion.
S10.09.A03
Answer and checking points — teacher-written
  1. A linked list can insert between neighbours without shifting all later act data.
  2. The new node points to the original successor, and the known predecessor points to the new node.
Common error: The advantage assumes the insertion point has been located.
