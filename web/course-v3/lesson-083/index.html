Program a booking system · Concept 38

Divide the requirement into clear responsibilities

Observe

Complete booking contract

ResponsibilityRequired behaviour
Accept a slotRetry until its quantity is within 1 to 6
Record a bookingAdd seats and count a group when Seats >= 3
Finish the runAfter three accepted slots, output both completed results

Look, then discuss

Which part decides whether a request is valid, and which part changes the running total?

The desk must accept exactly three bookings. Each quantity must be an integer from 1 to 6. Invalid attempts are retried. The final report gives total seats and the number of group bookings with at least three seats.

Recall

Recall functions and procedures

A function can return the Boolean validity decision. A procedure can update caller accumulators by reference. The main program controls how often those responsibilities are performed.

Explain

Explanation · 1 / 3

Write the data flow before code

Seats holds the current attempt; Index counts accepted booking slots; Total and Groups hold accumulated results. Start both accumulators at 0. The number of input attempts may exceed three.

Explanation · 2 / 3

Give each subprogram a precise contract

ValidSeats(Quantity) returns BOOLEAN for the inclusive 1-to-6 rule. RecordBooking reads the accepted quantity by value and updates Total and Groups by reference. The caller must validate before calling the recording procedure.

Explanation · 3 / 3

Choose the control structures from the contract

FOR controls the three accepted slots. REPEAT inside each slot obtains at least one attempt and stops on a valid value. Recording occurs after validation, then the next outer slot begins. Final output occurs after the FOR loop.

Work together

Predict a complete run before implementing it

Attempts are 0, 3, 7, 2, 4.

Work together · 1 / 2

Assign attempts to accepted slots

Slot 1 retries 0 and accepts 3. Slot 2 retries 7 and accepts 2. Slot 3 accepts 4. Thus five attempts create three accepted bookings.

Work together · 2 / 2

Calculate the required final report

Accepted seats total 3 + 2 + 4 = 9. Quantities 3 and 4 meet the group threshold, so Groups is 2.

A precise expected outcome lets you test the entire design rather than isolated syntax.

Check

Try it yourself · Teacher-written

Should an invalid attempt increment Index or update Total? Explain using the contract.

Check your reasoning

No. Index advances only when its outer slot completes after a valid quantity, and Total is updated only by the recording action after validation.

When the input 7 is rejected, which loop repeats and which counter stays in the same slot?

Follow two counters mentally: the FOR loop’s accepted slot and the number of attempts made inside it. A retry belongs to the current slot.

Recall

Recall nested loops

The inner loop completes before the outer NEXT runs. For each new accepted slot, the inner REPEAT begins afresh and obtains at least one new input.

Explain

Explanation · 1 / 3

Validate the current slot completely

REPEAT INPUT Seats UNTIL the inclusive condition becomes TRUE. When 7 is rejected in slot 2, execution returns to INPUT in that same slot.

Explanation · 2 / 3

Accumulate only the accepted value

Total <- Total + Seats and the group-selection IF occur after UNTIL. Placing either inside the validation body would include rejected attempts.

Explanation · 3 / 3

Use a complete inline version to verify the structure

Before extracting subprograms, check the full inline logic. This makes each loop’s responsibility visible and gives a reference behaviour for the modular version.

DECLARE Index, Seats, Total, Groups : INTEGER
Total <- 0
Groups <- 0
FOR Index <- 1 TO 3
    REPEAT
        INPUT Seats
    UNTIL (Seats >= 1) AND (Seats <= 6)
    Total <- Total + Seats
    IF Seats >= 3 THEN
        Groups <- Groups + 1
    ENDIF
NEXT Index
OUTPUT Total, Groups

Look, then discuss

Do the main program and both subprograms implement exactly the same booking rules?

Compare the inline version with the complete modular version. The program should accept the same inputs and produce the same final totals after the change.

Recall

Recall call notation and modes

Use ValidSeats(Seats) as a Boolean expression in UNTIL. Use CALL RecordBooking(Seats, Total, Groups) for the action. The quantity is copied; the two accumulators must be passed by reference.

Explain

Explanation · 1 / 3

Define the exact interfaces

ValidSeats declares RETURNS BOOLEAN and returns the same inclusive condition as the inline version. RecordBooking declares its read-only Quantity BYVAL and both changed accumulators BYREF.

Explanation · 2 / 3

Match arguments and retain control placement

Each call supplies arguments in the declared order. The procedure remains after UNTIL and inside FOR. Refactoring into a subprogram does not change when the update should happen.

FUNCTION ValidSeats(Quantity : INTEGER) RETURNS BOOLEAN
    RETURN (Quantity >= 1) AND (Quantity <= 6)
ENDFUNCTION
PROCEDURE RecordBooking(BYVAL Quantity : INTEGER, BYREF RunningTotal : INTEGER, BYREF GroupCount : INTEGER)
    RunningTotal <- RunningTotal + Quantity
    IF Quantity >= 3 THEN
        GroupCount <- GroupCount + 1
    ENDIF
ENDPROCEDURE
DECLARE Index, Seats, Total, Groups : INTEGER
Total <- 0
Groups <- 0
FOR Index <- 1 TO 3
    REPEAT
        INPUT Seats
    UNTIL ValidSeats(Seats)
    CALL RecordBooking(Seats, Total, Groups)
NEXT Index
OUTPUT Total, Groups

Work together · 1 / 3

Use a returned decision

ValidSeats(0) returns FALSE, so REPEAT asks again. ValidSeats(3) returns TRUE and ends the validation loop. The function does not output or store the booking.

Apply the deliberate caller updates

RecordBooking receives Quantity 3, refers to Total and Groups, then changes them to 3 and 1. The next outer iteration retains those values. With all attempts 0,3,7,2,4, the final report is 9 and 2.

1. Implement a random-number guessing game

Cambridge 9618/21 · May/June 2025 · 3 · 8 marks

Selected parts: 3 [8].

Original insert · reference material

Hint — reading the question

Generate the target once. Repeat prompt/input until a correct guess, with different feedback for high and low guesses. The paper explicitly excludes input validation.

Reasoning and model answer — teacher-written
DECLARE GeneratedValue, Guess : INTEGER
GeneratedValue ← INT(RAND(100)) + 1
REPEAT
    OUTPUT "Enter a guess between 1 and 100: "
    INPUT Guess
    IF Guess > GeneratedValue THEN
        OUTPUT "Guess was too high"
    ENDIF
    IF Guess < GeneratedValue THEN
        OUTPUT "Guess was too low"
    ENDIF
UNTIL Guess = GeneratedValue
OUTPUT "Number guessed correctly"

Under this paper’s insert, RAND(100) is at least 0 and below 100. INT gives an integer from 0 to 99; adding 1 gives 1 to 100 inclusive. The equality case triggers neither incorrect-guess message and exits the loop.

Official mark scheme
Why this earns marks — teacher explanation

The official scheme lists nine possible points with a maximum of eight. It separately recognises RAND, INT, the final range, the loop and the feedback.

Common mistakes — teacher analysis

Generating a new target inside the loop makes the answer change after every attempt. INT(RAND(100)) alone allows 0 and excludes 100.

Answer and checking points — teacher-written

One valid pseudocode solution

FUNCTION ValidMark(Mark : INTEGER) RETURNS BOOLEAN
    RETURN (Mark >= 0) AND (Mark <= 100)
ENDFUNCTION
PROCEDURE RecordMark(BYVAL Mark : INTEGER, BYREF Total : INTEGER, BYREF Passed : INTEGER)
    Total <- Total + Mark
    IF Mark >= 50 THEN
        Passed <- Passed + 1
    ENDIF
ENDPROCEDURE
DECLARE Index, Mark, Total, Passed : INTEGER
Total <- 0
Passed <- 0
FOR Index <- 1 TO 3
    REPEAT
        INPUT Mark
    UNTIL ValidMark(Mark)
    CALL RecordMark(Mark, Total, Passed)
NEXT Index
OUTPUT Total / 3, Passed
  1. ValidMark returns BOOLEAN using the inclusive 0-to-100 test; its INTEGER mark is passed by value.
  2. RecordMark reads Mark by value and receives Total and Passed by reference.
  3. The procedure adds Mark to Total and increments Passed only for Mark >= 50.

Common error: RETURN supplies the validity decision; reference parameters carry the updates.
