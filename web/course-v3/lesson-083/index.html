Building a complete structured program

Integrate validation, a returned decision and reference updates in one complete marks program.

Do the design, subprogram interfaces and final program implement the same marking rules?

Before you start

The input sequence is -1, 0, 50, 101, 100. How many valid marks should a three-mark program record?

Check your answer

Three: 0, 50 and 100. The invalid attempts -1 and 101 must not update the totals.

Turn the complete design into responsibilities

S11.01.A01

Translate the complete marks requirement

Implement this structured English: initialise Total and Passed to zero; obtain three valid integer marks, accepting the interval zero to 100 inclusive; for each accepted mark add it to Total and increase Passed when it is at least 50; finally output the mean and pass count. Incorrectly typed inputs are outside this task's assumptions.

Give each component one responsibility

Separate deciding validity from updating the accumulated results. The main program controls the number of accepted marks, the validation function answers a Boolean question, and the recording procedure performs the updates. All three parts must use the same interval, threshold and accepted-mark count.

Make the input and output contract explicit

PartRule
InputIntegers; keep asking until exactly three valid marks have been accepted. Enough input is supplied to finish.
Validity0 through 100 inclusive. Invalid attempts are retried within the same slot.
StatisticsTotal all accepted marks; count marks >= 50.
OutputOne mean followed by the pass count after all three accepted marks.
ScopeNon-integer input handling, persistence and an attempt limit are not part of this task.

Connect responsibility to a precondition

The main program owns control and the accumulated state. ValidMark answers a question without updating those accumulators. RecordMark assumes it receives an accepted mark and updates the two statistics. Calling it before validation would violate that precondition even if its syntax were correct.

Core explanation · Exam essentials

  • State accepted-input count, validity bounds, pass threshold and final outputs together.
  • Keep validation decisions separate from accepted-data updates.
Common misconception

Three attempts are not necessarily three accepted marks.

Check your understanding

Should an invalid attempt consume one of the three accepted-mark slots?

Check your answer

No. Repeat that slot's input until it is valid.

02

Nest validation inside the known count

S11.04.A01S11.04.A03S11.04.A05

Visual overview

Repeat attempts within an accepted slot

Use a FOR loop for the three accepted-mark slots. Inside each iteration, use REPEAT to obtain at least one attempt and UNTIL ValidMark(Mark) to finish validation. Only then call RecordMark. The nested input loop may repeat many times while the outer loop still advances once per accepted mark.

Update only after acceptance

The pass comparison belongs to the recording action after validation. With inputs -1, 0, 50, 101, 100, the accepted values are 0, 50 and 100. Their sum is 150, their mean is 50 and two satisfy the inclusive pass threshold. Output the mean and count after all accepted marks have been recorded.

Follow the two levels separately

The outer FOR controls accepted slots. The inner REPEAT controls attempts for the current slot. An invalid attempt does not reach RecordMark or NEXT Index; it returns to INPUT within the same slot. Once accepted, exactly one recording update occurs before the outer loop advances.

Check the denominator and precision

The divisor is three because exactly three values contribute. For attempts 20, -5, 60, 80, the accepted total is 160, so the mathematical mean is 160 / 3 and Passed is 2. Approximately 53.33 is a display rounded to two decimal places, not the exact value specified by the arithmetic.

Core explanation · Exam essentials

  • Rejected attempts stay in the inner loop and change neither statistic.
  • Calculate the mean after all accepted marks have been recorded.
Common misconception

Updating Total inside validation would include rejected attempts.

Check your understanding

Where is the mean calculated?

Check your answer

After the outer FOR loop, using Total / 3.

Connect the subprograms and verify the result

S11.06.A01S11.06.A02S11.06.A03S11.06.A04S11.06.A05S11.07.A01S11.07.A02S11.07.A03S11.07.A04

Visual overview

Choose how data crosses each call

ValidMark takes its INTEGER argument by value and returns a BOOLEAN used by UNTIL. RecordMark receives Mark by value, because it only reads that mark, and Total and Passed by reference, because it must update the caller's accumulators. The order at CALL RecordMark(Mark, Total, Passed) matches the header.

Check the whole program

Read the complete program from definitions through initialisation, repetition and final output. Test all failing marks, all passing marks and rejected attempts followed by valid boundaries. A correct return condition is (Mark >= 0) AND (Mark <= 100); using equality at zero would reject every other valid mark.

Follow the accepted mark 50

  1. Decide: ValidMark receives a copy of 50 and returns TRUE to UNTIL.
  2. Match the call: RecordMark receives Mark by value and references to main Total and Passed.
  3. Update: With Total 0 and Passed 0, add 50 and increment Passed to 1.
  4. Resume: Control returns to main at NEXT Index. The updated accumulators persist for the next slot.

Use tests that expose different mistakes

Test rejected attempts, both valid endpoints, all failing marks and all passing marks. Three 49s produce mean 49 and pass count 0; three 100s produce mean 100 and pass count 3. If Total and Passed were BYVAL, local updates would not accumulate in the caller between calls.

Read definitions and caller as one program

The program definitions, main calls, interface diagram and trace all describe the same data flow. The BOOLEAN returned by ValidMark controls acceptance; RecordMark changes storage through reference parameters and provides no function result. Main performs the final division and output.

Worked example · Complete the validated marks program

  1. Requirements and starting conditions

    Read exactly three accepted INTEGER marks in [0,100]; retry invalid attempts. Output their mean and count >= 50. Provide enough inputs to finish.

  2. Cambridge pseudocode
    FUNCTION ValidMark(Mark : INTEGER) RETURNS BOOLEAN
    RETURN (Mark >= 0) AND (Mark <= 100)
ENDFUNCTION
PROCEDURE RecordMark(BYVAL Mark : INTEGER, BYREF Total : INTEGER, BYREF Passed : INTEGER)
    Total <- Total + Mark
    IF Mark >= 50 THEN
        Passed <- Passed + 1
    ENDIF
ENDPROCEDURE
DECLARE Index, Mark, Total, Passed : INTEGER
Total <- 0
Passed <- 0
FOR Index <- 1 TO 3
    REPEAT
        INPUT Mark
    UNTIL ValidMark(Mark)
    CALL RecordMark(Mark, Total, Passed)
NEXT Index
OUTPUT Total / 3, Passed
  3. Expected result

    -1, 0, 50, 101, 100 gives mean 50 and Passed 2, with Total 150. Three 49s give 49 and 0; three 100s give 100 and 3.

Core explanation · Exam essentials

  • Functions return decisions into expressions; reference parameters update caller state.
  • Check argument order, types, parameter modes and the placement of every update.
Optional extension: allow a variable number of accepted marks

The next complete program assumes a non-negative INTEGER Count. It keeps the validation rule, but checks Count > 0 before dividing. It illustrates the new empty-data requirement rather than changing the fixed-three-mark task above.

Worked example · Handle zero accepted slots

  1. Requirements and starting conditions

    Read non-negative INTEGER Count, then Count valid marks. Output the mean, or No marks when Count is zero.

  2. Cambridge pseudocode
    DECLARE Count, Index, Mark, Total : INTEGER
INPUT Count
Total <- 0
FOR Index <- 1 TO Count
    REPEAT
        INPUT Mark
    UNTIL (Mark >= 0) AND (Mark <= 100)
    Total <- Total + Mark
NEXT Index
IF Count > 0 THEN
    OUTPUT Total / Count
ELSE
    OUTPUT "No marks"
ENDIF
  3. Expected result

    0 outputs No marks without reading a mark; 1, 101, 50 outputs 50; 3, 0, 50, 100 outputs 50.

Common misconception

Passing Total and Passed by value would discard each recording update on return.

Check your understanding

Why does RecordMark use BYVAL for Mark but BYREF for Total?

Check your answer

It reads Mark without changing it, but must update the caller's accumulated Total.

Answer and checking points — teacher-written

One valid pseudocode solution

FUNCTION ValidMark(Mark : INTEGER) RETURNS BOOLEAN
    RETURN (Mark >= 0) AND (Mark <= 100)
ENDFUNCTION
PROCEDURE RecordMark(BYVAL Mark : INTEGER, BYREF Total : INTEGER, BYREF Passed : INTEGER)
    Total <- Total + Mark
    IF Mark >= 50 THEN
        Passed <- Passed + 1
    ENDIF
ENDPROCEDURE
DECLARE Index, Mark, Total, Passed : INTEGER
Total <- 0
Passed <- 0
FOR Index <- 1 TO 3
    REPEAT
        INPUT Mark
    UNTIL ValidMark(Mark)
    CALL RecordMark(Mark, Total, Passed)
NEXT Index
OUTPUT Total / 3, Passed
  1. ValidMark returns BOOLEAN using the inclusive 0-to-100 test; its INTEGER mark is passed by value.
  2. RecordMark reads Mark by value and receives Total and Passed by reference.
  3. The procedure adds Mark to Total and increments Passed only for Mark >= 50.

Common error: RETURN supplies the validity decision; reference parameters carry the updates.

Original question · Cambridge 9618/21

1. Implement a random-number guessing game

Cambridge 9618/21 · May/June 2025 · 3 · 8 marks

Selected parts: 3 [8].

Original insert · reference material

Reading the question — teacher guidance

Generate the target once. Repeat prompt/input until a correct guess, with different feedback for high and low guesses. The paper explicitly excludes input validation.

Solution / model answer — teacher-written
DECLARE GeneratedValue, Guess : INTEGER
GeneratedValue ← INT(RAND(100)) + 1
REPEAT
    OUTPUT "Enter a guess between 1 and 100: "
    INPUT Guess
    IF Guess > GeneratedValue THEN
        OUTPUT "Guess was too high"
    ENDIF
    IF Guess < GeneratedValue THEN
        OUTPUT "Guess was too low"
    ENDIF
UNTIL Guess = GeneratedValue
OUTPUT "Number guessed correctly"

Under this paper’s insert, RAND(100) is at least 0 and below 100. INT gives an integer from 0 to 99; adding 1 gives 1 to 100 inclusive. The equality case triggers neither incorrect-guess message and exits the loop.

Official mark scheme
Why this earns marks — teacher explanation

The official scheme lists nine possible points with a maximum of eight. It separately recognises RAND, INT, the final range, the loop and the feedback.

Common mistakes — teacher analysis

Generating a new target inside the loop makes the answer change after every attempt. INT(RAND(100)) alone allows 0 and excludes 100.

Summary

Keep one consistent design

The input rules, accepted count and thresholds agree across all parts.

Place updates after acceptance

Validation retries do not consume a slot or change totals.

Connect results correctly

Functions return decisions; reference parameters update caller state.
