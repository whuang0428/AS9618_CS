Develop a booking system · Concept 09

Keep the current state between events

Observe

One booking, three states

StateMeaning
DraftA request is being prepared
PendingA valid request has been submitted; payment is awaited
ConfirmedPayment has been received

Look, then discuss

Does pressing Pay have the same effect before and after Submit?

Begin in Draft with Seats 3 and Available 6. Predict Draft → Submit → Pay → Cancel. Each request is independent; this model does not subtract seats from availability.

Recall

Recall a stored value

A variable can keep a value until something changes it. Similarly, a state persists between events. An event is something that happens, such as Submit; it is not the name of the state that exists afterwards.

Explain

Explanation · 1 / 4

Identify the starting state

A state-transition diagram uses a node for each state and directed arrows for transitions. A starting arrow identifies the initial state. Begin the booking model in Draft, before consuming any event.

Explanation · 2 / 4

Choose a transition from the current state

For a valid request, Submit moves Draft to Pending. Pay moves Pending to Confirmed. Cancel moves Pending or Confirmed back to Draft. Read the event only against outgoing arrows from the current state.

Explanation · 3 / 4

Keep a state when an event does not advance it

In this teaching model, events not assigned a change leave the state unchanged. Pay in Draft therefore stays Draft; Submit in Confirmed stays Confirmed. Such a self-loop consumes an event without moving to a different state. That rule is explicitly specified here; do not invent missing transitions in another question.

Explanation · 4 / 4

Use the diagram for behaviour, not module hierarchy

A state diagram shows event-dependent behaviour over time. It does not divide the program into callable modules. The same booking system can have both a structure chart and a state diagram, each documenting a different aspect.

Change a booking state with events

Each booking is independent. Available is a fixed per-request limit, not a shared stock counter. submit is allowed only for a whole-number Seats from 1 to Available. pay confirms a Pending booking; cancel returns Pending or Confirmed to Draft. Other events leave the state unchanged.

    Develop a booking system · Concept 10

    Check the condition and read the action

    Observe

    Two submissions from Draft

    SeatsEventConditionResult
    3Submit1 <= Seats <= 6 is truePending
    7SubmitThe range condition is falseDraft; request is rejected

    Look, then discuss

    Why can the same event from the same state have different outcomes?

    The extra information is a guard: a condition that must hold for the transition. In Cambridge pseudocode the range condition is written as two comparisons joined by AND.

    Recall

    Recall an inclusive Boolean range

    (Seats >= 1) AND (Seats <= Available) is TRUE only when both bounds are met. A condition is evaluated from data; an event is the occurrence that prompts the system to consider a transition.

    Explain

    Explanation · 1 / 3

    Evaluate the guard before taking the arrow

    For a Draft booking, Submit with a true range guard moves to Pending. A false guard follows the specified rejection self-loop. Do not take both arrows or change the required limit to match the entered value.

    Explanation · 2 / 3

    Read event, condition and action separately

    A diagram may use an event [condition] / action label. The event triggers consideration, the guard chooses whether the transition is allowed, and the action is an output or update performed as the transition occurs. A label such as Cancel | Re-prompt in a supplied question separates input from output; use that question’s convention.

    Explanation · 3 / 3

    Transfer to an upload example

    The upload model starts Ready. Start enters Uploading; progress keeps Uploading. On complete, Valid TRUE returns to Ready, while Valid FALSE enters Error. Retry from Error returns to Uploading. The upload model defines only the listed transitions; no default response to an unlisted event is assumed.

    Work together

    Use a table to draw and trace transitions

    From Ready, process start, progress, complete with Valid FALSE, retry, complete with Valid TRUE.

    Work together · 1 / 2

    Carry the state and inspect each guard

    The resulting states are Uploading, Uploading, Error, Uploading, Ready. The two complete events differ because their Valid conditions differ.

    Work together · 2 / 2

    Construct arrows from a supplied table

    Create nodes for distinct states. For each row draw an arrow from its current state to its next state, then copy the event and any condition or output onto the arrow. Equal current and next states require a self-loop. Mark the initial state separately.

    The transition table and diagram should express the same cases, including loops and actions.

    State the turnstile state after each event in push, coin, pass, starting from Locked. Explain the first result.

    S12.03.A01
    Answer and checking points — teacher-written
    1. The states after the three events are Locked, Unlocked and Locked.
    2. The push transition is a self-loop on Locked, so it preserves that state.

    Common error: Use the current state before choosing the next arrow.

    Question 2 · Command word: Compare2 teacher marks

    Compare a structure chart and a state-transition diagram as ways of documenting a login system.

    S12.03.A01
    Answer and checking points — teacher-written
    1. The structure chart shows login module responsibilities and calling interfaces.
    2. The state diagram shows conditions such as LoggedOut and LoggedIn and the events that change them.

    Common error: Keep module hierarchy separate from persistent conditions.

    Question 3 · Command word: State3 teacher marks

    The supplied upload diagram starts in Ready. State every state after start, complete [Valid = FALSE], retry, progress, complete [Valid = TRUE]. Explain why the two complete events have different outcomes and whether a new start is possible at the end.

    S12.03.A01
    Answer and checking points — teacher-written
    1. The successive states are Uploading, Error, Uploading, Uploading and Ready.
    2. Both completion events start in Uploading, but their different Valid guards select different transitions.
    3. Ready has a start transition back to Uploading, so it is not a terminal state.

    Common error: Do not choose a transition by event name while ignoring its condition.

    Question 4 · Command word: Describe2 teacher marks

    Describe the purpose of a state-transition diagram and what an event-labelled arrow records.

    S12.03.A01
    Answer and checking points — teacher-written
    1. It documents the conditions a system can occupy and its possible changes of condition.
    2. A directed arrow identifies the event that moves the system from its source state to its destination state.

    Common error: Do not answer with the purpose of a walkthrough.
