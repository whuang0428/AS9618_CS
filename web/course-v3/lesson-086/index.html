01

Document persistent states and transitions

S12.03.A01

Visual overview

Model persistent conditions

A state is a condition a system can remain in while it waits for an event. A state-transition diagram documents possible changes from those conditions. The initial indicator supplies a starting state; a directed arrow specifies the source and destination of a transition, and its label tells the reader which event causes it.

Interpret the supplied model

The turnstile begins Locked. A coin moves it to Unlocked; passing moves it back to Locked. A push while Locked and another coin while Unlocked have explicit self-loops. A self-loop consumes an event without changing the state: it does not imply that the system briefly visits another state.

Separate state, event and action

A state such as Unlocked describes the system, whereas a module such as CalculateCost names a responsibility. An event such as coin is something that happens to the system. Keeping these roles separate prevents a state diagram from becoming a misleading list of instructions.

Core explanation · Exam essentials

  • Use state names for persistent conditions and labelled arrows for permitted changes.
  • Read the initial indicator and explicit self-loops before tracing events.
Common misconception

A state name describes a condition, not an instruction such as calculate the total.

Check your understanding

Does the push loop mean the turnstile becomes unlocked briefly?

Check your answer

No. Its source and destination are both Locked.

Trace without inventing behaviour

  1. Start: Write the specified initial state.
  2. Select: Look only at arrows leaving the current state; match the next event and any condition.
  3. Update: Record the destination as the new current state, even if it is the same state.
  4. Continue or clarify: Use that result for the next event. If no relevant transition is specified, report the missing behaviour rather than borrowing an arrow from another state.

Use the current state at every step

From Locked, coin, coin, pass gives Unlocked, Unlocked, Locked. The second coin uses the Unlocked loop; it cannot take the Locked-to-Unlocked arrow because its source does not match the current state. The intermediate states explain the result, rather than only naming the final state.

Core explanation · Exam essentials

  • Trace each event using its current source state, label and destination.
  • An omitted transition is unspecified unless the problem explicitly defines a default.
Common misconception

A matching event on an arrow from the wrong state is not an available transition.

Check your understanding

What follows coin, coin, pass from Locked?

Check your answer

Unlocked, Unlocked, Locked; the second coin takes the self-loop.

03

Trace transitions with conditions

S12.03.A01

Visual overview

Read the condition with the event

A guard is a condition attached to a transition. The upload example has Ready, Uploading and Error states. During Uploading, complete with Valid TRUE returns to Ready; complete with Valid FALSE leads to Error. These alternatives are exclusive and cover both BOOLEAN values. Event name alone is therefore insufficient to select the transition.

State what the model does and does not define

Ready can wait for a new start; it is not a terminal state merely because one upload has completed. The model also specifies cancellation from all three states, progress while Uploading and retry from Error. Other state/event pairs are unspecified. A real implementation would need a requirement for any additional events it must handle.

Use a table as supporting evidence

A transition table is a useful check on the diagram: give one row for each specified source, event, condition and destination. Reading and completing such a table supports understanding of the diagram. No formal automata notation or state-machine implementation is needed here.

Core explanation · Exam essentials

  • A guarded transition needs the current state, event and satisfied condition.
  • Check alternative guards and distinguish returning to a ready state from terminating.
Common misconception

Matching an event name is insufficient when the transition also has a condition.

Check your understanding

From Uploading, which state follows complete when Valid is FALSE?

Check your answer

Error. Select the outgoing complete transition whose guard is satisfied.

Practice questions

3 core tasks · 7 teacher marks · 11–16 minutes (teacher estimate). Explain your reasoning before checking the answer.

Question 1 · Command word: State2 teacher marks

State the turnstile state after each event in push, coin, pass, starting from Locked. Explain the first result.

S12.03.A01
Answer and checking points — teacher-written
  1. The states after the three events are Locked, Unlocked and Locked.
  2. The push transition is a self-loop on Locked, so it preserves that state.

Common error: Use the current state before choosing the next arrow.

Question 2 · Command word: Compare2 teacher marks

Compare a structure chart and a state-transition diagram as ways of documenting a login system.

S12.03.A01
Answer and checking points — teacher-written
  1. The structure chart shows login module responsibilities and calling interfaces.
  2. The state diagram shows conditions such as LoggedOut and LoggedIn and the events that change them.

Common error: Keep module hierarchy separate from persistent conditions.

Question 3 · Command word: State3 teacher marks

The supplied upload diagram starts in Ready. State every state after start, complete [Valid = FALSE], retry, progress, complete [Valid = TRUE]. Explain why the two complete events have different outcomes and whether a new start is possible at the end.

S12.03.A01
Answer and checking points — teacher-written
  1. The successive states are Uploading, Error, Uploading, Uploading and Ready.
  2. Both completion events start in Uploading, but their different Valid guards select different transitions.
  3. Ready has a start transition back to Uploading, so it is not a terminal state.

Common error: Do not choose a transition by event name while ignoring its condition.

Optional consolidation · 1 tasks · 2 teacher marks

Choose a task when you need another check of this idea.

Question 1 · Command word: Describe2 teacher marks

Describe the purpose of a state-transition diagram and what an event-labelled arrow records.

S12.03.A01
Answer and checking points — teacher-written
  1. It documents the conditions a system can occupy and its possible changes of condition.
  2. A directed arrow identifies the event that moves the system from its source state to its destination state.

Common error: Do not answer with the purpose of a walkthrough.

Why this earns marks — teacher explanation

The four marks cover the missing S1-to-S2 transition, the S2 loop label, S3 with its incoming label, and S4 with its incoming label. The already supplied cancel transition remains part of the complete diagram.

Common mistakes — teacher analysis

“Too many tries” belongs on the arrow, not as the name of a new state. Re-input keeps the system in S2; it does not return to S1.
