Design a ticket system · Concept 06

Let a condition choose the ticket price

Observe

Two routes from one subtotal

  • 2 × 25.00 = 50.00 subtotal
  • Student TRUE: pay 90% of 50.00
  • Student FALSE: pay the full 50.00
  • Expected totals: 45.00 and 50.00

Look, then discuss

How can one program charge students and other buyers differently?

Two buyers each request two tickets. Mina is a student and pays 45.00 after a 10% discount. Arun is not a student and pays 50.00. The quantity and unit price are the same; student status selects the calculation.

Recall

A condition has a truth value

A BOOLEAN value is TRUE or FALSE. IF uses that value to choose an action. A 10% discount removes one tenth of the subtotal, leaving 90%, so multiply by 0.90. Inputs have the stated types and requested tickets are available.

Explain

Explanation · 1 / 4

Calculate what both cases share

Read Quantity and Student, then calculate Subtotal ← Quantity * 25.00. Doing this before the decision gives both possible branches the same undiscounted amount.

Explanation · 2 / 4

Choose one branch

IF Student THEN selects the discounted calculation when Student is TRUE. ELSE selects the full subtotal when it is FALSE. Only the selected branch runs on one execution.

IF Student THEN
    Total ← Subtotal * 0.90
ELSE
    Total ← Subtotal
ENDIF

Explanation · 3 / 4

Continue after the decision

Place OUTPUT Total after ENDIF. Either branch assigns Total, so the output can use it whichever branch was selected. Two unconnected IF statements are not automatically equivalent to one IF with an ELSE.

Explanation · 4 / 4

Build conditions from comparisons

Paid >= Total is TRUE when payment is sufficient, including exact payment. For Total 45, Paid 44 is FALSE and Paid 45 is TRUE. The symbols >= include the boundary; > would wrongly reject exact payment.

Work together

Trace both student-status inputs

Quantity is 3 and TicketPrice is 25.00. Compare independent runs with Student TRUE and Student FALSE.

Work together · 1 / 3

Calculate the shared subtotal

Both runs read Quantity 3 and calculate Subtotal = 3 × 25.00 = 75.00.

Work together · 2 / 3

Take the selected branch

TRUE assigns Total = 75.00 × 0.90 = 67.50. FALSE assigns Total = 75.00. The other branch is skipped in each run.

Work together · 3 / 3

Follow the join and output

Each execution continues after ENDIF and outputs its own Total once. The student run displays 67.50; the other displays 75.00.

Selection uses a truth-valued condition to choose which operations are executed.

Experiment

Predict Total for each student-status value. The experiment uses an equivalent shorter version: first store the full price in Total, then change Total only when Student is TRUE. On FALSE, keeping that value gives the same result as the explicit ELSE assignment above.

A ticket costs 25.00. Trace one statement at a time and watch which values change.

Design a ticket system · Concept 10

Replace repeated additions with a FOR loop

Observe

Four quantities, one running total

  • Inputs in order: 2, 1, 3, 2
  • Start with zero tickets counted
  • Read and add one new quantity at a time
  • Display the final total once

Look, then discuss

How can the desk total four requests without writing the same instructions four times?

Four valid requests contain 2, 1, 3 and 2 tickets. We want the total number requested. These quantities are teaching inputs for a count-controlled calculation; payment and available capacity are outside this small task.

Recall

Update from the old value

In TotalTickets ← TotalTickets + Quantity, evaluate the right side using the old TotalTickets, then replace it with the new value. This is an update, not an algebraic claim that a number equals itself plus another number.

Explain

Explanation · 1 / 4

Perform the repeated work manually

Starting from zero, add 2 to get 2, then 1 to get 3, then 3 to get 6, then 2 to get 8. The repeated actions are reading the next quantity and adding it to the current total.

Explanation · 2 / 4

State the repetition count with FOR

FOR OrderNumber ← 1 TO 4 repeats its body for 1, 2, 3 and 4. The upper bound is included. OrderNumber is the loop counter; TotalTickets records a different quantity.

Explanation · 3 / 4

Place operations before, inside and after

Initialise TotalTickets to zero before the loop. Put INPUT Quantity and the addition inside it. Put OUTPUT TotalTickets after NEXT OrderNumber so that only the completed total is displayed.

Explanation · 4 / 4

Check the state after each pass

Record the new input and new total on each iteration. Resetting TotalTickets inside the loop would discard earlier additions. Reading Quantity only before the loop would repeatedly add one old value.

Use the inputs 2, 1, 3, 2. All inputs are positive integers and the task requests one final total.

Work together · 1 / 3

Prepare the state

Declare the three INTEGER variables and initialise the accumulator once. Its zero means no quantities have yet contributed.

Work together · 2 / 3

Write the repeated body

Use one input and one addition per iteration. The same statements operate on each newly obtained Quantity.

DECLARE OrderNumber, Quantity, TotalTickets : INTEGER
TotalTickets ← 0
FOR OrderNumber ← 1 TO 4
    INPUT Quantity
    TotalTickets ← TotalTickets + Quantity
NEXT OrderNumber
OUTPUT TotalTickets

Verify input count and final output

The loop consumes four quantities and produces a final total of 8. The output is after the loop; 2, 3 and 6 are intermediate stored values, not required outputs.

Use a count-controlled loop when the required number of repetitions is known.

Design a ticket system · Concept 11

Add only the inputs that qualify

Observe

Predict the changing total

  • Read exactly 3 integers: 2, -1, 3
  • Initial total: 0
  • Add a value only when it is greater than 0
  • Expected final total: 5

Look, then discuss

How can the desk read every entry but add only positive quantities?

A trial input list contains 2, -1 and 3. The rule for this small exercise is to total positive INTEGER values and ignore zero or negative values. It is a data-processing exercise, not a completed sale or a change to ticket availability.

Recall

Keep loop count and accepted total separate

A FOR loop controls how many inputs are read. An IF inside the loop controls whether the current input contributes. The number of iterations is not the number of accepted inputs and neither is automatically their sum.

Explain

Explanation · 1 / 4

Read every required input

For the small trial, use three iterations even though one value is negative. The negative entry still uses one input position. Reading until three positive values arrive would implement a different requirement.

Explanation · 2 / 4

Test the current value inside the loop

After obtaining the new value, evaluate Value > 0. If it is TRUE, add Value to Total. If it is FALSE, leave Total unchanged and continue to the next iteration.

Explanation · 3 / 4

Distinguish counting from totalling

Total ← Total + Value adds the accepted amount. AcceptedCount ← AcceptedCount + 1 would count qualifying entries instead. With 2, -1, 3, the sum is 5 but the number of positive entries is 2.

Explanation · 4 / 4

Prepare a complete response to the question

Include required declarations and any requested input prompt. Initialise before repetition and output after it. For E086, extend the count to exactly 100 integers and prompt before each input; do not change the positive-value condition.

Work together

Build the three-input algorithm

Read exactly three integers, prompt before each one and output the sum of the positive values once. Use 2, -1, 3.

Work together · 1 / 3

Initialise and choose the loop

Declare Index, Value and Total as INTEGER. Set Total to zero before FOR Index ← 1 TO 3. This establishes one running total for the whole task.

Work together · 2 / 3

Place input and selection in the repeated body

Each iteration prompts, reads a new Value and selects whether to add it. The indentation shows which operations belong to the loop.

DECLARE Index, Value, Total : INTEGER
Total ← 0
FOR Index ← 1 TO 3
    OUTPUT "Input an integer value"
    INPUT Value
    IF Value > 0 THEN
        Total ← Total + Value
    ENDIF
NEXT Index
OUTPUT Total

Work together · 3 / 3

Check normal and empty-contribution cases

The trial produces three prompts followed by final total 5. Inputs 0, -1, -3 still use all three iterations and give final total 0. No positive contribution does not mean no final output.

Sequence, iteration and selection cooperate, but each controls a different part of the solution.

Original question · Cambridge 9618/23

2. Write a complete positive-number total

Cambridge 9618/23 · October/November 2024 · 2(a) · 5 marks

Selected parts: 2(a) [5].

Hint — reading the question

Declare all variables, prompt before each input and process exactly 100 integers. Zero contributes nothing. Output once after the loop.

Reasoning and model answer — teacher-written
DECLARE Count, Total, NextNumber : INTEGER
Total ← 0
FOR Count ← 1 TO 100
    OUTPUT "Input an integer value"
    INPUT NextNumber
    IF NextNumber > 0 THEN
        Total ← Total + NextNumber
    ENDIF
NEXT Count
OUTPUT Total

The total starts at zero. Each positive input is added once; negatives and zero leave it unchanged. If every input is non-positive, the output is zero.

Official mark scheme
Why this earns marks — teacher explanation

The scheme lists six points but awards at most five. Declaration, iteration, prompt/input, condition, accumulation and final output all matter to a complete solution.

Common mistakes — teacher analysis

Initialising Total inside the loop loses earlier additions. Output inside the loop gives intermediate totals instead of the single requested result.

Design a ticket system · Concept 12

Stop a WHILE loop when its condition becomes false

Observe

A stream with an end signal

  • Inputs: 2, 1, 0
  • Continue while Quantity > 0
  • Do not process the stopping value
  • What if the very first input is 0?

Look, then discuss

How can the desk collect quantities when nobody knows how many entries will arrive?

For this separate input task, positive whole numbers are quantities and 0 means “finish”. The list is 2, 1, 0. Zero is a stopping signal and must not be treated as another request.

Recall

Separate a stopping signal from ordinary data

All inputs in this task are non-negative integers and the supplied stream eventually contains 0. A sentinel is a special value used to signal an end. Test the current input before deciding whether to process it.

Explain

Explanation · 1 / 4

Read the first value before the test

INPUT Quantity supplies the first value for Quantity > 0. Without an initial input, the condition would try to use an unavailable value. Initialise the running total before any additions.

Explanation · 2 / 4

Use WHILE as a pre-condition loop

WHILE Quantity > 0 tests before its body. If the first input is 0, the body runs zero times. The final output is still reached after ENDWHILE.

Explanation · 3 / 4

Make progress towards another test

Inside the body, add the current positive Quantity and read the next Quantity. Execution returns to the test with that new value. Omitting the new input would keep retesting the old positive value indefinitely.

Explanation · 4 / 4

Keep the exit value out of processing

For 2, 1, 0, only 2 and 1 enter the body. Zero makes the condition FALSE and exits. The total is 3, and a first input of zero leaves the initial total at 0.

Work together

Trace each condition check

Read non-negative quantities until 0 and output their total. Trace 2, 1, 0.

Work together · 1 / 3

Prepare and enter

Set Total to zero and read 2. Since 2 > 0 is TRUE, enter the body and add 2.

Work together · 2 / 3

Update the value used by the condition

Read 1 at the end of the body. The next test is TRUE, so add 1 and obtain total 3. Then read 0.

Work together · 3 / 3

Exit and report once

The test 0 > 0 is FALSE. Skip the body and output 3 after ENDWHILE.

DECLARE Quantity, Total : INTEGER
Total ← 0
INPUT Quantity
WHILE Quantity > 0
    Total ← Total + Quantity
    INPUT Quantity
ENDWHILE
OUTPUT Total

A WHILE loop may execute zero times because its condition is tested before the body.

Experiment

Compare a first input of zero with one positive input followed by zero. Count condition checks separately from executions of the body.

Connect

Keep this idea

A pre-condition loop repeats while its condition is true; its body must allow the stopping condition to be reached.

Design a ticket system · Concept 13

Use REPEAT when the body must run at least once

Observe

Ask, then decide whether to stop asking

  • Attempt 1: 0 → ask again
  • Attempt 2: -2 → ask again
  • Attempt 3: 3 → accept
  • The task must ask at least once

Look, then discuss

How can a loop test a quantity only after it has asked the buyer for one?

A request-entry task must ask for a positive whole-number quantity. The buyer enters 0, then -2, then 3. All entries are INTEGER values, but only the last satisfies this exercise’s rule.

Recall

This example checks a range, not a type

Assume every supplied input is an INTEGER and that a positive value will eventually be supplied. We only check positivity here; ticket availability will be checked separately. The input must happen before its value can be tested.

Explain

Explanation · 1 / 4

Place the first action before the condition

REPEAT starts the body immediately. Display the prompt and read Quantity inside the body, then test the input at UNTIL. No earlier input is needed for this structure.

Explanation · 2 / 4

State the condition that ends repetition

UNTIL Quantity > 0 stops when the quantity is acceptable. A FALSE result repeats the body; a TRUE result leaves the loop. This stopping meaning is the opposite of a WHILE condition that is true while repetition continues.

Explanation · 3 / 4

Trace rejected and accepted attempts

After 0, Quantity > 0 is FALSE, so ask again. The same happens for -2. After 3 it becomes TRUE, so leave the loop with Quantity holding 3.

Explanation · 4 / 4

Choose a loop from the required first behaviour

Use REPEAT when the body must run before the first test. Use WHILE when the condition may prevent every execution of the body. Equivalent solutions are possible if their input placement and condition polarity are adjusted together.

Work together

Request a positive quantity

Prompt for an INTEGER Quantity until it is positive, then output the accepted quantity. Use attempts 0, -2, 3.

Work together · 1 / 3

Write the action and stopping rule

Put the prompt and input after REPEAT. End with UNTIL Quantity > 0. The loop itself gives every attempt a prompt.

Work together · 2 / 3

Follow the three tests

The tests after 0 and -2 are FALSE, so both repeat. The test after 3 is TRUE and stops. The body executes three times; its minimum possible count is one.

Work together · 3 / 3

Use the accepted value afterwards

OUTPUT Quantity after the loop displays only the accepted value 3. Rejected inputs are not output as accepted requests.

DECLARE Quantity : INTEGER
REPEAT
    OUTPUT "Enter a positive quantity"
    INPUT Quantity
UNTIL Quantity > 0
OUTPUT Quantity

The REPEAT condition describes when to stop, and it is tested after the body.

Experiment

Predict the number of attempts for 3 alone and for 0, -2, 3. Compare the UNTIL condition with the WHILE version’s continuing condition.

Supply a short input sequence. Follow the loop control, the current input and the running total.

Predict: How often will the body execute? Which values contribute to Total?

Take it further · Optional challenge

The quantity must also fit PlacesLeft. State an UNTIL condition and explain what the program should do before the loop when PlacesLeft is 0.

Check the challenge

For positive PlacesLeft, use UNTIL (Quantity >= 1) AND (Quantity <= PlacesLeft). When PlacesLeft is 0, no quantity can satisfy that rule. Report that no places are available and skip the request loop; do not trap the buyer in endless attempts.

Connect

Keep this idea

REPEAT tests after the body and executes at least once. Its UNTIL condition is true when repetition finishes.

Question 1 · Command word: Write4 teacher marks

Write pseudocode to input a person's non-negative whole-number age and output "Adult" for an age of at least 18, or "Minor" otherwise. State the outputs at ages 17, 18 and 19.

S9.06.A01
Answer and checking points — teacher-written

One valid pseudocode solution

DECLARE Age : INTEGER
INPUT Age
IF Age >= 18 THEN
    OUTPUT "Adult"
ELSE
    OUTPUT "Minor"
ENDIF
  1. The program inputs Age and tests Age >= 18.
  2. The true branch outputs the literal "Adult".
  3. The false branch outputs the literal "Minor".
  4. The three outputs are Minor, Adult and Adult respectively.

Common error: Age = 18 rejects older adults; use the inclusive inequality.

Question 2 · Command word: Write4 teacher marks

Write pseudocode to input four integers and output their sum once. Explain where the accumulator must be initialised.

S9.06.A01
Answer and checking points — teacher-written

One valid pseudocode solution

DECLARE Index : INTEGER
DECLARE Value : INTEGER
DECLARE Total : INTEGER
Total <- 0
FOR Index <- 1 TO 4
    INPUT Value
    Total <- Total + Value
NEXT Index
OUTPUT Total
  1. Total is set to zero before repetition begins.
  2. A loop performs exactly four inputs.
  3. Each input is added to the current Total inside the loop.
  4. The final Total is output after the loop.

Common error: Do not reset Total during the repeated body.

Question 3 · Command word: Write4 teacher marks

Write pseudocode to read six temperature readings and output the number strictly greater than 80. The readings are integers; all six must be processed.

S9.06.A01
Answer and checking points — teacher-written

One valid pseudocode solution

DECLARE Index : INTEGER
DECLARE Reading : INTEGER
DECLARE WarningCount : INTEGER
WarningCount <- 0
FOR Index <- 1 TO 6
    INPUT Reading
    IF Reading > 80 THEN
        WarningCount <- WarningCount + 1
    ENDIF
NEXT Index
OUTPUT WarningCount
  1. A warning counter starts at zero.
  2. A loop inputs exactly six new readings.
  3. The condition uses Reading > 80.
  4. Only a true comparison increments the warning count, which is output after all readings.

Common error: A reading equal to 80 does not satisfy strictly greater than.
