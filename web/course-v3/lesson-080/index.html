Procedures and parameter passing

Define reusable actions and trace the effects of value and reference parameters.

Does the call need a copy of a value or permission to update the caller's variable?

Before you start

A procedure changes a BYVAL integer parameter. Must the caller's variable change?

Check your answer

No. The parameter holds a copy; changing that copy does not change the caller's integer.

Define and call procedures

S11.06.A01S11.06.A02S11.06.A03

Give an action one responsibility

A procedure groups statements that perform an action. Use it for a responsibility such as displaying a heading or updating a total when no function result is required in an expression. Define it with PROCEDURE Name(parameters) and ENDPROCEDURE; invoke it with CALL Name(arguments). A definition alone does not execute the body.

Separate the definition from its calls

A procedure can take no parameters, one parameter or several parameters. Heading() needs none, Show(Value) receives one value, and Add(Total, Amount) receives two. State each formal parameter's type and preserve the declared order at the call. Empty parentheses remain in a no-parameter definition and call.

Follow a procedure call

  1. Reach CALL: The main program reaches CALL Heading(). The definition itself has not printed anything.
  2. Enter the body: Control transfers to Heading and OUTPUT prints Results.
  3. Finish the action: ENDPROCEDURE completes this invocation.
  4. Resume the caller: Continue at the next statement after CALL, not at the beginning of the main program.

Explain when a procedure helps

Use a procedure when the caller requests an action, such as displaying a heading or updating a running total. Reusing one body avoids copying that action at each call site and gives one place to maintain it. That is a clarity and maintenance benefit; the call itself does not prove faster execution.

Keep three kinds of effect distinct

The interface in the next unit states which data an action receives. A procedure may have no parameters, one, or several. It does not provide a function result for an expression, but it may display output or deliberately update a caller variable through a reference parameter.

Worked example · Call an action, then resume the caller

  1. Requirements and starting conditions

    No keyboard input is required. Define a heading action, call it once, then display the next main-program message.

  2. Cambridge pseudocode
    PROCEDURE Heading()
    OUTPUT "Results"
ENDPROCEDURE
CALL Heading()
OUTPUT "Next action"
  3. Expected result

    The output is Results followed by Next action. The definition itself produces no output before CALL.

Core explanation · Exam essentials

  • Define with PROCEDURE … ENDPROCEDURE; invoke with CALL Name(arguments).
  • Control returns to the next caller statement; a procedure supplies an action, not a function result.
Common misconception

Do not assign the result of a procedure call; a procedure does not supply a function return value.

Check your understanding

What triggers Heading's body?

Check your answer

CALL Heading(), rather than the definition being encountered.

Match arguments to a procedure interface

S11.06.A03

Visual overview

Read the interface before making the call

The caller and the procedure need an agreed interface. Its name identifies the action; its ordered, typed parameters specify the data the caller must supply and which data may be updated.

Match CALL Add(Score, 3)

NameAddAdd selects the procedure.
First formal parameterBYREF Total : INTEGERScore supplies caller storage.
Second formal parameterBYVAL Amount : INTEGER3 supplies a value.
Intended effectAdd Amount to Total.Increase Score by 3.

Introduce the terms at the point of use

A formal parameter is the name declared in a subprogram header. An argument is the value, variable or expression supplied by the caller. The names need not be the same. Match the number, order, types and modes: Total receives the first argument because of its position, not because the caller must name its variable Total.

A valid type is not the whole contract

The header records the name and typed parameter list. The interface also needs the intended behaviour: Add increases Total by Amount, rather than setting it to Amount or printing it. A caller can use that contract without depending on the internal statements.

Check calls systematically

Heading() has an empty parameter list. Show(Score) supplies one argument. Add(Score, 3) supplies two. Supplying an extra argument, reversing unlike parameter roles or passing text where an INTEGER is required does not match the interface.

Worked example · Call actions and resume the main program

  1. Requirements and starting conditions

    No keyboard input is required. Score starts at 10. Heading displays a title; Show displays its argument; Add increases its first argument by the second.

  2. Cambridge pseudocode
    PROCEDURE Heading()
    OUTPUT "Results"
ENDPROCEDURE
PROCEDURE Show(BYVAL Value : INTEGER)
    OUTPUT Value
ENDPROCEDURE
PROCEDURE Add(BYREF Total : INTEGER, BYVAL Amount : INTEGER)
    Total <- Total + Amount
ENDPROCEDURE
DECLARE Score : INTEGER
Score <- 10
CALL Heading()
CALL Show(Score)
CALL Add(Score, 3)
CALL Show(Score)
  3. Expected result

    The outputs are Results, 10, 13. Add changes Score to 13; the later Show observes that value.

Core explanation · Exam essentials

  • A parameter is declared in the header; an argument is supplied at the call.
  • Match the number, order, types and passing modes, as well as the intended effect.
Common misconception

Matching names do not determine argument binding; position, type and passing mode do.

Check your understanding

In CALL Add(Score, 3), must the caller variable be named Total?

Check your answer

No. Score is matched to formal parameter Total by argument position.

Trace parameter passing

Choose by the intended effect

Use reference passing for data the procedure is intended to update. A literal such as 5 or a temporary expression cannot supply a BYREF variable.

Trace both sides of the call

Trace the local view and caller state separately. The value printed inside a BYVAL procedure does not establish that its caller has changed.

Separate the active local environment from the caller

Each call establishes its own parameters and local variables. A later call does not inherit the earlier BYVAL copy. A local name can match a caller name without sharing storage; sharing here is determined by BYREF, not spelling. This is enough scope information to trace these examples; no call-stack implementation is assumed.

Use two reference parameters for a complete swap

In Swap, Left and Right refer to the two distinct caller variables A and B. Temp must preserve the original left value before Left is overwritten. The BYVAL variant swaps only two local copies: its internal output can look correct while the caller remains unchanged.

Make reference updates intentional

When a procedure header specifies no passing mode, assume BYVAL. A single BYVAL or BYREF marker may cover several parameters passed in that mode; a missing repeated marker does not reset the mode. The examples here write the mode for each parameter to keep the calls unambiguous. A BYREF argument must be an assignable variable of the required type, not a literal or a calculated temporary value.

Worked example · Observe both local and caller values

  1. Requirements and starting conditions

    No keyboard input is needed. Number starts at 5. Follow the caller after each procedure finishes.

  2. Cambridge pseudocode
    PROCEDURE ChangeCopy(BYVAL Value : INTEGER)
    Value <- Value + 2
    OUTPUT Value
ENDPROCEDURE
PROCEDURE ChangeOriginal(BYREF Value : INTEGER)
    Value <- Value + 2
ENDPROCEDURE
DECLARE Number : INTEGER
Number <- 5
CALL ChangeCopy(Number)
OUTPUT Number
CALL ChangeOriginal(Number)
OUTPUT Number
  3. Expected result

    The output sequence is 7, 5, 7; Number is finally 7.

Worked example · Swap two distinct caller variables

  1. Requirements and starting conditions

    Input INTEGER A and B. Pass the two different variables by reference.

  2. Cambridge pseudocode
    PROCEDURE Swap(BYREF Left : INTEGER, BYREF Right : INTEGER)
    DECLARE Temp : INTEGER
    Temp <- Left
    Left <- Right
    Right <- Temp
ENDPROCEDURE
DECLARE A, B : INTEGER
INPUT A
INPUT B
CALL Swap(A, B)
OUTPUT A, B
  3. Expected result

    6, 2 becomes 2, 6. Equal inputs 5, 5 remain 5, 5. -3, 8 becomes 8, -3.

Worked example · Compare the same assignments on local copies

  1. Requirements and starting conditions

    A starts at 6 and B at 2. The procedure displays its changed parameters, then main displays its own variables.

  2. Cambridge pseudocode
    PROCEDURE SwapCopy(BYVAL Left : INTEGER, BYVAL Right : INTEGER)
    DECLARE Temp : INTEGER
    Temp <- Left
    Left <- Right
    Right <- Temp
    OUTPUT Left, Right
ENDPROCEDURE
DECLARE A, B : INTEGER
A <- 6
B <- 2
CALL SwapCopy(A, B)
OUTPUT A, B
  3. Expected result

    The procedure displays 2, 6; main still displays 6, 2. A correct local swap has not changed caller storage.

Core explanation · Exam essentials

  • BYVAL copies a value; BYREF provides access to the caller’s variable.
  • Trace local values and caller state separately; use a temporary value before overwriting either side of a swap.
Optional extension: compare the supporting Java lab

Java passes arguments by value. Reassigning a copied primitive parameter does not change its caller. The lab updates the caller by assigning a returned value; do not describe this as Cambridge BYREF. Follow the related Subprograms practical task for complete Java programs.

Common misconception

A display of 7 inside a BYVAL procedure does not show that the caller changed.

Check your understanding

Can CALL ChangeOriginal(5) supply a BYREF integer parameter?

Check your answer

No. The argument must be a variable whose stored value can be updated.

Question 1 · Command word: Write2 marks

Write a procedure Banner() that outputs "Welcome", and write its call. Explain why a procedure is suitable.

S11.06.A01S11.06.A02S11.06.A03
Answer and marking points

One valid solution to the requested statements

PROCEDURE Banner()
    OUTPUT "Welcome"
ENDPROCEDURE
CALL Banner()
  1. Use PROCEDURE Banner(), OUTPUT "Welcome" and ENDPROCEDURE.
  2. Invoke it with CALL Banner(); the required action is a display rather than a returned expression value.

Common error: Keep the definition and invocation distinct.

Question 2 · Command word: State2 marks

    OUTPUT Value
ENDPROCEDURE

ENDPROCEDURE

Number <- 5
CALL ChangeCopy(Number)
OUTPUT Number
CALL ChangeOriginal(Number)
OUTPUT Number

Answer and marking points
  1. The output sequence is 7, 5, 7.
  2. ChangeCopy modifies only its BYVAL parameter; Number remains 5 until the BYREF call.

Common error: Follow the caller's storage separately from the copied parameter.

Question 3 · Command word: Write2 marks

Write a procedure Increase(BYREF Total : INTEGER, BYVAL Amount : INTEGER) that adds Amount to Total. Write a call that adds 4 to caller variable Score.

S11.06.A01S11.06.A03S11.06.A04S11.06.A05
Answer and marking points

One valid solution to the requested statements

PROCEDURE Increase(BYREF Total : INTEGER, BYVAL Amount : INTEGER)
    Total <- Total + Amount
ENDPROCEDURE
// Score is the caller variable supplied by the question.
CALL Increase(Score, 4)
  1. The procedure body is Total <- Total + Amount, closed with ENDPROCEDURE.
  2. CALL Increase(Score, 4) updates Score through the first parameter while passing the second argument by value.

Common error: The position of the reference argument determines which caller variable changes.

Question 4 · Command word: State3 marks

State the caller values A and B after each assignment in Swap for inputs 6 and 2. Explain the role of Temp and give the caller result for equal inputs 5 and 5.

Use this complete program and the stated inputs.

PROCEDURE Swap(BYREF Left : INTEGER, BYREF Right : INTEGER)
    DECLARE Temp : INTEGER
    Temp <- Left
    Left <- Right
    Right <- Temp
ENDPROCEDURE
DECLARE A, B : INTEGER
INPUT A
INPUT B
CALL Swap(A, B)
OUTPUT A, B
S11.06.A03S11.06.A05
Answer and marking points
  1. After Temp <- Left, A/B remain 6/2; after Left <- Right they are 2/2; after Right <- Temp they are 2/6.
  2. Temp preserves the original left value before its caller variable is overwritten.
  3. Equal inputs 5 and 5 remain 5 and 5; the same complete swap rule still works.

Common error: Without saving the old left value, the two assignments would copy one value over both variables.

Question 5 · Command word: State3 marks

State all outputs of the supplied SwapCopy program. Identify its two formal parameters and explain why main still has the original values after the call.

Use this complete program and the stated inputs.

PROCEDURE SwapCopy(BYVAL Left : INTEGER, BYVAL Right : INTEGER)
    DECLARE Temp : INTEGER
    Temp <- Left
    Left <- Right
    Right <- Temp
    OUTPUT Left, Right
ENDPROCEDURE
DECLARE A, B : INTEGER
A <- 6
B <- 2
CALL SwapCopy(A, B)
OUTPUT A, B
S11.06.A03S11.06.A04S11.06.A05
Answer and marking points
  1. The procedure outputs 2 and 6; main then outputs 6 and 2.
  2. Left and Right are the formal parameters; caller A and B supply their argument values.
  3. BYVAL gives separate copies, so the assignments change the local parameters rather than caller A and B.

Common error: An apparently correct output inside a procedure does not prove that caller storage changed.

Question 1 · Command word: Explain · 3 marks

Explain why BYVAL is suitable for a procedure parameter Limit that is used only to print a warning threshold. State whether a literal argument 50 is permitted and why.

Answer and marking points
  • The procedure needs the threshold's value and is not intended to change the caller's threshold.
  • BYVAL supplies a copy and prevents assignments to the parameter from updating the caller's scalar variable.
  • A literal 50 is permitted for an INTEGER value parameter because it can be evaluated and copied.

Common error: Discuss parameter copying rather than RETURN or OUTPUT syntax.

Question 2 · Command word: Write · 3 marks

Write a procedure Clear(BYREF Count : INTEGER) that sets its parameter to zero. Caller variable Items starts at 12. Write a call and state Items afterwards; explain why a BYVAL version would give a different caller result.

Answer and marking points

One valid solution to the requested statements

PROCEDURE Clear(BYREF Count : INTEGER)
    Count <- 0
ENDPROCEDURE
DECLARE Items : INTEGER
Items <- 12
CALL Clear(Items)
  • PROCEDURE Clear(BYREF Count : INTEGER) contains Count <- 0 and ENDPROCEDURE.
  • CALL Clear(Items) leaves Items as 0.
  • A BYVAL version would change only the copy and leave Items as 12.

Common error: Pass Items as a variable, not the literal 12.

Question 3 · Command word: State · 3 marks

A procedure Move(BYREF Position : INTEGER, BYVAL Distance : INTEGER) executes Position <- Position + Distance. Cursor starts at 7. State the effect of CALL Move(Cursor, 2), identify the argument matched to each parameter, and explain why CALL Move(7, 2) is invalid.

Answer and marking points
  • Cursor supplies Position by reference and 2 supplies Distance by value.
  • Cursor becomes 9.
  • Literal 7 cannot provide caller storage for the BYREF Position parameter.

Common error: A numeric value alone is insufficient for a reference argument.
