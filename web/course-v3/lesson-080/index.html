Program a booking system · Concept 28

Define an action and call it when needed

Observe

One reusable action

  • Action name: Heading
  • Required effect: display "School bookings"
  • No information needs to be supplied to this action.

Look, then discuss

Does writing a procedure definition immediately print its receipt?

The desk wants the same heading before different booking outputs. Define that action once, then decide exactly where to call it.

Recall

Recall a routine call

A supplied routine has an interface the caller follows. A user-defined procedure gives your own action a name and interface. Its definition describes the action; a call performs it.

Explain

Explanation · 1 / 3

Write the procedure definition

Begin PROCEDURE Heading() and finish ENDPROCEDURE. The empty parentheses show that this procedure has no parameters.

Explanation · 2 / 3

Invoke the action with CALL

CALL Heading() transfers execution into the procedure body. At ENDPROCEDURE, execution resumes immediately after the call. Defining a procedure does not invoke it.

Explanation · 3 / 3

Choose a procedure for an action

Printing a heading is an effect. The caller does not need a returned value to use in a calculation, so a procedure is appropriate. Reuse also gives one place to maintain the heading.

PROCEDURE Heading()
    OUTPUT "School bookings"
ENDPROCEDURE
CALL Heading()
OUTPUT "First request"
CALL Heading()
OUTPUT "Second request"

Execute the complete program above.

Work together · 1 / 2

Enter the first call

The first call outputs School bookings, then returns to OUTPUT "First request".

Work together · 2 / 2

Enter the second call

The second call runs the same body again, then returns to OUTPUT "Second request". The definition is shared, but each call is a separate execution.

A named procedure packages an action; CALL determines when that action occurs.

Check

Match arguments to ordered parameters

Observe

One procedure, two calls

CallName suppliedSeats supplied
CALL ShowBooking("Mina", 3)Mina3
CALL ShowBooking("Jo", 2)Jo2

Look, then discuss

How can one procedure display Mina’s three seats and Jo’s two seats?

The action stays the same, but the name and quantity differ. Put those varying values into an interface rather than hard-coding them in the body.

Recall

Recall parameter versus argument

A parameter is an identifier declared in a subprogram header. An argument is an actual value, expression or variable supplied by a call. Position pairs each argument with its parameter.

Explain

Explanation · 1 / 3

Write an ordered, typed interface

ShowBooking has Name : STRING followed by Seats : INTEGER. BYVAL supplies copied values; the next group traces that mechanism in detail.

Explanation · 2 / 3

Match count, order and type

CALL ShowBooking("Mina", 3) supplies two compatible arguments in the declared order. The caller’s variable names need not match the parameter names. CALL ShowBooking(3, "Mina") reverses incompatible types.

Explanation · 3 / 3

Recognise zero, one and several parameters

Heading() needs none; ShowSeats(BYVAL Seats : INTEGER) needs one; ShowBooking needs two. Choose parameters from the information needed by the action, not from every variable in the main program.

PROCEDURE ShowBooking(BYVAL Name : STRING, BYVAL Seats : INTEGER)
    OUTPUT Name, " requested ", Seats, " seats"
ENDPROCEDURE
DECLARE Attendee : STRING
DECLARE Requested : INTEGER
Attendee <- "Mina"
Requested <- 3
CALL ShowBooking(Attendee, Requested)
CALL ShowBooking("Jo", 2)

Work together

Match by position, not spelling

Trace CALL ShowBooking(Attendee, Requested).

Work together · 1 / 2

Pair the arguments

Attendee supplies its value "Mina" to parameter Name. Requested supplies its value 3 to parameter Seats.

Work together · 2 / 2

Explain the body’s view

The body uses the parameter identifiers Name and Seats to display Mina requested 3 seats. It does not require caller variables with those same names.

The interface is the agreement between caller and procedure: name, ordered parameters, types and passing modes.

A parameter belongs to the definition; an argument belongs to a call and is matched by position.

Look, then discuss

If a procedure adds two to its BYVAL parameter, must the caller’s Seats also increase?

Place a caller box labelled Seats beside a separate parameter box labelled Quantity. At the call, copy the value 3 into Quantity, then change only the parameter box.

Recall

Recall value copying

SavedSeats <- Seats copied a scalar value without creating a permanent link. BYVAL likewise supplies a copy to a parameter for that call.

Explain

Explanation · 1 / 3

Create the parameter’s copy

On CALL PreviewExtra(Seats), the argument’s current value is copied into Quantity. The procedure can read it without sharing the caller’s storage. The experiment uses ShowBooking(BYVAL Quantity : INTEGER) to display a supplied quantity and return to a caller output; the worked PreviewExtra below additionally changes the copy to expose the distinction.

Explanation · 2 / 3

Trace assignments to the parameter separately

Quantity <- Quantity + 2 makes the parameter 5. OUTPUT Quantity displays 5 inside the procedure, but Seats remains 3.

Explanation · 3 / 3

Return to the caller’s original state

After ENDPROCEDURE, OUTPUT Seats displays 3. A display action is not a return value and does not assign anything to Seats.

PROCEDURE PreviewExtra(BYVAL Quantity : INTEGER)
    Quantity <- Quantity + 2
    OUTPUT Quantity
ENDPROCEDURE
DECLARE Seats : INTEGER
Seats <- 3
CALL PreviewExtra(Seats)
OUTPUT Seats

A procedure may change a BYVAL parameter locally while leaving the caller’s scalar value unchanged.

Program a booking system · Concept 31

Update caller storage through a reference

Observe

Call AddSeats(Seats, Total)

ParameterModeMeaning
QuantityBYVALCopy the request value 3
RunningTotalBYREFRefer to caller Total, currently 5

Look, then discuss

How can AddSeats change the main program’s running total?

The caller has Total 5 and a new request Seats 3. The procedure needs a copy of the request quantity but access to the original total location.

Recall

Recall an accumulator

Total <- Total + Seats must preserve earlier additions. A local copy of Total would discard each update from the caller’s perspective when the call ends.

Explain

Explanation · 1 / 3

State which parameter may update the caller

BYREF RunningTotal makes assignments to the parameter affect the caller variable supplied for it. BYVAL Quantity copies the read-only input quantity.

Explanation · 2 / 3

Supply a writable variable for the reference argument

CALL AddSeats(Seats, Total) can update Total. A literal such as 5 or a calculated expression such as Total + 1 cannot act as the caller destination for this reference parameter.

Explanation · 3 / 3

Trace the caller change and its consequences

RunningTotal <- RunningTotal + Quantity changes caller Total from 5 to 8. A reference update to a loop control variable can unexpectedly change later increments and termination, so trace the complete calling context.

PROCEDURE AddSeats(BYVAL Quantity : INTEGER, BYREF RunningTotal : INTEGER)
    RunningTotal <- RunningTotal + Quantity
ENDPROCEDURE
DECLARE Seats, Total : INTEGER
Seats <- 3
Total <- 5
CALL AddSeats(Seats, Total)
OUTPUT Total

Work together

Explain an unintended change in the real-paper setting

A caller sends its loop variable Num by reference to a procedure that assigns its square root to the parameter.

Work together · 1 / 2

Follow the shared location

If Num is 2, assigning SQRT(ThisNum) changes the caller’s Num to about 1.4142. The next caller increment makes it about 2.4142 rather than 3.

Work together · 2 / 2

Distinguish correctness from valid syntax

The passing mode and assignment can obey language rules while implementing the wrong algorithm. Passing by value or using a separate local result can avoid the unintended caller change; a compiler does not infer the intended counting sequence.

Choose reference passing deliberately, then trace every subsequent use of the changed caller variable.

1. Trace a parameter that changes its caller

Cambridge 9618/22 · May/June 2023 · 5(a), 5(b) · 4 marks

Selected parts: 5(a) [3]; 5(b) [1].

Hint — reading the question

The code compiles and SQRT is correct. Follow the shared variable through the procedure call and the increment in the calling loop.

Reasoning and model answer — teacher-written

5(a): Num is passed by reference, so ThisNum refers to the caller’s variable. Assigning SQRT(ThisNum) therefore changes Num itself. The loop then increments this modified value instead of the original whole number, disrupting the sequence and its termination.

Passing by value would let the procedure change a local copy while the caller continues with 1, 2, …, 10. Alternatively calculate the root into a separate local variable.

5(b): This is a logic/design error. The language rules have not been broken, so the compiler has no syntax violation to report.

The reference parameter is not an independent copy. Blaming SQRT ignores the supplied assumption that it is correct.

Question 3 · Command word: State3 teacher marks

State the caller values A and B after each assignment in Swap for inputs 6 and 2. Explain the role of Temp and give the caller result for equal inputs 5 and 5.

Use this complete program and the stated inputs.

PROCEDURE Swap(BYREF Left : INTEGER, BYREF Right : INTEGER)
    DECLARE Temp : INTEGER
    Temp <- Left
    Left <- Right
    Right <- Temp
ENDPROCEDURE
DECLARE A, B : INTEGER
INPUT A
INPUT B
CALL Swap(A, B)
OUTPUT A, B
S11.06.A03S11.06.A05
Answer and checking points — teacher-written
  1. After Temp <- Left, A/B remain 6/2; after Left <- Right they are 2/2; after Right <- Temp they are 2/6.
  2. Temp preserves the original left value before its caller variable is overwritten.
  3. Equal inputs 5 and 5 remain 5 and 5; the same complete swap rule still works.

Common error: Without saving the old left value, the two assignments would copy one value over both variables.

  2. Left and Right are the formal parameters; caller A and B supply their argument values.
