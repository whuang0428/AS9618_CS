Finding and correcting program errors

Distinguish syntax, logic and run-time errors, locate their causes and verify corrections.

Before you start

Is IF Mark < 50 always wrong when a mark of 50 should pass?

Check your answer

No. The condition is correct if its true branch assigns Fail and its false branch assigns Pass. The complete branches determine correctness.

Core explanation

Distinguish syntax, logic and run-time faults

A syntax error breaks the grammar of the language, such as an IF statement without its required ENDIF. A translator or syntax checker can report it. A logic error uses accepted syntax but implements the wrong requirement; execution may finish with an incorrect result. A run-time error occurs during execution, for example an attempted division by zero or opening a file that is not available.

Reduce faults and collect evidence

Clear requirements, modular design, meaningful identifiers, consistent indentation and review help avoid faults. Validate input where required, check preconditions before risky operations and use complete constructs. These practices reduce risk but do not prove a program fault-free. Tests, traces and diagnostics provide evidence about particular behaviours.

Common misconception

A translator checks language rules; it does not know every user requirement.

Check your understanding

Can a program with a logic error translate successfully?

Check your answer

Yes. Its statements may be grammatically valid while their meaning does not match the requirement.

Core explanation

Reproduce and narrow the failure

Begin with a specific input, an expected result derived from the requirement and the actual result. Reproduce the mismatch, then narrow the search using translator messages, a manual trace or debugger evidence. A diagnostic line may be where the failure becomes visible rather than where the incorrect value originated.

Trace the boundary case before changing the condition

For a pass rule of at least 50, trace the complete selection with Mark equal to 50. In the supplied faulty program, Mark > 50 evaluates to FALSE and the ELSE branch assigns Fail. This identifies the comparison as the cause. A condition Mark < 50 is not inherently faulty: it would be correct for a Fail branch with a Pass alternative.

Worked example · Locate a boundary fault

  1. Requirement

    Integer marks are from 0 to 100. Every mark of at least 50 must pass. This program deliberately contains a logic error.

  2. Pseudocode
    DECLARE Mark : INTEGER
DECLARE Result : STRING
INPUT Mark
IF Mark > 50 THEN
    Result <- "Pass"
ELSE
    Result <- "Fail"
ENDIF
OUTPUT Result
  3. Expected result

    At 50 it outputs Fail, contradicting the rule. At 49 and 51 its outputs happen to be correct.

Common misconception

Changing < to >= without seeing the branch actions can reverse a correct program.

Check your understanding

Why does testing only 49 and 51 miss this defect?

Check your answer

Those inputs have the expected outputs under both > 50 and >= 50; 50 distinguishes the conditions.

03

Correct the cause, then retest

S12.04.A06

Visual overview

Core explanation

Correct the diagnosed cause and test it
  1. Amend: For a pass rule of at least 50, replace the faulty > comparison with >=.
  2. Repeat the failure: Use Mark 50 and the required expected result to demonstrate the correction.
  3. Regression test: Retest relevant existing behaviours, including neighbouring values, to check that they still work.
Define behaviour for the exceptional case

A run-time fault needs a defined response as well. Guard averaging with Count > 0; for Count = 0, the requirement can specify No data. Test both zero and an ordinary nonzero case instead of merely hiding division by zero.

Worked example · Guard an average calculation

  1. Requirement

    Total is REAL; Count is a non-negative INTEGER. Output the average when Count is positive, otherwise output No data.

  2. Pseudocode
    DECLARE Total : REAL
DECLARE Count : INTEGER
INPUT Total
INPUT Count
IF Count > 0 THEN
    OUTPUT Total / Count
ELSE
    OUTPUT "No data"
ENDIF
  3. Expected result

    Total 24, Count 3 → 8; Total 0, Count 0 → No data.

Evidence after a correction

  1. Failing caseRepeat the exact input that exposed the fault.
  2. Expected resultUse the agreed requirement to decide the correct response.
  3. Regression casesRetest neighbouring values and unaffected paths.

Worked example · Verify the corrected selection

  1. Requirement

    Keep the same pass requirement and inputs; replace only the incorrect comparison.

  2. Pseudocode
    DECLARE Mark : INTEGER
DECLARE Result : STRING
INPUT Mark
IF Mark >= 50 THEN
    Result <- "Pass"
ELSE
    Result <- "Fail"
ENDIF
OUTPUT Result
  3. Expected result

    49 → Fail, 50 → Pass, 51 → Pass.

Common misconception

A new expected result must not be invented simply to match the faulty output.

Check your understanding

Which tests provide both correction evidence and regression evidence here?

Check your answer

50 exercises the repaired equality case; 49 and 51 confirm that the neighbouring fail and pass behaviours remain correct.

Answer and marking points

One valid pseudocode solution

DECLARE Mark : INTEGER
DECLARE Result : STRING
INPUT Mark
IF Mark >= 50 THEN
    Result <- "Pass"
ELSE
    Result <- "Fail"
ENDIF
OUTPUT Result
  1. 50 > 50 is FALSE, so the ELSE branch produces Fail.
  2. The requirement is Pass at 50.
  3. The comparison must be Mark >= 50 for this Pass branch.

Question 1 · Command word: State · 3 marks

A program accepts integer ages from 16 to 25 inclusive using IF Age > 16 AND Age <= 25 THEN OUTPUT "Accept" ELSE OUTPUT "Reject" ENDIF. State one input that exposes the defect, its actual and expected outputs, and the corrected condition.

Answer and marking points
  • Age 16 exposes the defect.
  • The program outputs Reject although Accept is required.
  • Use (Age >= 16) AND (Age <= 25).

Common error: Do not replace AND with OR.

Question 2 · Command word: Explain · 4 marks

A save routine reports a missing-file error only when the user chooses an archived folder. Explain how to locate and correct the cause and verify the correction.

Answer and marking points
  • Reproduce the failure with the archived-folder choice and inspect the path passed to the file operation.
  • Establish whether the path is wrong or the required file is absent; repair that cause or implement the specified unavailable-file response.
  • Repeat the archived-folder case to check the changed path.
  • Rerun saves to an ordinary folder to check existing functionality.

Common error: A run-time message alone does not establish that the translator is faulty.

Question 3 · Command word: Explain · 3 marks

Explain whether the supplied selection has a boundary defect, using Mark 50. It outputs Fail below 50 and Pass otherwise. Predict the effect of changing < to >= while leaving both output statements in place.

Use the stated input assumptions and this program.

DECLARE Mark : INTEGER
INPUT Mark
IF Mark < 50 THEN
    OUTPUT "Fail"
ELSE
    OUTPUT "Pass"
ENDIF
Answer and marking points
  • In the original, 50 < 50 is FALSE, so the ELSE branch correctly outputs Pass.
  • Changing the comparison alone makes the true branch execute at 50 and output Fail.
  • The original does not have this boundary defect; correctness depends on which action each branch takes.

Common error: Do not treat one relational operator as always correct or always faulty.
