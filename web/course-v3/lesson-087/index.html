Develop a booking system · Concept 11

Distinguish three different failures

Observe

Three reports from the booking desk

ReportEvidence
AThe translator rejects an IF with no THEN
BThe program runs but rejects a valid request for 6
CAverage calculation fails when Groups is 0

Look, then discuss

Which problem concerns grammar, which concerns the rule, and which occurs during execution?

The same phrase, “it does not work”, hides three different causes. Identify what was observed before proposing a repair.

Recall

Recall translation and execution

A translator checks whether code follows the language rules. Execution performs its operations on actual values. Correct grammar does not prove that those operations implement the specification.

Explain

Explanation · 1 / 4

Syntax: the statement does not follow the language rules

A missing THEN or mismatched loop ending prevents the construct being read correctly. Use translator feedback or a syntax checker to locate the malformed statement, then inspect the surrounding block. Error reporting may identify where the problem was noticed rather than its original cause.

Explanation · 2 / 4

Logic: valid instructions produce the wrong behaviour

The correct rule accepts Seats 6 when Available is 6. A complete condition using Seats < Available rejects it. The code can translate and finish, but the result disagrees with the requirement. Compare actual output with an independently expected output.

Explanation · 3 / 4

Run time: an invalid operation occurs when executing

Total / Groups with Groups 0 attempts division by zero. An array access outside its declared bounds can also cause a run-time error. Whether the failure occurs depends on the path and values reached during execution.

Explanation · 4 / 4

Reduce the chance of a fault and expose remaining faults

Use clear requirements, small modules, meaningful names and consistent indentation. Review interfaces and boundary cases; validate or guard inputs before unsafe operations. Then use translator checks, code review and purposeful tests. None of these alone proves the complete program correct.

Work together

Match each report to evidence

The required average is total seats divided by the number of bookings; zero bookings must display No data.

Work together · 1 / 2

Classify without guessing

A is syntax because the IF lacks required grammar. B is logic because a valid input produces the wrong decision. C is run time because execution attempts a forbidden division.

Work together · 2 / 2

Choose a useful next check

For A inspect the complete IF/ELSE/ENDIF block. For B trace exactly Seats 6, not only an ordinary value such as 3. For C inspect Groups immediately before division and test the zero-booking path.

A useful error label is supported by the observed cause, not just by a failed test.

Check

Try it yourself · Teacher-written

A program translates successfully and charges 25.00 for three seats costing 12.50 each. What kind of error does this evidence suggest, and what is the expected charge?

Check your reasoning

It suggests a logic error: the completed calculation disagrees with the required multiplication. The expected charge is 3 * 12.50 = 37.50.

Connect

Keep this idea

Syntax concerns language rules; logic concerns the required result; run-time errors arise from invalid executed operations.

An error category narrows the search. A trace shows the exact point where values or decisions diverge.

Look, then discuss

What is the first decision that differs from the intended algorithm?

The ordinary case passes. The exact-fit case fails. Read the quantity, evaluate both comparisons, then inspect which branch executes.

Recall

Recall a trace and a breakpoint

A dry run follows statements manually. A breakpoint pauses an executing program before or at a selected statement; stepping advances execution, and a watch displays selected variable values. Neither operation repairs code automatically.

Explain

Explanation · 1 / 4

Reproduce the failure with a small test

Use Seats 6 and Available 6. Record the exact input, expected Accepted and actual Rejected. Keeping one failing example removes unrelated interactions and allows the same fault to be checked after repair.

Explanation · 2 / 4

Inspect state just before the decision

Seats is 6 and Available is 6, so the input has been read correctly. Evaluate the existing comparisons. Seats >= 1 is TRUE, but Seats < Available is FALSE. This is the first discrepancy with the inclusive specification.

Explanation · 3 / 4

Follow the discrepancy to its consequence

TRUE AND FALSE is FALSE, so the ELSE branch produces Rejected. The output statement is doing what that branch tells it to do. Changing the word Rejected would hide the symptom and break other cases; the upper comparison is the cause.

Explanation · 4 / 4

Apply the same method to other paths

For division by zero, inspect the denominator and the path that allowed 0 to reach the division. For an array failure, compare the current index with the declared bounds before the access. For an unreachable branch, list possible expression results and the alternatives already covered.

Work together

Explain why an OTHERWISE is unreachable

Index is a non-negative integer. CASE OF Index MOD 2 already contains alternatives 0 and 1.

Work together · 1 / 2

Recall what MOD returns

MOD gives the remainder after integer division. Dividing a non-negative integer by 2 can leave only remainder 0 or 1.

Work together · 2 / 2

Check coverage before blaming execution

Both possible values already select named alternatives. No input in the stated domain reaches OTHERWISE. This conclusion comes from the expression’s possible values, not from simply failing to observe the branch in one test.

Locate a cause by comparing the first incorrect state or decision with the requirement.

Develop a booking system · Concept 13

Correct the cause and repeat the right tests

Observe

A proposed patch

  • Change Seats < Available to Seats <= Available.
  • Keep the lower bound Seats >= 1.
  • Re-run the original failure and nearby accepted and rejected cases.

Look, then discuss

Does passing Seats 6 establish that the correction is complete?

A patch that accepts every quantity would pass that one test. Choose additional inputs that distinguish a genuine repair from this new fault.

Recall

Recall a boundary and regression

A boundary is where a rule changes its decision. A regression is a previously correct required behaviour broken by a change. Repeating relevant old tests helps detect it.

Explain

Explanation · 1 / 5

Amend the smallest responsible operation

Use <= for the inclusive upper limit, leaving the correct lower bound and output branches intact. For a syntax error, restore the missing or matching keyword at the correct block position. Do not move a statement merely to silence an error message without understanding its role.

Explanation · 2 / 5

Guard an unsafe calculation before it happens

For a zero count, test the denominator before dividing. Putting the guard after the division is too late.

DECLARE Total : REAL
DECLARE Groups : INTEGER
INPUT Total
INPUT Groups
IF Groups > 0 THEN
    OUTPUT Total / Groups
ELSE
    OUTPUT "No data"
ENDIF

Explanation · 3 / 5

Repeat the failing case and surrounding cases

For the range repair, 6 must now pass. Check 5 remains accepted, 7 remains rejected, 1 remains accepted and 0 remains rejected. Record the new version and results while retaining the original failure record.

Explanation · 4 / 5

Read the supplied string and array interfaces

In the next paper, & joins string or character operands. Index is INTEGER, so convert it with NUM_TO_STR(Index) before concatenation, or use comma-separated OUTPUT items. Its supplied TO_UPPER and TO_LOWER routines accept STRING arguments; follow that insert rather than assuming another routine interface. An array declared from 1 to 200 has no element 0.

Explanation · 5 / 5

Recheck the full path affected by the change

If a repair changes loop initialisation, trace the first and last valid array positions. Changing an initial index from 0 to 1 may skip the first element when the loop also increments before access. Understand the existing flow before applying a plausible-looking correction.

Question 2 · Command word: Describe3 teacher marks

Describe the execution of the supplied faulty program with Mark 50. State the actual and required output, identify the faulty comparison and write a correction.

Use the stated input assumptions and this program.

DECLARE Mark : INTEGER
DECLARE Result : STRING
INPUT Mark
IF Mark > 50 THEN
    Result <- "Pass"
ELSE
    Result <- "Fail"
ENDIF
OUTPUT Result
S12.04.A03S12.04.A05S12.04.A06
Answer and checking points — teacher-written

One valid pseudocode solution

DECLARE Mark : INTEGER
DECLARE Result : STRING
INPUT Mark
IF Mark >= 50 THEN
    Result <- "Pass"
ELSE
    Result <- "Fail"
ENDIF
OUTPUT Result
  1. 50 > 50 is FALSE, so the ELSE branch produces Fail.
  2. The requirement is Pass at 50.
  3. The comparison must be Mark >= 50 for this Pass branch.

Common error: Both the condition and branch actions are supplied; use them.

Question 4 · Command word: Locate3 teacher marks

Locate and identify the fault in this supplied program, state the exact correction, and explain what can and cannot be concluded when the construct is repaired. The requirement is Pass for an INTEGER mark of at least 50, otherwise Fail.

Use the complete program and the stated input assumptions.

DECLARE Mark : INTEGER
INPUT Mark
IF Mark >= 50 THEN
    OUTPUT "Pass"
ELSE
    OUTPUT "Fail"
S12.04.A02S12.04.A05S12.04.A06
Answer and checking points — teacher-written

One complete Cambridge pseudocode solution

DECLARE Mark : INTEGER
INPUT Mark
IF Mark >= 50 THEN
    OUTPUT "Pass"
ELSE
    OUTPUT "Fail"
ENDIF
  1. The IF is missing its closing ENDIF, so this is a syntax error.
  2. Insert ENDIF after the ELSE branch’s OUTPUT "Fail".
  3. The closure repairs the construct, but behaviour still needs checking against the rule, for example 49 → Fail and 50 → Pass.

Common error: A diagnostic at the end of the text need not mean the final OUTPUT is itself malformed.
