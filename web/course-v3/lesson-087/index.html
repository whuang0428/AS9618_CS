Finding and correcting program errors

Distinguish syntax, logic and run-time errors, locate their causes and verify corrections.

Which evidence identifies the cause of a failure rather than just its symptom?

Before you start

Is IF Mark < 50 always wrong when a mark of 50 should pass?

Check your answer

No. The condition is correct if its true branch assigns Fail and its false branch assigns Pass. The complete branches determine correctness.

Connect prevention to the fault it helps expose

Use clear requirements to avoid implementing the wrong rule; use modular responsibilities and meaningful names to make mistakes easier to locate; indent nested constructs so missing boundaries are visible; check required preconditions before risky operations. These practices reduce the likelihood of faults but do not prove correctness.

Read the whole syntax-error context

The incomplete program below intends to display Pass for integer marks at least 50. Its IF has both branches but lacks ENDIF. A checker may complain when the program ends because that is where it discovers the unclosed construct. The cause is the missing closure, not the final valid OUTPUT statement. Cambridge pseudocode is being inspected here; no particular compiler diagnostic is assumed.

Worked example · Inspect an incomplete IF construct

  1. Requirements and initial conditions

    This intentionally malformed program is meant to display Pass for integer marks at least 50 and Fail otherwise. Locate the missing closure before attempting to trace it as a complete program.

  2. Cambridge pseudocode
    DECLARE Mark : INTEGER
INPUT Mark
IF Mark >= 50 THEN
    OUTPUT "Pass"
ELSE
    OUTPUT "Fail"
  3. Expected result and checks

    There is no valid complete-program result to claim. The IF remains open at the end of the supplied text.

Core explanation · Exam essentials

  • Distinguish a grammar violation, an incorrect rule and an execution failure.
  • Use prevention, review and tests together; successful translation cannot establish the required result.
Common misconception

A translator checks language rules; it does not know every user requirement.

Check your understanding

Can a program with a logic error translate successfully?

Check your answer

Yes. Its statements may be grammatically valid while their meaning does not match the requirement.

Separate failure evidence from diagnosis

Begin with a reproducible input and an independently expected result. Record the actual result, then follow the values and decisions that produced it. The statement where a symptom appears may be correct but use a value computed incorrectly earlier. Locating the cause means explaining that chain.

Use a discriminating input

The supplied Mark > 50 program outputs Fail for 50 because the comparison is FALSE and the ELSE branch assigns Fail. The requirement says at least 50 passes, so this is a logic error in that comparison. Inputs 49 and 51 cannot expose it: both the wrong and correct comparisons give the required outputs there.

Avoid correcting a symptom blindly

A condition Mark < 50 can be completely correct when its true branch outputs Fail and its alternative outputs Pass. Inspect branch actions before changing an operator. For a missing-file failure, reproduce the chosen path and inspect the actual file identifier before assuming the error message identifies the originating mistake.

Worked example · Locate a boundary fault

  1. Requirement

    Integer marks are from 0 to 100. Every mark of at least 50 must pass. This program deliberately contains a logic error.

  2. Pseudocode
    DECLARE Mark : INTEGER
DECLARE Result : STRING
INPUT Mark
IF Mark > 50 THEN
    Result <- "Pass"
ELSE
    Result <- "Fail"
ENDIF
OUTPUT Result
  3. Expected result

    At 50 it outputs Fail, contradicting the rule. At 49 and 51 its outputs happen to be correct.

Core explanation · Exam essentials

  • Use a specific input, expected result and actual path to locate the cause.
  • Inspect the whole condition and both branch actions before changing an operator.
Common misconception

Changing < to >= without seeing the branch actions can reverse a correct program.

Check your understanding

Why does testing only 49 and 51 miss this defect?

Check your answer

Those inputs have the expected outputs under both > 50 and >= 50; 50 distinguishes the conditions.

03

Correct the cause, then retest

S12.04.A06

Visual overview

Correct and collect new evidence

  1. Fix the diagnosed cause: Change the Pass condition from > 50 to >= 50, keeping the branch meanings.
  2. Retest the failure: Repeat Mark 50; it must now produce Pass.
  3. Check related behaviour: Run 49 and 51 to confirm the neighbouring outcomes still agree with the original requirement.
  4. Keep the evidence: Record the corrected version and results alongside the earlier failure rather than changing the expected result to fit the implementation.

Make the correction follow the contract

For syntax, closing the IF at its correct boundary repairs the malformed construct. For an average, Count > 0 guards the division and the zero-count alternative supplies the specified No data response. A zero denominator must not be “fixed” by silently changing Count to 1 or inventing an average of zero.

Explain the purpose of each repeat

Retesting asks whether the identified failure has been repaired. Regression testing asks whether a change has damaged previously correct behaviour that should remain. Some cases contribute to both kinds of evidence. Tests provide evidence for the cases examined; avoid treating a few passes as proof of every possible execution.

Evidence after a correction

  1. Failing caseRepeat the exact input that exposed the fault.
  2. Expected resultUse the agreed requirement to decide the correct response.
  3. Regression casesRetest neighbouring values and unaffected paths.

Worked example · Verify the corrected selection

  1. Requirement

    Keep the same pass requirement and inputs; replace only the incorrect comparison.

  2. Pseudocode
    DECLARE Mark : INTEGER
DECLARE Result : STRING
INPUT Mark
IF Mark >= 50 THEN
    Result <- "Pass"
ELSE
    Result <- "Fail"
ENDIF
OUTPUT Result
  3. Expected result

    49 → Fail, 50 → Pass, 51 → Pass.

Worked example · Guard an average calculation

  1. Requirement

    Total is REAL; Count is a non-negative INTEGER. Output the average when Count is positive, otherwise output No data.

  2. Pseudocode
    DECLARE Total : REAL
DECLARE Count : INTEGER
INPUT Total
INPUT Count
IF Count > 0 THEN
    OUTPUT Total / Count
ELSE
    OUTPUT "No data"
ENDIF
  3. Expected result

    Total 24, Count 3 → 8; Total 0, Count 0 → No data.

Worked example · Close the IF at the correct boundary

  1. Requirements and initial conditions

    Keep the same fixed-50 rule. ENDIF follows the two alternatives. Inputs are INTEGER marks from 0 to 100.

  2. Cambridge pseudocode
    DECLARE Mark : INTEGER
INPUT Mark
IF Mark >= 50 THEN
    OUTPUT "Pass"
ELSE
    OUTPUT "Fail"
ENDIF
  3. Expected result and checks

    49 outputs Fail; 50 outputs Pass. The structure now has a matching closure.

Core explanation · Exam essentials

  • Correct the cause and rerun its failing case.
  • Check relevant unchanged behaviour and define required exceptional-case results.
Common misconception

A new expected result must not be invented simply to match the faulty output.

Check your understanding

Which tests provide both correction evidence and regression evidence here?

Check your answer

50 exercises the repaired equality case; 49 and 51 confirm that the neighbouring fail and pass behaviours remain correct.

IF Mark >= 50 THEN

  2. The requirement is Pass at 50.

Question 4 · Command word: Locate3 teacher marks

Locate and identify the fault in this supplied program, state the exact correction, and explain what can and cannot be concluded when the construct is repaired. The requirement is Pass for an INTEGER mark of at least 50, otherwise Fail.

INPUT Mark
IF Mark >= 50 THEN
    OUTPUT "Pass"
ELSE
    OUTPUT "Fail"
S12.04.A02S12.04.A05S12.04.A06
Answer and checking points — teacher-written

One complete Cambridge pseudocode solution

DECLARE Mark : INTEGER
INPUT Mark
IF Mark >= 50 THEN
    OUTPUT "Pass"
ELSE
    OUTPUT "Fail"
ENDIF
  1. The IF is missing its closing ENDIF, so this is a syntax error.
  2. Insert ENDIF after the ELSE branch’s OUTPUT "Fail".
  3. The closure repairs the construct, but behaviour still needs checking against the rule, for example 49 → Fail and 50 → Pass.

Common error: A diagnostic at the end of the text need not mean the final OUTPUT is itself malformed.

Reading the question — teacher guidance

Find the requested two syntax errors and one other error in the actual code. Then explain why the redundant branch cannot be selected.

Solution / model answer — teacher-written
5(a)(i): errorCorrection
NEXT Index closes a WHILE loopUse ENDWHILE.
The final & concatenates an INTEGER with stringsConvert Index with NUM_TO_STR(Index), or use OUTPUT arguments separated by commas.
INPUT Data[Index] accesses index 0Remove this input statement: Process initialises the array from Label, and its valid indices are 1 to 200.

5(a)(ii): The OTHERWISE statement is unnecessary because Index MOD 2 can only produce 0 or 1 for these indices, and both cases are already present.

5(b): A run-time error.

Official mark scheme
Why this earns marks — teacher explanation

Part (a)(i) gives one mark per identified error. The original scheme categorises the concatenation problem as syntax; retain that classification for this paper. Part (a)(ii) gives one for the statement and one for the reason. Part (b) is one mark.

Common mistakes — teacher analysis

Changing Index to 1 at initialisation without adjusting the later increment skips Data[1]. Removing the inappropriate input preserves the intended loop from indices 1 to 200.
