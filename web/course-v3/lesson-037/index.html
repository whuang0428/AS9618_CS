Validation, verification, parity and checksums

Apply validation rules, compare entered data with its source, and calculate checks for transmitted data.

Does the value satisfy a rule, agree with its source, or reveal a transmission error?

Before you start

Both source and entered age say 200; the allowed range is 0 to 120. Which process rejects it?

Check your answer

Validation rejects the age. A comparison with that source would find agreement.

Teaching checkpoints
  • Stage 1 · Input rules: distinguish validation from source verification, then apply bounds, patterns, presence and lookup checks to the complete form.
  • Stage 2 · Identifier and entry checks: generate and test a check digit, including zero and a missed error; resolve double-entry differences against the source.
  • Stage 3 · Transfer checks: construct byte and block parity, calculate both checksum values, and finish rejection, correction or retransmission before evaluating limitations.

Validation and verification answer different questions

S6.07.A01S6.07.A09

Visual overview

A source mark of 46 is entered as 64

CheckTestResult
ValidationIs the mark between 0 and 75?64 passes
VerificationDoes the entry match the source value 46?Mismatch detected

Swipe horizontally to compare every column →

Choose the question the check must answer

Validation tests whether input satisfies stated rules and is reasonable for its purpose. Verification checks whether information has been entered, copied or transferred accurately relative to its source. They support integrity by detecting different kinds of error. First ask whether the task needs rule compliance, faithful copying, or both.

Separate acceptable, copied correctly and true

A source mark of 46 entered as 64 can pass the range 0–75 while failing comparison with the source. A source age of 200 copied correctly can pass that source comparison but fail a permitted range of 0–120. If a wrong source says 12 and both copies say 12, neither a matching copy nor a reasonable age proves the person is actually 12.

Use independent checks in a data-entry process

StageTestIf it fails
Input rulesDoes each field satisfy the specified bounds, pattern, required entry and lookup rules?Flag the relevant field and request correction.
Source verificationDoes the entered information agree with the original form?Investigate the difference against the source, correct and check again.

Follow the three learning stages

The next units first choose and apply individual validation methods, then combine them on one form. The second stage adds a check digit and source comparisons. The final stage follows checking information from sender to receiver. This is a progression from rule decisions to complete checking processes, not a requirement to implement a program here.

Worked example · Validate and verify a submitted mark

  1. Conditions

    The source form says 46; marks must be integers from 0 to 75 inclusive. An integer 64 is submitted.

  2. Validation

    64 satisfies the stated range, so that rule passes. It does not compare 64 with 46.

  3. Verification

    A visual comparison with the form finds the mismatch. Do not accept the entry as a faithful copy.

  4. Correction and result

    Re-enter 46, apply the range and source comparison again, and accept the corrected record once both pass.

  5. Boundary of the claim

    These results establish compliance with the checks, not an independent proof that the source form records the true examination performance.

Core explanation · Exam essentials

  • Validation checks stated acceptability rules; verification checks faithful entry or transfer relative to a source.
  • An acceptable wrong value or two matching wrong copies can pass a check. Neither proves the original fact true.
Common misconception

Passing a rule does not prove agreement with the source.

Check your understanding

Both source and entered age say 200; the allowed range is 0 to 120. Which process rejects it?

Check your answer

Validation rejects the age. A comparison with that source would find agreement.

Range and limit checks

S6.07.A02S6.07.A07

Read both bounds

A range check compares a value with both ends of an allowed interval. For integer marks with 0 <= Mark <= 75, both 0 and 75 are allowed. The two conditions must both hold. Replacing the upper <= with < excludes 75, so the exact comparison matters.

Distinguish the rule from supplied conditions

A limit check uses one upper or lower bound, such as UploadSize <= 10 MiB or Temperature >= -20. A lower limit alone does not impose an unstated upper limit. When a problem already supplies non-negative file sizes, that is an input condition; do not pretend the upper-limit comparison itself checked non-negativity.

Choose a discriminating test

Use values just inside, at and just outside the relevant boundary to expose a wrong comparison. For a whole-number mark, 74, 75 and 76 distinguish an inclusive maximum of 75 from a strict maximum. For continuous or measured data, choose test values according to the stated precision rather than always adding one.

Worked example · Test an inclusive temperature range

  1. Rule

    Accept temperatures from -20 to 50 degrees Celsius inclusive.

  2. Endpoints

    -20 and 50 pass because equality is included.

  3. Outside

    -21 and 51 fail because they lie beyond a bound.

  4. Single-bound alternative

    A minimum-only limit Temperature >= -20 would accept 51; it does not impose the upper bound.

Core explanation · Exam essentials

  • A range specifies lower and upper bounds; a limit specifies one bound.
  • Follow the stated inclusive or strict comparisons and test the endpoints as well as values just outside.
Common misconception

Do not describe a one-sided limit as if it also enforced an unstated second limit.

Check your understanding

A size is already known to be non-negative. Does Size <= 10 by itself impose a lower bound, and does it accept 10?

Check your answer

It imposes only an upper bound. It accepts 10 because equality is included; non-negativity comes from the stated input condition.

Format and length checks

S6.07.A03S6.07.A04

Visual overview

Code rule: two uppercase letters, then four digits

AB0123PassPass

AB123FailFail

Swipe horizontally to compare every column →

Count characters, then inspect positions

A length check tests the number of characters, such as exactly six or at most twenty. A format check tests the required arrangement, such as two uppercase letters followed by four digits. A format may imply a length, but the tests still ask distinguishable questions: 123456 has six characters yet fails the specified letter-and-digit pattern.

Keep the representation needed by the rule

Read the full pattern. AB0123 fits two uppercase letters and four digits, while A10123 has a digit where the second uppercase letter is required. AB123 has only five characters and too few trailing digits. A stored identifier is often a string: converting 001234 to a number would lose its leading zeros and change the representation being checked.

Identify what remains unchecked

Do not infer factual meaning from appearance. A correctly formatted date string may still describe an impossible date, and a correctly shaped customer code may not occur in the customer file. A format rule needs to be stated precisely; use an additional appropriate check for conditions the pattern does not establish.

Core explanation · Exam essentials

  • Length counts characters; format checks their required arrangement.
  • Preserve leading zeros in string identifiers and apply each stated check separately.
Common misconception

The correct length alone does not establish the correct character pattern.

Check your understanding

A six-character code must contain two uppercase letters and four digits. AB0007 passes. Does this prove the booking exists?

Check your answer

No. It passes length and format, but existence requires comparison with the specified stored booking data. The zeros remain part of the code.

State the required field and lookup

A presence check rejects an absent required entry. It does not test whether a supplied identifier corresponds to a real record. An existence check searches a specified stored lookup or file for the supplied value. The correct source matters: finding a customer code in an unrelated product file would not establish that the customer exists.

Explain the order of checking

In the simple examples, Blank means no characters were entered. If a real form also treats spaces-only input as empty, that must be a stated rule. Once a required field fails presence, the form can flag that error before trying its format or lookup. A skipped lookup is not a successful existence check.

Combine checks without changing their meaning

All required checks must pass for this form to be accepted under its input rules. Report the failed field and request correction rather than silently replacing an unknown customer or inventing an age. Leading zeros in the two codes are characters and must remain. Passing every rule still does not prove agreement with an original form.

05

Calculate and check an identifier's check digit

S6.07.A08

Visual overview

Distinguish generation from checking

A check digit is a digit calculated from the other digits in an identifier and stored with them. The system repeats the stated calculation when the full code is entered or scanned. It can compare the expected final digit with the supplied final digit or apply the equivalent rule to their combined total.

Use a complete stated algorithm

For this example only, use four data digits with weights 3, 1, 3, 1. Multiply corresponding digits and weights, add the products, then choose a digit from 0 to 9 that makes the total a multiple of 10. If the total already is a multiple of 10, choose 0; do not choose 10, which is not one digit. Different schemes use different weights and rules.

Generate three check digits under the same rule

Data digitsProductsWeighted totalCheck digitFull code
472612 + 7 + 6 + 631947269
24626 + 4 + 18 + 230024620
427612 + 2 + 21 + 641942769

Swipe horizontally to compare every column →

Explain a passing wrong value

47269 and 42769 both satisfy this rule even though their data digits differ. The totals 31 and 41 both need a final 9. This is a concrete undetected transposition, not proof that check digits are useless. They detect many errors cheaply, but cannot establish that an accepted identifier is the one intended or that its record exists.

Worked example · Check the scanned identifier and resolve an error

  1. Received full code

    47268 contains data digits 4726 and supplied check digit 8.

  2. Calculate

    4 × 3 + 7 × 1 + 2 × 3 + 6 × 1 = 31. The expected check digit is 9.

  3. Compare

    8 differs from 9; equivalently, 31 + 8 = 39 is not a multiple of 10. Reject or request re-entry.

  4. Consult the source

    The original label confirms 47269. Re-enter that full code and check again: 31 + 9 = 40, so the rule passes.

  5. Do not guess a repair

    A mismatch does not establish that only the last digit is wrong. Consult the source rather than automatically changing 8 to 9.

Core explanation · Exam essentials

  • Derive a check digit using the specified rule; on entry recalculate and compare with the supplied digit.
  • A mismatch detects an error but does not identify the intended identifier. Some wrong identifiers still pass.
Common misconception

The final check digit is not another data digit to which the four supplied weights are applied.

Check your understanding

If the weighted total is already 40, what check digit is needed?

Check your answer

0: the total already is a multiple of 10.

Make the comparison reference explicit

Visual verification means that a person compares the entered information with the original source. Looking at the entry alone and deciding it seems plausible is not that comparison. The original form, document or other stated source must be available, and the person must check the relevant characters or values.

Complete the mismatch-resolution process

For double entry, enter the value independently twice and let the computer compare the copies. The second entry should not simply copy the first displayed entry. A mismatch identifies disagreement but does not say which entry is right; consult the original source, correct and compare again.

Explain both agreement and disagreement

If source 640 is entered as 604 twice, both copies agree despite the repeated error. If the source itself is wrong, perfect copying preserves its error. These limitations explain why agreement is evidence from a particular check and why verification differs from validation of permitted values.

Worked example · Resolve a double-entry disagreement completely

  1. Conditions

    The original form reads 8371. Two independent entries are 8371 and 8731.

  2. Computer comparison

    The strings differ, so flag the disagreement; do not average them or automatically accept the first.

  3. Source check

    Compare both with the original 8371. Correct the second entry to 8371.

  4. Recheck and final state

    Both entries now read 8371 and match the source. Accept 8371 as the verified copy under these checks.

  5. Different failure

    If both entries had been 8731, double entry alone would pass; a visual source comparison would still detect the difference.

Core explanation · Exam essentials

  • A visual check compares the entry with its source; double entry compares two independently entered copies.
  • Resolve differences against the source and recheck. Identical copies can contain the same mistake.
Common misconception

Double entry compares copies; it does not use a numeric average of them.

Check your understanding

Source 640 is entered as 604 twice. Does double entry detect the mistake?

Check your answer

No. Both entered copies agree, so an independent source comparison is still useful.

Use parity on a byte

S6.08.A03S6.08.A05

Visual overview

Fix the convention and the bit positions

The sender and receiver agree a parity convention. Count the 1 bits in the data, then choose a parity bit so the whole transmitted group has an even or odd total as required. The example uses seven data bits followed by one parity bit to make an eight-bit group. Other questions may specify a different data width or bit position; follow the supplied arrangement.

Build both conventions for the same seven data bits

DataData 1sConventionParity bitComplete groupTotal 1s
10110014Even0101100104
10110014Odd1101100115

Swipe horizontally to compare every column →

Trace the receiving decision

The receiver checks the whole received group, including its received parity bit. If 10110010 becomes 10100010, the count falls from four to three and even parity fails. The changed bit could instead have been the parity bit itself; this check alone cannot identify which position changed. Reject or request retransmission rather than guessing a correction.

Derive the limitation from the count

Each bit flip changes the count of 1s by one in either direction. An odd number of flips changes whether the count is odd or even; an even number preserves it. Flipping the first two bits gives 01110010, still with four 1s. Therefore a passed parity check means no parity error was detected, not that the data is necessarily unchanged.

Worked example · A parity failure followed by successful retransmission

  1. Send

    Seven data bits 1011001 with even parity produce 10110010.

  2. Receive

    The first received group is 10100010. Counting all its bits gives three 1s, so reject it.

  3. Request again

    The protocol in this example requests retransmission; parity by itself does not perform this communication.

  4. Recheck

    The resent group arrives as 10110010. Four 1s satisfy even parity, so no parity error is detected and this example accepts the group.

  5. Limit

    The independent two-flip variant 01110010 also passes. Passing cannot prove every transmission was error-free.

Core explanation · Exam essentials

  • Choose the parity bit to make the total count of 1 bits, including that bit, meet the agreed odd/even convention.
  • Byte parity detects an odd number of bit flips; an even number can pass. It cannot locate the erroneous bit.
Common misconception

Passing parity means no parity error was detected; it is not proof of an error-free transfer.

Check your understanding

The parity bit alone flips in an even-parity group. Is an error detected, and can the check locate that bit?

Check your answer

Yes: one flip changes parity. No: a failed byte-parity check cannot distinguish that position from another single flipped bit.

Two-dimensional parity adds checking information in both directions. Start with the three seven-bit data rows below and use even parity throughout. Append one row-parity bit to each row. Explain how a column value is obtained

For data column 4, the sender's rows contain 1, 0, 0: one 1, so the final parity row needs 1 in that column. For column 1 they contain 1, 0, 1: two 1s, so the final bit is 0. Repeating across all eight columns gives 00010100. In this construction the lower-right bit completes the parity information consistently; it is not another original data bit.

State the correction condition

After exactly one bit changes, its row and column each have the wrong parity. Their intersection locates the bit; flip it and check the complete block again. This reasoning depends on the one-bit assumption. Multiple errors can produce several failed lines, ambiguous intersections or no parity failure. Do not promise correction from every pattern.

Optional extension · Four corner flips can be invisible

Flip the four corners of any rectangle in a correct block. Each affected row has two flips and each affected column has two flips, so their parity remains unchanged. The data can therefore change without a failed check. This explains a limitation; identifying every possible error pattern is not required.

Common misconception

Check your understanding

Check your answer

Flip the bit at their intersection, row 2 column 5, then recheck all rows and columns. Without the stated single-bit assumption, those indications alone do not guarantee that correction.

09

Calculate and compare a checksum

S6.08.A04S6.08.A05

Visual overview

Keep the two compared values distinct

A checksum is a value calculated from a block using an agreed algorithm. The sender transmits the data and its checksum. The receiver repeats that algorithm on the received data and compares the newly calculated value with the received checksum. For this example, the checksum is not included as another data byte in the receiver's sum.

Explain the remainder calculation

The stated rule adds the data bytes and keeps the remainder after division by 256. This is called sum modulo 256. For 84, 121 and 77, the sum is 282. Since 282 = 1 × 256 + 26, the remainder and eight-bit checksum value are 26, not the quotient 1 and not 282. Other checksum algorithms use different operations; do not substitute this rule when a question supplies another.

Continue from mismatch to a decision

If the received data is 84, 120, 77, its sum is 281 and its remainder is 25. Comparing 25 with the received 26 detects an error somewhere in the data/checking information. A mismatch does not locate the incorrect byte. The system can reject or request retransmission according to its protocol.

Compare purpose and limits

Changing the data to 85, 120, 77 preserves the sum 282 and checksum 26. The two changes cancel, so this algorithm misses them. It is not a digital signature and supplies no authenticated origin: an attacker who can replace both an unprotected block and its checksum can recompute the check. A check digit instead accompanies an identifier under its stated validation rule.

Worked example · Complete the sender–receiver exchange

  1. Send

    Original data 84,121,77 gives 282 modulo 256 = 26. Send those three data bytes and checksum 26.

  2. First arrival

    Receive data 84,120,77 and checksum 26. Recompute 281 modulo 256 = 25; 25 differs from 26.

  3. Decision

    Reject this block and, under this example’s protocol, request retransmission. Do not guess which byte to alter.

  4. Second arrival

    Receive 84,121,77 and checksum 26. Recompute 26; the values agree, so accept under this check.

  5. Unchanged check value is not proof

    The separate variant 85,120,77 also gives 26. State that no error was detected, rather than claiming a matching checksum proves truth or authenticity.

Core explanation · Exam essentials

  • Calculate a checksum from the data, send it with the block, recalculate from the received data and compare.
  • Use the specified algorithm. A mismatch detects an error; a match does not prove that the data is unchanged.
Common misconception

A checksum is used on a transferred block; a check digit is attached to an identifier under a validation rule.

Check your understanding

The received and recomputed checksums differ. What should the receiver conclude?

Check your answer

An error was detected; do not accept the block as verified. Reject it or request retransmission.

  1. The data has four 1 bits, so the even-parity bit is 0.
  2. The odd-parity bit is 1, giving five 1 bits in total.
  3. Two flips change the count by an even amount, preserving its odd/even parity.

Common error: Count the parity bit in the total.

Question 8 · Command word: Calculate5 teacher marks

Calculate the checking bits to complete an even-parity block from these three seven-bit data rows: 1110000, 0101010, 0011001. Append one parity bit at the right of each row, then calculate the transmitted column-parity row. Only the second complete row changes during transmission to 01011101. Identify the failed row and column, correct the bit under a single-bit error assumption, and state the final complete block.

S6.08.A03
Answer and checking points — teacher-written
  1. All three data rows have three 1s, so each row-parity bit is 1. The complete rows are 11100001, 01010101 and 00110011.
  2. The column-parity row is 10000111; it is sent with the complete data rows.
  3. Only row 2 and column 5 fail even parity, locating the single changed bit at their intersection.
  4. Change that bit from 1 to 0. The final block is 11100001 / 01010101 / 00110011 / 10000111.
  5. All final row counts are 4; column counts are 2,2,2,2,0,2,2,4. All are even, confirming the recheck.

Common error: Calculate from the data bits first. Do not silently generate replacement column parity from the corrupted block.

Question 9 · Command word: Calculate3 teacher marks

Calculate a checksum for data bytes 200,45,30 using sum modulo 256. If the receiver gets 200,46,30 with the original checksum, calculate its check value and state the decision.

S6.08.A04
Answer and checking points — teacher-written
  1. The original sum is 275, giving checksum 19.
  2. The received sum is 276, giving checksum 20.
  3. 20 differs from transmitted 19, so reject the block or request retransmission.

Common error: Apply the same modulo rule at both ends.

Question 10 · Command word: Explain2 teacher marks

Explain why both identical double-entry values and matching transfer checksums can still occur when the information is wrong.

S6.08.A05
Answer and checking points — teacher-written
  1. The operator can repeat the same incorrect entry, producing identical copies.
  2. Different data blocks can produce the same checksum, so a changed block may escape detection.

Common error: Agreement is evidence from a particular check, not proof of truth.

  1. CustomerID uses presence, format and existence checks. C99 passes presence and format but fails existence in the supplied customer set.
  2. 0042 passes the four-character length and digit-format requirements; preserve the leading zeros.

2. Describe two transmission-verification methods

Cambridge 9618/13 · May/June 2024 · 7(f)(i) · 4 marks

Selected parts: 7(f)(i) [4].

Reading the question — teacher guidance

The robot-to-computer link transfers data. Give two suitable methods and pair each name with its own detection process.

Solution / model answer — teacher-written
MethodDescription
Parity byte checkThe sender includes a parity bit so the byte has the agreed odd or even number of 1s. The receiver checks that parity; a mismatch indicates an error.
ChecksumThe sender calculates a value from the data and sends it with the data. The receiver repeats the same calculation and compares the result with the received checksum; a mismatch indicates an error.
Official mark scheme
Why this earns marks — teacher explanation

Each method-and-description pair can earn two marks, four in total. The official scheme also describes parity block checking as another valid method.

Common mistakes — teacher analysis

A matching checksum or parity does not guarantee that no error occurred: some changes preserve the check value. Encryption is a security mechanism, not a replacement for either requested verification description.

04

Lesson review

Summary

Validation

Test bounds, pattern, length, presence, lookup membership and a stated check-digit rule.

Entry verification

Compare with the source or compare two independent entries.

Byte and block parity

Count all 1 bits; row and column failures can locate one flipped bit.

Checksum

Calculate, send, recalculate and compare using the same algorithm.

Limits

Valid values can be false; agreeing checks can miss some errors.
