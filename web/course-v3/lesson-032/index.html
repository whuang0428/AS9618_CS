System software · Concept 01

Use suggestions and syntax feedback while entering code

Observe

DECLARE Quantity : INTEGER
DECLARE UnitPrice : INTEGER
DECLARE Delivery : INTEGER
DECLARE Cost : INTEGER
Quantity <- 3
UnitPrice <- 4
Delivery <- 2
Cost <- Quantity * Delivery
OUTPUT Cost

Start with a question

An editor suggests Delivery where UnitPrice was intended. Why might the resulting program still have valid syntax?

Quantity is 3, UnitPrice is 4 and Delivery is 2. The requirement is Cost = Quantity × UnitPrice. Both UnitPrice and Delivery are declared names, so a suggestion can be valid at the cursor yet wrong for the calculation.

Recall

Use what you already know

An integrated development environment

An IDE brings an editor and development tools into one environment. It may invoke a compiler or interpreter, show diagnostics and supply a debugger. It does not replace the distinction between compilation and interpretation; its selected tools determine that route.

Explain

Explanation · 1 / 4

Get suggestions from the current context

Context-sensitive prompts use the language and current editing position to suggest suitable keywords, names, methods or parameters. At a library call, a prompt may show the routine’s name and required arguments. It reduces typing and recall work while leaving the intended operation for the programmer to choose.

Explanation · 2 / 4

Check a complete example against its requirement

The following program is complete and grammatically valid in the teaching notation, but it multiplies by Delivery. The result is 3 × 2 = 6 instead of the required 3 × 4 = 12. Merely accepting a known identifier did not establish the correct meaning.

DECLARE Quantity : INTEGER
DECLARE UnitPrice : INTEGER
DECLARE Delivery : INTEGER
DECLARE Cost : INTEGER
Quantity <- 3
UnitPrice <- 4
Delivery <- 2
Cost <- Quantity * Delivery
OUTPUT Cost

Explanation · 3 / 4

Read feedback about language rules

Dynamic syntax checking examines source while it is entered and highlights rule violations. For example, Cost <- Quantity * is an incomplete expression because it lacks the right operand. A missing required keyword can also be flagged. The message and location guide inspection, including surrounding lines where the cause may have begun.

Explanation · 4 / 4

Use the right evidence for each problem

Completing the expression with Delivery can remove that grammar error while preserving the wrong calculation. Syntax checking tests language rules; it does not prove that the result meets the requirement. Correct the example to Cost <- Quantity * UnitPrice, then run and compare the result with the independently predicted 12.

What the IDE observesWhat it can establish
Both names exist at this positionBoth may be offered as context-sensitive choices
A required operand is missingA syntax diagnostic can identify a rule violation
Multiplication uses a declared but unintended variableThe grammar can be valid; check values and the requirement

Check

Explain it yourself · Teacher-written

A completed line has no syntax warning. What must you still check before calling the calculation correct?

Check your reasoning

Check that the selected operands and operation implement the requirement, then compare actual output with the expected result. Valid syntax alone is insufficient.

Connect

Keep this idea

Context-sensitive prompts suggest code appropriate to the editing position. Dynamic syntax checking flags language-rule errors while code is entered.

Before following execution, make the source structure easier to read and navigate.

Check a common misunderstanding

A valid suggestion can be the wrong variable for the task; no syntax warning does not prove correct logic.

System software · Concept 02

Make code readable without changing what it does

Observe

DECLARE Quantity, UnitPrice, Delivery, Cost : INTEGER
Quantity <- 3
UnitPrice <- 4
Delivery <- 2
IF Quantity > 0 THEN
    Cost <- Quantity * Delivery
    OUTPUT Cost
ENDIF

Start with a question

If the editor hides the cost calculation inside an IF block, will the calculation stop running?

Keep Quantity = 3, UnitPrice = 4 and Delivery = 2. The editor model wraps the cost calculation and its output in IF Quantity > 0 THEN. Initially it uses Delivery and prints 6. Compare unformatted, indented and collapsed views before correcting the chosen variable.

Explain

Explanation · 1 / 3

Expose the structure with pretty-printing

Pretty-printing applies readable presentation, such as consistent indentation and syntax colouring. Indenting the calculation and output makes it clear that both belong to the IF body. Colours can distinguish keywords and other language elements. Presentation helps reading; it does not correct the use of Delivery where UnitPrice was required.

DECLARE Quantity, UnitPrice, Delivery, Cost : INTEGER
Quantity <- 3
UnitPrice <- 4
Delivery <- 2
IF Quantity > 0 THEN
    Cost <- Quantity * Delivery
    OUTPUT Cost
ENDIF

Explanation · 2 / 3

Collapse a block to focus the view

Collapsing, also called folding, hides the body of a code block in the editor while leaving it in the source program. A compact header lets a developer focus on another section of a long program. Expanding the block reveals its statements again.

Explanation · 3 / 3

Keep display separate from control flow

Quantity is 3, so Quantity > 0 is true and the IF body executes even when collapsed. With Delivery selected, its output stays 6. After the source is corrected to use UnitPrice, its output is 12 whether the block is expanded or collapsed. Folding neither comments out nor deletes the statements. IF and ENDIF define this block; indentation makes its structure easier to see.

Editor actionVisible changeProgram behaviour
Pretty-printIndentation and styling expose structureThe specified calculation stays the same
Collapse the IF blockIts two statements are hidden in the editorThe calculation and output still execute when the condition is true
Expand the IF blockSource statements become visible againNo new statements are added

Separate a display change from a source correction

Work together · 1 / 2

Change the view and compare

Run the unformatted version: 3 × 2 gives 6. Pretty-print, collapse the IF body and run again. It still prints 6 because the same two statements execute.

Work together · 2 / 2

Change the calculation and compare

Select UnitPrice and accept that identifier to change the source. With ENDIF present, run again: 3 × 4 gives 12. Expanding or collapsing now leaves the corrected output at 12.

Formatting changes presentation; selecting and accepting a different identifier changes the calculation.

Experiment

Run the initial Delivery version, then pretty-print and fold it before running again. Predict why all three views produce 6. Select and accept UnitPrice and confirm 12. Finally remove ENDIF, inspect the syntax message and restore ENDIF before running the corrected program again.

What is the difference between collapsing a loop in the editor and changing its condition to false?

Check your reasoning

Collapsing hides the source text only. Changing the condition alters control flow and may prevent the loop body from executing.

Pause, inspect, step and verify the correction

Observe

DECLARE Quantity : INTEGER
DECLARE UnitPrice : INTEGER
DECLARE Delivery : INTEGER
DECLARE Cost : INTEGER
Quantity <- 3
UnitPrice <- 4
Delivery <- 2
Cost <- Quantity * Delivery
OUTPUT Cost

Start with a question

The program prints 6 instead of 12. Which observation would show whether the inputs or the multiplication caused it?

Return to Quantity = 3, UnitPrice = 4 and Delivery = 2. The faulty statement is Cost <- Quantity * Delivery. Use the complete listing below; the lab focuses its numbered display on the executable assignments and output.

Explain

Explanation · 1 / 5

Predict before starting the debugger

The requirement is quantity multiplied by unit price, so the expected cost is 3 × 4 = 12. Read the complete source and select a point immediately before the suspect assignment. That puts both the input values and the effect of the operation within reach.

DECLARE Quantity : INTEGER
DECLARE UnitPrice : INTEGER
DECLARE Delivery : INTEGER
DECLARE Cost : INTEGER
Quantity <- 3
UnitPrice <- 4
Delivery <- 2
Cost <- Quantity * Delivery
OUTPUT Cost

Explanation · 2 / 5

Pause at a breakpoint

A breakpoint tells the debugger to pause execution at a selected source location. In this model it pauses before the selected calculation. At that pause, Quantity is 3, UnitPrice is 4 and Delivery is 2; Cost has not yet been assigned. Reaching a breakpoint is different from executing the statement on that line.

Explanation · 3 / 5

Inspect values and evaluate a watch

Variable inspection shows stored values at the current pause. An expression watch can evaluate Quantity * UnitPrice as 12 using those values. This pure arithmetic expression does not assign 12 to Cost and does not execute OUTPUT. It supplies evidence for comparison.

Explanation · 4 / 5

Single-step the suspected statement

Single stepping executes one statement and pauses again. Stepping Cost <- Quantity * Delivery sets Cost to 6. The operands explain why: the program used 3 and 2. OUTPUT has not yet executed. A second step executes OUTPUT Cost and makes 6 appear in the program-output window.

PointCostWatch Quantity * UnitPriceOutput
Before the calculationNot assigned yet12None
After stepping the calculation612None
After stepping OUTPUT6126

Explanation · 5 / 5

Use the report window and complete the correction

An IDE’s report or diagnostic window can show source errors and runtime messages; program output may appear in its own panel. Read the message or output together with its stage. Correct the assignment to use UnitPrice, restart from the initial state and rebuild if the chosen execution route requires it. The corrected run should assign 12 and then display 12.

DECLARE UnitPrice : INTEGER
DECLARE Delivery : INTEGER

Work together

Separate the wrong variable from the wrong operator

The debugger offers a second fault: Cost <- Quantity + UnitPrice. The inputs and required result stay the same.

Work together · 1 / 2

Predict the faulty effect

Before this statement, the inputs are 3 and 4. Stepping addition produces 7, although the required multiplication would produce 12.

Work together · 2 / 2

Use evidence to correct the cause

For output 6, inspect the use of Delivery. For output 7, inspect the + operator. Replace the faulty expression with Quantity * UnitPrice and restart to confirm output 12.

A debugger reveals execution state; the programmer compares it with the requirement and corrects the cause.

Question 1 · Command word: Explain3 teacher marks

Explain how dynamic syntax checking and a diagnostic window help locate a missing keyword. State why they may not identify a valid but incorrect calculation.

S5.07.A02S5.07.A08
Answer and checking points — teacher-written
  1. Dynamic checking can highlight the grammar violation while the statement is entered.
  2. The diagnostic window can report a message and source location to guide inspection.
  3. An incorrect calculation can still obey the language grammar, so syntax checks alone cannot prove its result correct.

Common error: Distinguish a rule violation from a logic error.

Question 2 · Command word: Compare3 teacher marks

Compare pretty-printing with expanding and collapsing code blocks. Explain whether collapsing a block prevents it from executing.

S5.07.A03S5.07.A04
Answer and checking points — teacher-written
  1. Pretty-printing uses consistent indentation or syntax styling to make source structure clearer.
  2. Expand/collapse controls reveal or hide a block's text to aid navigation.
  3. Collapsing changes the editor view only; control flow can still execute the hidden block.

Common error: Do not confuse folding with removing statements.

Question 3 · Command word: Describe4 teacher marks

A debugger is paused before Amount <- Amount * 2 with Amount = 7. Describe how to execute just that statement, state Amount afterwards, and explain how to inspect Amount + 1 without assigning it to Amount. Name the facility that caused the initial pause.

S5.07.A05S5.07.A06S5.07.A07
Answer and checking points — teacher-written
  1. Single stepping executes the selected statement and pauses again.
  2. Amount is then 14.
  3. An expression watch or inspection evaluates Amount + 1 as 15 without that arithmetic expression assigning a new Amount.
  4. A breakpoint at the selected statement caused the initial pause.

Common error: A syntactically valid multiplication can still implement the wrong rule. Step and inspect the actual value to diagnose a logic error; expression inspection itself does not assign a new Amount.
