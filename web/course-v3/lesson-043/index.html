8.1.3

First, second and third normal form

First normal form (1NF): removing repeating groups

The shop permits each product at most once per order, with Quantity recording how many units are ordered. A product has one current UnitPrice in this deliberately simplified catalogue. CustomerID identifies a customer; OrderID identifies an order.

Unnormalised order records: repeating product groups
OrderIDCustomerIDCustomerNameProducts (ProductID, ProductName, UnitPrice, Quantity)
501C7Amina(P1, Pen, 2, 3); (P2, Pad, 5, 1)
502C7Amina(P1, Pen, 2, 2)

Order 501 contains a list of two product groups inside one field. It is difficult to address one product’s quantity independently. A table is in first normal form (1NF) when its fields hold single values, it contains no repeating groups, and records can be identified.

1NF: one product per order line
OrderIDCustomerIDCustomerNameProductIDProductNameUnitPriceQuantity
501C7AminaP1Pen23
501C7AminaP2Pad51
502C7AminaP1Pen22

Use (OrderID, ProductID) as the composite key. OrderID alone repeats because one order has several products; ProductID alone repeats because a product appears in several orders. The pair is unique under the stated one-product-per-order rule. Expanding the list preserves all three line items and both orders.

Further explanation

1NF does not prohibit every repeated value. CustomerName and ProductName still repeat after this change. Each field now contains a single value. Partial and transitive dependencies are considered when converting to 2NF and 3NF.

Practice question · teacher-written

Explain why adding LineID without separating the product groups does not put the original table in 1NF.

Suggested answer

A new identifier does not remove the repeating group. The products would still be stored as multiple structured values in one field. Split them into separately identifiable line records.

Second normal form (2NF): removing partial dependencies

The table below is in 1NF and has composite primary key (OrderID, ProductID). For 2NF, each non-key attribute must depend on the whole key. An attribute depending on only part of this key has a partial dependency.

Practice question · teacher-written

Explain why Quantity must remain in OrderLine when the table is converted to 2NF.

Suggested answer

P1 has quantity 3 in order 501 and quantity 2 in order 502. ProductID alone does not determine Quantity; the complete order-product pair does.

Third normal form (3NF): removing transitive dependencies

Now examine SalesOrder independently. Its key is OrderID, so there is no proper subset of that key on which a non-key field could depend. Nevertheless, the same customer name appears in more than one order.

In these examples, third normal form (3NF) means the table is in 2NF and no non-key attribute depends transitively on a key through another non-key attribute. Move CustomerName to Customer, where CustomerID is the primary key. Retain CustomerID as a foreign key in SalesOrder.

Changing Amina’s name now changes one Customer row. Both orders obtain the updated name through CustomerID C7. An order may be deleted without deleting the customer. The final design contains Customer, SalesOrder, Product and OrderLine.

Practice question · teacher-written

Explain why a table with a single-field primary key can fail to satisfy 3NF.

Suggested answer

A non-key attribute may depend on another non-key attribute. For example, OrderID determines CustomerID, and CustomerID determines CustomerName. This transitive dependency prevents the table from being in 3NF.

Check keys, reference targets and every original attribute. Splitting a table is not enough if a required fact or the link needed to reconstruct it disappears. The normalised design should also support adding a new customer or product before it is used on an order.

Further explanation

The price rule matters. Here ProductID determines the current catalogue UnitPrice. If the system must preserve an agreed sale price that varies by order, the order-specific price belongs in OrderLine. Normal forms follow functional dependencies under the actual business rules.

Practice question · teacher-written

Explain the problem caused by storing CustomerName in both Customer and SalesOrder.

Suggested answer

The name would be duplicated. Updating only some occurrences could cause data inconsistency. Store CustomerName in Customer and use SalesOrder.CustomerID to retrieve it.

8.1.4

Determine whether tables are in 3NF

Determining whether a table is in 3NF

Further explanation

A few distinct values in a sample do not establish a candidate key or dependency. Conversely, repeating a legitimate foreign key is not evidence that a table fails 3NF. “No many-to-many relationships” alone is not a sufficient proof of 3NF.

For each case below, first decide the highest normal form supported by the stated rules. Name the offending dependency, if any, and propose the smallest necessary change before revealing the answer.

Case A · a repeating group

Case A · a repeating group
MemberIDMemberNameBorrowedCopyIDs
1Asha101, 102
2Ben103

Business rules: MemberID identifies a member. BorrowedCopyIDs is a list of separate copy identifiers, not one indivisible value.

Practice question · teacher-written

State whether the table is in 3NF and explain your answer using the stated dependencies. If it is not in 3NF, give the required tables and identify their primary and foreign keys.

Suggested answer

Not in 1NF because BorrowedCopyIDs contains a repeating group, so the table is not in 3NF. Use Member(MemberID PK, MemberName) and Loan(LoanID PK, MemberID FK, CopyID FK), with one borrowing event per Loan record. Loan.MemberID references Member.MemberID and Loan.CopyID references Copy.CopyID in the library catalogue.

Case B · part of a composite key

Case B · part of a composite key
OrderID (PK part)ProductID (PK part)ProductNameQuantity
501P1Pen3
501P2Pad1
502P1Pen2

Business rules: Each product appears at most once on an order. ProductID determines ProductName; Quantity depends on the complete (OrderID, ProductID) key.

Practice question · teacher-written

State whether the table is in 3NF and explain your answer using the stated dependencies. If it is not in 3NF, give the required tables and identify their primary and foreign keys.

Suggested answer

In 1NF but not 2NF, therefore not 3NF. ProductName depends on only ProductID, part of the composite key. Use Product(ProductID PK, ProductName) and OrderLine(OrderID, ProductID, Quantity) with composite primary key (OrderID, ProductID). OrderLine.ProductID is a foreign key referencing Product.ProductID. OrderID links to the order header table.

Case C · a transitive dependency

Case C · a transitive dependency
OrderID (PK)CustomerIDCustomerName
501C7Amina
502C7Amina

Business rules: Each OrderID determines one CustomerID. CustomerID determines CustomerName. CustomerID can occur on several orders.

Practice question · teacher-written

State whether the table is in 3NF and explain your answer using the stated dependencies. If it is not in 3NF, give the required tables and identify their primary and foreign keys.

Suggested answer

In 2NF but not 3NF. CustomerName depends on OrderID through the non-key CustomerID. Use Customer(CustomerID PK, CustomerName) and SalesOrder(OrderID PK, CustomerID FK), where SalesOrder.CustomerID references Customer.CustomerID.

Case D · already in 3NF

Case D · already in 3NF
OrderID (PK part, FK)ProductID (PK part, FK)Quantity
501P13
501P21
502P12

Business rules: Each product appears at most once per order. Only the complete (OrderID, ProductID) pair determines Quantity; there are no other non-key attributes or dependencies.

Practice question · teacher-written

State whether the table is in 3NF and explain your answer using the stated dependencies. If it is not in 3NF, give the required tables and identify their primary and foreign keys.

Suggested answer

In 3NF under these rules. Values are single-valued; Quantity depends on the whole key; no non-key attribute determines another non-key attribute. No further split is needed.

Original question · Cambridge 9618/12

1. Explain the move to a relational database

Cambridge 9618/12 · October/November 2024 · 6(a) · 3 marks

Selected parts: 6(a) [3].

Original question
Reading the question — teacher guidance

Explain benefits compared with separately maintained files. Use the repair company to make the effect of each benefit clear.

Solution / model answer — teacher-written

A customer’s details can be stored once and referenced from their repair jobs, reducing repeated data. Updating that single customer record means that queries for their jobs use the same current details, improving consistency. Different views can show employees only the information needed for their work.

Official mark scheme
Why this earns marks — teacher explanation

The scheme accepts three points at most. Redundancy, consistency, independence, queries, views and concurrent access are alternatives, not a requirement to list everything.

Common mistakes — teacher analysis

A relational database does not automatically copy every change into every table. In this example, jobs reference the same customer record; referential constraints and update rules govern changes to keys.

4. Normalise the ice-cream batch table

Cambridge 9618/13 · October/November 2024 · 4(c)(ii) · 4 marks

Selected parts: 4(c)(ii) [4].

Original question
Reading the question — teacher guidance

Use the repeated product facts in the sample rows. The question explicitly forbids changing CUSTOMER and SALE; only redesign BATCH and its new related table.

Solution / model answer — teacher-written
BATCH(BatchID, IceCreamID, EndDate)
  Primary key: BatchID
  Foreign key: IceCreamID references ICE_CREAM(IceCreamID)
ICE_CREAM(IceCreamID, Type, Flavour, Size, SellingPrice)
  Primary key: IceCreamID

The same product can be made in several batches. Its type, flavour, size and selling price belong in ICE_CREAM; the batch’s identifier and end date remain in BATCH. Each batch references the appropriate product.

Official mark scheme
Why this earns marks — teacher explanation

The four marks cover the new product table, its product fields, a suitable primary key and the matching foreign key in BATCH. The official table definitions are labelled examples rather than a complete example answer: explicitly identifying the keys completes the response.

Common mistakes — teacher analysis

EndDate is a batch fact. Moving it to ICE_CREAM would force all batches of the product to share one end date. Do not redesign the two excluded tables.

Original question · Cambridge 9618/11

5. Explain why the work-experience tables are in 3NF

Cambridge 9618/11 · October/November 2025 · 2(b) · 2 marks

Selected parts: 2(b) [2].

Original question
Reading the question — teacher guidance

Use the stated business rules and all three table definitions. Explain the dependencies; do not infer normal form only from how a few sample values look.

Solution / model answer — teacher-written

Each table stores atomic values with no repeating groups. In each table, the non-key attributes describe its own identifier: StudentID identifies student details, PlacementID identifies one placement and CompanyID identifies company details. There is no partial-key dependency and no non-key attribute determines another non-key attribute under the supplied design. Therefore no transitive dependency remains.

Official mark scheme
Why this earns marks — teacher explanation

The official maximum is two marks. Give two valid normal-form reasons, such as no repeating groups and no partial or transitive dependencies, and relate the explanation to the supplied tables.

The unchanged official scheme also accepts that there are no many-to-many relationships. That observation alone does not prove 3NF: a table can have no many-to-many relationship and still contain a transitive dependency.

Common mistakes — teacher analysis

Do not claim that using primary keys, or merely splitting data into three tables, proves 3NF. Name the dependency or repeating-group condition that the design satisfies.

6. Design three related quiz tables

Cambridge 9618/11 · May/June 2024 · 6(a) · 6 marks

Selected parts: 6(a) [6].

Original question
Reading the question — teacher guidance

Separate facts about a user, a quiz and one user’s attempt at a quiz. Use the unique username and identify every primary and foreign key.

Solution / model answer — teacher-written
USER(Username, Email, DateOfBirth, Rating)
  Primary key: Username
QUIZ(QuizID, Date, Filename)
  Primary key: QuizID
USER_QUIZ(Username, QuizID, Score)
  Primary key: (Username, QuizID)
  Foreign key: Username references USER(Username)
  Foreign key: QuizID references QUIZ(QuizID)

A score belongs to the pairing of a user and a quiz. Rating belongs to the user. The linking table therefore holds Score, while USER holds Rating. The combination in the linking table distinguishes different users attempting the same quiz and one user attempting different quizzes.

Official mark scheme
Why this earns marks — teacher explanation

The official list contains seven possible points but the question is worth six. The answer supplies the required tables, fields and keys; the maximum remains six. Date or filename can also identify QUIZ in the official scheme when the remaining required quiz fields are included.

Common mistakes — teacher analysis

Putting Score in USER allows only one score per user. Merely listing three tables without primary keys or matching foreign keys leaves their relationships unclear.

Original question · Cambridge 9618/11

7. Apply referential integrity to placements

Cambridge 9618/11 · October/November 2025 · 2(d) · 3 marks

Selected parts: 2(d) [3].

Original question
Reading the question — teacher guidance

Explain the consistency rule, then use a specific pair of tables from WORKEXPERIENCE.

Solution / model answer — teacher-written

Referential integrity keeps related data consistent. Each non-null foreign-key value must match a referenced key. For example, PLACEMENT.CompanyID refers to COMPANY.CompanyID, so a placement cannot refer to a company that is absent.

Official mark scheme
Why this earns marks — teacher explanation

Three marks overall; at most two generic and at most two specific points. The response above supplies the rule and a concrete application.

The official scheme includes cascading actions. In an implemented database these depend on declared update/delete rules; a foreign key can instead restrict an operation. Do not infer that all foreign keys automatically cascade.

Teacher-written practice
Question 1 · Command word: Draw5 teacher marks

Draw an E-R diagram for a library where each Copy belongs to one Book and each Loan refers to one Copy. A book may have several copies and a copy may be loaned many times. Include primary keys, foreign keys and relationship cardinalities.

S8.03.A01
Answer and checking points — teacher-written
  1. Book has BookID as its primary key.
  2. Copy has CopyID as its primary key and BookID as a foreign key.
  3. Loan has LoanID as its primary key and CopyID as a foreign key.
  4. Book to Copy is one-to-many.
  5. Copy to Loan is one-to-many.

Common error: A loan identifies a physical copy, not just the book title.

Question 2 · Command word: Write3 teacher marks

An order row contains OrderID 70 and a repeating Items field with (P4, quantity 2) and (P8, quantity 5). Write a 1NF relation and its two rows, assuming each product appears once per order. State its key.

S8.04.A01
Answer and checking points — teacher-written
  1. Use OrderItem(OrderID, ProductID, Quantity) with one item per row.
  2. The rows are (70, P4, 2) and (70, P8, 5).
  3. The combined (OrderID, ProductID) identifies each row.

Common error: Retain OrderID in both item rows.

Question 3 · Command word: Explain4 teacher marks

Registration(StudentID, CourseID, CourseTitle, Grade) has key (StudentID, CourseID). CourseID determines CourseTitle; the entire key determines Grade. Explain the 2NF violation and give the corrected relations and keys.

S8.04.A02
Answer and checking points — teacher-written
  1. CourseTitle depends on CourseID, which is only part of the composite key.
  2. Create Course(CourseID, CourseTitle), keyed by CourseID.
  3. Retain Registration(StudentID, CourseID, Grade) with its composite key.
  4. Registration.CourseID references Course.CourseID.

Common error: A student's grade belongs to their registration, not to Course alone.

Question 4 · Command word: Explain4 teacher marks

A museum stores Item(ItemID, ItemName, RoomID, RoomName). ItemID is the key and RoomID determines RoomName. Explain whether this is in 3NF and produce a design that allows a room to be recorded before any items are assigned to it.

S8.04.A04S8.04.A05
Answer and checking points — teacher-written
  1. RoomName is transitively dependent on ItemID through RoomID, so the table is not in 3NF.
  2. Create Room(RoomID, RoomName) with RoomID as its key.
  3. Keep Item(ItemID, ItemName, RoomID) with ItemID as its key.
  4. Item.RoomID references Room, while an empty room can exist as a Room record without any Item records.

Common error: The room must have a place to store its own facts independently of an item.

Question 5 · Command word: Explain4 teacher marks

Product(ProductID, Description, CurrentPrice) has atomic values. ProductID is its only candidate key, and neither Description nor CurrentPrice determines another attribute. Explain why this table is in 3NF. A separate Employee(EmployeeID, DepartmentID, DepartmentName) has DepartmentID → DepartmentName. Explain whether adding a unique RowID removes its normalisation problem.

S8.04.A02S8.04.A03S8.04.A04
Answer and checking points — teacher-written
  1. Product is in 1NF because its values are atomic.
  2. Its only candidate key is a single attribute, so there is no partial-key dependency; it meets 2NF.
  3. There is no non-key dependency under the supplied rules, so it also meets the simple 3NF test.
  4. Adding RowID to Employee leaves DepartmentID → DepartmentName intact; store department names in Department and retain the DepartmentID reference in Employee.

Common error: A surrogate identifier does not change which entity owns a fact.

Question 6 · Command word: Explain3 teacher marks

Customer(CustomerID, Postcode, Town) has key CustomerID. Each postcode determines one town. Explain why the table fails 3NF and state a decomposition with its linking field.

S8.04.A03
Answer and checking points — teacher-written
  1. Town depends on the non-key Postcode, producing a transitive dependency from CustomerID.
  2. Use Customer(CustomerID, Postcode) and PostcodeArea(Postcode, Town).
  3. Customer.Postcode is a foreign key to PostcodeArea.Postcode.

Common error: Use the stated postcode-to-town rule rather than assuming Town uniquely determines Postcode.

Data management

A table stores records about an entity type. Each record contains values for its fields. Select a table to inspect its records, then use the form or SQL to maintain the data.

This form submits an INSERT statement to the database. The DBMS checks access rights and enforces primary key and unique constraints.

Data modelling and logical schema

Data modelling identifies entities, attributes and relationships. A logical schema describes the database design independently of a particular DBMS. The table definitions below implement that design in PostgreSQL.

Table designer: add an attribute

The designer issues ALTER TABLE. Inspect the same attribute in the data dictionary.

Data dictionary

The data dictionary contains metadata, including field names, data types, field sizes and constraints. The DBMS maintains this metadata when a table definition changes. Editing a record changes the stored data, not its field definitions.

Data integrity

Data integrity concerns the accuracy and consistency of stored data. The DBMS enforces validation rules and referential integrity constraints. Access rights control which operations a user may perform; authorised operations must still satisfy the constraints.

A foreign key alone permits NULL unless NOT NULL is also declared. This library requires every loan to identify a member and a copy. Its default referential action rejects deleting a referenced record.

Access rights for individuals and groups

Select a user above. Student inherits SELECT access rights from the library_readers group. Librarian inherits rights to retrieve, insert, update and delete records from library_writers. Administrator can change table definitions and assign access rights to individuals or groups.

Revoking an individual grant does not cancel a right still inherited from a group.

Backup and recovery procedures

A backup is a copy of data that can be used to recover from data loss or corruption. Backup procedures specify how often copies are made, where they are stored, how they are protected and retained, and how restoration is tested. This exercise creates and restores a copy of the database at a particular time.
