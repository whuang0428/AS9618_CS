Databases · Concept 01

Draw a design and test it with real events

Observe

Look, then discuss

Can the design record two copies of one title and repeated loans of the same copy?

The catalogue contains Book 11, Atlas. The library owns Copy 101 and Copy 102 of that title. Asha borrows Copy 101, returns it and borrows it again later. Decide which facts must remain separate.

Explain

Explanation · 1 / 4

Assign facts to their owner

Book stores title-level facts, such as BookID and Title. Copy stores a physical item’s CopyID and BookID. Member stores MemberID and MemberName. Loan stores LoanID, MemberID, CopyID and the event’s dates. A borrowing date belongs to an event, not permanently to a member or title.

EntityAttributes in this design
BookBookID PK; Title
CopyCopyID PK; BookID FK
MemberMemberID PK; MemberName
LoanLoanID PK; MemberID FK; CopyID FK; BorrowDate

Explanation · 2 / 4

Connect the entities from the rules

One Book may have many Copies; each Copy describes one Book. One Copy may take part in many Loans over time; each Loan names one Copy. One Member may take part in many Loans; each Loan names one Member. State the meaning of each line and mark keys in the boxes.

Explanation · 3 / 4

Read the diagram as a structure

An ER diagram documents entities, attributes, keys and relationships. A line describes an association rather than the next step in a process. Draw a notation legend showing the one and many ends, and include optional participation if the chosen notation represents it.

Explanation · 4 / 4

Test the model before implementation

A new member with no loans must fit. Two copies of Atlas must fit without duplicating its title record. Two later loans of Copy 101 need different LoanIDs. Preventing overlapping active loans for one copy is an additional business constraint, not something the cardinality line alone guarantees.

Work together

Trace two borrowing events

Book (11, Atlas), Copy (101, 11), Member (1, Asha). Asha borrows Copy 101 on two separate dates.

Work together · 1 / 2

Add the event records

Loan 201 contains MemberID 1, CopyID 101 and the first date. Loan 206 contains MemberID 1, CopyID 101 and the later date. Both references point to the existing parent records.

Work together · 2 / 2

Recover the description

From Loan 206 follow MemberID 1 to Asha. Follow CopyID 101 to BookID 11, then to Atlas. This is a design trace, not a request to write a three-table AS SQL query.

A usable ER design represents every allowed event without overwriting another fact.

Explain it yourself · Teacher-written

Why should Title be stored with Book instead of copied into every Loan? Where does BorrowDate belong?

Check your reasoning

Title describes the book and would be repeated across its copies and loans if copied into each event. BorrowDate describes a particular Loan and can differ when the same member borrows the same copy again.

Explanation · 2 / 4

Explain atomic values and repeating groups

First Normal Form requires atomic field values and no repeating groups. Atomic means a value is treated as one item for the application’s operations. The product list fails because its items and quantities must be queried separately. Product1, Product2 and Product3 columns also repeat the same group and impose an arbitrary item limit.

Explanation · 3 / 4

Create one row for each order-product pair

Expand the product list into three rows, repeating the order’s customer facts where necessary at this stage. Do not discard Quantity. Under the one-product-per-order rule the pair (OrderID, ProductID) distinguishes the rows.

Explanation · 4 / 4

Recognise what remains unresolved

The table now has addressable atomic records, but Amina and Pen are still repeated. 1NF is a starting condition, not a promise that all redundancy has gone. The next step asks which parts of the composite key determine each non-key fact.

Explanation · 1 / 4

Read a dependency

X → Y means each permitted X value determines one Y value under the business rules. ProductID → ProductName and UnitPrice. OrderID → CustomerID and CustomerName. Only (OrderID, ProductID) determines the line’s Quantity. The arrow describes determination, not a processing step.

DeterminantDependent facts
OrderIDCustomerID, CustomerName
ProductIDProductName, UnitPrice
OrderID + ProductIDQuantity

Explanation · 2 / 4

Identify partial dependencies

Second Normal Form requires 1NF and no non-key attribute depending on only part of a candidate key. In this example the candidate key is the pair. ProductName depends on ProductID alone, while customer facts depend on OrderID alone. These are partial dependencies.

Explanation · 3 / 4

Move product facts to Product

Product stores P1 once as Pen with price 2 and P2 once as Pad with price 5. This avoids changing the same product price separately in several order rows. The fixed current-price rule is essential; a price agreed separately for each order line would belong to that line instead.

Before decomposition the two P1 lines each store price 2. The correct current price changes to 3.

Work together · 1 / 2

Show the original anomaly

Changing only the order 501 copy leaves P1 priced at 3 and 2 simultaneously. Removing the last P2 order line would also remove the only stored Pad description. A product without an order has no suitable line key for insertion.

Explanation · 1 / 4

Trace the remaining dependency

OrderID determines CustomerID, and CustomerID determines CustomerName. Therefore OrderID → CustomerID → CustomerName is a transitive dependency through a non-key attribute. A single-field primary key does not rule out this problem.

SalesOrder at 2NF

Explanation · 2 / 4

Apply the simple 3NF test

Third Normal Form requires 2NF and, in these simple designs, no non-key attribute depending on another non-key attribute. Move CustomerName to the table identified by CustomerID. The exact determinant is the reason for splitting, rather than a general desire for more small tables.

Explanation · 3 / 4

Create Customer and retain its reference

Customer contains (C7, Amina). SalesOrder retains OrderID and CustomerID, so orders 501 and 502 still identify their customer. Removing CustomerID from SalesOrder would lose that association.

Explain it yourself · Teacher-written

Parcel(ParcelID, DepotID, DepotName) has atomic values and ParcelID as its only candidate key. Each depot has one name. Is the table in 3NF?

Check your reasoning

No. ParcelID → DepotID → DepotName is a transitive dependency. Use Parcel(ParcelID PK, DepotID FK) and Depot(DepotID PK, DepotName), retaining DepotID to retrieve each parcel’s depot name.

Connect

Keep this idea

Remove transitive dependencies by storing the dependent fact with the entity that determines it.

A finished design must pass both a dependency check and a reconstruction check.

Check a common misunderstanding

One primary-key field makes the partial-key test simple; it does not establish 3NF.

Check normal forms in order

Product(ProductID, ProductName, UnitPrice) is in 3NF if values are atomic, ProductID is the only candidate key and neither non-key attribute determines the other. Original question · Cambridge 9618/13

1. Normalise the ice-cream batch table

Cambridge 9618/13 · October/November 2024 · 4(c)(ii) · 4 marks

Selected parts: 4(c)(ii) [4].

Hint — reading the question

Use the repeated product facts in the sample rows. The question explicitly forbids changing CUSTOMER and SALE; only redesign BATCH and its new related table.

Reasoning and model answer — teacher-written
BATCH(BatchID, IceCreamID, EndDate)
  Primary key: BatchID
  Foreign key: IceCreamID references ICE_CREAM(IceCreamID)
ICE_CREAM(IceCreamID, Type, Flavour, Size, SellingPrice)
  Primary key: IceCreamID

The same product can be made in several batches. Its type, flavour, size and selling price belong in ICE_CREAM; the batch’s identifier and end date remain in BATCH. Each batch references the appropriate product.

Official mark scheme
Why this earns marks — teacher explanation

The four marks cover the new product table, its product fields, a suitable primary key and the matching foreign key in BATCH. The official table definitions are labelled examples rather than a complete example answer: explicitly identifying the keys completes the response.

Common mistakes — teacher analysis

EndDate is a batch fact. Moving it to ICE_CREAM would force all batches of the product to share one end date. Do not redesign the two excluded tables.

Original question · Cambridge 9618/11

2. Design three related quiz tables

Cambridge 9618/11 · May/June 2024 · 6(a) · 6 marks

Selected parts: 6(a) [6].

Hint — reading the question

Separate facts about a user, a quiz and one user’s attempt at a quiz. Use the unique username and identify every primary and foreign key.

Reasoning and model answer — teacher-written
USER(Username, Email, DateOfBirth, Rating)
  Primary key: Username
QUIZ(QuizID, Date, Filename)
  Primary key: QuizID
USER_QUIZ(Username, QuizID, Score)
  Primary key: (Username, QuizID)
  Foreign key: Username references USER(Username)
  Foreign key: QuizID references QUIZ(QuizID)

A score belongs to the pairing of a user and a quiz. Rating belongs to the user. The linking table therefore holds Score, while USER holds Rating. The combination in the linking table distinguishes different users attempting the same quiz and one user attempting different quizzes.

Official mark scheme
Why this earns marks — teacher explanation

The official list contains seven possible points but the question is worth six. The answer supplies the required tables, fields and keys; the maximum remains six. Date or filename can also identify QUIZ in the official scheme when the remaining required quiz fields are included.

Common mistakes — teacher analysis

Putting Score in USER allows only one score per user. Merely listing three tables without primary keys or matching foreign keys leaves their relationships unclear.

Question 1 · Command word: Draw5 teacher marks

Draw an E-R diagram for a library where each Copy belongs to one Book and each Loan refers to one Copy. A book may have several copies and a copy may be loaned many times. Include primary keys, foreign keys and relationship cardinalities.

S8.03.A01
Answer and checking points — teacher-written
  1. Book has BookID as its primary key.
  2. Copy has CopyID as its primary key and BookID as a foreign key.
  3. Loan has LoanID as its primary key and CopyID as a foreign key.
  4. Book to Copy is one-to-many.
  5. Copy to Loan is one-to-many.

Common error: A loan identifies a physical copy, not just the book title.

Question 2 · Command word: Write3 teacher marks

An order row contains OrderID 70 and a repeating Items field with (P4, quantity 2) and (P8, quantity 5). Write a 1NF relation and its two rows, assuming each product appears once per order. State its key.

S8.04.A01
Answer and checking points — teacher-written
  1. Use OrderItem(OrderID, ProductID, Quantity) with one item per row.
  2. The rows are (70, P4, 2) and (70, P8, 5).
  3. The combined (OrderID, ProductID) identifies each row.

Common error: Retain OrderID in both item rows.

Question 3 · Command word: Explain4 teacher marks

Registration(StudentID, CourseID, CourseTitle, Grade) has key (StudentID, CourseID). CourseID determines CourseTitle; the entire key determines Grade. Explain the 2NF violation and give the corrected relations and keys.

S8.04.A02
Answer and checking points — teacher-written
  1. CourseTitle depends on CourseID, which is only part of the composite key.
  2. Create Course(CourseID, CourseTitle), keyed by CourseID.
  3. Retain Registration(StudentID, CourseID, Grade) with its composite key.
  4. Registration.CourseID references Course.CourseID.

Common error: A student's grade belongs to their registration, not to Course alone.

Question 4 · Command word: Explain4 teacher marks

A museum stores Item(ItemID, ItemName, RoomID, RoomName). ItemID is the key and RoomID determines RoomName. Explain whether this is in 3NF and produce a design that allows a room to be recorded before any items are assigned to it.

S8.04.A04S8.04.A05
Answer and checking points — teacher-written
  1. RoomName is transitively dependent on ItemID through RoomID, so the table is not in 3NF.
  2. Create Room(RoomID, RoomName) with RoomID as its key.
  3. Keep Item(ItemID, ItemName, RoomID) with ItemID as its key.
  4. Item.RoomID references Room, while an empty room can exist as a Room record without any Item records.

Common error: The room must have a place to store its own facts independently of an item.

Question 5 · Command word: Explain4 teacher marks

Product(ProductID, Description, CurrentPrice) has atomic values. ProductID is its only candidate key, and neither Description nor CurrentPrice determines another attribute. Explain why this table is in 3NF. A separate Employee(EmployeeID, DepartmentID, DepartmentName) has DepartmentID → DepartmentName. Explain whether adding a unique RowID removes its normalisation problem.

S8.04.A02S8.04.A03S8.04.A04
Answer and checking points — teacher-written
  1. Product is in 1NF because its values are atomic.
  2. Its only candidate key is a single attribute, so there is no partial-key dependency; it meets 2NF.
  3. There is no non-key dependency under the supplied rules, so it also meets the simple 3NF test.
  4. Adding RowID to Employee leaves DepartmentID → DepartmentName intact; store department names in Department and retain the DepartmentID reference in Employee.

Common error: A surrogate identifier does not change which entity owns a fact.

Question 6 · Command word: Explain3 teacher marks

Customer(CustomerID, Postcode, Town) has key CustomerID. Each postcode determines one town. Explain why the table fails 3NF and state a decomposition with its linking field.

S8.04.A03
Answer and checking points — teacher-written
  1. Town depends on the non-key Postcode, producing a transitive dependency from CustomerID.
  2. Use Customer(CustomerID, Postcode) and PostcodeArea(Postcode, Town).
  3. Customer.Postcode is a foreign key to PostcodeArea.Postcode.

Common error: Use the stated postcode-to-town rule rather than assuming Town uniquely determines Postcode.
