Entity-relationship design and normalisation

Turn business rules into an E-R diagram, then remove repeating groups, partial dependencies and transitive dependencies.

Which entity should own each fact, and how can the original information still be retrieved after splitting tables?

Before you start

An order contains several products. Does OrderID alone uniquely identify each order-product line?

Check your answer

No. If each product appears once per order, the pair (OrderID, ProductID) identifies the line.

Teaching checkpoints
  • Model the entities and business rules before inspecting dependencies.
  • Trace the complete UNF → 1NF → 2NF → 3NF example, including each anomaly.
  • Reconstruct all original rows and diagnose a different design independently.

01

Document entities, keys and relationship cardinality

S8.03.A01

Visual overview

Derive the design from requirements

Extract entity types from the facts that the organisation needs to store, then identify each entity's key and relevant attributes. Connect entities only when the business rules support an association. An E-R diagram records this structure rather than a sequence of processing steps.

Identify a particular appointment

In this clinic, each appointment involves exactly one patient and one doctor. A patient or doctor may have many appointments. Appointment therefore stores both foreign keys, and its separate AppointmentID allows the same patient to visit the same doctor on different occasions.

Explain ownership of a fact

Begin with facts to store, not a list of all nouns in a paragraph. A clinic needs patient details, doctor details and the date of each appointment. The appointment is a distinct occurrence because a patient can see the same doctor again. Place VisitDate there rather than on Patient or Doctor, both of which take part in many visits.

Test the model against changed conditions

After drawing, test the design with a new patient who has no appointments, two appointments for one patient, and a later return to the same doctor. The diagram must permit the stated cases without overwriting an earlier visit. If an appointment can involve several doctors instead, the present single DoctorID field is insufficient; a separate appointment-doctor association is needed.

Worked example · From a clinic rule to a diagram

  1. Find entities

    Store patient facts in Patient, doctor facts in Doctor, and the date of a particular visit in Appointment.

  2. Identify rows

    Choose PatientID, DoctorID and AppointmentID as primary keys.

  3. Read both directions

    One appointment names one patient; one patient may attend many appointments. Apply the equivalent rule for Doctor.

  4. Place the references

    PatientID and DoctorID are foreign keys in Appointment, on the many side of each relationship.

Core explanation · Exam essentials

  • An E-R diagram records entities, keys and relationships justified by business rules.
  • Read cardinality in both directions and store facts on the entity or association they describe.
Common misconception

A pair of matching names is not a business rule, and a data-flow arrow does not replace relationship cardinality.

Check your understanding

Why not use (PatientID, DoctorID) as the only appointment key?

Check your answer

The pair can repeat on different visits, so it would not identify every appointment.

02

1NF: one value in each field

S8.04.A01

Visual overview

Remove the repeating group

First Normal Form requires atomic field values and no repeating groups. For this ordering system, a list of product entries in one order field is a repeating group. Give each product line its own row while retaining the order and customer information needed to interpret that row.

State the identity rule

Assume each product occurs at most once per order and the stored unit price is the product's current fixed price. The pair (OrderID, ProductID) identifies a line. Separating the list makes values atomic, but repeated customer and product details still remain to be addressed in later normal forms.

Rules for the complete order example

In the following worked example, each order has one customer; CustomerID determines CustomerName; ProductID determines ProductName and the current fixed UnitPrice. A product appears at most once per order. Quantity depends on the order-product pair. These are business rules, not conclusions obtained merely because a value repeats in this small sample.

Complete unnormalised input

501C7Amina(P1, Pen, 2, 3); (P2, Pad, 5, 1)
502C7Amina(P1, Pen, 2, 2)

Explain why the original structure fails

An atomic value is treated as one value for the operations this application needs. Here a product list is not atomic because the system must address each product and its quantity independently. Creating Product1, Product2 and Product3 columns would impose an arbitrary limit and repeat the same group of fields; give the items rows instead.

Worked example · Expand the repeating product group

  1. First order, first item

    (501, C7, Amina, P1, Pen, 2, 3)

  2. First order, second item

    (501, C7, Amina, P2, Pad, 5, 1)

  3. Second order

    (502, C7, Amina, P1, Pen, 2, 2)

Core explanation · Exam essentials

  • 1NF requires atomic field values and no repeating groups.
  • Expand each item into a row while retaining its order identity and all represented facts.
Common misconception

Splitting a list into rows does not by itself remove dependencies on part of a composite key.

Check your understanding

Why does the first order produce two rows?

Check your answer

It contains two distinct product entries, and each must be represented by an atomic product-line record.

03

2NF: depend on the whole composite key

S8.04.A02

Visual overview

Find partial dependencies

Second Normal Form requires 1NF and no partial dependency of a non-key attribute on part of a candidate key. In the order example, ProductName and UnitPrice depend on ProductID alone, while CustomerID and CustomerName depend on OrderID alone. Quantity depends on the whole line key.

Split without losing the relationship

Move the product facts to Product and the order-level facts to SalesOrder. Keep OrderLine for the association and quantity, retaining the two identifying fields as references. This decomposition removes partial dependencies but does not yet separate CustomerName from CustomerID inside SalesOrder.

Read a dependency and test the determinant

X → Y means that each permitted X value determines one Y value under the rules. It does not mean a processing arrow or that Y must determine X. ProductID P1 has the same product description in different orders, but its quantities are 3 and 2. ProductID alone therefore cannot determine Quantity. OrderID alone cannot determine it either because an order has several product lines.

Three independent changes to the original 1NF table

Requested changeProblem before decompositionHow separate relations help
Record a new product P3, Ruler, price 4 before any orderNo order-product key is available for the product-only fact: an insertion anomalyInsert P3 into Product without inventing an order.
Change P1 current price from 2 to 3 in only the order 501 rowOrder 502 still says 2 for the same product: an update anomalyUpdate the single P1 Product row.
Delete the only P2 line, (501, P2, 1)The only stored Pad description and price also disappear: a deletion anomalyRemove the line while retaining the P2 Product record.

Keep the connecting fields

A field appearing in a composite key can recur. In OrderLine, OrderID 501 appears twice and ProductID P1 appears twice; the pair is unique. Removing either identifier would merge distinct lines. Normalisation moves facts to their determinant, not every repeated identifier into isolation.

  3. Line facts
    OrderLine(OrderID, ProductID, Quantity)
PRIMARY KEY: (OrderID, ProductID)
FOREIGN KEYS: OrderID to SalesOrder; ProductID to Product
  4. Check a line

    OrderLine(501, P1, 3) links to Product(P1, Pen, 2) and SalesOrder(501, C7, Amina).

Core explanation · Exam essentials

  • 2NF requires 1NF and no non-key attribute depending on only part of a candidate key.
  • Separate order and product facts; retain the whole line key and Quantity in OrderLine.
Common misconception

Deleting ProductID from OrderLine would lose which product belongs to the order; keep the reference after moving product facts.

Check your understanding

Why is Quantity not stored as a single attribute of Product?

Check your answer

Different orders can request different quantities of the same product; quantity belongs to the order-product association.

04

3NF: remove transitive dependencies

S8.04.A03

Visual overview

Find the remaining transitive dependency

Third Normal Form requires 2NF and, in these simple designs, no dependency of one non-key attribute on another non-key attribute. SalesOrder still contains OrderID determining CustomerID and CustomerID determining CustomerName. The customer's name is transitively dependent on the order identifier.

Preserve the customer reference

Create Customer(CustomerID, CustomerName) and retain CustomerID as a foreign key in SalesOrder. Customer facts can then be updated in their own relation. Product and OrderLine remain unchanged; the existing keys allow the original order information to be reconstructed.

Explain why another split is needed

The two SalesOrder rows in 2NF still repeat Amina because both name customer C7. OrderID identifies an order, whereas CustomerID identifies the customer whose name is being stored. A change of name belongs to the customer independently of any particular order. The dependency is OrderID → CustomerID → CustomerName.

Check the new possibilities

The final database below contains one customer, two orders, two products and three order lines. Store a new customer in Customer before the customer places an order; deleting an order and its lines need not delete the customer record. Repeated foreign-key values remain useful references, not leftover customer-name copies.

Worked example · Reconstruct the original order line

  1. Start with the line

    OrderLine(501, P1, 3) supplies order, product and quantity.

  2. Follow the order reference

    SalesOrder(501, C7) identifies the customer.

  3. Retrieve the customer

    Customer(C7, Amina) supplies the name.

  4. Retrieve the product

    Product(P1, Pen, 2) supplies product name and price. All seven original line values remain available.

Core explanation · Exam essentials

  • 3NF requires 2NF and, in these simple designs, removal of dependencies between non-key attributes.
  • Move CustomerName to Customer and keep CustomerID in SalesOrder so the original facts remain retrievable.
Optional extension · Current price versus price charged

This example stores the current fixed product price. If the required fact becomes the actual price agreed for each order line, ProductID alone no longer determines that price. Store the agreed UnitPrice on OrderLine under the stated one-product-per-order rule. The price may then differ between two orders of P1 without inconsistency. The stopping point is fact ownership; historical pricing systems are not required.

Common misconception

Normalisation reduces particular redundancy and anomalies; it does not prove that every entered value is true.

Check your understanding

If Amina changes her name, how many Customer records require the change?

Check your answer

One: the record identified by C7. Her orders continue to reference that customer.

05

Judge and produce a complete 3NF design

S8.04.A04S8.04.A05

Visual overview

Explain a verdict with evidence

To judge a design, name its key, state the relevant dependencies and test each normal form in order. One row per entity is not sufficient evidence of 3NF. A non-key fact can still describe another entity, producing an update, insertion or deletion anomaly.

Check information preservation

To produce a design, assign each fact to its determinant and explicitly retain primary and foreign keys. Check that every original attribute is accounted for and that a representative original record can be reconstructed. State any assumptions about uniqueness instead of inventing extra dependencies.

Reconstruct every original line from the final 3NF tables

OrderIDCustomerIDCustomerNameProductIDProductNameUnitPriceQuantity

501C7AminaP2Pad51

Follow the full reconstruction

For each OrderLine, match its OrderID to SalesOrder to find CustomerID; match that identifier to Customer; match ProductID to Product. The three reconstructed rows above equal the three 1NF rows, including both different quantities of P1. No three- or four-table SQL statement is required here: this is a design trace. Section 8 SQL tasks remain limited to two tables.

Design and declared rulesVerdictReason
Product(ProductID, ProductName, UnitPrice); ProductID is the only candidate key; no non-key dependencies; atomic valuesIn 3NF under these rulesA single-field key has no proper subset; neither non-key field determines the other.
Employee gains RowID but still stores DepartmentID and DepartmentName, with DepartmentID determining DepartmentNameNot fixed by the new identifierThe department dependency remains; a new number does not change which entity owns the name.

Separate sample evidence from guarantees

Do not infer a dependency merely because all displayed products have different prices. If different products may share a price, UnitPrice does not determine ProductID. State a missing business rule as an assumption instead of silently inventing it. A design can be checked against the stated rules, not every unknown future requirement.

Worked example · Analyse a different relation

  1. Given

    Employee(EmployeeID, EmployeeName, DepartmentID, DepartmentName). EmployeeID is the key; DepartmentID determines DepartmentName.

  2. Diagnose

    DepartmentName depends on the non-key DepartmentID, so the relation fails the simple 3NF test.

  3. Decompose
    Employee(EmployeeID PK, EmployeeName, DepartmentID FK)
Department(DepartmentID PK, DepartmentName)
  4. Verify

    Each employee still identifies one department, whose name is stored in Department.

Core explanation · Exam essentials

  • Judge keys and dependencies in order: atomic values, partial dependencies, then transitive dependencies.
  • A complete design accounts for every fact and retains references that reconstruct the original information.
Optional extension · The scope of the single-key shortcut

An atomic table whose only candidate key is a single attribute cannot have a partial dependency on that key. Do not generalise this to a table with an additional composite candidate key, or conclude that 2NF also proves 3NF. Formal higher-normal-form proofs are outside this course.

Common misconception

A decomposition must preserve the relationships needed to recover the represented facts; unrelated fragments are not an adequate design.

Check your understanding

ProductID is the only candidate key in an atomic Product(ProductID, ProductName, UnitPrice) table, and neither non-key attribute determines the other. Explain why it is in 3NF.

Check your answer

It is in 1NF because the values are atomic. The single-field candidate key cannot have a partial dependency, so it meets 2NF. With no dependency between its non-key fields it also meets the simple 3NF test.

Practice questions

5 core tasks · 20 teacher marks · 28–36 minutes (teacher estimate). Explain your reasoning before checking the answer.

Question 1 · Command word: Draw5 teacher marks

Draw an E-R diagram for a library where each Copy belongs to one Book and each Loan refers to one Copy. A book may have several copies and a copy may be loaned many times. Include primary keys, foreign keys and relationship cardinalities.

S8.03.A01
Answer and checking points — teacher-written
  1. Book has BookID as its primary key.
  2. Copy has CopyID as its primary key and BookID as a foreign key.
  3. Loan has LoanID as its primary key and CopyID as a foreign key.
  4. Book to Copy is one-to-many.
  5. Copy to Loan is one-to-many.

Common error: A loan identifies a physical copy, not just the book title.

Question 2 · Command word: Write3 teacher marks

An order row contains OrderID 70 and a repeating Items field with (P4, quantity 2) and (P8, quantity 5). Write a 1NF relation and its two rows, assuming each product appears once per order. State its key.

S8.04.A01
Answer and checking points — teacher-written
  1. Use OrderItem(OrderID, ProductID, Quantity) with one item per row.
  2. The rows are (70, P4, 2) and (70, P8, 5).
  3. The combined (OrderID, ProductID) identifies each row.

Common error: Retain OrderID in both item rows.

Question 3 · Command word: Explain4 teacher marks

Registration(StudentID, CourseID, CourseTitle, Grade) has key (StudentID, CourseID). CourseID determines CourseTitle; the entire key determines Grade. Explain the 2NF violation and give the corrected relations and keys.

S8.04.A02
Answer and checking points — teacher-written
  1. CourseTitle depends on CourseID, which is only part of the composite key.
  2. Create Course(CourseID, CourseTitle), keyed by CourseID.
  3. Retain Registration(StudentID, CourseID, Grade) with its composite key.
  4. Registration.CourseID references Course.CourseID.

Common error: A student's grade belongs to their registration, not to Course alone.

Question 4 · Command word: Explain4 teacher marks

A museum stores Item(ItemID, ItemName, RoomID, RoomName). ItemID is the key and RoomID determines RoomName. Explain whether this is in 3NF and produce a design that allows a room to be recorded before any items are assigned to it.

S8.04.A04S8.04.A05
Answer and checking points — teacher-written
  1. RoomName is transitively dependent on ItemID through RoomID, so the table is not in 3NF.
  2. Create Room(RoomID, RoomName) with RoomID as its key.
  3. Keep Item(ItemID, ItemName, RoomID) with ItemID as its key.
  4. Item.RoomID references Room, while an empty room can exist as a Room record without any Item records.

Common error: The room must have a place to store its own facts independently of an item.

Question 5 · Command word: Explain4 teacher marks

Product(ProductID, Description, CurrentPrice) has atomic values. ProductID is its only candidate key, and neither Description nor CurrentPrice determines another attribute. Explain why this table is in 3NF. A separate Employee(EmployeeID, DepartmentID, DepartmentName) has DepartmentID → DepartmentName. Explain whether adding a unique RowID removes its normalisation problem.

S8.04.A02S8.04.A03S8.04.A04
Answer and checking points — teacher-written
  1. Product is in 1NF because its values are atomic.
  2. Its only candidate key is a single attribute, so there is no partial-key dependency; it meets 2NF.
  3. There is no non-key dependency under the supplied rules, so it also meets the simple 3NF test.
  4. Adding RowID to Employee leaves DepartmentID → DepartmentName intact; store department names in Department and retain the DepartmentID reference in Employee.

Common error: A surrogate identifier does not change which entity owns a fact.

Question 1 · Command word: Explain3 teacher marks

Customer(CustomerID, Postcode, Town) has key CustomerID. Each postcode determines one town. Explain why the table fails 3NF and state a decomposition with its linking field.

S8.04.A03
Answer and checking points — teacher-written
  1. Town depends on the non-key Postcode, producing a transitive dependency from CustomerID.
  2. Use Customer(CustomerID, Postcode) and PostcodeArea(Postcode, Town).
  3. Customer.Postcode is a foreign key to PostcodeArea.Postcode.

Common error: Use the stated postcode-to-town rule rather than assuming Town uniquely determines Postcode.

Original question · Cambridge 9618/11

1. Design three related quiz tables

Cambridge 9618/11 · May/June 2024 · 6(a) · 6 marks

Selected parts: 6(a) [6].

Reading the question — teacher guidance

Separate facts about a user, a quiz and one user’s attempt at a quiz. Use the unique username and identify every primary and foreign key.

Solution / model answer — teacher-written
USER(Username, Email, DateOfBirth, Rating)
  Primary key: Username
QUIZ(QuizID, Date, Filename)
  Primary key: QuizID
USER_QUIZ(Username, QuizID, Score)
  Primary key: (Username, QuizID)
  Foreign key: Username references USER(Username)
  Foreign key: QuizID references QUIZ(QuizID)

A score belongs to the pairing of a user and a quiz. Rating belongs to the user. The linking table therefore holds Score, while USER holds Rating. The combination in the linking table distinguishes different users attempting the same quiz and one user attempting different quizzes.

Official mark scheme
Why this earns marks — teacher explanation

The official list contains seven possible points but the question is worth six. The answer supplies the required tables, fields and keys; the maximum remains six. Date or filename can also identify QUIZ in the official scheme when the remaining required quiz fields are included.

Common mistakes — teacher analysis

Putting Score in USER allows only one score per user. Merely listing three tables without primary keys or matching foreign keys leaves their relationships unclear.

Original question · Cambridge 9618/13

2. Normalise the ice-cream batch table

Cambridge 9618/13 · October/November 2024 · 4(c)(ii) · 4 marks

Selected parts: 4(c)(ii) [4].

Reading the question — teacher guidance

Use the repeated product facts in the sample rows. The question explicitly forbids changing CUSTOMER and SALE; only redesign BATCH and its new related table.

Solution / model answer — teacher-written
BATCH(BatchID, IceCreamID, EndDate)
  Primary key: BatchID
  Foreign key: IceCreamID references ICE_CREAM(IceCreamID)
ICE_CREAM(IceCreamID, Type, Flavour, Size, SellingPrice)
  Primary key: IceCreamID

The same product can be made in several batches. Its type, flavour, size and selling price belong in ICE_CREAM; the batch’s identifier and end date remain in BATCH. Each batch references the appropriate product.

Official mark scheme
Why this earns marks — teacher explanation

The four marks cover the new product table, its product fields, a suitable primary key and the matching foreign key in BATCH. The official table definitions are labelled examples rather than a complete example answer: explicitly identifying the keys completes the response.

Common mistakes — teacher analysis

EndDate is a batch fact. Moving it to ICE_CREAM would force all batches of the product to share one end date. Do not redesign the two excluded tables.

Lesson review

Summary

Model first

Extract entities and read each relationship in both directions.

Check 1NF then 2NF

Use atomic values, then separate facts that depend on only part of a composite key.

Check 3NF

Move facts that depend on another non-key attribute to the relation identified by that attribute.

Preserve the design

Record all primary and foreign keys and reconstruct an original example to check that no facts were lost.
