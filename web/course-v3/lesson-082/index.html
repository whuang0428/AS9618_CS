Core explanation

Efficient pseudocode avoids unnecessary operations while remaining correct and understandable. Look for repeated calculations, repeated tests with unchanged operands and avoidable traversals. Meaningful identifiers and indentation support review, but a shorter line count alone does not establish fewer operations.

In the example, Mark is read once and is not changed between two identical Mark >= 50 tests. The first test increments Count and the second displays Pass. Both operations can share one true branch. This reduces two comparisons to one for every run while retaining the action order and final count.

Worked example · Inspect the original repeated tests

  1. Pseudocode
    DECLARE Mark, Count : INTEGER
INPUT Mark
Count <- 0
IF Mark >= 50 THEN
    Count <- Count + 1
ENDIF
IF Mark >= 50 THEN
    OUTPUT "Pass"
ENDIF
OUTPUT Count
  2. Trace and check

    49 outputs only 0; 50 outputs Pass and then 1. Each run tests the same unchanged mark twice.

Common misconception

A repeated-looking expression is not redundant if its input has changed between evaluations.

Check your understanding

Which value must stay unchanged for these two tests to be combined?

Core explanation

Move both pass-only actions inside one IF Mark >= 50 block, keeping Count's initialisation before the decision and OUTPUT Count afterwards. A failed mark then skips both actions, just as in the original. A passing mark increments before displaying Pass, preserving the observable sequence.

Compare original and revised versions for below-boundary, boundary and above-boundary inputs. Check outputs and updated values, not merely whether execution finishes. Reusable functions can also centralise a rule such as ValidMark, but a function call is not automatically a speed improvement; measure the operation or duplication that the change actually removes.

Worked example · Use one decision for the shared actions

  1. Pseudocode
    DECLARE Mark, Count : INTEGER
INPUT Mark
Count <- 0
IF Mark >= 50 THEN
    Count <- Count + 1
    OUTPUT "Pass"
ENDIF
OUTPUT Count
  2. Trace and check

    The revised code preserves both output paths while evaluating the threshold once.

Common misconception

Moving OUTPUT Pass outside the IF would print it for failed marks.

Check your understanding

What specific work has the revised version removed?

Check your answer

One repeated comparison per execution.

Practice questions

Question 1 · Command word: Explain2 marks

Explain why the two Mark >= 50 tests in the supplied program are redundant, and state a condition under which combining them would be unsafe.

Use this complete program for the stated task.

DECLARE Mark, Count : INTEGER
INPUT Mark
Count <- 0
IF Mark >= 50 THEN
    Count <- Count + 1
ENDIF
IF Mark >= 50 THEN
    OUTPUT "Pass"
ENDIF
OUTPUT Count
S11.09.A01
Answer and marking points
  1. Mark is unchanged between the identical comparisons, so their truth values must agree.
  2. Combining would need reconsideration if intervening code changed Mark or the required order of effects.

Common error: Check state dependencies before removing a repeated condition.

Question 2 · Command word: Write3 marks

Write a revised version of the supplied repeated-test program to use one threshold comparison while preserving outputs. State the output for Mark 50.

Use this complete program for the stated task.

DECLARE Mark, Count : INTEGER
INPUT Mark
Count <- 0
IF Mark >= 50 THEN
    Count <- Count + 1
ENDIF
IF Mark >= 50 THEN
    OUTPUT "Pass"
ENDIF
OUTPUT Count
S11.09.A01
Answer and marking points

One valid pseudocode solution

DECLARE Mark, Count : INTEGER
INPUT Mark
Count <- 0
IF Mark >= 50 THEN
    Count <- Count + 1
    OUTPUT "Pass"
ENDIF
OUTPUT Count
  1. Put Count <- Count + 1 and OUTPUT "Pass" in the same true branch.
  2. Leave Count initialisation before the IF and final count output after it.
  3. Mark 50 outputs Pass and 1.

Common error: Preserve actions on both the passing and failing paths.

Question 3 · Command word: Explain2 marks

A loop computes Width * Height on every iteration although neither variable changes. Explain when the product can be calculated once before the loop and give the benefit.

S11.09.A01
Answer and marking points
  1. If the product is needed and both operands remain unchanged, calculate Area <- Width * Height before repetition and reuse Area.
  2. This avoids repeating the multiplication for each iteration.

Common error: Do not move a calculation ahead of inputs needed to evaluate it.

Question 1 · Command word: Describe · 3 marks

A program traverses the same 30 already stored marks once to find their total and again to count marks at least 50. Describe how one traversal can produce both results and state the reduction in element visits. Include the required initialisation.

Answer and marking points
  • Set Total and Passed to zero before traversal.
  • For each mark, add it to Total and increment Passed only if the mark is at least 50.
  • The visit count falls from 60 to 30 while both results are accumulated.

Common error: Do not reset accumulators inside the traversal.

Question 2 · Command word: Explain · 2 marks

A loop handles ten parcels. Inside it, Charge <- Weight * Rate uses the current parcel's Weight; Rate stays fixed. A proposed optimisation moves the full multiplication outside the loop. Explain why it is wrong and describe what could safely remain outside.

Answer and marking points
  • Weight changes between parcels, so one stored product would not give each parcel's correct charge.
  • Obtain or define the fixed Rate outside, but calculate Weight * Rate after reading each parcel's Weight.

Common error: A fixed multiplier does not make a changing product invariant.

Question 3 · Command word: Identify · 3 marks

A pupil replaces IF Mark >= 50 THEN Count <- Count + 1; OUTPUT "Pass" ENDIF with IF Mark > 50 THEN Count <- Count + 1 ENDIF followed by OUTPUT "Pass". Identify two behavioural changes and choose inputs that expose them.

Answer and marking points
  • Mark 50 no longer increments Count because >= was changed to >.
  • A failing value such as 49 now outputs Pass because the display moved outside the IF.
  • Testing 49 and 50 distinguishes the changed false path and changed boundary.

Common error: Reducing or rearranging statements must retain both conditions and side effects.
