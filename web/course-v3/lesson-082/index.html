Identify work whose result cannot have changed

Efficient pseudocode avoids unnecessary operations while remaining correct and understandable. Look for repeated calculations, repeated tests with unchanged operands and avoidable traversals. Meaningful identifiers and indentation support review, but a shorter line count alone does not establish fewer operations.

Make a specific improvement

Combine the pass-count increment and Pass output inside one IF Mark >= 50 block. Keep their order, keep Count initialisation before the branch and keep the final count output afterwards. The change removes one comparison, not either of the required actions.

Preserve behaviour before counting a benefit

If intervening code changed Mark, the two comparisons could have different results and could not simply be combined. Check data dependencies and output order before removing repeated-looking work. Tests below, at and above the boundary expose different possible mistakes, although a few passing tests are not a proof for every input.

Separate clarity, reuse and execution work

Meaningful names and indentation make code easier to inspect. Factoring repeated code into a procedure can improve maintenance. Fewer repeated comparisons, calculations or data visits can reduce computational work. These are related benefits, but they are not interchangeable measurements.

Worked example · Inspect the original repeated comparison

  1. Requirements and starting conditions

    Input one INTEGER Mark from 0 to 100. Count it if >= 50 and display Pass, then display Count.

  2. Cambridge pseudocode
    DECLARE Mark, Count : INTEGER
INPUT Mark
Count <- 0
IF Mark >= 50 THEN
    Count <- Count + 1
ENDIF
IF Mark >= 50 THEN
    OUTPUT "Pass"
ENDIF
OUTPUT Count
  3. Expected result

    49 outputs 0; 50 and 80 output Pass followed by 1. Mark is compared twice.

Worked example · Preserve the actions with one comparison

  1. Requirements and starting conditions

    Implement exactly the same input and output contract as the original.

  2. Cambridge pseudocode
    DECLARE Mark, Count : INTEGER
INPUT Mark
Count <- 0
IF Mark >= 50 THEN
    Count <- Count + 1
    OUTPUT "Pass"
ENDIF
OUTPUT Count
  3. Expected result

    The outputs and final Count match the original; one threshold comparison is performed instead of two.

Core explanation · Exam essentials

  • Remove repeated work only when its inputs and required effects permit it.
  • State the operation saved, then compare outputs, state and boundary behaviour.
Common misconception

A repeated-looking expression is not redundant if its input has changed between evaluations.

Reuse a calculation whose inputs do not change

Move an unchanged calculation outside repetition

A loop-invariant calculation has the same result on every iteration because its inputs remain unchanged. Reusing its result can avoid repeated work, provided the new placement preserves the program’s required behaviour.

Check whether Width * Height is loop-invariant

  1. Defined before entry: Width and Height are both read before the loop.
  2. Unchanged through repetition: Neither value is assigned or input inside the loop.
  3. Same required value: Each of the Count reports must show the same product.
  4. Safe placement: Calculate Area once after input, then reuse it for each output.

Count exactly what changes

The complete examples assume a positive integer Count and non-negative real dimensions. With Width 3, Height 4 and Count 3, both output 12 three times. The original multiplies three times; the revised program multiplies once. In general the multiplication count falls from N to 1 for positive N, while the N outputs remain.

Consider a skipped loop before moving work

If Count could be zero, the revised version would calculate an unused product once, while the original would not. Its output would still be empty for these valid operands, but the claim of saving work would not apply. If the moved expression could fail, evaluating it on a previously skipped path could also change behaviour.

Use a counterexample

A parcel program reads a new Weight on each iteration. Even with fixed Rate, Weight * Rate changes, so the full product must stay after that input. Only obtaining the fixed rate can remain outside. A constant multiplier does not make the whole expression invariant.

Worked example · Calculate the unchanged area on every iteration

  1. Requirements and starting conditions

    Input non-negative REAL Width and Height, then positive INTEGER Count. Output their product Count times.

  2. Cambridge pseudocode
    DECLARE Width, Height, Area : REAL
DECLARE Count, Index : INTEGER
INPUT Width
INPUT Height
INPUT Count
FOR Index <- 1 TO Count
    Area <- Width * Height
    OUTPUT Area
NEXT Index
  3. Expected result

    3, 4, 3 outputs 12 three times and performs three multiplications.

Worked example · Calculate once after input, then reuse

  1. Requirements and starting conditions

    Use the same positive-count and fixed-dimension contract.

  2. Cambridge pseudocode
    DECLARE Width, Height, Area : REAL
DECLARE Count, Index : INTEGER
INPUT Width
INPUT Height
INPUT Count
Area <- Width * Height
FOR Index <- 1 TO Count
    OUTPUT Area
NEXT Index
  3. Expected result

    3, 4, 3 still outputs 12 three times, with one multiplication. Count 1 also performs one multiplication in each version.

Core explanation · Exam essentials

  • Move a calculation only after its inputs are defined and when they remain unchanged.
  • Compare operation counts under stated input conditions, including any newly executed path.
Common misconception

One fixed operand does not make a calculation invariant when the other operand changes.

Check your understanding

May Weight * Rate move out of a loop that reads a new Weight for every parcel?

Check your answer

No. Fixed Rate does not make the changing Weight * Rate product invariant.

Accumulate independent results during one traversal

Two computations can share one traversal when both can use the same current element and neither needs the other’s completed result first. The total and pass count of a set of marks meet this condition.

Identify shared access without changing the data

The supplied programs first store five already valid marks, each from 0 to 100. One then traverses them to calculate Total and traverses again to count passes. The revised version reads one element into Mark, uses that value for both updates and continues. Both accumulators are initialised before the processing loop.

Define the work being counted

Count processing reads separately from the input stage, which is unchanged. The original reads five elements for the total and five for the count; the revised reads each once, giving 10 versus 5 reads. For 30 elements the same comparison is 60 versus 30. This does not establish that wall-clock runtime halves: input, output and other operations still exist.

Recognise a necessary second pass

Combine only computations whose dependencies allow it. Counting values greater than the final mean normally needs that mean first; it cannot use the still-changing partial mean as a substitute. A second pass over retained values is then meaningful work rather than redundant work.

Worked example · Compute two statistics in separate passes

  1. Requirements and starting conditions

    Input five INTEGER marks from 0 to 100, store them, then output their total and the count >= 50.

  2. Cambridge pseudocode
    DECLARE Marks : ARRAY[1:5] OF INTEGER
DECLARE Index, Total, Passed : INTEGER
FOR Index <- 1 TO 5
    INPUT Marks[Index]
NEXT Index
Total <- 0
Passed <- 0
FOR Index <- 1 TO 5
    Total <- Total + Marks[Index]
NEXT Index
FOR Index <- 1 TO 5
    IF Marks[Index] >= 50 THEN
        Passed <- Passed + 1
    ENDIF
NEXT Index
OUTPUT Total, Passed
  3. Expected result

    49, 50, 80, 21, 50 outputs 250 and 3. The processing passes read ten array elements in total.

Worked example · Reuse each element for both statistics

  1. Requirements and starting conditions

    Use the same five stored marks and output contract. Mark holds the current element for both updates.

  2. Cambridge pseudocode
    DECLARE Marks : ARRAY[1:5] OF INTEGER
DECLARE Index, Total, Passed, Mark : INTEGER
FOR Index <- 1 TO 5
    INPUT Marks[Index]
NEXT Index
Total <- 0
Passed <- 0
FOR Index <- 1 TO 5
    Mark <- Marks[Index]
    Total <- Total + Mark
    IF Mark >= 50 THEN
        Passed <- Passed + 1
    ENDIF
NEXT Index
OUTPUT Total, Passed
  3. Expected result

    The outputs remain 250 and 3, with five processing reads. Five zeros give 0 and 0; five 100s give 500 and 5 in both versions.

Core explanation · Exam essentials

  • One traversal can update independent results from the same element.
  • Initialise each accumulator once; preserve dependencies on results that are not yet available.
Common misconception

A second pass is necessary when its work depends on a result that must be completed first.

Check your understanding

Why can counting marks above the final mean require another pass?

Check your answer

The final mean is unknown until the total and count are complete; a partial mean is not equivalent.

Original question · Cambridge 9618/22

1. Find and fill the first unused loan record

Cambridge 9618/22 · October/November 2025 · 8(b) · 7 marks

Selected parts: 8(b) [7].

Reading the question — teacher guidance

Unused means StudentID is empty, not OnLoan is FALSE. Stop as soon as one unused record has been filled. Returned books still occupy historical records.

Solution / model answer — teacher-written
FUNCTION NewLoan(ThisStudentID : STRING, ThisBookID : STRING) RETURNS BOOLEAN
    DECLARE Index : INTEGER
    FOR Index ← 1 TO 7000
        IF Loan[Index].StudentID = "" THEN
            Loan[Index].StudentID ← ThisStudentID
            Loan[Index].BookID ← ThisBookID
            Loan[Index].OnLoan ← TRUE
            RETURN TRUE
        ENDIF
    NEXT Index
    RETURN FALSE
ENDFUNCTION

If slot 1 is unused, it is filled and the function returns immediately. If only slot 7000 is unused, the search reaches and fills it. With no unused slot, no record is changed and FALSE is returned.

Official mark scheme
Why this earns marks — teacher explanation

Seven points include the bounded search, early termination, indexed record notation, empty-ID test, the two identifier assignments, OnLoan = TRUE and correct Boolean returns. The official alternative explicitly permits RETURN inside a FOR loop.

Common mistakes — teacher analysis

Continuing after success fills multiple slots with the same loan. Testing OnLoan = FALSE would overwrite returned-loan history. Do not access Loan[7001] after an unsuccessful search.
