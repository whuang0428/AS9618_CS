Program a booking system · Concept 35

Combine a repeated unchanged decision

Observe

Repeated work

  • Test Seats >= 3; if TRUE, increment GroupCount.
  • Test Seats >= 3 again; if TRUE, display "Group booking".
  • Seats does not change between these tests.

Look, then discuss

If Seats has not changed, why test Seats >= 3 twice?

A group booking must increment GroupCount and display a group message. Both actions currently use the same unchanged threshold test.

Recall

Recall independent IF statements

Two separate IF conditions are evaluated independently. If their expression and all its inputs are unchanged, their truth values agree, but the order of their actions can still matter.

Explain

Explanation · 1 / 3

Identify the redundant operation precisely

The second identical comparison repeats a result already known for the same Seats value. The claim is about removing one comparison, not a measured execution-time percentage.

Explanation · 2 / 3

Keep both actions in the same selected block

Increment GroupCount, then output Group booking inside one IF. Keep the original order. A final output of GroupCount remains after ENDIF.

DECLARE Seats, GroupCount : INTEGER
INPUT Seats
GroupCount <- 0
IF Seats >= 3 THEN
    GroupCount <- GroupCount + 1
    OUTPUT "Group booking"
ENDIF
OUTPUT GroupCount

Explanation · 3 / 3

Check whether combining is safe

If intervening code changed Seats, the two original tests might differ. Moving an output outside the branch would change the false path. Reducing code length alone does not establish correctness.

Work together

Compare below, at and above the threshold

Test Seats 2, 3 and 4.

Work together · 1 / 2

Check the false path

Seats 2 must produce no group message and final count 0 in both versions.

Work together · 2 / 2

Check true paths and output order

Seats 3 and 4 must first display Group booking and then 1. The revised version uses one comparison instead of two while preserving these effects.

An efficiency claim should identify removed work and demonstrate preserved behaviour.

Check

Try it yourself · Teacher-written

Would replacing >= 3 with > 3 while combining the tests preserve the program?

Check your reasoning

No. Seats 3 would no longer increment the count or display the group message. The boundary rule would change.

Connect

Keep this idea

Combine repeated conditions only when their inputs and required action order permit it.

A calculation can also be reused if all of its operands stay fixed across repetition.

Calculate a fixed amount once

Observe

One booking, repeated copies

FactValueChanges between copies?
Seats3No
Price12.50No
Copies3Controls repetition

Look, then discuss

Should printing three identical copies of one receipt multiply Seats by Price three times?

One booking has three seats at 12.50. Printing several copies changes neither Seats nor Price, so every multiplication produces the same 37.5.

Recall

Recall a loop-invariant value

A calculation is invariant across a loop when its inputs remain unchanged, so it produces the same result each iteration. Check when the inputs become available before moving it.

Explain

Explanation · 1 / 3

Locate the unchanged operands

Seats and Price are read before the copy loop and remain fixed. Multiplying them inside every iteration performs avoidable repeated work.

Explanation · 2 / 3

Reuse the calculated result

Assign Cost <- Seats * Price before repetition, then OUTPUT Cost in each iteration. For a positive Copies count, this uses one multiplication instead of Copies multiplications while keeping every required receipt output.

DECLARE Seats, Copies, Index : INTEGER
DECLARE Price, Cost : REAL
INPUT Seats
INPUT Price
INPUT Copies
IF Copies > 0 THEN
    Cost <- Seats * Price
    FOR Index <- 1 TO Copies
        OUTPUT Cost
    NEXT Index
ENDIF

Explanation · 3 / 3

Check zero work and changing inputs

The guard avoids a new calculation when Copies is zero, matching an original zero-iteration loop. If each iteration instead reads a new Seats quantity, its charge changes and that multiplication must remain after the new input.

Work together

Count the work removed

Seat quantity is 3, price 12.50 and three copies are required.

Work together · 1 / 2

Compare calculation counts

The original body multiplies three times. The revised program multiplies once and reuses Cost, removing two multiplications.

Work together · 2 / 2

Compare observable results

Both produce three outputs of 37.5. Moving OUTPUT outside the loop would wrongly produce only one copy, even though it would reduce work further.

Reuse the value while retaining the number, order and conditions of required actions.

A parcel loop reads a different Weight each time but Rate stays fixed. May Weight * Rate move before the loop?

Check your reasoning

No. Weight changes, so the product is not invariant. The fixed Rate may be obtained before the loop, but each charge must use that parcel’s Weight.

Program a booking system · Concept 37

Collect independent results in one pass

Observe

One stored request list

Index12345
Seats31423

Look, then discuss

Can the desk total all requested seats and count group bookings during the same visit to each request?

Stored requests are 3, 1, 4, 2 and 3. Each current value is enough both to add its seats and to decide whether it is a group of at least three.

Recall

Recall a complete array traversal

A FOR loop visits each permitted index. Accumulators are initialised before the loop. Different results may use the same current value without waiting for the other’s final result.

Explain

Explanation · 1 / 3

Identify the two original passes

One pass adds all seat quantities; another counts values at least 3. For five entries, these perform ten element visits during analysis, after the input phase.

Explanation · 2 / 3

Update both results for each current value

Read Requests[Index] into Seats once, add Seats to Total and increment GroupCount when Seats >= 3. Both accumulators begin at 0.

DECLARE Requests : ARRAY[1:5] OF INTEGER
DECLARE Index, Seats, Total, GroupCount : INTEGER
FOR Index <- 1 TO 5
    INPUT Requests[Index]
NEXT Index
Total <- 0
GroupCount <- 0
FOR Index <- 1 TO 5
    Seats <- Requests[Index]
    Total <- Total + Seats
    IF Seats >= 3 THEN
        GroupCount <- GroupCount + 1
    ENDIF
NEXT Index
OUTPUT Total, GroupCount

Explanation · 3 / 3

Check for a dependency on a completed result

Counting requests above the final mean is different: the final mean is unknown until the total and count are complete. A running mean is not a substitute for the final mean, so merging those calculations naively changes the rule.

Work together

Trace two accumulators without extra visits

Use stored requests 3, 1, 4, 2, 3.

Work together · 1 / 2

Follow Total and GroupCount

Their states after each request are (3,1), (4,1), (8,2), (10,2) and (13,3).

Work together · 2 / 2

State the reduction accurately

The analysis uses five element reads rather than ten, while still computing total 13 and group count 3. The five earlier input writes are unchanged.

Share a pass when both results depend only on available current data and preserved state.

Check

Try it yourself · Teacher-written

Two independent analyses traverse 30 elements each. If they can share a pass, how many analysis visits are removed?

Check your reasoning

Thirty visits are removed: the count falls from 60 to 30. This is an operation count, not a claim that the entire program takes exactly half the time.

Connect

Keep this idea

Count the specific work removed and verify that neither result requires the other’s completed value first.

One valid Cambridge pseudocode solution

DECLARE Count, Index : INTEGER
INPUT Width
INPUT Height
INPUT Count
Area <- Width * Height

Answer and checking points — teacher-written

One valid Cambridge pseudocode solution

DECLARE Marks : ARRAY[1:5] OF INTEGER
DECLARE Index, Total, Passed, Mark : INTEGER
FOR Index <- 1 TO 5
    INPUT Marks[Index]
NEXT Index
Total <- 0
Passed <- 0
FOR Index <- 1 TO 5
    Mark <- Marks[Index]
    Total <- Total + Mark
    IF Mark >= 50 THEN
        Passed <- Passed + 1
    ENDIF
NEXT Index
OUTPUT Total, Passed
  1. Keep the input loop and initialise Total and Passed to zero before processing.
  2. In one loop assign Mark <- Marks[Index], add Mark to Total, and increment Passed only for Mark >= 50.
  3. Output both after the loop: Total 250 and Passed 3.
  4. The original processing reads ten elements; the revised processing reads five, reusing Mark for the two operations.

Common error: Resetting an accumulator inside processing would discard earlier elements.
