Stepwise refinement to programmable detail

Expand a high-level task through successive levels until every leaf operation can be implemented.

What decision would a programmer still have to invent at the current level of detail?

Before you start

Is 'work out the average' ready to program if neither the number of values nor the calculation has been specified?

Check your answer

No. The input count, accumulation and divisor must be defined.

01

Expand the unresolved operations

S9.08.A01

Visual overview

Core explanation

Expand a high-level solution
  1. Start from the result: Name the required outcome and its preconditions.
  2. Expand an unresolved step: Replace it with operations that achieve the same result.
  3. Continue to programmable detail: Stop when no remaining action requires the programmer to invent a missing rule.
Add rules, not just headings

Decomposition identifies smaller sub-problems; refinement develops the internal detail of a solution. For an average, specify how inputs are read, how Total is updated and when division happens. For the diagram’s algorithm, N must be positive.

Refine one unfinished leaf at a time

  1. InspectFind a step whose rule or order is still unspecified.
  2. ExpandReplace it with enough smaller operations to perform that task.
  3. ReconnectKeep the surrounding inputs, dependencies and outputs consistent.
  4. StopCheck that every leaf has an implementable operation and stated conditions.
Common misconception

Adding more headings is not refinement if the same unknown calculations remain hidden.

Check your understanding

Which leaf still needs refinement: Total <- Total + Score or process the scores?

Check your answer

Process the scores, because it does not define the required processing.

Core explanation

Stop only when the actions are programmable

A useful endpoint states the inputs, initial values, arithmetic, decisions, repetition and outputs required by the task. A programmer should be able to translate the resulting pseudocode directly. The refinement must preserve the original requirement at every level.

Resolve the example’s missing rules

Check the final version with concrete data. For three-score averaging, reading all three values and dividing once by three distinguishes the intended mean from a running sum, a last-value calculation or an off-by-one loop. Assumptions about permitted input types and ranges should be stated separately from unfinished operations.

Worked example · The final refined algorithm

  1. Requirements

    Read exactly three integer scores and output their arithmetic mean.

  2. Pseudocode
    DECLARE Index : INTEGER
DECLARE Score : INTEGER
DECLARE Total : INTEGER
DECLARE Average : REAL
Total <- 0
FOR Index <- 1 TO 3
    INPUT Score
    Total <- Total + Score
NEXT Index
Average <- Total / 3
OUTPUT Average
  3. Check

    6, 8 and 10 give Total 24 and Average 8; three zeroes give Average 0.

Common misconception

A leaf called calculate mean remains too vague when the task asks for the level of detail from which it may be programmed.

Check your understanding

Why check an all-zero set as well as mixed values?

Check your answer

It checks that initialisation and accumulation do not introduce an unintended non-zero amount.

Practice questions

Question 1 · Command word: Develop4 marks

Develop successive refinements of 'calculate the total cost of four entered prices' through one intermediate level to programmable operations. State where the total is initialised and output.

S9.08.A01
Answer and marking points
  1. An intermediate level separates obtaining prices, accumulating their sum and reporting it.
  2. Set Total to 0 before processing any price.
  3. Repeat INPUT Price and Total <- Total + Price exactly four times.
  4. OUTPUT Total occurs after the repetition.

Common error: Give actual operations at the final level, not another vague heading.

Question 2 · Command word: Develop4 marks

A taxi charges 5.00 for up to and including 3 km, plus 2.00 for each kilometre beyond 3. Develop fare calculation into complete pseudocode for a non-negative distance, allowing fractional kilometres.

S9.08.A01
Answer and marking points

One valid pseudocode solution

DECLARE Distance : REAL
DECLARE Fare : REAL
INPUT Distance
IF Distance <= 3 THEN
    Fare <- 5.00
ELSE
    Fare <- 5.00 + (Distance - 3) * 2.00
ENDIF
OUTPUT Fare
  1. Input Distance using a type that allows fractions.
  2. Test Distance <= 3.
  3. Use Fare <- 5 on the true path and Fare <- 5 + (Distance - 3) * 2 on the other.
  4. Output Fare after the decision.

Common error: Only the distance beyond 3 incurs the extra rate.

Question 3 · Command word: Identify2 marks

An intermediate design reads three marks and says 'find and show their mean'. Identify two unresolved operations and replace each with an explicit step.

S9.08.A01
Answer and marking points
  1. The calculation is unresolved: assign Mean <- (Mark1 + Mark2 + Mark3) / 3.
  2. The reporting operation is unresolved: OUTPUT Mean.

Common error: Retain the stated three inputs and arithmetic mean.

Question 1 · Command word: Develop · 4 marks

Develop successive refinements of 'process a badge order', giving an intermediate IPO outline and then explicit pseudocode. A badge costs 2.20 and every order has a fixed handling charge of 1.50. Assume a positive integer quantity and output only the amount due.

Answer and marking points
  • The outline identifies quantity input, amount calculation and amount output.
  • INPUT Quantity obtains the order size.
  • AmountDue <- Quantity * 2.20 + 1.50 defines the complete rule.
  • OUTPUT AmountDue presents the required result.

Common error: Charge handling once per order rather than once per badge.

Question 2 · Command word: Explain · 4 marks

A rainfall algorithm must read five non-negative daily amounts and output their total. Its refinement currently says 'repeat input, add rain, display total'. Explain two missing details and give the corrected final sequence.

Answer and marking points
  • The total needs an initial value of zero before any addition.
  • The repetition count and placement of the final output must be explicit.
  • Set Total <- 0, then repeat INPUT Rain and Total <- Total + Rain exactly five times.
  • OUTPUT Total follows the completed loop.

Common error: A final five-day total should not be displayed inside every iteration.

Question 3 · Command word: Explain · 3 marks

Explain why replacing 'calculate delivery charge' with 'calculate the correct delivery charge' is insufficient refinement. For a rule of 4.00 up to and including 2 kg and 6.50 above 2 kg, give the missing decision and branch assignments.

Answer and marking points
  • The replacement still gives no operations that implement the charge rule.
  • The condition is Mass <= 2.
  • The true branch assigns Charge <- 4.00 and the false branch assigns Charge <- 6.50.

Common error: A more emphatic adjective adds no programmable detail.

Lesson review

Summary

Refine repeatedly

Expand unfinished operations until their rules and order are explicit.

Preserve the task

Each expansion must still implement the original requirements.

Reach an endpoint

Complete pseudocode and a trace show whether the final detail is sufficient to program.
