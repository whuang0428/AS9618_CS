Design a ticket system · Concept 17

Refine an unfinished step into programmable actions

Observe

One unfinished leaf

  • High-level step: complete payment
  • Known values: Quantity, PlacesLeft, Total
  • New input required: Paid
  • Success and failure must have different effects

Look, then discuss

When has “complete the payment” become detailed enough for a programmer?

A plan says “check request; calculate charge; complete payment”. Those are useful responsibilities, but the last step does not yet say when to confirm, calculate change or change the available places.

Recall

Decomposition and refinement answer different questions

Decomposition identifies smaller responsibilities. Stepwise refinement adds the internal detail of a chosen step while preserving its purpose. We already know the statements and conditions needed to express that detail.

Explain

Explanation · 1 / 4

State the result before expanding

CompletePayment must either confirm a sufficiently paid sale or reject underpayment. Keep this result visible so that each expansion serves the same purpose rather than adding unrelated features.

Explanation · 2 / 4

Replace a broad action with smaller actions

Expand the step into obtain payment, compare it with Total, perform successful-sale updates or report failure. This first expansion exposes the decision but still leaves arithmetic to define.

Explanation · 3 / 4

Continue until the rules are explicit

On success, Change ← Paid - Total and PlacesLeft ← PlacesLeft - Quantity provide the missing calculations. On failure, display insufficient payment and leave PlacesLeft unchanged. Use Paid >= Total to include exact payment.

Explanation · 4 / 4

Check the endpoint against examples

A leaf such as “process payment correctly” is still unresolved. A comparison, assignment or output with defined operands can be programmed. Trace exact payment and underpayment to check that the refined version preserves the parent task.

Work together

Refine a selected-number total in words

Read exactly four INTEGER values and total only those from 30 to 70 inclusive. This smaller teaching task prepares the control structure used by E072.

Work together · 1 / 3

Write the high-level outline

Obtain the values, decide which qualify, accumulate their contributions and report the total. This describes the jobs but does not yet state initial values, loop count or the complete condition.

Work together · 2 / 3

Resolve each unfinished detail

Set Total to zero. Read the next value. If it is at least 30 and at most 70, add it to Total. Repeat the reading and decision until four values have been input. Output Total afterwards.

Work together · 3 / 3

Test the finished refinement

For 29, 30, 70, 71, only 30 and 70 contribute, giving 100. Read all four inputs even though two are rejected. For E072, apply its stated count and requested five-step response in words.

A final refinement states enough detail for implementation without requiring invented rules.

Try it yourself · Teacher-written

Refine “calculate the ticket total” through an intermediate level to programmable operations. Use fixed price 25.00 and a 10% student discount.

Check your reasoning

Intermediate: obtain Quantity and Student; calculate the undiscounted amount; select the final amount; display it. Final: INPUT Quantity; INPUT Student; Subtotal ← Quantity * 25.00; IF Student THEN Total ← Subtotal * 0.90 ELSE Total ← Subtotal ENDIF; OUTPUT Total. Declare suitable variables and assume a positive available quantity.

Take it further · Optional challenge

A refinement says “repeat input; add qualifying values; display total”. Name four details it must resolve.

Check the challenge

State the initial total; the exact repetition count or stopping rule; the full qualifying condition; and whether the total is displayed inside or after the loop. Also ensure each repetition reads a new value.

Original question · Cambridge 9618/21

1. Refine a fixed-input algorithm in words

Cambridge 9618/21 · October/November 2023 · 2(a) · 5 marks

Selected parts: 2(a) [5].

Hint — reading the question

The answer must have five steps in words, not pseudocode statements. Include both boundaries and produce one output after all inputs.

Reasoning and model answer — teacher-written

1. Set the running total to zero.

2. Input the next number.

3. If this number is at least 30 and at most 70, add it to the running total.

4. Repeat steps 2 and 3 until exactly 100 numbers have been input.

5. Output the final total.

Official mark scheme
Why this earns marks — teacher explanation

The official scheme lists six marking points but caps the result at five. The third step combines the condition and addition. The paper says numbers; use inclusive comparisons so fractional numbers near the boundaries are handled correctly, rather than relying on an integer-only shortcut.

Common mistakes — teacher analysis

“Repeat 100 times” after processing one input can imply 101 inputs. “Between” without stating inclusive endpoints can obscure whether 30 and 70 are accepted.

Question 1 · Command word: Develop4 teacher marks

Develop successive refinements of 'calculate the total cost of four entered prices' through one intermediate level to programmable operations. State where the total is initialised and output.

S9.08.A01
Answer and checking points — teacher-written
  1. An intermediate level separates obtaining prices, accumulating their sum and reporting it.
  2. Set Total to 0 before processing any price.
  3. Repeat INPUT Price and Total <- Total + Price exactly four times.
  4. OUTPUT Total occurs after the repetition.

Common error: Give actual operations at the final level, not another vague heading.

Question 2 · Command word: Develop4 teacher marks

A taxi charges 5.00 for up to and including 3 km, plus 2.00 for each kilometre beyond 3. Develop fare calculation into complete pseudocode for a non-negative distance, allowing fractional kilometres.

S9.08.A01
Answer and checking points — teacher-written

One valid pseudocode solution

DECLARE Distance : REAL
DECLARE Fare : REAL
INPUT Distance
IF Distance <= 3 THEN
    Fare <- 5.00
ELSE
    Fare <- 5.00 + (Distance - 3) * 2.00
ENDIF
OUTPUT Fare
  1. Input Distance using a type that allows fractions.
  2. Test Distance <= 3.
  3. Use Fare <- 5 on the true path and Fare <- 5 + (Distance - 3) * 2 on the other.
  4. Output Fare after the decision.

Common error: Only the distance beyond 3 incurs the extra rate.

Question 3 · Command word: Identify2 teacher marks

An intermediate design reads three marks and says 'find and show their mean'. Identify two unresolved operations and replace each with an explicit step.

S9.08.A01
Answer and checking points — teacher-written
  1. The calculation is unresolved: assign Mean <- (Mark1 + Mark2 + Mark3) / 3.
  2. The reporting operation is unresolved: OUTPUT Mean.

Common error: Retain the stated three inputs and arithmetic mean.
