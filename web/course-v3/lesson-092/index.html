Analysing and amending an existing program

Trace an existing program, add a requested feature and test both new and preserved behaviour.

Where should the new behaviour be added so the original result stays correct?

Before you start

A program already counts passing marks. If a new merit count is needed, must the pass count be removed?

Check your answer

No. Retain the original result and add the new counter and condition unless the new requirement explicitly replaces the old one.

Core explanation

Read the existing program and state its purpose, inputs, outputs, data and control flow. Identify assumptions and trace representative inputs so you know what the current result means. Then compare the new requirement with that behaviour to locate where extra data or processing belongs.

The supplied program reads four already validated integer marks from 0 to 100 and counts those at least 50. PassCount is initialised once before the loop, updated inside the selection and output after all four inputs. The requested enhancement is to output an additional MeritCount for marks at least 70 while preserving the original pass count.

Worked example · Understand the original mark counter

  1. Requirement

    Four valid marks are supplied. The new requirement has not yet been implemented.

  2. Pseudocode
    DECLARE Index : INTEGER
DECLARE Mark : INTEGER
DECLARE PassCount : INTEGER
PassCount <- 0
FOR Index <- 1 TO 4
    INPUT Mark
    IF Mark >= 50 THEN
        PassCount <- PassCount + 1
    ENDIF
NEXT Index
OUTPUT PassCount
  3. Expected result

    For 49, 50, 69 and 70, the original output is 3.

Common misconception

A description of the new feature is not analysis of what the existing statements do.

Check your understanding

Why does MeritCount need to be initialised before the loop?

Check your answer

The count must accumulate across all four marks rather than restart at each input.

Core explanation

Add the declaration, initialisation, update and output needed for the new feature. The merit condition belongs inside the same traversal, after each Mark is obtained. A mark of 70 qualifies for both counts, so use two independent selections; an ELSE branch between them would make the categories mutually exclusive.

Keep the old pass comparison and output unless the request explicitly changes them. A focused amendment is easier to explain and test than an unrelated rewrite. The complete amended program below allows both counts to be compared with the original behaviour for the same input sequence.

Worked example · Add merit counting without losing passes

  1. Requirement

    In addition to PassCount, count marks of at least 70 and output MeritCount after PassCount.

  2. Pseudocode
    DECLARE Index : INTEGER
DECLARE Mark : INTEGER
DECLARE PassCount : INTEGER
DECLARE MeritCount : INTEGER
PassCount <- 0
MeritCount <- 0
FOR Index <- 1 TO 4
    INPUT Mark
    IF Mark >= 50 THEN
        PassCount <- PassCount + 1
    ENDIF
    IF Mark >= 70 THEN
        MeritCount <- MeritCount + 1
    ENDIF
NEXT Index
OUTPUT PassCount
OUTPUT MeritCount
  3. Expected result

    49, 50, 69, 70 → PassCount 3, MeritCount 1; 70, 80, 90, 100 → 4 and 4.

Common misconception

Merit is a subset of passing marks here, not an alternative to passing.

Check your understanding

What would ELSE IF Mark >= 70 after IF Mark >= 50 do?

Check your answer

It would never count merits because every merit mark has already taken the pass branch.

Core explanation

Test the new decision with values that exercise its boundary and both outcomes. Also repeat cases that protect the original decision. For this example 69 and 70 distinguish the merit threshold, while 49 and 50 protect the pass threshold. Compute both expected counts before executing the amended program.

Test collections of inputs as well as one isolated value. All marks below 50 must leave both counters zero; four merit marks must increment both counters four times. Such cases expose misplaced initialisation, missing increments and incorrect mutual exclusion. Record the amended outputs alongside the original output so preservation is explicit.

Common misconception

Testing only the new feature can miss damage to the original output.

Check your understanding

Which all-merit run catches accidental exclusive branches?

Check your answer

70, 80, 90, 100 must produce both PassCount 4 and MeritCount 4.

S12.09.A01
Answer and marking points
  1. It reads four already valid integer marks and counts those at least 50.
  2. The count is initialised outside the loop and incremented for each qualifying mark.
  3. It outputs the final count 3 after the traversal.

S12.09.A01
Answer and marking points

One valid pseudocode solution

DECLARE Index : INTEGER
DECLARE Mark : INTEGER
DECLARE PassCount : INTEGER
DECLARE MeritCount : INTEGER
PassCount <- 0
MeritCount <- 0
FOR Index <- 1 TO 4
    INPUT Mark
    IF Mark >= 50 THEN
        PassCount <- PassCount + 1
    ENDIF
    IF Mark >= 70 THEN
        MeritCount <- MeritCount + 1
    ENDIF
NEXT Index
OUTPUT PassCount
OUTPUT MeritCount
  1. MeritCount is declared INTEGER.
  2. It is initialised to zero before the loop.
  3. An independent IF Mark >= 70 increments it inside the loop.
  4. The existing pass rule and accumulation remain in place.
  5. Both final counters are output after the loop and all constructs close.

Common error: Do not use ELSE to separate merit and pass categories.

Question 3 · Command word: State3 marks

State the expected outputs of the amended program for 49, 50, 69, 70 and for 70, 80, 90, 100. Explain the purpose of each set.

S12.09.A01
Answer and marking points
  1. The first set produces PassCount 3 and MeritCount 1.
  2. It tests both decisions at their two boundaries.
  3. The second produces 4 and 4 and checks that a mark can contribute to both totals.

Common error: A merit mark must still count as a pass.

Question 4 · Command word: Explain2 marks

Explain why placing MeritCount <- 0 immediately after INPUT Mark would be a defect in the enhancement, using four marks of 70.

S12.09.A01
Answer and marking points
  1. Each iteration would erase the merit count from earlier inputs.
  2. After the last mark the merit count would be 1 instead of the expected 4.

Common error: A correct condition cannot compensate for resetting the accumulated value.

Question 1 · Command word: Write · 5 marks

Write an amendment to the supplied rainfall program. Preserve the total rainfall and add WetDays, counting inputs greater than zero. Inputs are three non-negative REAL values. Output Total followed by WetDays, and state the outputs for 0, 2.0, 0.5.

Use the stated input assumptions and this program.

DECLARE Day : INTEGER
DECLARE Rain : REAL
DECLARE Total : REAL
Total <- 0.0
FOR Day <- 1 TO 3
    INPUT Rain
    Total <- Total + Rain
NEXT Day
OUTPUT Total
Answer and marking points

One valid pseudocode solution

DECLARE Day : INTEGER
DECLARE Rain : REAL
DECLARE Total : REAL
DECLARE WetDays : INTEGER
Total <- 0.0
WetDays <- 0
FOR Day <- 1 TO 3
    INPUT Rain
    Total <- Total + Rain
    IF Rain > 0.0 THEN
        WetDays <- WetDays + 1
    ENDIF
NEXT Day
OUTPUT Total
OUTPUT WetDays
  • Declare WetDays as INTEGER and initialise it once to zero.
  • Inside the existing loop, increment WetDays only when Rain > 0.0.
  • Preserve Total <- Total + Rain for every input.
  • Output WetDays after Total and close the constructs correctly.
  • The specified inputs produce 2.5 followed by 2.

Common error: A day with zero rain must not be counted as wet.

Question 2 · Command word: Write · 4 marks

The supplied parcel program counts masses from 2 to 5 kg inclusive. Write an amendment that also counts and outputs Rejected after Accepted, preserving the four-input traversal. State the outputs for 1.9, 2, 5, 5.1.

Use the stated input assumptions and this program.

DECLARE Index : INTEGER
DECLARE Mass : REAL
DECLARE Accepted : INTEGER
Accepted <- 0
FOR Index <- 1 TO 4
    INPUT Mass
    IF (Mass >= 2.0) AND (Mass <= 5.0) THEN
        Accepted <- Accepted + 1
    ENDIF
NEXT Index
OUTPUT Accepted
Answer and marking points

One valid pseudocode solution

DECLARE Index : INTEGER
DECLARE Mass : REAL
DECLARE Accepted : INTEGER
DECLARE Rejected : INTEGER
Accepted <- 0
Rejected <- 0
FOR Index <- 1 TO 4
    INPUT Mass
    IF (Mass >= 2.0) AND (Mass <= 5.0) THEN
        Accepted <- Accepted + 1
    ELSE
        Rejected <- Rejected + 1
    ENDIF
NEXT Index
OUTPUT Accepted
OUTPUT Rejected
  • Declare an INTEGER Rejected and initialise it before the loop.
  • Increment Rejected on the existing selection's ELSE branch.
  • Keep the inclusive acceptance condition and its increment.
  • Output both totals after processing all inputs; the stated case gives 2 and 2.

Common error: Rejected is the complement of accepted here, so ELSE is appropriate.

Question 3 · Command word: Explain · 4 marks

Explain how to verify that the enhanced rainfall program adds wet-day counting without damaging total rainfall. Give two three-day datasets and expected results that distinguish zero-rain and all-wet cases.

Answer and marking points
  • For 0, 0, 0, the expected total is 0 and wet-day count is 0.
  • For 1, 2, 3, the expected total is 6 and wet-day count is 3.
  • Compare the enhanced totals with the original program's totals for the same datasets.
  • The differing wet-day results exercise the new decision while the total comparisons check preserved behaviour.

Common error: State both outputs and connect the old-output check to regression testing.
