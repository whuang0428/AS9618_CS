Analysing and amending an existing program

Trace an existing program, add a requested feature and test both new and preserved behaviour.

Where should the new behaviour be added so the original result stays correct?

Before you start

A program already counts passing marks. If a new merit count is needed, must the pass count be removed?

Check your answer

No. Retain the original result and add the new counter and condition unless the new requirement explicitly replaces the old one.

Establish the original contract

Analyse the current program before designing the amendment. State its purpose, inputs, outputs, assumptions and changing data. Trace representative inputs and identify which statements initialise, update and report each result. This establishes the behaviour that a new request may need to preserve.

Locate the proposed change in the old flow

The mark program reads four already validated INTEGER marks in 0–100 and counts those at least 50. PassCount starts at zero before the loop, increments inside the pass branch, and is output after all four inputs. For 49, 50, 69 and 70 the output is 3. Adding a merit count changes the reported information without replacing this pass rule.

Make preservation explicit

A useful impact list names the data declaration, initialisation, update condition and output affected by the extra count. It also names what stays: four input visits, the valid-mark assumption, the existing threshold and the position of the original output. The new requirement alone is not a description of the old program.

Worked example · Understand the original mark counter

  1. Requirement

    Four valid marks are supplied. The new requirement has not yet been implemented.

  2. Pseudocode
    DECLARE Index : INTEGER
DECLARE Mark : INTEGER
DECLARE PassCount : INTEGER
PassCount <- 0
FOR Index <- 1 TO 4
    INPUT Mark
    IF Mark >= 50 THEN
        PassCount <- PassCount + 1
    ENDIF
NEXT Index
OUTPUT PassCount
  3. Expected result

    For 49, 50, 69 and 70, the original output is 3.

Core explanation · Exam essentials

  • Describe and trace the supplied program before amending it.
  • Identify affected data and operations, and state which existing behaviours must remain.
Common misconception

A description of the new feature is not analysis of what the existing statements do.

Check your understanding

Why does MeritCount need to be initialised before the loop?

Check your answer

The count must accumulate across all four marks rather than restart at each input.

Amend all affected parts coherently

S12.09.A01

Visual overview

Make every part of the amendment agree

MeritCount needs an INTEGER declaration, zero initialisation before the loop, an update after each input and a final output. Every merit mark is also a pass, so Mark >= 70 must be tested independently of the pass selection. ELSE would make the categories exclusive and lose one required count.

Check placement as well as the condition

Moving MeritCount <- 0 inside the loop erases prior updates; placing its final OUTPUT inside the loop reports intermediate values. Keeping the original pass comparison while adding the new condition is a focused amendment. An unrelated rewrite creates more behaviour to inspect without helping this request.

Transfer the reasoning to a different relationship

The parcel exercise uses a different relationship: rejected is the complement of accepted, so ELSE is appropriate there. The rainfall exercise preserves a total while counting positive days. Select control flow from the category relationship, not by mechanically copying the two-IF pattern.

Worked example · Add merit counting without losing passes

  1. Requirement

    In addition to PassCount, count marks of at least 70 and output MeritCount after PassCount.

  2. Pseudocode
    DECLARE Index : INTEGER
DECLARE Mark : INTEGER
DECLARE PassCount : INTEGER
DECLARE MeritCount : INTEGER
PassCount <- 0
MeritCount <- 0
FOR Index <- 1 TO 4
    INPUT Mark
    IF Mark >= 50 THEN
        PassCount <- PassCount + 1
    ENDIF
    IF Mark >= 70 THEN
        MeritCount <- MeritCount + 1
    ENDIF
NEXT Index
OUTPUT PassCount
OUTPUT MeritCount
  3. Expected result

    49, 50, 69, 70 → PassCount 3, MeritCount 1; 70, 80, 90, 100 → 4 and 4.

Core explanation · Exam essentials

  • Update declaration, initialisation, processing and output coherently.
  • Overlapping categories need independent updates; complementary categories can use ELSE.
Common misconception

Merit is a subset of passing marks here, not an alternative to passing.

Check your understanding

What would ELSE IF Mark >= 70 after IF Mark >= 50 do?

Check your answer

It would never count merits because every merit mark has already taken the pass branch.

Test old and new responsibilities

Derive both expected outputs before running or tracing the enhanced program. 49 and 50 challenge the old pass boundary; 69 and 70 challenge the new merit boundary. Four zeros must leave both counts at zero. Four merit marks must produce both counts as four, which exposes accidental exclusive branching.

Choose a case that would fail under the wrong amendment

Compare complete input sets, not only a single qualifying mark. Resetting a counter inside the loop may still give the right result when the only merit is the final value. The all-merit run reveals the lost earlier increments. State which potential mistake each dataset distinguishes.

Carry verification into changed requirements

For the added merit feature, the original PassCount must remain identical for the same four marks. The next interface change deliberately allows a different pass rule, so preservation must be tested under the old threshold while changed-threshold expectations come from the new requirement. A changed output is not automatically a regression.

Core explanation · Exam essentials

  • Check new boundaries and relevant old behaviour with independently expected results.
  • Use datasets that reveal misplaced initialisation, missing updates and incorrect exclusivity.
Common misconception

Testing only the new feature can miss damage to the original output.

Check your understanding

Which all-merit run catches accidental exclusive branches?

Check your answer

70, 80, 90, 100 must produce both PassCount 4 and MeritCount 4.

04

Change a function interface and its callers

S12.09.A01

Visual overview

Change the function contract deliberately

The existing modular program uses IsPass(Mark), which compares against 50. The enhancement lets the user choose PassMark once before the four marks. PassMark and every Mark are already validated INTEGER values from 0 to 100. The function becomes IsPass(Mark, PassMark), still returning BOOLEAN; main still counts four marks and prints one final count.

Explain why a coordinated change is necessary

If main reads PassMark inside the loop, it changes the required input sequence and can apply different thresholds to different marks. If a call is left with one argument, it no longer matches the header. If the arguments are reversed, their types still match but the comparison answers the wrong question. These are interface faults that adding a counter alone does not exercise.

Worked example · Analyse the original modular pass counter

  1. Requirements and initial conditions

    Input four validated INTEGER marks from 0 to 100. IsPass uses the fixed threshold 50.

  2. Cambridge pseudocode
    FUNCTION IsPass(Mark : INTEGER) RETURNS BOOLEAN
    RETURN Mark >= 50
ENDFUNCTION

DECLARE Index : INTEGER
DECLARE Mark : INTEGER
DECLARE PassCount : INTEGER
PassCount <- 0
FOR Index <- 1 TO 4
    INPUT Mark
    IF IsPass(Mark) THEN
        PassCount <- PassCount + 1
    ENDIF
NEXT Index
OUTPUT PassCount
  3. Expected result and checks

    49, 50, 69, 70 produces 3. Trace which data cross the one-parameter interface.

Worked example · Implement the new two-parameter interface

  1. Requirements and initial conditions

    Read INTEGER PassMark in 0–100 once, followed by four validated marks in 0–100. Count marks >= PassMark and output one final count.

  2. Cambridge pseudocode
    FUNCTION IsPass(Mark : INTEGER, PassMark : INTEGER) RETURNS BOOLEAN
    RETURN Mark >= PassMark
ENDFUNCTION

DECLARE Index : INTEGER
DECLARE Mark : INTEGER
DECLARE PassCount : INTEGER
DECLARE PassMark : INTEGER
INPUT PassMark
PassCount <- 0
FOR Index <- 1 TO 4
    INPUT Mark
    IF IsPass(Mark, PassMark) THEN
        PassCount <- PassCount + 1
    ENDIF
NEXT Index
OUTPUT PassCount
  3. Expected result and checks

    50, 49, 50, 69, 70 produces 3; 60, 49, 50, 69, 70 produces 2; 60, 59, 60, 61, 0 produces 2.

Core explanation · Exam essentials

  • Update the header, implementation, every call, input contract and tests together.
  • Use the original parameter value for compatibility and changed values for the new requirement.

Common misconception

Matching data types alone does not make reversed arguments correct.

Check your understanding

Why must the first input in the revised fixture be the threshold?

Check your answer

The revised program reads PassMark before the four marks; leaving it out shifts every later input into the wrong role.

        MeritCount <- MeritCount + 1
    ENDIF
NEXT Index

  1. MeritCount is declared INTEGER.
  2. It is initialised to zero before the loop.
  3. An independent IF Mark >= 70 increments it inside the loop.
  4. The existing pass rule and accumulation remain in place.
  5. Both final counters are output after the loop and all constructs close.

Original question · Cambridge 9618/22

1. Redesign a record format when separators can occur in data

Cambridge 9618/22 · October/November 2025 · 3(c) · 3 marks

Selected parts: 3(c) [3].

Original insert · reference material

Reading the question — teacher guidance

The encrypted fields may contain any separator you choose. Their maximum length of 99 makes a fixed two-digit length prefix sufficient for each field. Preserve one physical record line as required.

Solution / model answer — teacher-written

Add a separator after the original email field to identify where the new section begins. Calculate the length of each encrypted item and write it as a fixed-width two-digit decimal string immediately before that item. Read the first two digits, then exactly that many characters, then repeat for the next item.

Teacher example with invented encrypted data:
AB1234\Freddie Jones\FreddieJ909@Cambridge.org\03A\B02xy

After the email separator, 03 means read the next three characters A, backslash, B. The following 02 means read x and y. The embedded backslash is data because the length determines the boundary. If “any character” includes a line break, encode it before writing and measure the encoded representation consistently so the record remains on one line; the printed examples use visible characters.

Official mark scheme
Why this earns marks — teacher explanation

The scheme lists four points with a maximum of three: boundary after the third original field, length calculation, stored lengths, and a fixed-width or separated representation of the lengths.

Common mistakes — teacher analysis

Picking a different delimiter does not solve “any character”. An unseparated variable-width length is itself ambiguous. Document whether lengths describe the stored representation or decoded data.
