Manage a working library database

A design needs software to manage its definitions, control changes and recover data. Follow one library request through the tools and rules, and distinguish what a DBMS can check from what people still need to verify.

Explanation · 1 / 4

Use data modelling to describe the organisation

Data modelling identifies entities, attributes and relationships from requirements. A modelling tool can draw Member and Loan, mark their keys and record a one-to-many association. It helps document and revise the design, but cannot decide whether the real library permits several responsible members per loan.

Explanation · 2 / 4

Define the logical organisation precisely

The logical schema defines tables, attributes, types, keys, relationships and other constraints. Here MemberID and LoanID are INTEGER fields, MemberName is limited to 40 characters, and Loan.MemberID must refer to Member. A schema describes the permitted structure even when the tables contain no records.

Explanation · 3 / 4

Distinguish definition from current contents

The schema permits Member (1, Asha, TRUE), but does not itself state that Asha is registered. Inserting Dara changes the contents while leaving the same table definition. Adding a new Email field changes the schema.

Explanation · 4 / 4

Keep physical storage separate

The logical schema does not tell a user which disk sector holds a loan. The DBMS manages storage and retrieval behind the table interface. A file move or different storage device need not change the meaning of MemberID or the application’s logical queries.

Work together

Change a borrowing rule

The existing model assigns exactly one responsible member to each loan. A proposed group-borrowing service permits several members to share responsibility.

Work together · 1 / 2

Revise the conceptual relationship

A single MemberID in Loan cannot represent every member of a group loan. Introduce a LoanMember association with LoanID and MemberID, if the revised business rule is accepted.

Work together · 2 / 2

Revise the schema deliberately

Define the association’s fields, key and references, and decide how existing loans map to it. Merely drawing another line without changing the definitions does not implement the new rule.

A model states the intended facts and associations; a logical schema specifies their database structure.

Check

Explain it yourself · Teacher-written

Classify each change: add member Dara; add a Member.Email attribute; move the physical database files to another device.

Check your reasoning

Adding Dara changes stored data. Adding Email changes the logical schema. Moving the files concerns physical storage and need not change the logical schema. The model may need revision if the facts or relationships required by the organisation change.

Connect

Keep this idea

Separate the organisation’s model, the logical definitions and the records currently stored.

The DBMS records those definitions as metadata in its data dictionary.

Check a common misunderstanding

A modelling tool draws the rules it is given; it does not establish whether those rules match the organisation.

Explanation · 1 / 4

Identify the DBMS

A database management system is software that manages database definitions, storage, retrieval and controlled changes. It provides a shared way for applications and users to work with data. The database is the managed collection; the DBMS is the software managing it.

Explanation · 2 / 4

Identify metadata

The data dictionary stores metadata: descriptions of tables, fields, data types, lengths, keys and constraints. MemberName has a declared maximum length of 40; MemberID is the primary key. These descriptions differ from records such as member 1 being named Asha.

Explanation · 3 / 4

Use a definition to check a request

A query requesting MembrName contains a field name absent from the schema. The DBMS cannot treat it as MemberName just because the intended spelling seems obvious. A declared length or key constraint also provides rules for proposed data changes.

Explanation · 4 / 4

Connect the dictionary to shared management

The dictionary records definitions that tools and processing components can consult. A developer’s field inspector can show the same type and key information used to check requests. Central definitions reduce the need for each application to invent its own incompatible interpretation.

Reasoning and model answer — teacher-written

A data dictionary stores metadata describing the database, such as field names, data types, keys and validation rules.

A logical schema is a conceptual, platform-independent design of the database, showing entities and their relationships before a physical implementation is chosen.

Name the different constraints

Enforce the rule wherever requests originate

A fee of 20 satisfies a non-negative numeric rule even if the librarian meant 2. Constraints check declared properties; they cannot independently know every real-world fact. Verification against the borrowing record is still needed.

Explanation · 1 / 4

Interpret and check the request

The query processor interprets SQL, checks its syntax and resolves referenced tables and fields using metadata. The DBMS also checks applicable permissions. A request containing Ffee instead of Fee cannot be evaluated as the intended field.

SELECT LoanID, Fee
FROM Loan
WHERE Fee >= 3
ORDER BY LoanID;

Explanation · 2 / 4

Choose an execution approach

The processor plans how to carry out the query, considering available access paths such as scans and indexes. Different plans can produce the same logical result. An index is useful only when it suits the request and the data.

Explanation · 3 / 4

Execute and return the result

The DBMS carries out the chosen operations, tests conditions and returns the requested columns in the specified order. Here loans 202, 203 and 205 qualify. This SELECT does not remove non-matching stored loans.

Explanation · 4 / 4

Keep the diagram at the right level

Checking, planning and executing is a conceptual explanation of responsibilities. It is not a claim that every database performs all internal checks in one fixed sequence. A query builder helps construct a request; the processor executes it.

Work together

Trace the five fees

The fees for loans 201–205 are 2, 4, 6, 0 and 3.

Work together · 1 / 2

Establish the logical result

Compare each fee with 3. Fees 4, 6 and 3 qualify, giving (202, 4), (203, 6) and (205, 3). The inclusive comparison retains fee 3.

Work together · 2 / 2

Compare possible access plans

A scan can test all five rows; a suitable index may locate qualifying references. Either correct plan must return the same ordered values. Execution efficiency does not change the meaning of >= or ORDER BY.

Explain interpretation, metadata checks, planning and execution through the actual requested result.

Check

Explain it yourself · Teacher-written

A new index changes the execution plan. Should the same SELECT now return a different set of qualifying loans?

Check your reasoning

No. The plan changes how the DBMS obtains the result, not the query’s logical condition. With unchanged data and query, qualifying rows remain the same; ORDER BY supplies the required order.

Keep this idea

The query processor translates a request into an execution plan and operations that return its defined result.

  2. It chooses a suitable sequence of access and filtering operations.
  3. It executes those operations and returns the matching member names.

Common error: Do not substitute the design of the entry form for executing the request.

Question 9 · Command word: State4 teacher marks

Class contains ClassID 4. Pupil initially contains (10, Ana, 4), with fields PupilID primary key, PupilName and required ClassID referencing Class. Editors can insert; Readers can only retrieve. Starting again from that initial state for each attempt, explain the result of: an Editor inserting (11, Bo, 4); a Reader inserting the same row; and an Editor inserting (11, Bo, 7). S8.05.A04S8.05.A05
Answer and checking points — teacher-written

  2. The Reader is denied insertion even though the proposed values satisfy the stated integrity rules.
  3. Class 7 is absent, so the Editor’s third proposal is rejected by the foreign-key rule.
  4. Only the accepted attempt produces two rows: (10, Ana, 4), (11, Bo, 4). Each rejected independent attempt leaves only (10, Ana, 4).

Topic recap
  • Turn the library model into a logical schema

    Separate the organisation’s model, the logical definitions and the records currently stored.

  • Read the data about the data

    The data dictionary contains definitions and constraints, not a second copy of the members’ records.

  • Build forms and reports from defined fields

    Explain a developer tool by naming the object it builds and the practical work it enables.

  • Check valid values before accepting a change

    Integrity rules enforce defined identities, references and permitted values across request routes.

  • Decide who may perform each operation

    Grant individuals and groups the data and operations their work requires, while preserving integrity checks.

  • Recover a known consistent state

    A backup restores a saved consistent state; later changes need a further recovery source.

  • Follow a request from SQL to its result

    The query processor translates a request into an execution plan and operations that return its defined result.
