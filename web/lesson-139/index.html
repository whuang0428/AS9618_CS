Robust programs expect trouble and still behave politely.

Robust design means writing programs that cope with invalid input, reduce avoidable errors and remain easy to understand. This lesson links validation with modularity: check data before using it, and split the solution into clear procedures and functions. Why this matters

Exam answers often need causes and consequences: validation prevents invalid data being processed; modularity makes code easier to test and maintain.

Common trap

Validation is not the same as verification. Validation checks whether data is reasonable; verification checks whether data was copied or entered accurately.

Validation

Validation checks whether data is acceptable for the program

Cambridge-style pseudocode

REPEAT
    INPUT Mark
    IF Mark >= 0 AND Mark <= 100 THEN
        Valid <- TRUE
    ELSE
        OUTPUT "Enter a mark from 0 to 100"
        Valid <- FALSE
    ENDIF
UNTIL Valid = TRUE

Reasoning

The loop repeats until acceptable data is entered. The program does not calculate a grade from invalid data.

Robustness is not guessing what the user meant. It is refusing bad data with a calm face.

Combine ideas

Validation and modularity support each other

Function example

FUNCTION IsValidMark(Mark : INTEGER) RETURNS BOOLEAN
    IF Mark >= 0 AND Mark <= 100 THEN
        RETURN TRUE
    ELSE
        RETURN FALSE
    ENDIF
ENDFUNCTION

Why this is robust

The validation rule is written once and can be tested separately. Other code can call the function instead of repeating the condition.

Java support only

FUNCTION IsValidMark(Mark : INTEGER) RETURNS BOOLEAN

ENDFUNCTION
